# 测试时计算扩展（Test-Time Compute Scaling）

> **一句话定义**：在推理阶段（而非训练阶段）增加计算量以提升输出质量——通过并行探索多条推理路径（宽度）和迭代精化结论（深度），用更多算力换取更好答案。

## 寓言学习

### 寓言正文

精密零件厂的质检站,平时的螺栓订单走得很快:质检员老韩扫一眼、拿卡尺量一次,数据在公差范围内就盖章放行,一天能过几百个。

航空发动机的一批叶片订单送来后,流程完全变了。老韩不再一个人干,厂里同时派了三名质检员,各自用不同的检测方法独立测一遍同一批叶片(声波探伤、X光、人工卡尺),互不通气。每个人测完还不算完,还要对同一片叶片反复复测三次,确认读数没有漂移。最后把三人、三轮的结果放在一起比对,只有全部吻合才放行,任何一处不一致就返工重测。这批订单验收周期是普通螺栓的十几倍,但零件送去总装后一次通过。

有次实习生图省事,把这套"三人三测"流程原样套用到一批普通螺栓订单上,结果是产能被拖慢了近三分之二,复测出来的结果和最开始老韩一个人扫一眼的结论完全一样,没有多测出任何问题。主管把这批订单退回来,让他按普通流程重走一遍。

### 概念解析

**概念名称**：测试时计算扩展(Test-Time Compute Scaling),属于大语言模型推理部署/产品工程问题域。

**学习卡片**
- 核心张力：用固定的一次性计算给出答案(便宜、快) vs 在推理阶段投入更多计算换取更好答案(贵、慢)——多花的计算是否值得,取决于任务本身的难度和出错代价。
- 关键不变量：计算量的分配应该是非均匀的,由任务难度和错误成本决定,而不是所有任务一刀切用同样的资源投入;额外投入体现在“宽度”(多路径并行探索)和“深度”(单路径反复精化)两个维度。
- 触发条件：任务复杂、有明确验证标准、出错代价高时,增加计算量才有意义;简单、低风险任务不需要。
- 常见误解/失败模式：以为“投入越多资源结果一定越好”,在简单任务上也套用重型流程,浪费资源却没有提升;或者反过来,在高风险任务上舍不得多花资源导致漏判。
- 非适用边界：如果没有办法判断“这次多测的结果比之前更准”(缺少可靠的验证/裁决机制),多花计算量也只是多算几遍,不会自动变成更好的答案。

**一句话核心定义**：测试时计算扩展是在推理/执行阶段(而非训练阶段)按任务难度动态投入更多计算资源——通过并行探索多条路径(宽度)和反复精化单条路径(深度)换取更高准确率,但收益随投入呈对数增长,简单任务几乎无收益。

**它试图解决的问题**：同一套能力面对难度不同的任务,如何决定要不要、要花多少额外资源去换取更可靠的结果,而不是用同一套流程处理所有任务。

**故事元素映射**：
- 老韩一个人扫一眼放行普通螺栓 = 标准模式(1x compute),基础性能够用,不需要额外投入。
- 航空叶片订单派三人独立检测(宽度)+ 每人复测三轮(深度) = 测试时计算扩展的两个维度,用并行多轨迹和迭代精化对抗单点误判和短视判断。
- 三人三测的结果需要相互吻合才放行 = 需要一个可靠的“裁决/验证”机制来判断多轮结果是否一致,对应 Verifier。
- 实习生把重型流程套用到普通螺栓上产能被拖慢却没多测出问题 = 简单任务上额外计算投入收益趋近于零,纯属浪费,呼应“收益是对数增长、成本是线性增长”。

**比喻边界**：故事把“计算量”具象成了“派几个人测几轮”,但现实中的测试时计算扩展是同一个模型在推理时生成多条候选轨迹、用价值函数或投票机制选出最优答案,不涉及“多雇几个人”这种边际成本递增的资源,这一点故事做了简化。

**非适用例**：如果订单要求质检员“给这批零件的外观设计打个审美分”,不管派多少人、测多少轮,都不会因为“多测几遍”而让审美判断更“正确”——审美没有可供多轮验证收敛的客观标准,这不是测试时计算扩展能发挥作用的场景。

**现实例子**：OpenAI o1/o3 在推理阶段通过内部多路径探索和延长思维链来提升复杂任务准确率;LongCat 的 Heavy Thinking 模式对普通调用和高价值决策调用收取不同价格,让用户按需为“更好的答案”付费,和普通 API 调用形成明确的产品分层。

### 检验问题

1. 理解检验：故事里航空叶片订单为什么要“三人独立测三轮”而不是“一个人测九轮”?这和测试时计算扩展里“宽度”与“深度”两个维度分别对应什么机制?
2. 迁移检验：一个在线教育产品想给“批改学生的开放式作文”这个功能加上测试时计算扩展,你觉得这个功能值得投入额外算力吗?作文批改和数学解题这两类任务在“是否适合测试时计算扩展”上有什么本质区别?

## 核心机制

```
标准模式（1x compute）：
Prompt → [单次推理] → Answer

Heavy Thinking 模式（Nx compute）：
Prompt → [轨迹1] → 候选答案1
       → [轨迹2] → 候选答案2      → 综合/最优选择 → Final Answer
       → [轨迹N] → 候选答案N
              ↑
         + 每条轨迹内部迭代精化（深度）
```

两个维度：
- **宽度（Width）**：N 路并行轨迹探索，用多样性对抗单点推理失误
- **深度（Depth）**：每条轨迹内迭代检查和精化，用持续修正对抗短视推理

## 代表性实现

| 系统 | 宽度实现 | 深度实现 |
|------|---------|---------|
| **OpenAI o1/o3** | 内部多路探索 | Chain-of-Thought 延长推理链 |
| **LongCat Heavy Thinking** | 并行轨迹采样 | 迭代推理精化 |
| **DeepSeek R1** | Best-of-N 采样 | 长 CoT 训练 |
| **AlphaZero MCTS** | 树搜索展开 | 价值函数深度评估 |

## 产品层含义

### 作为差异化功能

```
普通 API 调用（低价）     ←→    Heavy Thinking 调用（高价）
  快速、便宜、适合日常             慢、贵、适合高价值决策
  ↓                                ↓
  问："今天吃什么？"          问："帮我分析这份合同风险"
```

**类比**：Uber Pool（快捷、低价）vs. Uber Black（精细、高价）

### 工程成本结构

| 计算量 | 预期效果 | 成本 |
|--------|---------|------|
| 1x | 基础性能 | $1 |
| 4x | +5-15% 性能提升 | $4 |
| 16x | +10-25% 性能提升 | $16 |
| 64x | 收益递减 | $64 |

关键：收益是对数增长，成本是线性增长——高难度任务收益更大，简单任务几乎无收益。

## PM 决策指南

### 什么任务值得 Heavy Thinking？

| 任务特征 | 推荐计算量 | 理由 |
|---------|---------|------|
| 合同审查、法律分析 | 高（16x+） | 错误成本极高 |
| 代码 Debug | 中（4x） | 错误有明显代价 |
| 创意写作建议 | 低（1x） | 质量判断主观，多路无明显提升 |
| 事实性问答 | 低（1x） | 答案确定，多路无意义 |
| 复杂 Agent 规划 | 高（16x+） | 规划错误会导致后续步骤全失败 |

### 部署考量

| 维度 | 挑战 | 对策 |
|------|------|------|
| 💰 成本 | Nx 调用 = Nx 成本 | 按任务重要性路由（见[[Wiki/概念/04_Agent框架/模型路由与CAF循环]]） |
| ⏱️ 延迟 | 并行探索增加响应时间 | 异步返回 + 进度显示 |
| 📊 质量 | 如何判断"最优"轨迹？ | 需要内置 Verifier（类似 CAF 中的 Verifier） |
| 🔧 工程 | 并发推理资源管理 | DORA 异步框架 |

## 与训练时计算扩展的区别

| | 训练时扩展（Scale-up Training） | 测试时扩展（Scale-up Inference） |
|--|-------------------------------|-------------------------------|
| **时机** | 模型发布前 | 每次推理时 |
| **成本归属** | 固定（研发成本） | 可变（用户按需付费） |
| **持久性** | 永久提升模型能力 | 只对当前请求有效 |
| **灵活性** | 低（需重训模型） | 高（可实时调整） |
| **适用场景** | 通用能力提升 | 特定高价值任务 |

**趋势**：两者互补，不是替代。训练时扩展建立基础，测试时扩展让用户按需付费购买"更好的答案"。

## 局限

- 在简单任务上，多路探索几乎不提升质量，纯属浪费
- 需要可靠的"轨迹选择"机制来判断哪条最优
- 长轨迹的 KV Cache 管理成本显著增加
- 用户体验上需要接受更长等待时间
