# 混合精度训练（Mixed Precision Training）

## 一句话定义

混合精度训练是指训练时权重的"主副本"用 FP32 保存，前向/反向计算用 BF16 做以省显存、提速度，但梯度累加必须回到 FP32 完成——因为 BF16 没有足够的精度去表示"给一个较大的权重加上一个很小的梯度"这个操作。

---

## 寓言学习

### 寓言正文

小吴在制剂室配一批营养输液袋。每袋的基础生理盐水要配到500毫升，配液台上那把大号量杯，刻度只精确到10毫升——配基础盐水完全够用，量个大概，几秒钟一袋，一天能配出上百袋。

这批袋子里还要额外加一种活性成分，每次只能加一丁点，0.05毫升一滴，得分四十多次、每隔几分钟滴一滴，累积滴够0.6毫升才算达标浓度，滴多了或滴少了都不合格。小吴嫌来回换量具麻烦，就用配盐水那把大号量杯顺手记录每次加了多少——量杯刻度只到10毫升，0.05毫升的滴量在上面读不出任何变化，他每次都如实记成"0"。四十多滴加完，记录本上活性成分那一栏，数字还是0，整袋输液其实只有最后收尾时不小心多倒的那一点点算数，配液台上一整批全部作废，只能报废重配。

主管老陈复盘后没有换掉那把大号量杯——配盐水本来就不需要那么精细，换了反而拖慢速度。她只加了一件东西：专门给活性成分那一栏配了一支独立的精密滴定管，每一滴都记在这支管子上，滴完累加。基础盐水还是用大号量杯配，快而且够用；活性成分的累加，全程走精密滴定管这条单独账。返工那批，四十多滴加完，滴定管上准确显示0.6毫升，一次达标。

### 概念解析

**概念名称**：混合精度训练（Mixed Precision Training），属于深度学习训练系统工程/数值精度问题域。

**学习卡片**
- 核心张力：大部分计算可以用便宜、粗糙的方式做（省时间省资源），但"把一个很小的增量累加到一个已经很大的基数上"这个动作，如果也用粗糙精度做，增量会被直接舍入抹掉，等于没做。
- 关键不变量：无论计算过程多快多粗，那个专门负责累加小增量的"总账"必须保留在足够精细的记录方式里。
- 触发条件：当增量相对基数非常小，且需要多次反复累积。
- 常见误解/失败模式：图省事，把"累积小增量"这一步也放进粗糙记录里，结果账面上完全体现不出小增量的存在，更新等于白做。
- 非适用边界：如果每次增量本身和基数量级相当（不是"小加大"），粗糙精度已经够用，没必要单独设精细记录。

**一句话核心定义**：混合精度训练是指大部分计算用低精度、高效率的方式完成，但涉及"把小梯度累加到大权重上"这一步必须保留在高精度下，否则更新会被舍入抹掉。

**它试图解决的问题**：如何在不牺牲权重更新数值准确性的前提下，尽可能用便宜的低精度计算换取训练速度和显存的节省。

**故事元素映射**：
- 大号量杯配基础盐水（粗精度，快） = 前向/反向传播里的矩阵乘法用 BF16 计算，对舍入噪声容忍度较高。
- 活性成分每次0.05毫升累加到0.6毫升目标 = 梯度累加到权重上这个更新动作，单次增量相对权重通常很小。
- 用大号量杯记录活性成分导致读数一直为0 = BF16 精度不足以表示"较大权重加上一个很小梯度"后的变化，更新被舍入抹平。
- 专门配的精密滴定管 = 用 FP32 保存的主权重（master weights），确保梯度累加不丢失。
- 基础盐水仍用粗量具、只把活性成分累加换成精密记录 = 混合精度训练里"大部分计算用 BF16，只有权重更新累加保留在 FP32"这一分工。

**比喻边界**：故事把"精度"简化成了两种量具（粗/精），现实中 BF16/FP32 的差异体现在具体的指数位、尾数位二进制表示和硬件算子支持速度上，这些工程细节没有对应到故事里；此外故事只呈现了"权重更新"这一处需要高精度，实际训练中优化器状态（如 Adam 的动量项）等其他累积量往往也需要类似的高精度处理，不只是这一条通道。

**非适用例**：如果配液台上要配的是"一次性倒入一大瓶，占基础盐水一半体积"的另一种成分（增量本身就很大，不是小增量累加），那就没必要单独配精密滴定管，直接用大号量杯量一下就够了——量级相当的增减，粗精度量具完全能读出变化。

**现实例子**：主流深度学习框架（PyTorch AMP、DeepSpeed）里，权重的"主副本"用 FP32 保存，前向和反向传播中的矩阵乘法用 BF16 计算（省显存、提速度），但每个参数的梯度会被自动转换（cast）到 FP32 再累加到主权重上，这也是为什么模型显存占用不能简单按"参数量 × 2字节"估算，还要留出这份 FP32 主权重和优化器状态的空间。

### 检验问题

1. 理解检验：故事里第一次报废，问题出在"配液员操作失误"，还是别的哪个环节？如果换一把刻度更细的量杯，只用来配基础盐水，但活性成分依然用它来记录累加，问题能解决吗？
2. 迁移检验：如果一个客服系统要统计"这个月一共有多少分钟的短会话被合并成一次长报告"，每次合并时把新会话的时长四舍五入到10分钟为单位再累加进总时长，你觉得这和故事里的问题是不是同一类机制？换成"直接把每次的分钟数精确记录，最后再合计"会不会更合适？

## 核心机制

### 为什么要"主权重 FP32 + 计算 BF16"分开

标准混合精度训练的做法：

- **master weights（主权重）用 FP32 保存**
- 前向、反向传播用权重的 **BF16 副本**计算
- 激活值（activations）用 BF16 计算
- 梯度用 BF16 计算，但**累加到 FP32**

原因在于浮点数的表示方式：BF16 在数值靠近 0 的区间精度比较高，能表示一个像 0.0001 这样的小梯度；但当权重本身是一个较大的数（比如 1.0），要表示"1.0 加上 0.0001 之后变成 1.0001"这个更新结果，需要的有效数字位数超过了 BF16 的表示能力——BF16 的尾数位太少，1.0001 很可能会被舍入抹平回 1.0，更新等于白做。

所以真正需要保留高精度的不是"每一次计算"，而是**梯度累加到权重上这个更新动作**——单次梯度相对权重本身通常很小，只要保证累加发生在 FP32 精度下，就不会因为精度不够而丢失更新量。PyTorch 里每个参数的 `.grad` 会和参数本身保持同一 dtype，所以单个梯度会被自动转换（cast）到 FP32 再参与累加。

**直觉总结**：矩阵乘法本身对舍入噪声容忍度较高，所以前向/反向用 BF16 计算没问题；但激活值比权重更难量化；而"权重更新"这一步必须留在 FP32，因为它涉及大数加小数这种对精度极度敏感的操作。

### 精度选项对比

| 精度 | 每参数字节数 | 特点 |
|------|------------|------|
| FP32 | 4 字节 | 全精度，训练权重更新最安全的选择 |
| FP16 | 2 字节 | 显存减半，但动态范围小，容易上溢/下溢 |
| BF16 | 2 字节 | 和 FP16 同样占 2 字节，但动态范围更大（数值稳定性更好），是目前训练的主流选择 |
| INT8 | 1 字节 | FP32 的四分之一，需要额外的量化步骤才能使用 |
| INT4 | 0.5 字节 | 更激进的压缩，精度损失更明显 |

（数据加载侧的配套技巧：用 `memmap` 避免一次性把全部训练数据读进内存。）

### HuggingFace 实践中的几种精度选项，分别在干什么

- **`torch_dtype=torch.bfloat16`**（`from_pretrained()` 加载时指定）：权重和激活值都直接以 BF16 形式加载和运行。这是官方推荐的默认选择，尤其适合推理场景——"整个流程都跑在 BF16 下"对推理而言通常完全够用。
- **`load_in_8bit=True`**：走的是 LLM.int8() 量化路线——权重被量化为 INT8，但激活值仍保留在 FP16。它带来的是**权重压缩带来的显存节省**，不等于整个计算过程都是 INT8 算子（激活值精度更高，不是"纯 INT8 计算"）。这是推理时的量化选项，不是训练时的精度策略。
- **`model.half()` / `model.to(torch.bfloat16)`**：对一个已经训练好的模型做整体精度转换，把所有权重和后续运算都转到 BF16/FP16 下，常见做法是先 `load_state_dict()` 加载好全精度权重，再调用 `.half()` 转换。同样主要用于推理场景，"整体跑在 BF16 下"对推理是安全的。
- **`torch.autocast()`**：这是训练场景下的"自动混合精度"（AMP）。权重本身保持 FP32 不变，但 `autocast` 会对每个算子按其数值敏感度**选择性地**决定用 BF16 还是 FP32——例如矩阵乘法用 BF16（能容忍较低精度），但 softmax、layernorm 这类需要做归约（reduction）的操作放在 FP32（对精度敏感）。`autocast` 只管"每个算子用什么精度"，**不负责维护 FP32 的主权重副本**，因此它比"整体转 BF16"占用更多显存，但在模型本身是 FP32、不方便整体转换，或者纯 BF16 出现数值问题时更稳妥。

```python
with torch.autocast(device_type='cuda', dtype=torch.bfloat16):
    output = model(x)
```

### bitsandbytes 的量化替换实践

如果要用 `bitsandbytes` 做训练/推理时的权重量化，做法是把模型里所有 `nn.Linear` 替换成 `bnb.nn.Linear8bitLt`（或 4-bit 版本 `bnb.nn.Linear4bit`）：

```python
def replace_linear_with_8bit(model):
    """Replace all nn.Linear with bnb.nn.Linear8bitLt"""
    for name, child in model.named_children():
        if isinstance(child, nn.Linear):
            new_layer = bnb.nn.Linear8bitLt(
                child.in_features, child.out_features,
                bias=child.bias is not None,
                has_fp16_weights=False,
            )
            new_layer.weight = bnb.nn.Int8Params(
                child.weight.data, requires_grad=False,
            )
            if child.bias is not None:
                new_layer.bias = nn.Parameter(child.bias.data)
            setattr(model, name, new_layer)
        else:
            replace_linear_with_8bit(child)  # 递归处理子模块
    return model

model = MyTransformer()
model.load_state_dict(torch.load('model.pt'))
model = replace_linear_with_8bit(model)
model = model.to('cuda')  # 量化实际发生在这一步
```

## 为什么 AI PM 要懂这个

- **训练成本估算**：混合精度训练直接决定显存占用（主权重 FP32 + 优化器状态 + BF16 计算副本，各部分要分别估算，不是简单"参数量 × 2 字节"），是判断"这批卡够不够训一个多大的模型"的基础输入。
- **和工程师对话时分清楚"精度策略"说的是训练还是推理**：`torch_dtype=bfloat16`、`load_in_8bit`、`autocast` 听起来都是"降精度"，但适用阶段和目的完全不同——需要能听出对方说的是训练时的数值稳定性权衡，还是推理时的成本压缩。
- **判断"要不要自建混合精度训练能力"**：现代训练框架（HuggingFace Trainer、DeepSpeed、Megatron）都默认内置了混合精度支持，绝大多数团队不需要自己实现这套机制，理解原理是为了看懂技术方案里"我们用 BF16 训练"这句话背后的取舍，而不是要求 PM 自己去调 autocast。

## 相关概念

混合精度训练解决的是**训练阶段**"如何又快又稳地更新参数"的问题；而 [[Wiki/概念/01_架构技术/量化技术]] 解决的是**推理阶段**"如何压缩一个已经训练好的模型以降低部署成本"的问题。两者都在同一根"精度"杠杆上做取舍，但决策点不同：混合精度训练发生在训练过程内部（权重更新的数值稳定性），量化发生在模型训练完成之后（部署时的显存/算力压缩），两者可以叠加使用——比如先用 BF16 混合精度训练出模型，再对训练好的模型做 INT4 量化部署。
