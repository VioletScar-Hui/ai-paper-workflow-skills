# 流水线并行与张量并行

## 一句话定义

流水线并行把模型按层切开分布到不同设备上、用 micro-batch 让多台设备流水作业以避免相互空等；张量并行把单层内部的权重矩阵切开分布到不同设备上，配合"列并行→行并行"的组合，让 MLP 和注意力层各自只需要一次 all-reduce 就能完成跨设备协作。

## 寓言学习

### 寓言正文

改装工坊有四个工位——拆解、喷漆、内饰、总装，车辆依次经过。

以前的做法是：一辆车进厂，先在拆解工位待到全部拆完，整车挪去喷漆工位，喷漆工位忙的时候，拆解工位和内饰工位都闲着没事干；喷完挪去内饰，喷漆工位又闲下来。同一时刻，四个工位里永远只有一个真正在干活，其余三个都在空等——就算老板多招几个工位的师傅，接单量再多，整体产能也提不上去。

老板后来把订单拆成一辆辆车错峰送进厂：车1在拆解工位干了没多久，车2就跟着送进厂门口候着；车1挪去喷漆工位后，车2立刻接上拆解工位，车3随后跟进。四个工位现在几乎同时都在忙各自手头那一辆车，不再互相空等，整体产能明显提了上去。

喷漆工位活儿最重：一辆车的车身要拆成十几块面板——引擎盖、四个车门、后备箱——分别喷成客户定制的颜色。老板给这个工位配了三个喷漆工，每人只管其中几块面板，各喷各的，互不干扰，喷完直接拼回车身，谁都不用等谁的进度、也不用互相核对。

有一次客户要做"渐变拉丝"效果，颜色要跨越好几块面板连续过渡，某种特调颜料的实际混合比例得根据"这几块面板各自用了多重的漆"才能算准——三个喷漆工各自只记得自己那几块用了多少漆，谁都没有全局数字。这一步必须停下来短暂碰个头：三人各自报出用量，加总算出总重量，才能判断这批颜料够不够、下一步该怎么调配比。加总一算完，三人立刻各自散开继续下一辆车的活，不用一直凑在一起。

老板后来坚持要求，凡是要干这种"喷完得凑总数"活的三个喷漆工，必须留在同一个车间里，不能分散去不同厂区——分开的话，每次要碰头对总数，光是跑腿传话就得多花老半天。至于拆解、喷漆、内饰、总装这四个工位之间，因为不需要频繁碰头核对，分设在不同厂区反而没什么影响。

### 概念解析

**概念名称**：流水线并行（Pipeline Parallelism）与张量并行（Tensor Parallelism），属于大规模分布式训练工程问题域。

**学习卡片**
- 核心张力：模型太大、单台设备放不下时，必须把工作拆给多台设备分担，但"拆开"本身容易造成设备互相空等（谁都得等上一环干完才能动手），如何拆分才能让多台设备真正同时都在忙碌、且额外的协调沟通降到最少。
- 关键不变量：把不同阶段的工作交给不同设备、再用"错峰送入小批次"填满空闲时间，是流水线并行的核心（时间维度的并行）；把单个阶段内部的工作按"互不依赖"的方式（列切分）分给多设备各自独立完成、只在真正需要合并结果时（行切分）才做一次通信，是张量并行的核心（空间维度的并行），且精心设计的切分顺序能把一整段计算的通信次数压缩到只需要一次。
- 触发条件：单个模型/任务的计算量或参数量大到单台设备处理不了，必须拆给多台设备；流水线并行适用于"能按阶段/按层切开"的场景，张量并行适用于"单层内部本身就大到放不下"的场景。
- 常见误解/失败模式：以为把工作简单地按阶段分给不同设备就能提速（朴素模型并行），却没意识到如果不做批次错峰处理，同一时刻永远只有一个设备在干活，堆再多设备也不涨速度；另外容易忽视"参与同一次张量并行合并的设备必须离得足够近、沟通足够快"，把它们分散部署会让本该很快的一次合并变得异常缓慢。
- 非适用边界：如果订单量很小、一次只有一两辆车要处理，根本排不满多个工位同时开工，那么错峰流水或拆分工位内部工作这套办法都没有意义，直接一个工位接一个工位串行做完反而最快——对应"模型本来就能放进单张设备、批量不大"时不需要引入流水线/张量并行。

**一句话核心定义**：流水线并行把模型按层/阶段拆开分布到不同设备，靠把一个批次切成多个 micro-batch 错峰送入，让各设备几乎同时都在忙碌、减少互相空等；张量并行把单层内部的权重矩阵切开分布到不同设备，通过"先按列切分（各自独立、无需通信）、再按行切分（各自算出部分和、最后合并）"的组合，让一整层计算只需要一次通信就能完成协作。

**它试图解决的问题**：当一个模型/任务大到单台设备既放不下全部层、也放不下某一层内部全部参数时，如何把工作拆到多台设备上，既能让所有设备真正同时忙碌起来（不是互相空等），又能把设备之间必须的协调沟通压缩到最少、最集中的几次。

**故事元素映射**：
- 拆解→喷漆→内饰→总装四个工位 = 模型被切分成的不同层/阶段。
- 一辆车走完全程再换下一辆时其余工位空等 = 朴素模型并行的核心缺陷（同一时刻只有一台设备在工作）。
- 车辆错峰送入、四个工位几乎同时都在忙 = 流水线并行用 micro-batch 填满设备空闲时间。
- 三个喷漆工各管几块互不干扰的面板 = 张量并行的列切分（column parallel），各设备独立计算，无需通信。
- 渐变拉丝颜料用量需要三人碰头加总 = 张量并行的行切分（row parallel）+ all-reduce，各设备算出部分和，需要一次归约才能得到完整结果。
- 要求同一次"凑总数"的喷漆工必须留在同一车间 = 张量并行对设备间高速互联（如 NVLink）的现实要求，因为频繁的 all-reduce 对通信延迟很敏感。

**比喻边界**：故事里"三个喷漆工各管几块面板"是一个直觉化的列切分类比，真实的张量并行是把权重矩阵本身按数学上的列/行维度切开，而不是像分面板那样按物理部位切分；此外，真实张量并行里"列切分→激活→行切分"这个顺序背后有严格的矩阵分块乘法依据（保证只需要一次 all-reduce），故事没有展开这层数学证明，只呈现了它的效果。

**非适用例**：如果改装工坊只有一个工位、活儿本身也不大（比如只是简单贴个膜），既不需要拆成多个阶段流水处理，也不需要把单个工位内部的工作再拆给多人分担——这种规模下引入流水线或张量并行的协调成本，反而会比直接一个人做完更慢。

**现实例子**：训练超大规模语言模型时，工程团队会同时用上流水线并行（把 Transformer 的不同层分布到不同机器，用多个 micro-batch 错峰喂入减少空闲）和张量并行（把单层内部的 MLP、注意力头切分到同一台机器内的多张 GPU，靠 NVLink 支撑频繁的 all-reduce）；这也是为什么工程师说"这几张卡必须放在同一台机器上做张量并行"——背后正是"频繁碰头对总数、离得越近越省事"这条约束。

### 检验问题

1. 理解检验：故事里如果老板不做"车辆错峰送入"，只是简单地把四个工位分给不同人，产能会提升吗？为什么朴素地"拆给更多人干"本身不等于提速？
2. 迁移检验：一个跨国团队要把一份大型演示文稿拆给多个人同时赶工——有的方案是"每人负责几页互不相关的内容，各写各的，最后拼在一起"，有的方案是"每人负责同一页里的一部分数据、需要最后核对汇总成一张完整表格"。这两种分工方式，分别更接近张量并行里的列切分还是行切分？如果团队成员分散在时差很大的不同国家，哪种分工方式受到的影响更大？

## 核心机制

### 朴素模型并行为什么不好

最直接的模型并行想法：把模型的每一层放到不同的 GPU 上，前向传播时把隐藏状态（hidden states）依次搬运到下一层所在的 GPU。

问题在于：在任意时刻，只有当前正在计算的那台 GPU 在工作，其余 GPU 都在**空等**数据传过来——设备之间来回等待，整体吞吐量并没有因为多用了几张卡而提升。这是朴素模型并行的核心缺陷。

### 异步流水线并行

为了让多台设备能同时忙起来，流水线并行把一个批次切成多个 **micro-batch**，让不同 micro-batch 在流水线的不同阶段同时被处理——类似工厂流水线：当第一台设备处理完第一个 micro-batch 传给第二台设备时，第一台设备立刻开始处理第二个 micro-batch，而不是干等。

PyTorch 提供了对应的实现（`torch.distributed.pipeline.sync.Pipe`）：

```python
from torch.distributed.pipeline.sync import Pipe

model = nn.Sequential(
    nn.Linear(512, 512).to('cuda:0'),
    nn.ReLU().to('cuda:0'),
    nn.Linear(512, 512).to('cuda:1'),
    nn.ReLU().to('cuda:1'),
)
model = Pipe(model, chunks=8)  # 把一个 batch 切成 8 个 micro-batch
output = model(x)
```

`chunks=8` 就是把一个 batch 切成 8 份 micro-batch，让流水线上的多个阶段能交替处理不同 micro-batch，从而减少设备的空闲等待时间。

### 张量并行的核心思想

张量并行（Tensor Parallelism, TP）不是把不同的层放到不同设备上，而是把**单层内部**的权重矩阵切开，让多台设备各自负责一部分计算。它可以和 FSDP 有效结合：分片批次维度 $B$ 能缩小 all-gather 的规模，分片 FFN 维度 $F$ 能降低 FSDP 本身的通信开销。

**MLP 的列并行 → 行并行组合**：一个标准 MLP（两个线性层中间夹一个激活函数）可以这样切分：

1. 第一个权重矩阵 $W^{\text{up}}$ 按**列**切分（column parallel）：每台设备只拿到权重矩阵的一部分列，各自算出输出的一部分，并在本地直接应用激活函数——这一步不需要任何通信，因为列切分让每台设备的计算天然独立。
2. 第二个权重矩阵 $W^{\text{down}}$ 按**行**切分（row parallel）：每台设备用自己那部分激活值乘以自己那部分权重，得到的是最终结果的一个"部分和"，需要一次 **all-reduce** 把各设备的部分和加总，才能得到完整、正确的输出。

关键洞察可以用一个简单的分块乘法等式来理解：如果 $h$ 被切成 $[h_0, h_1]$，$W_2$ 按行切成 $\begin{bmatrix}W_{2,0}\\W_{2,1}\end{bmatrix}$，那么

$$y = h \cdot W_2 = [h_0, h_1]\cdot\begin{bmatrix}W_{2,0}\\W_{2,1}\end{bmatrix} = h_0 W_{2,0} + h_1 W_{2,1} = y_0 + y_1$$

——两台设备各自算出 $y_0$、$y_1$，加起来才是真正的 $y$，这个"加起来"就是 all-reduce 在做的事。整个 MLP（列并行 → 激活 → 行并行）从头到尾**只需要一次 all-reduce**。任何其他的切分组合方式，都会在中间强行插入额外的通信。

对于 SwiGLU 风格的 MLP（$W_{\text{gate}}$、$W_{\text{up}}$、$W_{\text{down}}$ 三个矩阵），做法是把 $W_{\text{gate}}$ 和 $W_{\text{up}}$ 都按列切分，逐元素相乘的结果自然也沿 FFN 维度分片，再把 $W_{\text{down}}$ 按行切分，最后做一次 all-reduce。

一个更一般的规律：对矩阵乘法 $Y = XW$，把 $W$ 按**列**切分，每台设备算出的是输出的一个自然分片，不需要额外通信；把 $W$ 按**行**切分，每台设备算出的只是完整输出的一个部分和，需要做归约才能拿到最终结果。

**代码示例（列并行 / 行并行的分工）**：

```python
class ColumnParallelLinear(nn.Module):
    def __init__(self, in_features, out_features, world_size, rank):
        super().__init__()
        self.out_features_per_rank = out_features // world_size
        self.linear = nn.Linear(
            in_features, self.out_features_per_rank,
            bias=False, device=f"cuda:{rank}")

    def forward(self, x):
        return self.linear(x)  # 各设备只算出输出的一部分列，无需通信


class RowParallelLinear(nn.Module):
    def __init__(self, in_features, out_features, world_size, rank):
        super().__init__()
        self.in_features_per_rank = in_features // world_size
        self.linear = nn.Linear(
            self.in_features_per_rank, out_features,
            bias=False, device=f"cuda:{rank}")

    def forward(self, x):
        # x 是部分输入: (batch, in_features_per_rank)
        partial = self.linear(x)  # 每台设备算出部分和
        dist.all_reduce(partial, op=dist.ReduceOp.SUM)  # 归约求和得到完整结果
        return partial


class TensorParallelMLP(nn.Module):
    """列并行 -> 激活 -> 行并行，全程只需要一次 all-reduce"""
    def __init__(self, d_model, d_ff, world_size, rank):
        super().__init__()
        self.fc1 = ColumnParallelLinear(d_model, d_ff, world_size, rank)
        self.fc2 = RowParallelLinear(d_ff, d_model, world_size, rank)

    def forward(self, x):
        x = self.fc1(x)              # (batch, seq, d_ff // world_size)
        x = nn.functional.silu(x)
        x = self.fc2(x)              # (batch, seq, d_model)，已 all-reduce
        return x
```

### 注意力层的张量并行：按 head 切分,天然无需通信

注意力机制的切分方式更巧妙：每台设备只负责一部分注意力头（attention heads）。因为不同 head 之间的计算本来就是相互独立的，**按 head 切分意味着注意力计算本身完全不需要跨设备通信**——只需要在最后的输出投影（output projection）之后做一次 all-reduce，和 MLP 的模式完全一致：列并行（QKV 投影）→ 本地计算 → 行并行（输出投影 + all-reduce）。

```python
class TensorParallelAttention(nn.Module):
    def __init__(self, d_model, num_heads, world_size, rank):
        super().__init__()
        self.rank = rank
        # 每台 GPU 只负责一部分 head
        self.qkv = ColumnParallelLinear(d_model, 3 * d_model, world_size, rank)
        self.out_proj = RowParallelLinear(d_model, d_model, world_size, rank)

    def forward(self, x):
        batch, seq_len, _ = x.shape
        qkv = self.qkv(x)  # 只投影出本地负责的那些 head
        qkv = qkv.reshape(batch, seq_len, 3, self.num_heads_per_rank, self.head_dim)
        q, k, v = qkv.unbind(dim=2)
        q, k, v = q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2)
        attn_out = nn.functional.scaled_dot_product_attention(q, k, v)  # 本地 head 上独立计算，无需通信
        attn_out = attn_out.transpose(1, 2).reshape(batch, seq_len, -1)
        return self.out_proj(attn_out)  # 行并行 + all-reduce 得到完整输出
```

## 为什么 AI PM 要懂这个

- **判断训练/推理集群的组网需求**：张量并行需要设备间频繁做 all-reduce，通信延迟敏感，因此通常要求参与 TP 的设备在同一台机器内、由高速互联（如 NVLink）连接；而流水线并行的通信频率低得多，更适合跨机器部署。工程师说"这几张卡必须放在同一台机器上做张量并行"背后就是这个约束。
- **理解"多卡训练不是简单的算力叠加"**：朴素模型并行吞吐不提升的教训说明，堆卡本身不等于提速，并行方案设计得不好（比如没做流水线、没把等待时间填满）会让增加的硬件投入打水漂——这是评估"要不要多花预算上更多卡"时该问的问题。
- **和工程师对齐"我们需要多少卡"**：模型能否放进单机、需要几路张量并行、流水线要切几段，这些决定了最终采购/租用的 GPU 数量和机型（是否需要 NVLink 互联），是训练成本估算里绕不开的一环。
