# 分布式训练通信原语与数据并行

## 一句话定义

数据并行是把同一份完整模型复制到多张卡上、各自处理一部分数据后再同步梯度；模型并行则是把单次前向计算本身拆开分布到多张卡上——理解四种基础通信原语（broadcast/all-gather/reduce-scatter/all-reduce）和 ZeRO 的分片思路，是理解一切大规模分布式训练方案的公共地基。

## 寓言学习

### 寓言正文

气象局中心调度室的屏幕上，十个区域观测站各自上传自己辖区的当日数据。

平时最简单的一种任务是这样的：总局要给全部十个站更新同一份新的预警阈值表（比如"连续两小时降雨超过多少毫米就发预警"），这份表只有一份，总局原样复制发给十个站，每个站收到的是一模一样的内容。

复杂一点的任务发生在台风过境后：总局想要一张"全市完整降雨分布图"。这张图被十个站各自守着自己辖区那一块，谁也没有完整版本。总局把十块拼在一起、生成完整图，再把这张完整图整个发回给十个站——拼完之后，十个站手上现在都握着同一份完整的全市分布图，谁都不用再猜邻区的情况。

日常另一件事更麻烦：十个站除了各自的降雨量，还分别记着当天"平均气压"这项原始读数，谁都没有汇总过。防汛值班员需要"全市平均气压"这一个数，用来判断是否要联合调度。十个站把各自的读数报上来，总局求和算出全市平均值——但这个平均值只需要交回给"负责统筹气压数据校核"的那个站备案，其余站不需要留一份。

真正要命的是有一次紧急会商，值班员发现"只让一个站留着全市平均值"不够用——现场调度需要**每个站**都直接知道这个全市平均值，不能只有一个站知道。总局只好把刚才那次求和的结果，再原样发给全部十个站。事后复盘，值班员才想明白：这后一种做法，其实就是"先求和归总，再把结果发给所有人"这两步拼在一起做。

后来邻市也并进了这套系统，观测站从十个变成三十个，值班员原以为同步一次"全市汇总降雨图"的时间会跟着站点数目一起涨，结果发现实际耗时几乎没怎么变——因为真正拖慢速度的是那张图本身有多大，不是分给了多少个站去存。

### 概念解析

**概念名称**：分布式训练中的集合通信原语（broadcast / all-gather / reduce-scatter / all-reduce），属于分布式系统 / 大模型训练工程问题域。

**学习卡片**
- 核心张力：多个执行者各自只掌握全部信息的一部分，但某些决策需要基于"合并后的整体信息"才能做出——如何在不同场景下选择最省事的"合并 + 分发"方式，是通信开销的关键变量。
- 关键不变量：无论最终是"只让一部分人拿到归约结果"（reduce-scatter）还是"让所有人都拿到归约结果"（all-reduce，即 reduce-scatter 再加一次 all-gather），通信耗时只取决于被传输数据本身的大小，跟这份数据被分片存放在多少个执行者手里无关。
- 触发条件：数据分布在多个独立执行者身上，且某个下游决策需要"完整拼合的数据"（all-gather 场景）或"归约求和后的结果"（reduce-scatter/all-reduce 场景），而不是单个执行者手里那一小份局部数据。
- 常见误解/失败模式：把"广播同一份数据给所有人"（broadcast）和"归约后再发给所有人"（all-reduce）混为一谈——前者是复制一份已有的完整数据，后者是先做求和之类的归约运算，再把归约结果分发出去，中间多了一步真正的计算；另外容易忽视"归约结果分片给部分人"和"归约结果广播给所有人"之间只差一步 all-gather，而不是两套完全独立的机制。
- 非适用边界：如果各个执行者手上的工作彼此完全独立、不需要合并出一个共同结果（比如十个站只是各自记录自己的数据，从不需要跨站对照），就不需要引入这套"归约 + 分发"机制，各干各的就够了。

**一句话核心定义**：broadcast 是把一份完整数据原样复制给所有人；all-gather 是把分散在各处的数据分片拼合成完整版本、让所有人都拿到；reduce-scatter 是把分散的未归约数据先求和，归约结果按原来的分工重新分片；all-reduce 是"归约求和后，再让所有人都拿到完整归约结果"——本质是 reduce-scatter 后再做一次 all-gather。

**它试图解决的问题**：当计算任务被拆分到多个设备/执行者上并行处理后，如何用最省通信量的方式，把各自产出的局部结果重新组织成下游决策真正需要的形式（完整拼合版本，或归约求和后的结果，或两者都要）。

**故事元素映射**：
- 十个观测站各自守着自己辖区的数据 = 分布在多个设备上的分片数据（比如各设备算出的局部梯度）。
- 总局把同一份新阈值表原样发给十个站 = broadcast。
- 十个站各自守着的那一块拼成完整图、再发回给所有站 = all-gather（去掉分片状态，人人拿到拼合后的整体）。
- 十个站各自记的气压原始读数求和、结果只交回一个站备案 = reduce-scatter（归约的同时，给结果加上分片状态）。
- 求和结果再发给全部十个站 = all-reduce（reduce-scatter + all-gather 两阶段的组合）。
- 站点数从十个变三十个，但同步耗时几乎没变 = 通信耗时只取决于数据大小、与分片数量无关这一不变量。

**比喻边界**：故事里"总局"扮演了一个中心化的协调者，而真实的 ring all-reduce 等实现是完全去中心化的——每个设备只和环上的两个邻居通信，没有一个"总局"角色去统一收集再分发；此外，故事简化了"归约"具体在算什么（真实场景通常是对多个设备算出的梯度求和或平均），并非任意运算都能这样拆分成 reduce-scatter + all-gather 两阶段。

**非适用例**：如果总局只是想知道"某一个具体站今天的降雨量是多少"，直接问那一个站要数据就行，不需要动用整套跨站归约或拼合机制——这类"只需要一份局部数据、不涉及合并"的查询，不属于这套通信原语要解决的问题。

**现实例子**：数据并行训练（DDP）里，每张 GPU 在自己的 micro-batch 上算出局部梯度后，对梯度做一次 all-reduce，让每张卡都拿到平均后的梯度，再各自独立更新参数；ZeRO stage 1 进一步利用"all-reduce 本来就是 reduce-scatter 再加 all-gather"这个事实，只让每张卡常驻自己负责更新那部分参数对应的优化器状态（而不是像朴素 DDP 那样人人都存一整份），通信总量完全没有增加，却省下了可观的显存——这正是故事结尾"站点变多但同步耗时几乎不变"这条不变量能推出的直接工程收益。

### 检验问题

1. 理解检验：故事里"气压平均值只交回一个站"和"气压平均值发给全部十个站"，这两种做法在通信步骤上具体差了哪一步？为什么后者的通信总量不是前者的两倍，而只是多了一部分？
2. 迁移检验：假设有一个众包标注平台，一百个标注员各自标注了数据集的一部分，平台想统计"全部标注数据里，每个类别一共出现了多少次"，然后把这个统计结果分别反馈给"负责复核对应类别"的标注小组（不是所有人都需要拿到全部类别的统计）。这个场景更接近 all-gather、reduce-scatter 还是 all-reduce？为什么？

## 核心机制

### 数据并行 vs 模型并行

- **数据并行（Data Parallelism, DP）**：把一个批次（batch）的数据切分到多张设备上，每张设备持有**完整**的模型副本，各自做前向/反向后再同步梯度。
- **模型并行（Model Parallelism）**：把单次前向传播的**计算本身**拆开分布到多张设备上——模型本身放不下一张卡时才需要。

**FSDP 一句话**：FSDP（Fully Sharded Data Parallel）把参数分片存储在各个 rank 上以节省显存，但真正计算时，每个 rank 会在需要用到某层参数前，通过 all-gather 把完整参数临时拼出来，算完再丢弃——本质上是"数据并行 + 参数按需展开"的混合思路。

### 数据并行的局限

- 要求设备数 $M$ 小于批大小 $B$（$M<B$），而 $B$ 也不能无限增大——超过"临界批大小"（critical batch size）之后再增大 batch，对收敛帮助有限。
- 即便是 ZeRO stage 3，模型依然可能放不进单张设备——ZeRO 分片的是参数/梯度/优化器状态，并不会减少每张设备上的**激活值**显存占用。
- **强扩展（strong scaling）**：理想情况下增加芯片数量应带来吞吐量（FLOPs/秒）的成比例提升。粗略地说：DP 提升的是吞吐量，TP/PP 解决的是模型放不下的问题（分摊模型参数显存），SP 分摊的是激活值显存。

### 5D 并行分类

大规模训练把并行策略拆成五个正交的维度，各自解决不同的瓶颈：

| 并行方式 | 拆分对象 | 解决的问题 |
|---------|---------|-----------|
| 数据并行（DP） | 批次数据 | 单卡算力/吞吐不够 |
| 张量并行（TP） | 单层内部的权重矩阵 | 单层参数太大放不下 |
| 流水线并行（PP） | 不同层/不同 stage | 整个模型深度上放不下 |
| 序列并行（SP） | 输入序列长度 | 长序列的激活值显存爆炸 |
| 专家并行（EP） | MoE 模型中的不同专家 | 单卡装不下全部专家参数 |

### 四种集合通信原语（collective operations）

这是拼出上面所有并行方式的公共积木：

- **broadcast（一对多，相同数据）**：一张卡拥有数据，把它原样复制发给所有其他卡。
- **all-gather（多对多，拼合）**：每张卡各自持有数据的一部分（一个 shard），操作结束后每张卡都拿到完整拼合的数据。作用是**去掉某个轴上的分片状态**。
- **reduce-scatter（多对多，先求和再分片）**：每张卡持有的是"未归约"的数据（比如各自算出的局部梯度），先做归约（比如求和），归约后的结果再按某个轴分片，分发到各张卡上（每张卡只拿一部分）。和 all-gather 很像，区别在于 all-gather 是把各分片原样保留并拼起来，reduce-scatter 是把各分片累加起来再重新切分。作用是**在归约的同时给某个轴加上分片状态**。
- **all-reduce（多对多，全归约）**：每张卡持有未归约的数据，做归约后，**每张卡都拿到完整的归约结果**（不分片）。

**ring all-reduce 的两阶段直觉**：all-reduce 在工程实现上常拆成"reduce-scatter + all-gather"两个阶段，每个进程只和它环上的两个邻居通信：

1. 第一阶段（reduce-scatter）：把数据做归约求和，归约的结果分片落在不同卡上——这一步做的是"所有的算术运算（求和），不做多余的数据搬运"。
2. 第二阶段（all-gather）：把第一阶段各自得到的归约分片再传播给所有卡，凑成完整结果——这一步做的是"所有的数据搬运，不涉及任何算术运算"。

一个重要性质：无论 all-gather、reduce-scatter 还是 all-reduce，通信耗时只取决于数组本身的大小和带宽，**和这个数组被分片到多少张设备上无关**。

### 反向传播中 all-gather 与 reduce-scatter 互为对方的反向

这是一个很值得记住的对称性，可以用"分叉/求和"的类比理解：

- **前向做 all-gather → 反向做 reduce-scatter**。all-gather 把同一份数据广播给所有下游设备，各设备拿它去做不同的下游计算——这就好比前向计算图里发生了一次"分叉"（fan-out，同一个值被多处使用）。而在反向传播里，"分叉"对应的操作永远是"把各处流回来的上游梯度加总"（因为 $x=a+b$ 时 $\partial f/\partial x$ 会从多条路径累加）。把多张卡上产生的上游梯度加总、且结果按来源分片存放，这恰好就是一次 reduce-scatter。**一句话：前向"分叉"，反向就"求和"。**
- **前向做 reduce-scatter → 反向做 all-gather**。reduce-scatter 把多份输入求和压缩成一份（再分片存放）——这好比前向计算图里发生了一次"求和"节点。反向传播经过一个求和节点时，永远是把上游梯度原样复制给每一个加数（求和节点的反向就是"广播/复制"）。把归约后的梯度广播回每个贡献者，这恰好就是一次 all-gather。**一句话：前向"求和"，反向就"分叉"。**

由此可以推出：all-reduce（本质是 reduce-scatter + all-gather 两阶段）的反向传播，恰好又是另一次 all-reduce。

### 设备网格（mesh）与分片记号

把设备排列成一个多维网格，比如两个轴 $(X, Y)$；矩阵 $A$ 有自己的轴 $(I, J)$（行、列）。记号约定：

- $I_X$：把 $A$ 的行（$I$ 轴）按设备网格的 $X$ 轴切分（沿网格的每一行方向切）
- $I_Y$：把 $A$ 的行按网格的 $Y$ 轴切分
- $J_Y$、$J_X$：分别把 $A$ 的列按网格的 $Y$ 轴 / $X$ 轴切分
- $I_{XY}$：把 $A$ 的行沿着"把 $X,Y$ 拉平合并后的整个网格"切分（切得更细）
- 单独的 $I$（不带下标）：这个轴完全不切分
- **如果某个网格维度没有出现在下标里，说明数据在这个维度上是复制（replicated）的**——比如 $Y$ 没出现，意味着网格里每一列上的设备都持有相同的数据

### 矩阵乘法在分片下的四种情况

矩阵分块表示时，矩阵乘法可以写成分块矩阵的乘法——这个性质是分布式矩阵乘法的基础。设 $C = A \cdot B$：

1. **两个矩阵的收缩维度（contracting dimension，即乘法中被求和消掉的那一维）都没有被分片**：不需要任何通信，各设备直接做本地分块乘法，输出自然就是期望的分片形式。
2. **$A$ 或 $B$ 其中一个的收缩维度被分片**：先对被分片的那个矩阵做 all-gather，拼出完整版本，再和另一个矩阵相乘。
3. **$A$ 和 $B$ 的收缩维度都被分片（且分片方式一致）**：乘法本身可以做，但每台设备算出来的只是最终结果的一个"部分和"（未归约状态，记作 $\{U_X\}$），需要做一次 all-reduce 才能得到每台设备都一致的最终结果。
4. **$A$、$B$ 的非收缩维度沿同一个轴被分片**：这是更复杂的组合情况，实践中对应张量并行里更精细的切分方案（比如后文张量并行页面里 MLP 的列并行/行并行切分）。

### 朴素数据并行（DDP）

把一个大小为 $B$ 的批次切成 $M$ 份分给 $M$ 台设备，交换梯度，四个步骤：

1. 每台设备在本地的 micro-batch 上跑前向传播
2. 计算所有参数的梯度
3. 对梯度做 all-reduce，让每台设备都拿到平均后的梯度
4. 每台设备独立地用这份（相同的）平均梯度更新全部参数——这一步每台设备做的是完全一样的重复工作

要点：通信只发生在反向传播之后；只要模型能放进单张设备，就应该优先用这种最简单的方案；它允许把批大小随着设备数量近乎无限地扩大。

### ZeRO：分片什么、为什么"几乎免费"

ZeRO（Zero Redundancy Optimizer）针对朴素 DDP"每台设备都完整保留一份优化器状态+梯度+参数"这种冗余做优化，按分片粒度分三个 stage：

- **ZeRO stage 1：只分片优化器状态**。每台设备只保存 $1/M$ 的 Adam 优化器状态（比如动量、二阶矩），只负责更新自己持有优化器状态的那部分参数。流程：本地前向 → 计算全部参数梯度 → reduce-scatter 梯度（每台设备拿到自己负责的那部分参数的归约梯度）→ 用本地的优化器状态更新自己负责的参数子集 → all-gather 拿回更新后的完整参数。**关键洞察**：一次 all-reduce 的通信开销本来就等价于"reduce-scatter + all-gather"，所以 ZeRO-1 相比朴素 DDP 并没有增加额外通信量，却省下了优化器状态的显存——这正是它被称为"几乎免费的内存优化"的原因。
- **ZeRO stage 2：优化器状态 + 梯度都分片**。每台设备只保留 $1/M$ 的梯度——每层梯度算出来后立刻 reduce-scatter，只保留自己负责的那部分,其余的立即释放。
- **ZeRO stage 3（约等于 FSDP）：优化器状态 + 梯度 + 参数都分片**。每台设备只常驻 $1/M$ 的参数，需要用某一层时才 just-in-time 地 all-gather 出完整参数，用完即丢弃。这是唯一能让"单卡放不下的模型"也能训练的方案。
- **ZeRO 三个 stage 的通信开销总量是相同的**——只是被分片、被节省显存的对象不同（stage 越高，省的显存越多，但也意味着更频繁地按需 all-gather 参数）。

## 为什么 AI PM 要懂这个

- **判断"我们需要多少张卡"**：数据并行受限于"模型必须能放进单张卡"，一旦谈到 70B 以上模型的训练/微调，工程师说"需要上 ZeRO-3"或"需要张量并行"，本质是在说"单卡显存不够，需要把参数本身切开"——这决定了硬件采购和排期。
- **听懂"为什么要上更贵的并行方案"**：ZeRO-1 几乎是免费的优化，很多团队会默认开启；但 stage 3/张量并行/流水线并行都会引入额外的通信开销和工程复杂度，是否值得上，取决于模型是否真的放不进现有硬件——这是一个可以和工程师一起做的成本-收益判断，而不是"能上就上"。
- **和工程师对齐语言**：当工程师说"这一步需要 all-gather"或"通信瓶颈在 reduce-scatter"，PM 能听懂这些术语指的是"把分片数据拼起来"还是"把结果归约后重新分片"，能更准确判断某个方案是通信密集型还是计算密集型。
