# SSM 状态空间模型

## 一句话定义
> 状态空间模型（SSM）是一类将序列映射通过隐状态递推实现的模型，Mamba 通过引入输入依赖的选择性参数，使 SSM 同时具备 RNN 的线性推理复杂度和 Transformer 的上下文建模能力。

## 寓言学习

### 寓言正文

地铁站值班室以前的规矩是，每个进出站的异常都要写进一本值班日志——谁在几点几分做了什么、说了什么，事无巨细都记下来。夜班站长交接时，要把当天日志从头翻一遍讲给接班的人听，日志越写越厚，赶上客流大的周末，翻完日志天都快亮了，接班的人还没来得及去巡站，天亮的高峰已经开始了。

后来值班室换了个交接方式：站长不再逐条念日志，而是脑子里始终维护着一句话的"当前情况"，比如"3号口闸机偶发卡顿，客流正常，无异常滞留"。每来一件新情况，站长会判断这件事对当前状况的影响大不大——一个乘客问路，"当前情况"基本不用改；闸机连续卡顿三次，就要把这句话整个改写。交接时，只需要把这一句"当前情况"讲给接班站长，几分钟就能交接完，不管值了多久的班，交接内容始终是那么长，不会越攒越厚。

有一次巡警回来问，前一晚具体是几点几分、有没有一个穿红色外套的人在3号口停留超过五分钟——值班站长答不上来，只记得"3号口那阵子有点乱，但排查过没事"，具体是谁、几点几分，那句"当前情况"早就被后面几轮更新覆盖掉了，只有翻回最早那种事无巨细写日志的做法，才可能查到这么精确的细节。

### 概念解析

**概念名称**：SSM 状态空间模型（以 Mamba 的选择性 SSM 为例），属于序列建模架构问题域。

**学习卡片**
- 核心张力：把序列里发生的一切都完整记下来（信息不丢失，但记录会随序列变长无限增长）vs. 只维护一个固定大小的"当前状态摘要"、每来一条新信息就判断要不要更新它（不管序列多长，占用的空间始终不变，但旧的细节会被后续更新覆盖掉）。
- 关键不变量：不管处理了多长的序列，"当前状态"的大小始终固定不变；新信息对状态的影响程度不是固定的，而是由新信息本身的重要性决定（重要的强烈改写状态，不重要的基本不改）。
- 触发条件：序列很长甚至无限延续，且不能承受"记录量随长度线性增长"的存储/计算代价时，用固定大小的滚动状态摘要来处理。
- 常见误解/失败模式：以为固定大小的状态摘要能像完整日志一样精确回答"某个很久以前的具体细节是什么"——实际上状态是有损压缩，久远的具体细节会被后续更新逐步覆盖掉，只能靠完整记录（对应 Attention 的 KV Cache）才能精确检索。
- 非适用边界：如果任务恰恰需要精确检索很久以前的具体某一条信息（而不是掌握"当前大致情况"），固定大小的压缩状态无法胜任，需要保留完整记录的方式。

**一句话核心定义**：状态空间模型用一个随输入动态更新、大小固定的隐状态来递推处理序列，选择性机制让模型根据当前输入决定"多大程度上更新状态、多大程度上保留旧状态"，从而以固定的计算和存储代价处理任意长度的序列。

**它试图解决的问题**：Transformer 的注意力机制需要保留整个历史（KV Cache），序列越长占用越大；如何用一个大小恒定的机制，也能处理很长甚至无限延续的序列，同时依然具备一定的"选择性关注"能力。

**故事元素映射**：
- "当前情况"这句话 = 隐状态 h_t，大小固定，不随交班时长增长。
- 站长判断新情况对"当前情况"影响大不大，决定改写多少 = 选择性参数 Δ（输入依赖的更新强度），重要输入强烈更新状态，普通输入基本不改。
- 交接只需要讲这一句话，不用翻全部日志 = 推理时每步计算和存储代价固定（O(d²)），不随上下文长度增长。
- 巡警问具体细节答不上来 = SSM 的状态是有损压缩，无法像完整记录（Attention 的 KV Cache）一样精确检索久远的具体内容（对应 Passkey Retrieval 等任务上的弱项）。

**比喻边界**：故事把状态简化成一句人类可读的话，真实的隐状态是一个高维的数值向量，"重要性判断"也不是显式的人工判断，而是由 B、C、Δ 这几个依赖输入的参数通过训练学出来的连续函数；此外故事没有体现训练阶段可以用并行扫描加速这一部分。

**非适用例**：如果值班室的任务是"随时能精确回答任何一名乘客几点几分做了什么"，那从一开始就该坚持写完整日志而不是维护一句话摘要——这对应需要精确 in-context 检索的任务，应该优先选择保留完整历史的架构（如 Transformer），而不是纯 SSM。

**现实例子**：Mamba 处理超长序列时，推理阶段每一步的计算量和显存占用是固定的（O(d²)），不随上下文长度增长，适合流式、无限长输入场景；但在需要精确检索久远具体内容的 Passkey Retrieval 类任务上，表现明显弱于保留完整 KV Cache 的 Transformer，因此 TurboS 等实际系统采用 Mamba 与 Attention 混合的层级分配，用少量 Attention 层弥补精确检索能力。

### 检验问题

1. 理解检验：值班站长答不上巡警的具体问题，这说明他交接时用的方法本身是错的吗？故事想让你区分的是"记录方式"造成的哪两种不同能力？
2. 迁移检验：如果有人说"我们要做一个需要处理超长文档、还要能精确回答文档里任意一句原话的系统，纯 SSM 架构应该完全够用"，结合这个故事，你会提出什么疑问？

## 核心原理

**经典线性状态空间模型：**

连续时间形式：
```
h'(t) = A·h(t) + B·x(t)   # 状态更新
y(t) = C·h(t) + D·x(t)    # 输出
```

离散化（零阶保持）后用于序列建模：
```
hₜ = Ā·hₜ₋₁ + B̄·xₜ       # 离散状态更新
yₜ = C·hₜ                  # 输出
其中 Ā = exp(Δ·A), B̄ = (Δ·A)⁻¹(Ā-I)·Δ·B
Δ 是步长（time step），A 是状态转移矩阵
```

**S4（Structured State Space Sequence Model）：**

S4（Gu et al. 2021）是 Mamba 的前身：
- A 矩阵使用 HiPPO 结构化初始化（近似历史多项式投影）
- 训练时用卷积模式（并行），推理时用递推模式（高效）

但 S4 的 A/B/C 矩阵对所有 token 是固定的（LTI: Linear Time Invariant），无法根据输入动态调整关注什么。

**Mamba 的核心创新：选择性 SSM（S6）：**

Mamba 让 B、C、Δ 参数依赖于输入 xₜ：
```
Bₜ = Linear_B(xₜ)    # 不同 token 有不同的状态写入权重
Cₜ = Linear_C(xₜ)    # 不同 token 有不同的状态读取权重
Δₜ = Softplus(Linear_Δ(xₜ))  # 步长控制遗忘速度
```

直觉：
- Δ 大 → 强烈更新状态（关注当前 token）
- Δ 小 → 维持旧状态（忽略当前 token）
- B 控制"写入什么"，C 控制"读取什么"

这使 SSM 能像 Attention 一样选择性地关注序列中的不同部分，但时间复杂度仍为 O(n)。

**Mamba vs Transformer 对比：**

```
维度              Transformer          Mamba (SSM)
计算复杂度（训练）  O(n²·d)             O(n·d²)（并行扫描）
计算复杂度（推理）  O(n·d) per step     O(d²) per step （固定！）
内存（推理）       O(n·d) KV Cache     O(d²) 固定状态
长序列建模         直接，但慢           理论无限，但状态压缩有损
训练并行性         完全并行             并行前缀扫描（略逊）
内容寻址能力       精确（softmax）      近似（状态压缩）
```

**长序列上的优势与劣势：**

优势：
- 推理时每步计算量固定（O(d²)），不随上下文长度增长
- 显存占用固定，支持无限长序列流式推理
- 对长程依赖的"记忆"以压缩状态形式存储

劣势：
- 状态是有损压缩，无法精确检索久远 token 的具体内容
- 在需要精确 in-context 检索的任务上弱于 Transformer（如 Passkey Retrieval）
- 训练时并行扫描的效率仍低于 Transformer（尤其短序列）

**Hybrid（Mamba + Transformer）趋势：**

纯 SSM 在精确检索任务上表现不足，纯 Transformer 在超长序列上代价高昂，Hybrid 架构是目前的实用折中：

```
Hybrid 层级分配示意（以 TurboS 为例）：
Layer 1:  Mamba    # 高效处理局部序列模式
Layer 2:  Mamba
Layer 3:  Attention  # 全局精确关注
Layer 4:  Mamba
Layer 5:  Mamba
Layer 6:  Attention
...
```

TurboS（DeepSeek 系列推理优化模型）采用 Mamba-Transformer 混合架构：
- 大部分层用 Mamba 处理长上下文，降低 KV Cache 压力
- 关键层保留 Attention 保证精确检索能力
- 整体推理速度显著高于纯 Transformer，精度接近

**其他代表性 SSM 变体：**

| 模型 | 特点 |
|------|------|
| Mamba-1 (2023) | 选择性 SSM，硬件感知扫描 |
| Mamba-2 (2024) | 结构化状态空间对偶（SSD），与注意力统一框架 |
| RWKV-v6 | 类 SSM 的线性注意力，纯 RNN 推理 |
| Griffin (Google) | 线性递推 + 局部注意力混合 |
| Jamba (AI21) | Mamba + Transformer + MoE 混合 |

## 演进时间线

- **2021** — S4（Gu et al.，Stanford），结构化状态空间模型奠基
- **2022** — H3、Hyena，试验 SSM 语言建模能力
- **2023-12** — Mamba（Gu & Dao），选择性 SSM，首次在语言建模上接近 Transformer
- **2024-05** — Mamba-2，SSD 框架统一 SSM 和注意力
- **2024-05** — Jamba（AI21），首个商用 Mamba-Transformer 混合 LLM
- **2024-07** — Griffin（Google DeepMind），线性递推+局部注意力
- **2024-Q4** — TurboS（DeepSeek），Mamba-Transformer 混合应用于超长上下文推理

## PM 决策视角

**何时考虑 SSM/Mamba：**
- 需要处理极长序列（>100k token），且 KV Cache 是主要瓶颈
- 流式推理场景，每步延迟必须固定（自动驾驶、实时 ASR）
- 显存严格受限，KV Cache 无法增长
- 对检索精度要求不极高的任务（摘要、分类、生成）

**何时坚持 Transformer：**
- 任务需要精确 in-context 检索（RAG、Few-shot 示例检索）
- 需要与成熟生态（vLLM、FlashAttn、LoRA）直接兼容
- 训练数据和计算资源充足，Transformer 的扩展律更可预测

**实用建议：**

| 需求 | 推荐架构 |
|------|---------|
| 通用 LLM（<128k ctx） | Transformer（GQA + Flash Attn） |
| 超长上下文（>256k） | Hybrid（Mamba + Attn） |
| 边缘实时推理 | 纯 SSM（固定延迟） |
| 精度优先长文档 | Transformer + 稀疏注意力 |

## 补充:更严谨的机制与公式(源自 Alisa's Book of LLMs)

### 三方复杂度对比:SSM vs Transformer vs RNN

本页已给出 Mamba 与 Transformer 的对比表，源笔记强调的是一个更完整的三方对比，这里补充 RNN 这一列：

| 架构 | 训练复杂度 | 训练是否并行 | 推理复杂度(每步) | 推理是否并行 |
|------|-----------|------------|----------------|------------|
| Transformer | O(n²) | 并行 | O(n)（需重新关注全部历史） | 串行（逐 token） |
| RNN | O(n) | 不可并行 | O(1) | 串行 |
| SSM | O(n) | 可并行（并行扫描） | O(1) | 串行 |

关键结论：SSM 在训练阶段同时具备了 RNN 无法做到的"可并行"，又在推理阶段保持了和 RNN 一样的 O(1) 常数级开销；而 Transformer 训练虽然可以并行，但训练和推理复杂度都因为 attention 的 O(n²) 而比 SSM/RNN 更重。这正是 SSM 试图同时兼顾"可并行训练"与"轻量推理"两个目标的定位依据。

（本页已有的"Mamba vs Transformer 对比"表格中的 O(n·d²)/O(d²) 是把隐状态维度 d 也算进去的更细粒度写法，与这里的 O(n)/O(1) 是同一结论的不同粒度表述，二者并不矛盾。）
