# 原生多模态嵌入（Native Multimodal Embedding）

## 一句话定义

将文本、图片、音频、视频任意组合（包括交错输入）直接映射到同一向量空间——而不需要先将非文本模态转换为文字——从而支持真正的跨模态语义检索。

---

## 寓言学习

### 寓言正文

二手交易平台有个纠纷受理台，买卖双方产生争议时会提交各种证据——一张商品照片、一段语音留言、一张带文字的聊天截图，有时还有一段开箱视频。以前受理台的规矩是，不管证据原本是什么形式，都要先转换成一段文字描述才能归档比对：语音要先转成文字记录，照片要先由受理员写一句"商品外包装有破损"这类描述，然后拿这段文字去和历史案例库里同样是文字描述的旧案子做匹配。转换这一步很费时间，而且照片里具体破损的位置、语音里的语气这些细节，一转成文字就丢掉了大半，匹配出来的相似案例常常文不对题。

平台后来换了套系统，图片、语音、文字、视频不用先转换成文字，直接原样存进同一个档案库里，可以互相比对。受理员现在可以直接拿一张新照片加一段新语音留言作为一个组合线索，去检索档案库里"外观和语气都类似"的历史案例，检索速度快了很多，命中的相似案例也更贴切。

不过受理员发现，这套系统只擅长从几万个旧案子里很快挑出十几个"看起来像"的候选，具体这张照片上的破损到底有多严重、包装单上那行小字写的是什么型号，还是得转给资深审核员一张张放大了细看——受理台干的是"从很多里面快速挑出一小撮相近的"，不是把每个细节都看懂。

### 概念解析

**概念名称**：原生多模态嵌入（Native Multimodal Embedding），属于多模态检索 / 向量表示问题域。

**学习卡片**
- 核心张力：先把每种形式的证据都转换成统一的文字描述、再用文字去匹配（转换有损、慢，且只能处理"文字对文字"的匹配）vs. 让不同形式的证据直接映射进同一个空间、不经过文字这一层中转（能保留更多原始细节，还能支持"照片+语音"这种混合线索直接检索）。
- 关键不变量：不管原始证据是照片、语音、文字还是视频，最终都要落进同一个可比较的空间里，检索时才能拿任意模态组合的新线索去匹配任意模态组合的旧案例。
- 触发条件：需要跨形式（跨模态）做相似度检索、且查询本身可能是多种形式的组合（比如一张图加一段话）时，统一映射的方式比"先转文字再匹配"更合适。
- 常见误解/失败模式：以为这套检索系统能直接看懂细节、下判断——实际上它只负责从海量历史案例里快速圈出一批"看起来相近"的候选，具体的精细判断（读清一行小字、判断损坏程度）仍需要专门的理解环节来完成。
- 非适用边界：如果任务本身不需要"从大量历史里找相似"，而是"仔细看懂眼前这一份证据的每个细节"，这不是检索系统该干的活，应该直接交给专门做精细理解的环节。

**一句话核心定义**：原生多模态嵌入把文本、图像、音频、视频等任意组合的输入直接映射到同一个向量空间，不需要先把非文本模态转换成文字，从而支持跨模态、跨组合的语义检索。

**它试图解决的问题**：传统方案要么只能处理预先定义好的模态对（比如只做"文字搜图"），要么必须先把语音等模态转成文字才能检索，这个转换过程既慢又丢失细节；如何让任意模态、任意组合的输入都能直接互相比较相似度。

**故事元素映射**：
- 受理台的档案库 = 统一的多模态向量空间。
- 语音先转文字、照片先写文字描述再归档 = 传统双塔方案（如 CLIP）需要为每种模态单独编码、且往往要先转成文字才能跨模态比较，转换过程有损耗。
- 新系统里图片、语音、文字、视频直接原样存入同一档案库 = 原生多模态嵌入用统一的 backbone 直接把各模态映射进同一向量空间。
- 拿"一张照片+一段语音"作为组合线索直接检索 = 支持任意模态组合甚至交错输入作为一次查询。
- 受理员只负责挑候选、细节要交给资深审核员 = 嵌入检索负责粗召回，精细理解（读清数值、判断损坏程度）是下游专门环节（如 VLM）的工作，二者分工而非互相替代。

**比喻边界**：故事把"映射进同一档案库"简化成了物理意义上的合并存放，真实的原生多模态嵌入是通过统一的 LLM 结构（改成双向注意力）加多阶段训练（粗训练、细调、权重混合）学出来的一个连续向量空间，检索靠的是向量相似度计算，而不是像人工归档那样按类别摆放。

**非适用例**：如果受理台只需要判断"眼前这一份证据里，包装单上那行小字写的具体型号是什么"，这属于对单一证据的精细理解任务，用不上"从海量历史里检索相似案例"这套机制，应该直接交给擅长精细读取的环节处理。

**现实例子**：Gemini Embedding 2 支持文本、图像、音频、视频的任意组合甚至交错输入，直接映射到最高 3072 维的同一向量空间，使得"用一段视频+一句文字去检索相关图片"这类以前做不到的复合查询成为可能，音频也无需先经过语音识别转文字即可直接参与跨语言检索。

### 检验问题

1. 理解检验：受理员用新系统检索出候选案例后，为什么还要把细节判断转给资深审核员？这说明原生多模态嵌入这套机制本身负责解决的是什么问题，不负责解决的是什么问题？
2. 迁移检验：如果有人说"我们上了原生多模态嵌入之后，图片里文字的精确识别应该也会跟着变准"，结合这个故事，你会怎么回应？

## 对比：双塔 vs. 原生多模态

```
传统双塔方案（CLIP/ALIGN）：
  Text → [Text Encoder] → 向量A
  Image → [Image Encoder] → 向量B
  
  局限：
  ① 只能处理预定义的模态对（text-image，不能做 text-video）
  ② 无法处理交错输入（"这张图+这段文字"作为一个查询）
  ③ 音频必须先 ASR 转文字才能 embed

原生多模态方案（Gemini Embedding 2）：
  [Text + Image + Audio + Video] (任意组合)
       ↓
  [统一 LLM backbone（双向注意力）]
       ↓
  同一向量空间（最高 3072 维）
  
  优势：
  ① 处理任意模态组合（Video+Text → Image 检索）
  ② 交错输入（图片中间插文字再插视频帧）
  ③ 音频直接 embed（跨语言检索+5pp）
```

## 核心机制

```
训练关键：
1. 从生成式 LLM 适配为编码器（修改注意力为双向）
2. 多任务多阶段训练：
   PFT（粗训练）→ FT（细调）→ Model Souping（权重混合）
3. NCE 对比损失 + Hard Negative 采样
4. Mean Pooling → Linear Projection 输出固定维度向量

为什么 Gemini backbone 有优势：
  LLM 预训练已有跨模态语义理解能力
  → embed 的"迁移学习起点"比 CLIP 更高
```

## VLM（视觉语言模型）视角：理解 vs 检索的分工

原生多模态嵌入解决的是"检索"问题——把图文音视频映射到同一向量空间以支持相似度搜索；而视觉语言模型（VLM，如 GPT-4V/Claude Vision）解决的是"理解与生成"问题——对视觉输入做元素定位、OCR、图表解读、自由文本描述。两者在多模态 RAG/检索 pipeline 中通常分工协作而非互相替代：

```
多模态检索 Pipeline 中的两种角色：

[原生多模态嵌入]                    [VLM]
  职责：粗召回                       职责：精理解
  把 query 和候选内容映射到          对召回的截图/图像做视觉元素
  同一向量空间，做 Top-K 相似度检索  定位、表格边界识别、数值 OCR、
                                    图表类型分类
  优势：可对海量内容做低成本         优势：理解精度高（尤其密集
  向量召回                          文本/表格），但计算成本高，
  局限：无法做精细的表格/图表        不适合对全量内容做召回
  数值提取
```

例如 Project Fetch Phase 2（152号论文）的网页多模态检索架构中，VLM 承担的是"对截图做视觉元素定位、表格边界识别、数值 OCR"这类精理解工作，而非承担大规模候选召回——这与原生多模态嵌入"先粗召回、后精理解"的分工逻辑一致。实践中，VLM 的密集表格 OCR 精度仍低于专用 OCR 引擎，且截图分辨率压缩会导致小字体/密集图表细节丢失，这是当前 VLM 视觉理解链路的主要瓶颈，与原生多模态嵌入"召回阶段语义匹配"的瓶颈（专业术语/罕见组合的向量对齐不准）是两类不同的失败模式。

## PM 决策指南

**选择嵌入方案时**：

| 场景需求 | 推荐方案 |
|---------|---------|
| 只做文本检索 | text-embedding-3-large (OpenAI) 或 Gemini Embedding V1 |
| 图文检索（文字搜图） | Voyage-3.5-multimodal 或 Gemini Embedding 2 |
| 视频检索 | Gemini Embedding 2（目前最强） |
| 音频检索（跨语言） | Gemini Embedding 2（原生音频，无需ASR） |
| 复合查询（图片+文字→视频） | Gemini Embedding 2（唯一原生支持） |
| 成本敏感 + 开源 | mGTE-Qwen2 (MTEB榜上的开源选手) |

**产品设计洞察**：
- 多模态 RAG 产品不再需要"把所有内容都转成文字"的预处理管道
- 用户可以用截图/录音直接查文档——更自然的交互范式
- 但 API 成本（特别是视频帧的 token 消耗）需纳入产品定价考量

---

## 局限性

- 闭源：只能通过 Google Vertex AI 调用，不能本地部署
- 视频成本：每帧需要消耗 token，长视频 embedding 成本高
- 评测尚无大型开放基准：跨模态 RAG 没有业界公认的综合评测

## 时间锚

- 📅 2021：CLIP 奠定双塔多模态 embed 基础方案

- 📅 2026.01：Amazon Nova MME 发布（视频+图文，但无原生音频）
