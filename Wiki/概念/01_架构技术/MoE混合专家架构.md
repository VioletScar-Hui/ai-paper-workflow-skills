# MoE（Mixture of Experts）混合专家架构

> **一句话定义**：将模型的 FFN 层替换为多个"专家"网络，每次推理时用一个轻量路由器将每个 token 分配给少数几个专家——激活参数量只是总参数量的一小部分，实现"大容量、低成本推理"。

---

## 寓言学习

### 寓言正文

设计院有一整层楼的专业顾问室——结构、给排水、电气、声学、幕墙……十几个方向，每个方向都有专职顾问常驻。项目协调员接到一个新项目，不会把所有顾问都叫来开会，而是看项目情况，只挑两位最相关的顾问参与，其余顾问那天照常在自己办公室待着，工资和办公室照付，只是这个项目用不上他们。

协调员挑人一开始凭经验，结果发现大部分项目都被她挑向了同两三位资历最老、口碑最好的顾问——这几位常年连轴转，评审意见经常要拖好几天才能给，反而拖慢了项目；而其他顾问的办公室灯亮着，却整月接不到一个项目，渐渐生疏了自己的专长。

后来行政上做了个调整：协调员分配项目时，除了看专业是否对口，还要看这位顾问最近手头项目的数量——手头项目多的，即使专业再对口，这次也稍微往后排一排，把机会匀给同样专业对口、但最近比较闲的顾问。几轮下来，各个顾问室的项目量明显均匀了很多，那几位资历老的顾问也不再是每次都被挑中，出评审意见反而更快了。

### 概念解析

**概念名称**：MoE（混合专家架构），属于大模型稀疏化扩展架构问题域。

**学习卡片**
- 核心张力：想要覆盖足够多的专业方向（大容量、强能力）vs. 每处理一件具体事情只想付出少量成本（不需要每次都动用全部专业力量）——用一个轻量的分配者，每次只挑其中一小部分参与，来同时满足这两点。
- 关键不变量：不管一次任务实际用了多少个专家，全部专家的"驻场成本"（显存/办公空间）始终要留着——省下来的只是"计算/参与"这一部分成本，不是"容纳"这一部分成本。
- 触发条件：任务集合足够多样、需要覆盖的专业方向足够广，且大多数单个任务只需要其中一小部分专业能力时，用"分配到少数专家"比"每次都动用全部能力"更划算。
- 常见误解/失败模式：以为专家分工少激活了、显存/存储需求也会跟着降低——实际上所有专家都要常驻待命，占用的空间/显存并不会减少；另一个常见问题是分配长期集中到少数"热门专家"，导致他们过载、其他专家闲置荒废。
- 非适用边界：如果任务种类很单一、不需要覆盖多个差异化专业方向，养一整层楼各科专职顾问反而是浪费——不如让同一批人什么都做（对应 Dense 架构在任务同质化场景下更合适）。

**一句话核心定义**：MoE 把模型中一层的处理换成"多个专家网络 + 一个轻量路由器"，每次只激活其中少数几个专家参与计算，用远小于总参数量的激活成本，撑起远大于单一网络的总容量。

**它试图解决的问题**：想要模型覆盖足够广的知识和能力（大容量），又不想让每一次推理都付出与总容量成正比的计算代价——如何只让"用得上"的那一小部分参数参与计算，而不是每次都动用全部参数。

**故事元素映射**：
- 各专业方向的顾问室 = 各个专家网络。
- 项目协调员挑两位最相关顾问 = 路由器（Router）选出 Top-K 个专家参与当前 token 的计算。
- 没被挑中的顾问仍占着办公室、拿着工资 = 未激活的专家依然占用显存，MoE 降低的是计算量，不是存储/显存需求。
- 项目扎堆流向少数资深顾问、其他顾问荒废 = 负载不均衡问题：路由长期偏向少数"热门专家"。
- 按"最近手头项目数量"调整分配、不动主评审标准 = 用 router bias 之类的方式做负载均衡调整，不干扰主任务本身的判断质量。

**比喻边界**：故事把"专业对口程度"简化成协调员的主观判断，真实的路由器是通过对 token 表征做打分（softmax）后选 Top-K，是一个可学习、随数据自动调整的函数，而不是人工经验；此外真实 MoE 系统还涉及专家并行（跨设备分配专家）带来的通信开销，这在故事里没有体现。

**非适用例**：如果一家小型工作室业务高度单一（比如只做小户型室内装修），根本用不上结构、声学、幕墙这些差异化专业方向，养一整层楼的专职顾问室纯属浪费——这时候让同一批全能型设计师什么都做（对应 Dense 架构）反而更划算，这不是 MoE 该解决的场景。

**现实例子**：DeepSeek-V3 总参数量 671B，但每次推理只激活约 37B（5.5%），用细粒度专家划分和"仅调整路由偏置而不加辅助损失"的方式做负载均衡，在远低于同等 Dense 模型的推理成本下达到接近的效果，但部署时依然需要把全部 671B 参数加载到显存/内存中。

### 检验问题

1. 理解检验：故事里"没被挑中的顾问仍要占着办公室、拿着工资"，这在 MoE 架构里对应的是省下的哪部分成本、没省下的又是哪部分成本？
2. 迁移检验：如果有人说"我们把模型换成 MoE 架构了，显存应该能省下来，可以在更小的显卡上部署"，结合这个故事，你会怎么纠正他？

## 核心原理

```
标准 Transformer FFN（Dense）：
  每个 token → 单一 FFN → 输出
  激活参数 = 总参数（100%）

MoE FFN：
  每个 token → Router（轻量门控）→ 选 Top-K 专家 → 加权求和 → 输出
  激活参数 = K/N × 总参数（如 K=2, N=64 → 仅 3.1%）

Router（门控函数）：
  scores = softmax(token_embedding · W_router)
  selected = Top-K(scores)
  output = Σ score_i · Expert_i(token)   对 i ∈ selected
```

## 关键设计选项

| 维度 | 选项 | 优劣 |
|------|------|------|
| **激活专家数 K** | K=1（稀疏）vs K=2（常见）vs K=8 | K 小→节省计算；K 大→表达力强 |
| **路由粒度** | Token级（每 token 选专家）vs 句子级 | Token 级更灵活，但通信开销大 |
| **负载均衡** | Auxiliary Loss（GLaM）vs Bias-only（DeepSeek-V3）| Bias-only 不干扰主任务 |
| **专家并行** | Expert Parallelism（跨设备分配专家）| 通信成本高，是 MoE 的工程难点 |
| **共享专家** | DeepSeekMoE：部分专家所有 token 共享 | 保留通用知识，专家专注细化 |

## 主要实现系列

| 模型 | 总参数 | 激活参数 | 专家数 | 年份 |
|------|--------|---------|--------|------|
| GLaM（Google）| 1.2T | 96.6B（8%) | 64/层 | 2022 |
| Mixtral 8x7B | 46.7B | 12.9B（28%）| 8/层 | 2023 |
| DeepSeek-V3 | 671B | 37B（5.5%）| 细粒度 MoE | 2024 |
| DeepSeek-V4-Pro | 1.6T | 49B（3.1%）| — | 2025 |
| GLM-5 | 744B | 40B（5.4%）| 256 专家 | 2026 |

## MoE vs Dense 的权衡

| 维度 | Dense | MoE |
|------|-------|-----|
| **训练成本** | O(参数量) | 比同性能 Dense 便宜 ~3-5x |
| **推理计算** | 高（全参数激活）| 低（仅激活 K/N 参数）|
| **显存需求** | 低（只需加载用到的参数）| **高**（需加载全部参数到显存/内存）|
| **推理延迟** | 稳定 | 受专家分配影响 |
| **工程复杂度** | 低 | 高（Expert Parallelism、负载均衡）|

**关键陷阱**：MoE 降低计算量，但不降低显存占用！671B MoE 仍需加载 671B 参数到内存/显存。

## 负载均衡问题

```
问题：所有 token 都选同一批"热门专家"→ 其他专家浪费
      热门专家过载 → 推理批次处理困难

解决方案演进：
  GLaM/Switch Transformer：Auxiliary Loss（辅助均衡损失）
    → 有效，但干扰主任务训练
    
  DeepSeek-V3/V4：无辅助损失，仅调整 router bias
    → 不影响主任务梯度，训练更稳定
```

## 细粒度 MoE（DeepSeek 创新）

```
传统粗粒度：8 个大专家，每次选 2 个
DeepSeekMoE 细粒度：64 个小专家，每次选 6 个（激活比例相同）

优势：
  → 更细的专家分工（每个专家更专业化）
  → 更好的负载均衡（选择空间更大）
  → 同等性能下激活参数更少
  
+ 共享专家（Shared Experts）：
  → 部分专家始终被所有 token 激活（通用知识）
  → 路由专家负责特殊知识
```

## PM 决策参考

| 需求 | 建议 |
|------|------|
| **最大化推理吞吐（算力受限）**| MoE（同算力下服务更大模型）|
| **最小化显存（显存受限）**| Dense（MoE 需要加载全部参数）|
| **部署简单性** | Dense（工程复杂度低）|
| **最优成本效益**| MoE（DeepSeek-V3 为例：$5.5M 训练=GPT-4 水平）|
