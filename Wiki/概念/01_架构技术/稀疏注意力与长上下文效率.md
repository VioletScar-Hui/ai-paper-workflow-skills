# 稀疏注意力与长上下文效率

> **一句话定义**：标准 Attention 的计算量随序列长度 L 呈 O(L²) 增长——稀疏注意力通过只对少数高相关 token 做完整 Attention，将复杂度降低为 O(Lk)（k≪L），从而在几乎不损失性能的前提下支持百万级上下文。

---


## 寓言学习

### 寓言正文

仓库刚到一箱新货，按规矩要跟仓库里所有旧货箱逐一核对，看有没有重复入库或者信息冲突。库存只有几十箱的时候，质检员一箱箱翻，一天就能核完。后来仓库扩到几万箱，还是这么一箱箱比对，核一箱新货要花掉大半天，新货天天堆在门口进不了库。

仓库主管加了道工序：新货一到，先由一个人拿着扫码枪，把它的条码和关键特征跟所有旧箱子快速扫一遍，只挑出最像有关联的几十箱，标好号，再交给质检员做详细核对。质检员不用再面对几万箱，只用看这几十箱，核对时间一下缩短到几分钟。

有一次新到的一箱货物涉及一次旧订单的退换，但那批旧货物的标签因为受潮，条码模糊，扫描没识别出来，扫码枪没把它列进"最像有关联"的那几十箱里。质检员照常核对完那几十箱，没发现问题，就放行入库了。半个月后客户投诉，主管翻查才发现，真正对应的那箱旧货一直没被扫码枪筛出来，从一开始就没进入质检员的视野。

### 概念解析

**概念名称**：稀疏注意力（Sparse Attention）与长上下文效率，属于 Transformer 模型架构/推理效率问题域。

**学习卡片**
- 核心张力：对新元素跟历史所有元素逐一完整比对（不遗漏，但计算量随规模平方增长）vs 先用便宜的方法筛出最相关的一小部分再精细比对（省资源，但可能漏掉关键信息）。
- 关键不变量：并非所有历史元素对当前判断同等重要，可以先用一个低成本的筛选步骤缩小范围，再对缩小后的范围做完整、精细的比对。
- 触发条件：处理对象的规模持续增长，全量两两比对的成本变得不可承受（比如序列长度到几十万、上百万时）。
- 常见误解/失败模式：以为筛选步骤和精细比对的效果一样可靠，忽视筛选环节本身可能因为信息不清晰、特征弱而漏筛掉真正关键但不起眼的内容。
- 非适用边界：当元素总数本来就很小，全量比对成本完全可以承受时，引入筛选机制反而增加了额外的复杂度和误筛风险，没有必要。

**一句话核心定义**：稀疏注意力是指不对序列中所有 token 做完整的两两比对，而是先用一个低成本的方法筛出与当前 token 最相关的一小部分，只对这一小部分做完整注意力计算，从而把计算复杂度从随长度平方增长降低到接近线性增长。

**它试图解决的问题**：当需要处理的上下文长度从几千 token 涨到百万级时，如何避免"每个新 token 都要和所有历史 token 逐一比对"带来的计算量和显存爆炸式增长。

**故事元素映射**：
- 每一箱新货 = 当前要处理的 query token。
- 仓库里所有旧货箱 = 序列中所有历史 key/value。
- 逐箱核对 = 标准 Attention 的 O(L²) 全量两两比对。
- 扫码枪快速预筛选出几十箱 = Lightning Indexer 用低精度、低维度的方式快速计算相关性分数。
- 质检员只对筛出来的几十箱详细核对 = Top-k 稀疏 Attention，只对筛出的高分 token 做完整注意力计算。
- 受潮标签导致漏筛、遗漏了真正关键的旧货 = 稀疏注意力的核心失败模式：筛选环节本身不准，可能漏掉关键但特征模糊的历史信息。

**比喻边界**：故事把"筛选"简化成条码扫描这种离散的、一次性的动作，但真实的稀疏注意力筛选（如 DeepSeek 的 Lightning Indexer）是在每一层、每一次推理中都重新计算的连续打分过程，且往往和 KV Cache 压缩（如 MLA）等其他技术组合使用，故事只呈现了"筛选降低计算量"这一层机制，没有涉及显存压缩这条并行的优化路径。

**非适用例**：如果仓库只有十几箱货，质检员完全可以每次都逐一核对完，不需要额外加一道扫码预筛选的工序——序列很短时，标准 Attention 的成本本身就不高，引入稀疏机制反而多此一举。

**现实例子**：DeepSeek-V3.2 提出的 DSA（DeepSeek Sparse Attention）用一个轻量级 Lightning Indexer 为每个 token 计算与历史 token 的相关分数，只对 Top-k 高分 token 做完整注意力计算，配合 DeepSeek-V4 的 CSA+HCA 混合压缩策略，在百万 token 场景下把推理 FLOPs 降到基线的 10%~27%。

### 检验问题

1. 理解检验：故事里那次核对遗漏，问题出在"质检员核对不仔细"，还是别的哪个环节？稀疏注意力的失败模式通常出在哪一步？
2. 迁移检验：如果一个电商平台要给每个新用户推荐商品，用户历史行为已经积累到几十万条，你觉得"先粗筛出一小部分相关历史行为，再精细计算推荐分数"这种思路，和稀疏注意力是不是同一类机制？说说理由。


## 为什么 O(L²) 是瓶颈

```
标准 Multi-Head Attention：
  注意力矩阵 = Q × K^T ∈ R^{L×L}
  计算量：O(L² × d)
  KV Cache 大小：O(L × n_heads × d_head)

序列长度影响：
  L=4K：基准 (1x)
  L=32K：16x 计算量，16x KV Cache
  L=128K：1024x 计算量，1024x KV Cache  ← 已经很贵了
  L=1M：65536x 计算量，65536x KV Cache  ← 不可能的标准 Attention

结论：支持百万 token 上下文，必须解决 O(L²) 瓶颈
```

## 主要解决方案

### MLA（Multi-head Latent Attention，DeepSeek-V3 创新）

```
传统 MHA：KV Cache = L × n_heads × d_head （每层完整保存）
MLA：将 K,V 压缩到低秩潜在向量 c ∈ R^{d_c}，d_c << n_heads×d_head

推理时：只缓存 c（而非完整 KV）
解压：从 c 恢复 K, V（实时计算）

效果：KV Cache 大小 ≈ 降低 5-10x（取决于压缩率）
副作用：解压增加计算量（但远小于 Cache 节省的收益）
```

### DSA（DeepSeek Sparse Attention，V3.2/GLM-5 创新）

```
核心思路：不是所有 token 对当前位置都重要 → 只计算重要的

Lightning Indexer（轻量索引器）：
  计算 query token h_t 与所有 preceding token h_s 的相关分数
  I_{t,s} = Σ_j w_{t,j}^I · ReLU(q_{t,j}^I · k_s^I)
  
  特点：低头数（d_I << d），FP8 精度，计算高效

Top-k 稀疏 Attention：
  只选 Top-k 个高分 token 做完整 Attention
  复杂度：O(L²) → O(Lk)，k << L

性能保证：
  在短序列上性能与标准 Attention 持平
  长序列上大幅提升速度
```

### CSA + HCA 混合（DeepSeek-V4 创新）

```
CSA（Compressed Sparse Attention）：
  稀疏 + KV 压缩，基于 Top-k 选择
  
HCA（Heavily Compressed Attention）：
  激进压缩 KV Cache
  
混合策略：部分层用 CSA，部分层用 HCA，部分层用标准 Attention

效果（1M token 场景，vs DeepSeek-V3.2）：
  V4-Pro：推理 FLOPs 降至 27%，KV Cache 降至 10%
  V4-Flash：推理 FLOPs 降至 10%，KV Cache 降至 7%
```

## 各方案对比

| 方案 | 降低计算量 | 降低 KV Cache | 性能损失 | 适用场景 |
|------|---------|-------------|---------|---------|
| MLA | ✗（无影响）| ✅ 显著 | 极低 | 推理显存受限 |
| DSA | ✅ 显著 | ✗ | 极低 | 长序列训练速度 |
| CSA+HCA | ✅ 显著 | ✅ 显著 | 低 | 百万 token 在线推理 |
| FlashAttention | ✅ 内存效率 | ✗ | 无损 | 中等长度训练优化 |
| Sliding Window | ✅ 固定窗口 | ✅ 固定 | 高（丢失远程依赖）| 局部注意力任务 |

## 实际性能数据（📅 2025）

```
DeepSeek-V4 在 1M token 场景（vs V3.2 基准 100%）：
  V4-Pro：
    推理 FLOPs：27%（节省 73%）
    KV Cache：10%（节省 90%）
    
  V4-Flash：
    推理 FLOPs：10%（节省 90%）
    KV Cache：7%（节省 93%）

意义：原本需要 100 张 H100 服务 1M 上下文
      现在 V4-Flash 只需 10 张
```

## 长上下文的工程挑战

```
1. KV Cache 大小（显存爆炸）
   对策：MLA 压缩 + 磁盘 KV Cache Offload

2. Prefill 延迟（处理长输入）
   对策：Chunked Prefill + Pipeline Parallelism

3. 注意力"迷失在中间"问题
   即使 context 放进去了，模型也不一定注意到中间的信息
   对策：RAG 补充（只放相关信息）、RoPE 位置编码优化

4. KV Cache 传输成本（分布式推理）
   对策：Contextual Parallelism for Long-Context Attention（V4的实现）
```
