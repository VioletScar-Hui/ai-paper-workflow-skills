# Agent 发现机制

> **来源**: 引自 [[06_LLM-Agent通信协议分类]]
> **类型**: 基础架构概念
> **关联**: [[MCP]] · [[A2A]] · [[分层Agent协议栈]]
> **成熟度**: ⚠️ 概念成熟，但去中心化实现仍是最大技术空白

## 一句话定义
在分布式 Agent 网络中，一个 Agent **如何找到、识别、并了解其他 Agent 能做什么**的机制——从最基础的手动配置，到自动化注册发现，再到去中心化的 P2P 发现。

## 寓言学习

### 寓言正文

老周这次接的活在城东新区,以前干的单子全在城西。城西那几个水电工、瓦工,他闭着眼都能报出电话号码——谁手艺稳、谁准时到场,他心里有本账,一个电话打过去,当天就能开工。

城东这边他一个熟人都没有。他打给装修公司总部,申请查了一份工人花名册。花名册按片区和工种分类,城东那一栏列着六七个名字,注明工种和联系方式。老周挑了个标注"水电,五星"的师傅打过去。

接电话的人说,水电确实做过,不过去年就转去干瓦工了,花名册上的工种一直没改。老周又拨了名单上第二个号码,是空号。第三个人倒是接了,说人还在城西那片赶工,半个月抽不出身。

老周把情况反馈给总部对接人,对方说花名册按季度核一次,城东这批本来更新就慢,让他自己再想办法。老周没再指望名单,翻出手机通讯录,一个一个给以前搭过班的老熟人打电话,托他们问问谁认识城东靠谱的水电工。绕了三层关系,总算凑齐了人,比原计划晚开工两天。

### 概念解析

**概念名称**:Agent 发现机制(Agent Discovery),属于多 Agent 系统设计/分布式系统互操作问题域。

**学习卡片**
- 核心张力:提前手动配置/依赖中心化目录(当前唯一可用、可控,但覆盖范围和更新时效有限)vs 真正自主、动态发现任意协作对象的能力(理想目标,但几乎没有生产级实现,尤其去中心化方向)。
- 关键不变量:无论用哪种方式,"知道对方存在、能查到对方信息"和"真正能顺利协作起来"是两件独立的事——查到不等于能用。
- 触发条件:当协作范围超出预先配置或登记覆盖的范围时(新场景、新类型的协作对象),发现机制的真实上限才会暴露。
- 常见误解/失败模式:把"有一个可查询的目录"误当成"具备自主发现能力";忽视目录信息本身会过时、覆盖不全,导致"查得到"但"接不上"。
- 非适用边界:如果协作范围本来就封闭、固定,不会扩张到目录之外(比如内部几个固定系统互相调用),静态配置本身就是合适方案,不需要为不会发生的"扩展"预留发现机制。

**一句话核心定义**:Agent 发现机制是一个 Agent 找到、识别并了解另一个 Agent 能力的方式,现实中几乎都停留在提前手动配置或依赖集中式目录,离真正开放、自主的发现仍有明显差距。

**它试图解决的问题**:在协作对象的数量和范围不断变化时,如何让一方能够找到并了解另一方的能力,而不需要每次协作前都由人工重新对接。

**故事元素映射**:
- 老周 = 需要发起协作的一方,对应发起查找请求的 Agent。
- 城西的固定熟人 = 静态/手动配置:提前建立好的、数量有限的已知连接。
- 总部花名册 = 集中式目录:可按需查询,但覆盖范围和更新时效取决于维护方。
- 名单上号码已空、师傅已转行、人在外地抽不出身 = 目录信息过时、覆盖不全导致的"查得到但用不了"。
- 打电话问老熟人拼凑团队 = 现实中弥补缺口的手段——退回到人工关系网,而不是真正的自动发现。
- 比原计划晚开工两天 = 发现机制的真实成本被低估:能查到名字不等于协作能顺利落地。

**比喻边界**:故事把"发现"简化成打电话确认对方还在不在这行,现实中的发现机制还涉及标准化的能力描述、身份验证、协议兼容性等更复杂的问题——即便信息准确及时,两方能否真正协作,还取决于它们是否说同一套"语言"(接口、协议),这一层故事里没有展开。

**非适用例**:如果老周只固定跟三个长期合作的师傅接活,从不接不熟悉片区的单子,那这就是一个封闭、稳定的协作范围,直接用熟人电话簿就够了——这种场景不需要讨论发现机制的覆盖上限,因为它从未被真正测试到。

**现实例子**:论文分析的 9 个 Agent 通信协议中,8 个依赖静态配置或集中式目录(如 A2A 的 Agent Card),只有 LMOS 一个尝试去中心化 P2P 发现;几乎所有宣称"接入上千个 Agent 自主协作"的产品演示,背后都是工程师提前配置好的连接,而非真正开放网络中的自动发现。

### 检验问题

1. 理解检验:老周查花名册,确实查到了一个"水电,五星"师傅的名字和电话,但最终没能顺利接上活——问题出在"查"这个动作本身失败了,还是别的环节?
2. 迁移检验:如果一个多 Agent 系统的宣传语是"可接入任意第三方 Agent,自动匹配最合适的协作对象",你会追问哪些问题,来判断这是真正的动态发现,还是本质上仍是提前配置好的静态/集中式方案?

## 四种发现方式

| 方式 | 含义 | 代表协议 | 规模上限 |
|------|------|---------|:-------:|
| **静态** | 必须提前手动配置对方地址 | MCP, LAP, agents.json | ❌ 无法扩展 |
| **集中式** | 注册中心维护 Agent 目录，按需查找 | A2A, ACP, agntcy, ANP | ⚠️ 中心化瓶颈 |
| **部分去中心** | 少量超级节点辅助发现 | —（当前无主流实现）| 👍 中等 |
| **去中心化** | P2P 广播，无需中央权威 | LMOS（9个协议中唯一一个）| ✅ 真正可扩展 |

**关键数据**：论文分析的 9 个协议中，**8 个依赖静态或集中式发现**，只有 LMOS 真正实现了去中心化发现。

## 现实状况 vs 宣传愿景

**宣传愿景**："Internet of Agents"——Agent 像网页一样，自主地在全球范围内发现彼此、协作完成任务。

**现实情况（2026）**：所有你能在产品里用上的多 Agent 系统，Agent 发现都依赖提前的人工配置或集中注册中心。

```
宣传说的：Agent A → [自动搜索] → 找到 Agent B → 自主协作
实际上的：人工配置 Agent A 的地址 → Agent B 提前注册到注册中心 → 手动建立连接
```

**这意味着**：所有"AI Agent 自主协作"的产品演示，背后都有工程师提前做好了连接配置。自主性是在已知 Agent 集合内的自主，不是开放网络中的真正自主。

## 产品决策要点

**现在（2026）该怎么做**：
- 接受静态/集中式发现的现实，不要在产品规划里假设 Agent 能"自动找到"未预先配置的服务
- 用 Agent Card（A2A 的方式）做 Agent 能力的标准化描述，为将来的动态发现打基础
- 注册中心方案已经够用——关键是把"Agent 能做什么"描述清楚，不是发现机制本身

**不要被迷惑的几个场景**：
- "我们的平台有 1000 个 Agent 可以协作" → 追问：这些 Agent 是提前注册好的，还是真的能动态发现任意外部 Agent？
- "Agent 会自动选择最合适的工具/Agent 来完成任务" → 追问：从一个预设的列表里选，还是从整个互联网上搜？

**中长期（3-5 年）关注点**：
去中心化发现是论文明确点出的最大研究缺口。一旦出现可用的去中心化 Agent 发现标准，将会显著改变多 Agent 产品的架构可能性。

## 局限
- 去中心化 Agent 发现目前是**最大的未解技术问题**——没有它，"Internet of Agents"停留在愿景层面
- 集中式注册中心面临单点故障风险和规模瓶颈，但目前没有更好的替代
