# 函数调用与工具使用

## 一句话定义
函数调用（Function Calling）是大语言模型通过结构化输出触发外部工具、将自然语言推理延伸至真实世界操作的核心机制。

## 寓言学习

### 寓言正文

阿哲入职三个月，第一次报销出差费用，在系统里填了"其他费用"，金额栏规规矩矩填了"300"，格式一点问题没有。财务当天就把单子退回来了，备注写着"用途不明，无法核对预算科目"。阿哲改了两次，把说明写清楚："7月3日出差北京，机场到客户办公室往返网约车费，发票已附"——同样的300元，同样的数字格式，这次一次就批了。

后来阿哲学乖了，一次要报四笔不同款项——打车、住宿、餐补、打印，他不再一笔笔提交等批完再交下一笔，而是把四张单子一起交上去，财务那边同时处理，四笔一起下来的时间比排队报快了不止一倍。

公司后来把报销系统跟行政的用品申领系统、IT 的设备申请系统对接到了同一个电子入口——以前市场部报销走一套流程，技术部申领电脑走另一套流程，各自要学一遍规矩；现在不管报的是差旅费还是申领的是新键盘，入口都是同一个，单子里该填什么字段、说明要写多细，各自还是各自的规矩，只是不用再为每个部门重新学一遍"往哪儿交、怎么交"。

### 概念解析

**概念名称**：函数调用与工具使用（Function Calling / Tool Use），属于 LLM Agent 系统设计中的"语言到行动"接口问题域。

**学习卡片**
- 核心张力：让语言输出自由表达意图（灵活但无法被系统直接执行）vs 用结构化申请单精确表达意图（可执行，但要求填写规范）。
- 关键不变量：申请单里"说明文字"的清晰度对处理准确率的影响，通常比数值/类型字段是否合规更大；同一时刻提交的多张独立申请单可以并行处理，不必排队串行等待。
- 触发条件：语言输出需要触发外部真实动作（转账、发货、改库存、发通知），而不只是给出一段回答文字时。
- 常见误解/失败模式：把说明文字写得笼统、字段格式虽对但语义不清，导致后台处理出错；把"申请单该长什么样"（调用约定）和"申请单通过什么统一渠道送到哪个系统"（传输/接入协议）混为一谈。
- 非适用边界：只是口头交流、不产生任何需要外部系统执行的动作，不需要走结构化申请单流程。

**一句话核心定义**：函数调用是让语言模型把"我想做什么"输出成结构化、可被宿主系统解析执行的申请单，而不是自由文本，从而把语言推理接到真实世界的操作上。

**它试图解决的问题**：语言模型本身不能直接执行代码或操作外部系统，函数调用解决的是"语言输出如何被准确无误地转译成一次真实执行"。

**故事元素映射**：
- 阿哲 = 语言模型，负责表达意图（该报销什么）。
- 报销单的说明文字 = 工具的 description 字段，其清晰度比参数格式更影响执行准确率。
- 一次提交四张单子、财务同时处理 = 并行函数调用，把多次串行执行压缩成一次并发处理。
- 报销、申领对接到同一个电子入口 = MCP 作为标准化传输层，解决的是"渠道统一"，不是"单子该怎么填"这件事本身。

**比喻边界**：故事里申请单的字段是提前定好的，现实中工具 Schema 的设计本身就是一项需要反复打磨的工程工作（粒度过粗、字段过多都会拉低模型的调用准确率），寓言没有展现这个设计过程本身的复杂度。

**非适用例**：如果阿哲只是找同事口头吐槽"这次报销好麻烦"，没有触发任何系统要处理的动作，这就是普通对话，不涉及申请单流程。

**现实例子**：现代 LLM 平台（GPT-4o、Claude 3.5）支持单次推理中输出多个工具调用，宿主并发执行后统一回注，在"同时查天气+查日历+查联系人"这类信息聚合任务中，能把延迟降低 60% 以上；而 Anthropic 2024 年发布的 MCP，解决的正是"同一套工具怎么被不同客户端复用"的传输层标准化问题，与函数调用本身的调用语义是两回事。

### 检验问题

1. 理解检验：阿哲第一次报销被退回，问题出在金额"300"这个数字的格式上吗？如果不是，真正出问题的是申请单的哪个部分？
2. 迁移检验：如果一个系统里，不同部门用不同的接口协议对接同一个 AI 助手，助手每换一个部门就要重新学一套调用格式——这属于"申请单该怎么填"的问题，还是"申请单通过什么渠道送达"的问题？为什么？

## 核心原理

### 机制本质
LLM本质上是文本预测器，无法直接执行代码或访问外部系统。函数调用通过约定的协议，让模型输出一个结构化的"意图声明"（而非自由文本），宿主系统解析该声明并代为执行，再将结果回注对话上下文，形成闭环。

### JSON Schema 工具定义
每个工具以 JSON Schema 描述其签名：名称、描述、参数类型与约束。模型在推理时将这些 Schema 注入 System Prompt 或专用 Token 空间，推理过程中"选择"调用哪个工具并填写参数。质量上，工具描述的自然语言部分（description 字段）对调用准确率的影响往往大于参数类型约束本身。

### 并行函数调用
现代实现（GPT-4o、Claude 3.5）支持在单次推理中输出多个工具调用，宿主并发执行后统一回注。这将多步串行工具链压缩为一次模型调用，在信息聚合类任务（同时查天气+查日历+查联系人）中延迟可降低 60% 以上。

### 三大平台实现差异

| 维度 | OpenAI | Anthropic | Google Gemini |
|------|--------|-----------|----------------|
| 协议名称 | Function Calling / Tools | Tool Use | Function Calling |
| 并行调用 | 支持（tool_calls 数组） | 支持（tool_use block） | 支持 |
| 强制调用 | tool_choice: required/forced | 无直接等价，需 Prompt 引导 | ANY / AUTO |
| 流式支持 | 支持增量 delta | 支持 input_json_delta | 支持 |
| 结果注入格式 | tool 角色消息 | user 角色 tool_result block | functionResponse |
| 扩展能力 | Code Interpreter、Retrieval | Computer Use、Files | Code Execution、Grounding |

## 演进时间线

- **2023-03**：OpenAI 在 GPT-3.5/4 引入 Function Calling，工具调用第一次成为 API 一等公民。
- **2023-06**：Toolformer 论文（Meta）展示模型可自监督学习何时调用工具，奠定理论基础。
- **2023-11**：OpenAI DevDay 发布 Parallel Function Calling，支持批量工具调用。
- **2024-04**：Anthropic Claude 3 引入 Tool Use，格式与 OpenAI 有差异但语义等价。
- **2024-11**：Anthropic 发布 Model Context Protocol（MCP），将工具定义、传输、认证标准化为跨客户端协议。
- **2025-Q1**：主流框架（LangChain、LlamaIndex）统一适配 MCP，工具市场生态初步形成。

## MCP 的角色
MCP（Model Context Protocol）是工具使用的**标准化传输层**。类比：Function Calling 是"调用约定"（calling convention），MCP 是"总线协议"（bus protocol）。MCP 解决的是工具如何被发现、认证、跨应用复用的问题，而非调用本身的语义。一个 MCP Server 可以向任意兼容客户端暴露同一套工具，无需为每个 LLM 平台单独适配。

## PM 决策视角

### 工具设计原则
1. **粒度原则**：工具应原子化，避免"上帝工具"（一个工具做太多事）。粒度过粗导致参数空间爆炸，模型填参错误率上升。
2. **描述质量**：description 字段是"给模型的 API 文档"，比正式参数约束更影响调用准确率。投入描述撰写的时间往往 ROI 最高。
3. **错误设计**：工具应返回结构化错误（而非抛异常），让模型有机会重试或降级。
4. **幂等性**：写操作工具尽量设计为幂等，因为模型可能因上下文混淆重复调用。

### 平台选型建议
- 需要最大生态兼容性 → OpenAI Tools 格式（最多第三方支持）
- 需要 Computer Use / Files → Anthropic
- 需要原生 Google 服务 Grounding → Gemini
- 跨平台工具复用 → 优先接入 MCP，抽象平台差异

## 工具调用优化：用 EFC 的 I/V/R 因子指导返回设计

Agent-Harness 有效反馈计算扩展律（EFC，见 [[Wiki/概念/04_Agent框架/Harness设计模式]]）发现，工具返回内容的"质量"（而非返回速度或数据量）才是决定任务成功率的主导因素，可拆解为三个可操作的设计维度：

- **信息量 I**：返回是否包含 Agent 尚不知道的新信息？例如报错时返回具体的错误堆栈（高 I）远优于笼统的 `{"status": "failed"}`（低 I）。
- **有效性 V**：返回是否实际改变了 Agent 的下一步决策？格式正确但语义空洞的返回（如重复确认已知状态）即使调用成功，V 也接近 0。
- **不冗余 R**：连续调用的返回是否与之前高度重复？对同一状态的重复查询应被去重或摘要压缩，而非原样堆入上下文。

工程含义：优化工具调用不应只盯着"减少调用次数"或"压缩返回体积"，而应优先诊断返回内容的 I/V/R 是否偏低——论文实测显示多数 harness 只有 15%-45% 的计算量转化为有效反馈，其余被低信息量/低有效性/高冗余的返回浪费掉。
