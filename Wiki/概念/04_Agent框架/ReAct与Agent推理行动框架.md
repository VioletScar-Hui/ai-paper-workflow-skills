# ReAct 与 Agent 推理行动框架

> **一句话定义**：ReAct 将"推理（Reason）"和"行动（Act）"交错进行——模型不仅采取动作（工具调用），还显式生成思维步骤（Thought），形成 Thought→Action→Observation 循环，是所有现代 Agent 框架的直接原型。

---

## 寓言学习

### 寓言正文

社区诊所周一上午，候诊的人排到走廊。老陈接诊第一个病人：乏力、心口闷、体重掉了些。他瞄一眼病历，凭经验觉得可能是甲状腺、贫血、心脏，三个方向都想到了，于是一口气开出血常规、甲功五项、心电图、腹部超声四张单子，让病人自己拿去排队做，他转头就接诊下一个人，中间没停下来看任何一张单子的结果。病人跑了一上午，四项全做完，拿着报告回来找他。老陈这才对着报告一张张看：血常规已经能说明是贫血引起的乏力和体重下降，心电图其实不用开；甲功五项报告里最要紧的促甲状腺激素那一项，因为检验科当时缺试剂没做，得再让病人跑一趟去补。病人前后跑了两趟，多耗了大半天。

隔壁诊室的小林，这天接的是个反复腹痛的病人。他没开任何检查单，坐在桌前把病人说的每处不舒服在脑子里过了一遍，想了小十分钟，觉得像是老毛病肠胃炎，直接开了肠胃药让病人回去吃。病人吃了三天没见好，自己去了大医院，做超声一查，是胆囊出了问题——跟小林脑子里想的对不上。

老陈中午听说了这事。下午来了个关节疼、低烧反复的病人，他换了个做法：先开口说"我现在怀疑是感染，所以先查血常规和C反应蛋白"，报告出来，他看着数值说"炎症指标偏高，那我把范围缩小到风湿这一类，接下来查类风湿因子"；这张报告出来，他又说"这项也是阳性的,基本能定下来了，我再开一张关节超声确认范围就够"。三张单子分三次开，每次都是先说清楚当下怀疑什么、为什么开这张，报告一出来就先说这项结果说明了什么、怀疑范围因此怎么收窄，再决定下一张开什么。病人上午就把病看完，没再跑第二趟。

### 概念解析

**概念名称**：ReAct（Reasoning + Acting）框架，属于 LLM Agent 系统设计 / 提示范式问题域。

**学习卡片**
- 核心张力：只行动不显式思考（行动像黑盒，容易多开、漏开、走弯路）vs 只思考不行动验证（脑内推理没有外部结果校准，容易凭空下错结论）——两者不能互相替代，"想"和"做"必须交织推进。
- 关键不变量：每一次行动前先生成一步显式的中间判断（说明当前怀疑什么、为什么要这么做），行动的结果出来后，先用这个结果更新判断，再决定下一次行动，如此循环，而不是行动和思考各自独立发生。
- 触发条件：任务需要多步完成，且每一步该做什么依赖上一步的结果（多跳信息收集、诊断类任务、需要外部反馈验证假设的任务）。
- 常见误解/失败模式：把所有可能用到的行动一次性连续发出、中途不看任何一个结果（对应纯行动模式，容易多开漏开、出错要返工）；或者只在脑内推演却不采取任何行动去验证，结论和真实结果对不上（对应纯推理模式，凭空下错结论）。
- 非适用边界：任务本身一步就能确定、或者每次行动成本极高、不能反复试探时（比如结果不可逆、资源只有一次），交错试探式的做法不划算，应该一次性想清楚再行动，或者干脆走一套固定流程。

**一句话核心定义**：ReAct 是让模型在每次行动前先显式生成一步中间判断（当前怎么想、为什么这么做），行动后再用观察到的结果更新这个判断，如此反复推进，让"想"和"做"相互校准的循环范式。

**它试图解决的问题**：纯行动模式下，工具调用之间没有显式的中间判断支撑，行动是黑盒，容易走弯路、白跑一趟；纯推理模式下，模型只能靠脑子里已有的信息推演，没有外部结果验证假设，容易得出经不起检验的结论。ReAct 要解决的是怎么让"想"和"做"互相喂养、彼此校准。

**故事元素映射**：
- 老陈上午一口气开四张单子、中途不停下来看任何一张结果 = 纯行动模式：行动连续发生但没有显式的中间判断穿插，是黑盒操作，容易多开漏开，出错要返工。
- 小林只想不查、凭脑内推断直接下结论开药 = 纯推理模式：只有内部判断没有外部行动去验证，结论和真实结果（复查结果）对不上。
- 老陈下午换的做法——每开一张单前先说当下怀疑什么，结果出来先说明这个结果意味着什么、怀疑范围怎么收窄，再决定下一步查什么 = 交错循环：行动前先显式生成判断，行动后的观察结果被显式整合进下一步判断，判断和行动交替推进。
- 病人上午就看完、没再跑第二趟 = 交错模式的结果：比单纯行动更少走弯路，比单纯推理更贴合真实结果，效率更高。

**比喻边界**：故事把"中间判断"简化成医生说出口的一句话，但真实框架里这一步判断的质量完全取决于底层模型的推理能力——模型说出的"怀疑"未必总是合理，也可能像那两位不理想的问诊一样想错方向；故事也没有展现真实系统里判断与行动格式对不上导致解析失败、长任务里判断链堆积超出上下文窗口这类工程问题，这些是真实场景要额外考虑的。

**非适用例**：如果病人是普通感冒，看一眼症状就能确定用药，不需要开任何检查单——这种一步到位、不涉及多轮外部验证的简单问诊，套用"先说怀疑、再查、再调整"这套循环反而是多此一举，直接一次判断到位即可。这套循环针对的是需要多步骤、且步骤之间彼此依赖的任务，不是所有任务都要走一遍。

**现实例子**：模型在做需要多次检索的问答任务时，先说一句"我需要先查X来确认Y"，调用搜索工具拿到结果后，再说"根据这个结果，我还需要查证Z"，如此判断和行动交替进行，而不是一次性把所有可能用到的检索请求都发出去、也不是完全不检索凭内部知识直接作答。

### 检验问题

1. 理解检验：老陈上午问诊出问题、下午问诊顺利，两次的关键差别不在"手艺"或"经验"，而在哪个具体环节？请说出这个环节。
2. 迁移检验：一个 AI 客服在处理"用户投诉商品破损要退款"这类需要先核实订单、再核实破损照片、最后决定是否退款的多步任务时，你觉得该用"一次性把所有可能用到的工具全部调用一遍再统一看结果"，还是用"每步先说明当前判断依据、调用一个工具、再根据结果调整下一步"？为什么？

## ReAct 的核心范式

```
传统方式：
  [行动模式] 模型 → Action（调用工具）→ Observation → Action → ...
  [推理模式] 模型 → Thought → Thought → Answer（不能用工具）
  
  → 两种模式不能共存，"想"和"做"分离

ReAct：
  [Thought] 我需要搜索 X 来回答这个问题
  [Action]  Search("X")
  [Observation] 搜索结果：...
  [Thought] 根据结果，我需要进一步查找 Y
  [Action]  Search("Y")
  [Observation] 搜索结果：...
  [Thought] 现在我有足够信息了
  [Action]  Finish("最终答案")
  
  → 推理和行动交织：推理引导行动，行动的观察结果反馈给推理
```

## 为什么 ReAct 有效？

```
关键洞察1：推理步骤本身就是有价值的中间状态
  Thought 让模型"知道自己在哪里"、"下一步该做什么"
  没有 Thought → 工具调用就是黑盒，模型迷路

关键洞察2：观察结果需要被推理整合
  Observation → 下一个 Thought（整合信息）→ 下一个 Action
  简单行动-观察循环无法处理多跳推理

关键洞察3：错误恢复需要推理能力
  Thought："上一步的结果不够准确，我换个搜索关键词"
  → 只有 Action/Observation 循环无法做到反思式错误恢复
```

## ReAct 的局限与演进

```
ReAct 的问题：
  1. Thought 质量依赖基础模型推理能力（早期模型 Thought 质量差）
  2. 工具调用格式需要精确遵循（格式错误 → 解析失败）
  3. 状态追踪完全在 LLM 上下文中 → 长任务中状态丢失

演进方向：

1. Harness 外化状态（论文39，Harness-1）：
   Thought 只做语义决策
   状态管理交给外部 Harness
   → 解决状态追踪问题

2. Toolformer（论文74）：
   模型自学何时/如何调用 API
   通过自监督学习决定插入 API 调用
   → 解决工具调用格式问题

3. Function Calling（OpenAI API）：
   强制 JSON 格式的工具调用
   Harness 解析执行，结果返回
   → 工业标准化的 ReAct 实现

4. 推理模型（o1/R1）：
   内部 Thought 极大加长（Long CoT）
   Thought 对用户不可见
   → ReAct + 长推理链的融合
```

| 框架 | Thought 实现 | Action 实现 | 状态管理 |
|------|------------|-----------|---------|
| **LangChain Agent** | 模型自生成 | Function Calling | 上下文窗口 |
| **LangGraph** | 模型自生成 | 节点-边图 | 外部图状态 |
| **Claude 工具使用** | 内部 Extended Thinking | Tool Use XML | 上下文+外部 |
| **Harness-1（论文39）**| 纯语义决策 | 工具调用 | 完全外化（7组件）|
| **AutoGPT** | 自生成计划 | 代码执行 | 文件系统 |

## 什么情况 ReAct 失败？

```
1. 工具返回错误或无用信息
   Thought 卡住，无法推进
   对策：Harness 层的错误处理 + 重试机制
   
2. 推理和行动不对齐
   Thought 说"我要搜索X"，但 Action 调用了错误工具
   对策：训练时强化 Thought-Action 一致性
   
3. 长任务上下文溢出
   Thought-Action-Observation 堆积 → 超出 context window
   对策：定期压缩历史 + 状态外化
   
4. 循环行为（Action Loop）
   同样的 Action 被重复调用
   对策：Harness 维护搜索历史，检测重复
```

## PM 视角的关键判断

| 问题 | 答案 |
|------|------|
| "Thought 对用户是否可见？" | 取决于产品设计；o1 不可见，Sonnet 可以用 Extended Thinking 可见 |
| "Thought 消耗 token 吗？" | 是的，Thought 每步都有 token 成本 |
| "ReAct vs 纯 Function Calling？" | ReAct 有 Thought 步骤（更可解释，更贵）；FC 无 Thought（更快，更便宜）|
| "Agent 调试怎么做？" | Thought 是最好的调试日志！保存并分析 Thought 链 |
