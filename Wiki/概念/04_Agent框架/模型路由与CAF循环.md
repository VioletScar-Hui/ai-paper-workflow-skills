# 模型路由与 C-A-F 循环（Model Routing & Context-Action-Feedback Loop）

> **一句话定义**：将每个用户任务动态分发给最适合的 LLM（而非总用同一个），通过 Context→Action→Feedback→Context 的闭环不断积累经验、提升路由精准度，同时降低成本。

## 寓言学习

### 寓言正文

转运站里，班长要把每天到的包裹分给三条线：手脚麻利但偶尔磕碰的甲线、动作稳但慢一拍的乙线，还有专门走冷链的丙线。班长刚接手那阵子，全凭包裹外包装"看着像什么"来分——纸箱看着结实就分去甲线，哪怕里面装的是易碎的玻璃制品，也照样分过去，磕坏了才知道分错了。

后来班长养成了个习惯：分线之前先翻一眼每周的货损统计表——不再单看包裹外观的第一印象，而是先查"这一类包裹过去分到哪条线，破损率最低"，再照着这个记录分线。同样一批易碎品，翻过记录之后大多分去了乙线，破损率明显降了下来，比她自己再怎么仔细端详外包装都管用。

每条线分拣完，质检口还会实际拆箱抽检，记录这一趟到底有没有真的完好送达——这份记录不是分线时凭感觉打的分，而是拆箱看到的真实结果，这份结果又会汇进下周的货损统计表，供下一次分线参考。有一次丙线新来的司机图省事，自己在交接单上写了"本趟全部完好"，没等质检口拆箱核实，这一条记录被直接当真送进了统计表——后来发现那趟其实有两件货在冷链中途化了冻，可账面上的"完好"记录已经混进了历史数据，往后好一阵子丙线的破损率统计都失真了。

### 概念解析

**概念名称**：模型路由与 C-A-F 循环，属于多 LLM 系统设计 / 成本与性能优化问题域。

**学习卡片**
- 核心张力：凭第一印象/直觉当场分派任务（快，但容易带偏见、越用越偏）vs 参考历史同类任务分给谁、结果好不好的记录再决定（多一步查询，但更准）。
- 关键不变量：分派准确率的提升主要来自"有没有可靠的历史结果统计"，而不是分派者本身想得多深；分派后必须有独立于分派者之外的真实核验（拆箱抽检，而非分派者自己说了算），这份核验结果才能被信任地记入历史统计，供下一次分派参考。
- 触发条件：任务类型混杂、多个处理者各有强项弱项，且每次分派之后能获得真实结果反馈时。
- 常见误解/失败模式：只凭对处理者的第一印象或包裹外观分派，不追踪真实结果，导致分派越用越偏；把处理者自称的结果（未经独立核验）当真实反馈写入历史记录，污染后续所有决策依据。
- 非适用边界：只有一种任务类型或只有一条处理线，不存在"分给谁"的问题，不需要这套分派+核验+记忆的闭环。

**一句话核心定义**：模型路由是把每个任务动态分给最合适的处理者，并通过"分派→核验→记入历史→再分派"的闭环不断积累经验、提升分派准确率的机制。

**它试图解决的问题**：面对多种类型的任务和多个各有所长的处理者，如何让"分给谁"这个决策越用越准，而不是始终停留在凭第一印象判断的水平。

**故事元素映射**：
- 班长 = 编排器（Orchestrator），负责查历史、做分派决策。
- 甲/乙/丙三条线 = 模型池中各有所长的候选模型。
- 货损统计表 = 记忆模块（Memory），存储历史任务-决策-结果三元组。
- 质检口拆箱抽检 = 验证器（Verifier），独立于分派决策的确定性结果核验。
- 司机自己写"全部完好"未经核实就录入统计表 = 缺失独立验证的反馈污染了记忆模块，导致后续分派依据失真。

**比喻边界**：故事里货损统计表相对简单，现实中的路由记忆模块要支持按相似任务做 kNN 检索，且需要专门的评估指标（累积遗憾）来衡量分派策略与"每次都选最优"之间的差距，故事没有展现这套定量评估过程。

**非适用例**：如果转运站只处理一种包裹、只有一条线，不存在"该分给哪条线"的问题，直接送上那条线就行，不需要货损统计表和历史查询这一整套机制。

**现实例子**：论文《Agent 路由器》的实测发现，给路由器补充"历史性能统计"信息后，平均性能分从零样本基线的 41.41% 提升到 47.74%（+15.3%），提升幅度超过单纯改进路由器本身的推理能力——这与故事里"翻货损统计表比再怎么端详包装都管用"是同一个道理，评估路由策略优劣时用的"累积遗憾"指标，衡量的正是与"每次都选最优处理线"之间的差距。

### 检验问题

1. 理解检验：班长后来分线准确率提升，靠的是她把包裹端详得更仔细了，还是别的什么？
2. 迁移检验：如果一个系统的"验证结果"其实是由做决策的同一个模型自己打分给出的（而不是独立的核验环节），结合这个故事，你觉得这套记忆库积累下来的历史数据还可靠吗？

## 解锁了什么产品能力

- **性能 + 成本双赢**：把简单任务路由到便宜小模型，复杂任务到强大模型，不用每次都调用最贵的 LLM
- **超越任意单一模型**：跨模型的最优路由理论上超过最强单模型（因为每个模型有擅长的任务类型）
- **自适应优化**：路由系统在运行过程中积累经验，越用越准

## C-A-F 循环架构

```
              ┌──────────────────────────────┐
              │         记忆模块（Memory）      │
              │  历史任务-决策-结果 三元组       │
              │  kNN 检索相似历史              │
              └──────────┬─────────────────┬─┘
                         │ 查历史经验        │ 存新经验
                         ↓                  ↑
任务 t_i → [Context c_i] → 编排器决策 → [Action a_i: 选模型] 
              ↑                                  ↓
              └── [Context c_{i+1}] ←── [Feedback f_i: 得分+成本]
                        更新                 验证器执行 + 打分
```

**三个核心模块**：
1. **Orchestrator（编排器）**：结合历史经验 + 任务元数据，选择模型（核心是 Qwen3.5-0.8B 微调版 + 启发式规则投票）
2. **Verifier（验证器）**：执行模型输出（沙箱运行），生成真实得分（AST解析 + 代码执行）
3. **Memory（记忆）**：存储历史经验，支持 kNN 检索"哪类任务用哪个模型最好"

## 关键发现：路由瓶颈是信息缺失，不是推理能力

| 路由器配置 | 平均性能分 | 提升 |
|-----------|---------|------|
| Vanilla（零样本）| 41.41% | baseline |
| + 任务维度信息 | 43.xx% | +小幅 |
| **+ 历史性能统计** | **47.74%** | **+15.3%** |
| 最优单一启发式路由 | 47.50% | 对比项 |
| Per-task Oracle | 更高 | 上界 |

**结论**：给 LLM 路由器补充"历史经验统计"比改进其推理能力收益更大。

## 评估指标：累积遗憾（Cumulative Regret）

```
CumReg(π) = Σ(最优决策奖励 - 实际决策奖励)

越低 = 越接近"每次都选最优模型"的理论上界
适合流式任务评估（每条任务来了就决策，不能提前知道答案）
```

这是一个比"平均精度"更严格的指标，因为它考虑了每次决策的机会成本。

## 落地代价

| 维度 | 评估 |
|------|------|
| 💰 算力 | 低：编排器用 0.8B 小模型，额外开销极小；验证器需要代码执行环境 |
| 📊 数据 | 需要 probing set（历史任务-模型-得分 数据）来初始化；冷启动问题 |
| ⏱️ 延迟 | 验证器执行增加延迟（沙箱运行）；适合异步/批量场景 |
| 🔧 工程 | 开源代码可用；需要沙箱执行环境（代码任务特有） |

## 适用场景

| 场景 | 适用性 |
|------|-------|
| 代码生成/编程助手（不同任务类型差异大） | ✅ 最适合（论文验证场景） |
| 多类型任务混合（代码/数学/写作/分析） | ✅ 适合 |
| 单一同质任务流（如纯翻译） | ⚠️ 提升有限 |
| 实时低延迟（<100ms） | ❌ 验证器执行增加延迟 |

## 局限与生产风险

- **冷启动**：初始无历史经验时路由效果差，需要 probing set 预热
- **验证器依赖可执行性**：非代码任务（如写作、分析）没有客观验证信号
- **模型池固定**：新增/删除模型需要更新历史统计；模型 API 变化影响历史可比性
- **代码任务特化**：论文主要在编程任务上验证，其他领域迁移效果未知
