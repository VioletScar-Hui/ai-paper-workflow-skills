# 动态智能体脚手架（Dynamic Agentic Scaffold）

> **一句话定义**：在推理时由编排器模型按需生成的 Agent 协作结构——路由哪些模型、如何通信、怎么汇总——与预先人工硬编码的固定流程相对。


## 寓言学习

### 寓言正文

深夜食堂只有一个厨师值班，接单全看订单本身：一碗阳春面，他自己下锅、自己装碗，五分钟端出去。碰上一桌要红烧狮子头配三个热炒的宴席单，他一个人根本忙不过来，得从后场喊人：切配的、掌勺的、摆盘的，谁先来、谁接谁的手，都得他现场吼着安排，没有两桌单子的分工是完全一样的。

隔壁连锁店走另一条路：不管来的是什么单，永远是"切配台先处理，传给炒锅台，再传给摆盘台"，三个人各守一个岗位，谁也不用现场商量。新来的服务员一眼就能看懂流程哪一步卡住了。

深夜食堂那晚来了一张写得潦草的订单，厨师扫了一眼以为是道简单小炒，只喊了个帮厨来打下手。菜端上桌客人才说，这其实是要配三道点心的整套宴席，两个人根本忙不过来，出餐拖了四十分钟，配菜的食材还临时多买了一份，最后算下来比走连锁店那套流程贵了不少。

厨师后来复盘，问题不是他手艺不到位，是那晚看订单看错了——他自己就是那个临场分配人手的人，他一旦判断错，喊来的人手就跟着错，没人能替他把这个判断兜住。

### 概念解析

**概念名称**：动态智能体脚手架（Dynamic Agentic Scaffold），属于多智能体系统设计/Agent 编排问题域。

**学习卡片**
- 核心张力：提前固定好协作流程（可控、可审计，但遇到新任务类型会僵化）vs 临场按任务现组织协作结构（灵活自适应，但不透明、出错难溯源，成本难预估）。
- 关键不变量：协作结构（谁参与、什么顺序、怎么汇总）是由一个"调度者"针对当前具体任务临场决定的产物，而不是预先写死的模板。
- 触发条件：任务类型多变、边界模糊，没有一套固定流程能覆盖所有情况时，动态编排才有优势。
- 常见误解/失败模式：调度者本身判断失误，整个协作结构从源头出错，且没有别的机制能纠正；协作成本随任务复杂度浮动，难以提前预算。
- 非适用边界：任务高度重复、流程本身就该标准化（比如合规审批、金融流水），此时固定死的静态流程更可靠、更可审计，动态编排反而增加不必要的不确定性。

**一句话核心定义**：动态智能体脚手架是指在推理时由一个编排模型根据当前具体任务，临场决定调用哪些执行角色、以什么顺序协作、如何汇总结果的协作结构，与预先由人工设计好的固定流程相对。

**它试图解决的问题**：当任务种类太多、边界太模糊，没办法用一套固定的多角色协作模板覆盖所有情况时，如何让协作结构本身随任务自动调整。

**故事元素映射**：
- 深夜食堂厨师 = 编排器（orchestrator），负责临场决定协作结构。
- 现场喊人分工、谁先做谁后做 = 动态选择执行角色（Worker）与协作拓扑（串行/并行/汇总方式）。
- 连锁店固定三个岗位流程 = 静态脚手架，流程透明、可复用，但无法灵活适配特殊订单。
- 厨师看错订单难度、人手安排错误导致出餐延误、成本超支 = 动态脚手架的核心局限：整个系统依赖调度者自身的判断力，调度一旦出错，没有其他机制能兜底纠正。

**比喻边界**：故事把"编排"简化成一个人临场喊人分工，但真实系统中的编排器本身是一个模型，它的决策过程（选模型、定拓扑、合并策略）比故事复杂得多，且往往难以像人一样事后被追问"你当时为什么这么判断"，可解释性比故事暗示的更低。

**非适用例**：如果这家食堂只卖一种阳春面，每天流程完全一样，那就不需要一个临场调度的厨师，直接按固定步骤走标准化流程即可——这种高度重复、边界清晰的场景更适合静态脚手架，动态编排是浪费。

**现实例子**：Sakana AI 的 Fugu 技术报告中，编排器模型根据输入查询实时决定调用哪些子模型、以何种拓扑（串行/并行/辩论）协作、如何合并结果，而不是像 LangChain Pipeline 那样使用人工预先设计好的固定流程图。

### 检验问题
> 判分点随笔记入库；自测先作答再展开。答错即记进「卡点记录」。

> [!question]- 1. 理解检验：故事里厨师那晚出餐延误、成本超支的根本原因是什么？是"手艺不够好"，还是别的什么环节出了问题？
> **参考答案**：不是手艺问题，是编排/调度判断出错——厨师看错了订单难度，喊来的人手配置从源头就错了；动态脚手架的核心局限正是"系统依赖调度者自身的判断力，调度一旦出错，没有其他机制能兜底纠正"。
> **判分点**：必须答出"根因是编排判断而非执行能力"+ 点出"无兜底机制"这一局限（缺一即卡点）

> [!question]- 2. 迁移检验：如果一家银行想用 AI 处理客户的转账申请，你觉得这类任务更适合动态智能体脚手架，还是固定的静态流程？说说你的理由。
> **参考答案**：更适合静态脚手架——转账申请是高度重复、边界清晰、需要合规可审计的场景，对应"非适用边界"里明确排除的情形；动态脚手架的不可解释性和成本不可预估在合规场景是负资产而非优势。
> **判分点**：必须选静态并说出"合规可审计"这一理由，仅说"重复任务"不说合规审计要求算未完全命中


## 与静态脚手架的对比

| | 静态脚手架（传统） | 动态脚手架（Fugu 等） |
|--|--|--|
| 设计时间 | 产品开发时人工设计 | 推理时模型自动生成 |
| 灵活性 | 固定，适配特定任务类 | 任意查询自适应 |
| 维护成本 | 高（新场景要重新设计） | 低（模型自适应） |
| 可解释性 | 高（流程透明） | 低（决策在模型内部） |
| 代表产品 | LangChain Pipeline, AutoGen Graph | Sakana Fugu, Trinity |

## 工程实现方式

```
查询输入 → 编排器 LM 编码
                ↓
    动态决策（三个关键维度）：
    ① 选模型：哪些 Worker 参与？
    ② 定拓扑：串行/并行/辩论/投票？
    ③ 合并策略：直接用最好的？取共识？投票？
                ↓
    运行时构建 Agent 图 → 执行 → 合成输出
```

## 易混淆拷问

- **vs [[Wiki/概念/04_Agent框架/Harness设计模式]]**：Harness 是围绕单个 LLM 策略的执行框架（状态管理/工具调用/错误恢复），解决的是"一个决策者怎么被支持"；动态脚手架是编排器决定"要不要、召集哪些个决策者、怎么组织他们协作"，解决的是"协作结构本身怎么生成"。混用后果：把 Harness 的"状态外化"当成动态脚手架的"协作拓扑生成"，会误以为给单 Agent 配好 Harness 就等于有了多智能体编排能力——两者是正交的设计层，Harness 可以是动态脚手架里每个 Worker 的地基，但不能替代编排器的调度职能。
- **vs [[Wiki/概念/04_Agent框架/学习型编排器]]**：学习型编排器是动态脚手架里"做临场调度决策的那个模型本身"（因），动态脚手架是这个编排器运行后产出的"协作结构"（果）。混用后果：把两者当同义词会导致讨论失焦——"编排器判断错了"和"这次生成的协作结构不合理"是可以分开诊断的两件事，前者是模型能力问题，后者可能是拓扑生成策略问题。

## 产品决策要点

- **当你需要固定可审计的流程时**（合规/金融/医疗）：优先用静态脚手架
- **当你需要覆盖多种任务类型，且任务边界模糊**：动态脚手架有显著优势
- **成本控制**：动态脚手架容易造成"不必要的多模型调用"，需要硬性 budget 限制

## 局限

- 编排决策不透明，难以在出错时定位是哪个 Worker 的问题
- 推理成本随任务复杂度动态变化，成本预算难以估算
- 依赖编排器 LM 自身的能力，若编排判断错误，整体系统会失败
