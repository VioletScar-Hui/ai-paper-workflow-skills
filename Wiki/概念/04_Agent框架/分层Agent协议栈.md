# 分层 Agent 协议栈

> **来源**: 引自 [[06_LLM-Agent通信协议分类]]
> **类型**: 架构预测 / 产品趋势判断
> **关联**: [[MCP]] · [[A2A]] · [[Agent通信三元困境]]
> **成熟度**: ⚠️ 分析预测，尚未完全成形，但趋势已清晰

## 一句话定义
AI Agent 通信协议不会走向"单一标准赢家通吃"，而是像互联网的 OSI 模型一样，形成**分层的协议栈**——不同层解决不同问题，多协议共存协作。

## 寓言学习

### 寓言正文

工地大门口的登记岗只认一件事：进出的人是谁，刷脸核对身份，一秒钟放行。往里走，材料库房的验收关卡管的完全是另一件事：核对这批钢筋的规格、数量跟采购单是不是对得上，跟"这个人是谁"没有任何关系。每天上午的调度会上，电工队和水暖队对着同一张进度表交接谁先谁后进场施工。最底下，工地所有设备最终都接到市政统一供的那一路电上，谁也绕不开它。

新来的项目经理觉得四道关卡太麻烦，想推一张"一卡通"——刷同一张卡进大门、领材料、连电闸都用它开。用了两周就出问题：材料验收要核对的是规格数量，门禁要核对的是人脸和身份，两件事的规则被硬塞进同一张卡的同一套逻辑里，要么门禁为了兼容材料信息变得又慢又繁琐，要么材料验收为了保持门禁的速度而变得敷衍——有一批规格不对的钢筋就这么被放进了工地。

最后工地放弃了"一卡通"，改回四道关卡各管各的规则，只在一件事上做了统一：门口登记的那串人员编号，材料库和调度会都认得出、对得上号。谁负责什么、怎么核对，还是各自的老规矩。

### 概念解析

**概念名称**：分层 Agent 协议栈，属于 AI Agent 通信协议架构 / 系统设计问题域（架构预测类概念，尚未完全定型）。

**学习卡片**
- 核心张力：用一套统一的规则/接口覆盖所有不同性质的协作问题（简单，但顾此失彼）vs 按问题性质分成几层、每层各管一段、层间只用少量标准接口对接（复杂一点，但每层都能把自己的问题做到位）。
- 关键不变量：没有一套规则能同时在多功能性、效率、可移植性上都做到最优——身份核验、内容核对、进度协调这些性质不同的问题硬塞进同一套逻辑，必然要牺牲其中一项；层与层之间只需要在少数"公共编号/接口"上对齐，不需要每层用同一套细则。
- 触发条件：系统内同时存在多种性质不同的协作/通信需求（比如"我是谁" vs "这批东西对不对" vs "谁先谁后"）时。
- 常见误解/失败模式：迷信"一套万能规则/协议能解决所有层的问题"，强行统一后要么某一层变笨重、要么某一层变敷衍；反过来完全不做层间对接，每层各自为政导致互相认不出对方的凭证。
- 非适用边界：系统内部通信角色单一、不跨越"身份/内容/协调/底层连接"这几类不同性质问题，不需要分层设计，一套规则就够。

**一句话核心定义**：AI Agent 通信协议不会收敛成单一大一统标准，而会像工地的多道关卡一样，按问题性质分层，每层用各自最合适的规则，层间通过少量标准接口对接。

**它试图解决的问题**：判断"要不要押注某个协议成为解决 Agent 通信一切问题的唯一标准"，以及在采购/技术选型时该按什么框架去做取舍。

**故事元素映射**：
- 四道关卡（门禁、材料验收、调度会、供电）= 协议栈的四层（能力发现/身份、工具数据接入、Agent 间协作、底层模型 API），每层解决性质不同的问题。
- "一卡通"改造失败 = 押注单一协议同时覆盖所有层，导致效率或功能其中一项被牺牲。
- 门口人员编号在各关卡通用 = 层间通过标准接口对接，而不是要求各层用同一套细则。

**比喻边界**：故事里的四道关卡是相对稳定、边界清晰的，现实中的 Agent 协议栈里"能力发现层"和"身份/安全层"这两层的标准还没有收敛，处于研究阶段，故事没有展现这种不确定性本身。

**非适用例**：如果工地只有一道岗亭，一个人既登记身份又顺手看看材料对不对，规模小、角色不复杂，就不需要拆成四层各自建规则——这对应通信需求单一、不涉及多种性质问题的小系统，不需要分层协议栈。

**现实例子**：目前 MCP（LLM ↔ 工具/数据接入）与 A2A（Agent ↔ Agent 协作）已经形成事实上的标准组合，Google 官方也把 A2A 定位为 MCP 的互补协议而非替代品——这正是"当前收敛的两层"，而"能力发现层"和"身份安全层"仍然是空白，尚待新协议填补。

### 检验问题

1. 理解检验：故事里"一卡通"失败，问题出在门禁和材料验收谁的规则更好，还是出在别的地方？
2. 迁移检验：如果有厂商告诉你"我们的协议能同时解决 Agent 身份认证、工具调用和 Agent 间协作三件事"，结合这个故事，你会用什么问题去追问它做了哪些取舍？

## 类比 OSI 模型

| OSI 网络层 | Agent 协议栈（预测）| 代表协议 |
|-----------|-------------------|---------|
| 应用层（HTTP/SMTP）| Agent 间任务协作 | [[A2A]] |
| 传输层（TCP）| Agent 工具 / 数据接入 | [[MCP]] |
| 网络层（IP）| Agent 静态能力发现 | agents.json |
| 物理层 | 底层 LLM API | OpenAI/Anthropic/etc. |

**核心逻辑**：每一层解决一类问题，层间通过标准接口对接。上层协议不需要关心下层的实现细节。

## 当前已收敛的部分

**MCP + A2A 正在成为实际标准组合**：
- MCP：LLM ↔ 工具/数据（已是行业标配 ✅）
- A2A：Agent ↔ Agent（正在成为标准 🏭）
- Google 官方定位 A2A 为 MCP 的互补协议，而非替代

```
用户
  ↓
主 Agent（通过 A2A 协调其他 Agent，通过 MCP 调用工具）
  ├── 子 Agent A（A2A 接入）
  ├── 子 Agent B（A2A 接入）
  └── 工具（MCP 接入）：数据库 / 搜索 / API
```

## 尚未收敛的部分

- **Agent 发现层**：去中心化发现机制仍是空白（见 [[Agent发现机制]]）
- **运行时协商层**：Agent 动态协商通信格式还是研究阶段
- **身份 / 安全层**：Agent 间身份认证和权限管理标准尚未统一

## 为什么"单一赢家"不会出现

源于 [[Agent通信三元困境]]：
- 没有单一协议能同时最大化多功能性、效率、可移植性
- 历史证明（TCP/IP、HTTP 的演进）：网络标准总是分层的，各层有各自的专属标准

**论文原文结论**："no single protocol is likely to maximize versatility, efficiency, and portability simultaneously. The field will more likely evolve toward a federated, layered protocol stack."

## 产品决策要点

1. **现在**：用 MCP 做工具集成，用 A2A 做 Agent 间通信——这个组合是当前最稳的选择
2. **不要押注单一协议赢定了**：市场上会持续出现新协议，但分层结构不会变——关注你的场景在哪一层，选那一层的最佳协议
3. **识别销售话术**：如果有厂商说"我们的协议能解决 Agent 通信的所有问题"，用三元困境框架追问它的取舍
