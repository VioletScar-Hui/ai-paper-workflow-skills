# Agent 寿命工程

## 一句话定义
Agent 寿命工程研究 AI Agent 在部署后随时间自然老化（性能衰退）的规律，并建立维护策略，使 Agent 在动态环境中保持可接受的任务完成率。

## 寓言学习

### 寓言正文

商场的问询台设在中庭正中间，引导员上岗第一周就把两百多家店的位置、怎么走、电梯在哪层拐弯记得清清楚楚。头三个月里，几乎没人回头找他麻烦——顾客问哪家鞋店、哪层有母婴用品，他张口就来，连哪条通道正在装修都提前提醒一句。

第四个月起，情况开始有点不一样。一个顾客回来找他，说三楼那家他指的运动品牌根本不在原处，问了店员才知道两周前就换了另一个牌子进场。引导员愣了一下，赔了不是，把新位置记下来。这种事一个月总会撞上一两回——不算多，他每次都能当场改口，顾客也没太计较。

半年后赶上换季大促，商场把好几层的临时活动区、快闪店铺全部重新摆过，价目牌也跟着换了一轮。那天中午人流最密的时候，引导员一连给三拨顾客指错了地方——先是报出一个已经撤场的品牌位置，接着把促销区入口的方向说反了，最后连价目牌上的活动时间报的都是上周的版本。有顾客直接找到了服务台投诉。

值班主管把他叫到一边，没说他记性差，只问了一句："你多久回去把楼层重新走一遍、跟店员对一遍最新情况？"引导员想了想，答不上来——上岗培训之后他就再没系统地重新核实过，都是等顾客回头找他，才临时改一条记录。主管定了个规矩：不管当时有没有人投诉，都要隔一段时间主动把楼层重新走一遍，找店员核实清单有没有变。

商场东南角有个开了很多年的小吃区，招牌、菜品、价格几乎没怎么变过。引导员对那一片几乎从来不用特意重新核实，顾客问起来随口一指，很少出错。

### 概念解析

**概念名称**：Agent 寿命工程中的"时间性衰退"（temporal degradation），属于 AI Agent 部署运维、纵向评测与系统工程问题域（AgentOps）。

**学习卡片**
- 核心张力：部署时刻对环境形成的固定认知 vs 环境本身持续变化——两者之间的差距会随时间自然扩大，不会自动弥合。
- 关键不变量：性能下降的根源是"环境状态"和"内部认知"之间的差距在拉大，而不是能力本身在退化；要处理的是"世界变了、没跟上"，不是"变笨了"。
- 触发条件：部署后所处的环境持续发生变化（信息、规则、依赖的外部条件更新），且没有建立定期重新核实的机制。
- 常见误解/失败模式：把偶发的失误当孤立事件临时打补丁，不建立定期重新核实的机制；或者早期错误率低就误判"不需要维护"，直到变化最密集的时段集中爆发，才被迫紧急介入，此时损失已经造成。
- 非适用边界：环境本身几乎不变的场景，差距扩大得极慢，谈不上明显的时间性衰退；此外，"从一开始就不准确"也不属于此列——那是能力不足，不是先准后不准的时间性下滑。

**一句话核心定义**：这个概念描述的是一套系统在部署后，因为所依赖的外部环境持续变化、而自身认知没有同步更新，导致准确率随时间呈规律性下滑的现象，以及针对这种下滑建立定期评测与维护机制的做法。

**它试图解决的问题**：当一套系统部署后表现会随时间自然下滑，且下滑速度和所处环境的变化剧烈程度相关时，如何在问题积累到集中爆发之前，就用定期重新核实、按变化类型归因、决定该打补丁还是整体重建的机制把它兜住，而不是等顾客投诉了才补救。

**故事元素映射**：
- 引导员头脑里记的店铺信息 = 部署时刻对环境形成的认知。
- 商场持续换招牌、换品牌、改价目 = 所依赖环境的持续变化。
- 头三个月零失误 = 部署初期表现相对稳定的阶段。
- 四五个月零星被顾客指出指错 = 中期开始出现可见但还不严重的下滑。
- 大促期间连续指错好几拨人 = 变化密集的环境窗口里下滑集中爆发、损失被放大的阶段。
- 值班主管要求定期巡场、跟店员核实清单 = 建立定期重新评测、按变化类型归因、主动维护的机制，取代"出问题才补救"。
- 东南角多年不变的小吃区 = 变化缓慢的环境里，差距扩大得慢，不需要频繁重新核实。

**比喻边界**：故事里商场的变化都是眼睛能看到、店员能当场证实的显性变化，而现实系统里环境的变化常常是隐性的——比如某个外部接口悄悄改了一个参数但调用不报错，或者页面结构变了但看起来和以前一样，不容易靠"随口一问"就发现。此外，真实的维护决策还涉及量化的成本比较（持续打补丁的累计投入 vs 一次性重建的投入），故事只呈现了"要不要定期巡场"，没有呈现这层权衡。

**非适用例**：如果一个刚上岗的引导员从第一天起就总是指错路，那不属于这个概念要处理的情况——他压根没把商场摸熟，不存在一段"曾经准确、后来逐渐失准"的时间过程，这是能力没建立起来，不是随时间衰退。

**现实例子**：一个基于网页操作的客服系统上线后三个月表现稳定，半年后随着所依赖的电商平台改版、优惠券规则调整，任务成功率明显下滑；团队定期用同一批任务重新测试它的表现，把下降原因拆成"页面结构变了"还是"促销规则变了"，再决定是打补丁还是重新训练。

### 检验问题

1. 理解检验：引导员半年后在大促期间连续指错好几拨人，根本原因是他自己指路的本事下降了，还是别的什么原因？具体说说变化发生在哪里。
2. 迁移检验：一家连锁药房的智能客服，一部分工作是回答"某种药品是否有货、多少钱"——库存和价格几乎每天都在变；另一部分工作是回答"某类药品的常见禁忌症"——这类知识几年才修订一次。这两类问题是否需要用同样频率去重新核实内容？为什么？

## 核心发现（Paper 48: "Your Agents Are Aging Too"）

### 老化的本质
Agent 在训练/部署时刻对环境的"快照理解"会随时间失效。老化不是模型本身退化，而是**环境与模型知识之间的 Gap 持续扩大**：

1. **Web 环境变化**：网站改版、元素重排、URL 结构变更，导致 GUI Agent 的定位策略失效
2. **知识过时**：世界知识（价格/政策/人员/组织结构）变化，模型的事实性判断出错
3. **API 变更**：第三方 API 版本迭代、参数重命名、端点废弃，工具调用失败
4. **依赖漂移**：Agent 依赖的子服务（搜索引擎结果格式/数据库 Schema）静默变化

### 老化曲线特征
- 部署后前三个月：性能相对稳定（训练数据时效性覆盖）
- 三至六个月：性能开始可见下滑（约 10-20% 任务成功率下降）
- 六个月以上：在高动态环境（新闻/电商/政务）中，老化效应显著，部分 Agent 成功率下降 40%+
- 低动态环境（内部工具/稳定 API）：老化速度慢得多，一年内可接受

## LIFESPAN 评测框架

### 框架设计
LIFESPAN（Longitudinal Intelligence Framework for Evaluating System Performance Across Nodes）提供了一套纵向评测方法论：

- **快照采样**：在 T0、T+3月、T+6月等节点对同一任务集重新评测
- **变化归因**：将性能下降分解为环境变化类/知识类/API类，便于针对性修复
- **衰退率指标（DR）**：每月性能下降百分比，作为维护决策触发阈值
- **恢复成本估算**：预测将 Agent 性能恢复至基线所需的重训/微调/Prompt工程投入

### 核心指标
| 指标 | 含义 | 建议阈值 |
|------|------|---------|
| 月衰退率（MDR） | 任务成功率每月下降幅度 | > 5% 触发维护 |
| 环境变化率（ECR） | 任务环境要素月变化比例 | 预测 MDR 的领先指标 |
| 恢复 ROI | 维护投入 vs 性能恢复收益 | < 1 时考虑重部署 |

## 维护 Agent vs 重训 Agent 的成本曲线

### 维护策略（增量成本低，但有上限）
- **Prompt 修补**：针对新环境写新的 few-shot 示例，成本最低，适合局部变化
- **工具更新**：更新 API 调用代码和 Schema，成本适中
- **RAG 知识库更新**：定期刷新外部知识索引，将时效性问题转移到检索层
- **适应性上限**：当环境变化幅度超过可 Patch 范围，维护边际成本急升

### 重训策略（一次性高成本，重置时钟）
- 微调（Fine-tuning）：用新数据更新模型权重，恢复时效知识
- 完整重训：环境变化根本性（如从旧 UI 范式到新 UI 范式），需全面重训
- **重训触发点**：当维护 6 个月累计成本 > 一次重训成本时，重训更划算

### 经济学视角
```
累计维护成本 = Σ(每次Patch成本) + 运维人员时间成本
重训成本 = 数据采集 + 计算资源 + 评测 + 部署
决策原则：维护成本/重训成本 > 0.8 时，启动重训
```

## 对产品运维的启示

### 建立 Agent 健康监控
- 每周/每月运行任务集回归测试，追踪成功率趋势
- 设置自动告警：成功率单周下降超过阈值，自动通知维护团队
- 区分"用户行为变化导致的表面下降"与"真实老化"

### 分级维护策略
- **绿色（MDR < 2%）**：常规监控，季度评估
- **黄色（MDR 2-5%）**：月度 Prompt 审查，准备 Patch
- **红色（MDR > 5%）**：立即介入，评估维护/重训决策

### 架构层预防
- 工具层与知识层解耦：API 调用逻辑外置，变更时无需动模型
- 知识新鲜度标注：给 RAG 文档打时间戳，检索时降权过期内容
- 环境变化监测：对 Agent 依赖的外部端点设置 Diff 监控

## 演进时间线
- **2023**：早期 Agent 论文开始注意到"测试集与部署环境漂移"问题
- **2024**：WebArena 等基准的时效性局限引发学界关注
- **2024-Q4**：Paper 48 正式提出老化框架，LIFESPAN 评测方法发布
- **2025**：Agent 运维（AgentOps）作为独立工程方向兴起

## PM 决策视角
- **部署前**：评估任务所在环境的动态性，预估 Agent 生命周期
- **SLA 设定**：不应承诺 Agent 永久准确，应定义维护窗口和性能保证期
- **运维预算**：Agent 项目预算应包含持续维护成本（通常为初始开发成本的 30-50%/年）
- **用户透明度**：向用户说明 Agent 可能随时间性能下滑，建立定期更新机制的预期
