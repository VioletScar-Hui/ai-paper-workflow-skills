# MCP（模型上下文协议）

> **来源**: [modelcontextprotocol.io](https://modelcontextprotocol.io) / 引自 [[Wiki/论文笔记/03_Agent系统设计/06_LLM-Agent通信协议分类]]
> **发布方**: Anthropic，2024
> **成熟度**: ✅ 行业标配
> **开源实现**: 有（[github.com/modelcontextprotocol](https://github.com/modelcontextprotocol)）
> **商业 API**: 协议规范本身免费，各平台自行实现

## 一句话定义
MCP 是 Anthropic 制定的标准，让 LLM 以**统一接口**连接任何工具、数据库或 API——一次实现，所有支持 MCP 的 LLM Host 都能用。

## 寓言学习

### 寓言正文

打印店的柜台后面摆着三台打印机,牌子不同。店员老周最怕接到新客户的文件——有人用几年前买断的老式排版软件导出,有人干脆是手写稿拍的照片,还有个开工作室的客户,坚持用他们单位内部才认的格式存文件。同一份文件,老周得挨个想办法:扫描件要先描一遍字迹再排版,老软件导出的要手动调段落间距,内部格式那份甚至要先拆开看目录结构才能猜出该往哪贴。三台机器,三套办法,活儿压根没法攒着做,新来的帮工站在旁边学了一个月都学不齐。

后来店里改了规矩:不管客户原来用的什么软件,拿到柜台前必须先导出成一种约定好的格式——固定的排版结构,固定的字段顺序。三台打印机也跟着换了一批新驱动,不认别的,只认这一种格式。客户只要照着规矩导出一次,老周随手往哪台机器上一放都能直接打,不用再为每台机器单独想办法。

上周那位工作室客户又来了,带来的是同一批文件的修改版,只改了封面和其中两页。他以为柜台会记得上周那批文件的底子,就只把改动的两页递了过来。老周对着打印机捣鼓了半天才想起来——机器压根不留这回事,每次接单都是从头认一份完整文件,改动前那部分不重新交上来,机器根本不知道该接在哪儿。客户只好回去把整份文件重新导出一遍,连没改的部分一起,重新交上来。

没过几天店里添了台新打印机,速度更快。有位客户导出的格式一点问题没有,在前台却怎么也选不到这台新机器——一问才知道,柜台的接单清单上压根没登记它,得店长先把这台机器停在哪个工位、什么型号,补写进清单里,客户才能在前台的选项里看到它、点中它。

### 概念解析

**概念名称**:MCP(模型上下文协议,Model Context Protocol),属于 AI Agent 系统设计 / 工具调用协议 / 人机协作问题域。

**学习卡片**
- 核心张力:为每个 LLM 单独定制工具对接代码(灵活但重复劳动、换一家就要重写)vs 用统一协议一次实现、所有支持者都能直接调用(省重复劳动,但只能表达协议规定好的那几种交互)。
- 关键不变量:工具/数据一方只需按统一接口实现一次,任何遵循同一协议的调用方都能直接用,不用为每个调用方单独适配;这个接口只连"工具/数据/API",不连接"另一个智能体";每次调用相互独立,不跨请求保留记忆;调用方必须提前知道并登记好对方的地址,才能在使用时找到它。
- 触发条件:同一份能力(工具/数据)需要被多个不同的 LLM 应用调用、且这些调用方原本各自要专门适配时,统一协议才有意义。
- 常见误解/失败模式:以为它能记住上次交互留下的上下文(其实每次调用都从头认,不留记忆);以为新加入的工具会被自动发现(其实要靠人先登记好地址);以为它能用来连接另一个智能体做任务委托(其实它只连工具/数据/API,不连智能体)。
- 非适用边界:如果需求是两个智能体之间相互委托任务、协商谁来做、怎么分工,这不是这套统一接口规则要处理的问题。

**一句话核心定义**:MCP 是让 LLM 以统一接口连接任何工具、数据库或 API 的标准协议——工具只需实现一次,所有支持该协议的 LLM 应用都能直接调用它。

**它试图解决的问题**:避免每接入一个工具就要为每个 LLM 应用单独写一套专用对接代码、换一个 LLM 又要重写一遍的重复劳动。

**故事元素映射**:
- 各类客户带来的老式排版稿、手写扫描件、单位内部格式 = 统一协议出现之前,每个工具各有各的对接方式。
- 三台打印机各自要不同处理办法 = 每接入一个 LLM,都要为它单独写一套适配代码。
- "必须先导出成约定好的格式"这条规矩 = 统一协议本身:一次约定,处处适用。
- 客户导出一次、任何一台打印机都能直接打 = 工具只需实现一次接口,所有支持这套协议的 LLM 应用都能直接调用。
- 修改版文件必须整份重新提交,机器不记得上周的底子 = 无状态:每次调用相互独立,不跨请求保留记忆。
- 新打印机格式没问题却在前台选不到,须店长先登记进清单 = 静态发现:调用方必须提前配置好对方地址,不会自动发现新加入的一方。

**比喻边界**:故事把"统一格式"简化成一份要提交的文件,而真实协议里双方来回传递的是结构化的调用请求和执行结果,是一问一答式的交互,不只是单向提交一份稿子那么简单。另外,故事里没有专门体现"只连工具、不连另一个智能体"这条边界——因为打印机本身天然就是工具,这个场景里不容易出现"另一个智能体"这个角色,这一点要单靠故事去感受是不够的,需要在非适用例里单独澄清。

**非适用例**:如果这家店后来还想做"联系另一家分店的师傅,由那位师傅按客户需求现场加工定制、再送回来打印"这种业务,那就不是"文件先导出成统一格式"能解决的了——这已经是两个"人"之间怎么商量分工、谁听谁的、结果怎么合并的问题,不属于这条格式统一规矩要管的范围。

**现实例子**:Claude Desktop 连接文件系统、GitHub、数据库等各种服务时,工具方只需实现一次对接,Claude、Cursor、VS Code Copilot 等所有支持这套协议的应用都能直接调用它,不用为每个应用单独写一套对接代码。

### 检验问题

1. 理解检验:故事里那位工作室客户交修改版文件时,为什么不能只把改动的两页递上去,必须把整份文件重新交一遍?这说明格式统一之后,还留下了什么问题没有被这条规矩解决?
2. 迁移检验:如果这家打印店以后想开发一个新业务——店员帮客户联系另一家分店的师傅,由那位师傅按客户需求现场加工定制内容、再送回来打印,你觉得"文件必须先导出成统一格式"这条规矩,能不能覆盖这种新业务?为什么?

## 解锁了什么产品能力
**之前**：每接入一个工具（搜索、数据库、日历…），需要为每个 LLM 手写专用的 function calling 代码，重复劳动，且换一个 LLM 就要重写。

**之后**：工具只需实现一次 MCP Server，Claude、Cursor、VS Code Copilot 等所有支持 MCP 的 Host 都能自动发现和调用这个工具。

## 核心原理（工程师版）

**三个角色**：

```
Host（如 Claude Desktop）
  └── Client（MCP 客户端，内嵌在 Host 里）
        └── Server（MCP 服务器，工具/数据的一端）
```

**数据流**：Host 的 LLM 需要某工具 → Client 向已知地址的 Server 发请求 → Server 执行工具 → 返回结构化结果 → LLM 继续处理

**关键设计决策**：
- **Counterparty**（连谁）：工具 / 数据 / API，**不是另一个 Agent**
- **Payload**（传什么）：结构化数据 + Artifacts（JSON 格式的工具调用结果）
- **Interaction State**（有无状态）：**无状态**——每次调用独立，不跨请求记忆
- **Discovery**（怎么找 Server）：**静态**——Host 必须提前配置 Server 地址

## 落地代价

| 维度 | 评估 | 备注 |
|------|:----:|------|
| 💰 算力 | 低 | 协议层，不增加模型计算量 |
| 📊 数据 | 无需 | 纯工程集成，不需要训练数据 |
| ⏱️ 延迟 | 低 | 协议本身几乎不增加延迟 |
| 🔧 工程复杂度 | 低 | SDK 完善（Python/TypeScript），文档清晰 |

## 工业落地案例
- **Claude Desktop**：Anthropic 官方，连接文件系统、GitHub、数据库等 MCP Server
- **Cursor / VS Code**：编程助手通过 MCP 接入代码库、Terminal、测试工具
- **Zapier**：开始提供 MCP Server，让 AI 产品接入 5000+ 自动化应用
- **社区**：数百个开源 MCP Server（[smithery.ai](https://smithery.ai) 有目录）

## 与替代方案对比

| 对比维度 | MCP | 手写 Function Calling |
|----------|-----|----------------------|
| 互操作性 | 跨 LLM Host 通用 | 仅限当前产品 |
| 开发成本 | 工具写一次，处处用 | 每次重新适配 |
| 维护成本 | 统一规范，升级有保障 | 各家各自维护 |
| 适用范围 | LLM ↔ 工具/数据 | 同左，但更灵活 |

**MCP 不做的事**：Agent 和 Agent 之间的通信——这是 [[Wiki/概念/04_Agent框架/A2A]] 的职责。两者互补，不竞争。

## Server 端 5 种可复用架构模式（来自 159 号论文的产线实证）

从 15 个真实生产级 MCP Server（5 个语音 AI 生产环境 + 10 个官方公共 Server）归纳出的模式分类：

| 模式 | 职责 | 适用场景 |
|------|------|---------|
| Resource Gateway | 把已有 REST/GraphQL API 包一层 MCP 接口，不改造底层系统 | 快速把存量系统接入 MCP 生态 |
| Tool Orchestrator | Server 内部编排多个原子操作成一个高层工具 | 需要减少 LLM 侧多轮调用次数的复杂任务 |
| Stateful Session Server | 在 Server 侧维护跨调用的会话状态 | 需要多轮交互保持上下文，而 Host 侧不便管理状态时 |
| Proxy Aggregator | 聚合多个下游 Server/API，对外暴露统一接口 | 整合多个工具源，降低 Host 侧配置复杂度 |
| Domain-Specific Adapter | 针对垂直领域（如语音、医疗）定制化的语义封装层 | 需要将领域专业知识编码进工具描述本身的场景 |

**4 种反模式**（论文实测会显著拖累工具调用准确率）：过度细粒度拆分工具（导致 Server 暴露的工具数超过 10-15 个后，Claude Haiku 4.5 场景下工具选择准确率跌破 90%）、工具描述语义重叠、隐藏状态依赖未在描述中声明、错误处理不透明。

**关键工程硬指标**：单个 Server 暴露的工具数量是一个需要主动控制的设计变量，不是"越全越好"——详见 [[Wiki/论文笔记/03_Agent系统设计/159_MCP服务器架构模式]]。

## 产品决策要点
1. **如果你的 AI 产品需要接入任何外部工具/数据**，MCP 是现在的默认选择，不要再手写 function calling 了
2. **工具 = MCP Server，AI 助手 = MCP Client**，这个思维模型清晰后，产品集成设计会简单很多
3. MCP 管的是"AI 能用什么"，不管"AI 和 AI 怎么协作"——后者需要搭配 [[Wiki/概念/04_Agent框架/A2A]]
4. **设计 Server 时严格控制单 Server 暴露的工具数**（参考上方 10-15 个的准确率拐点），优先用 Tool Orchestrator 模式把细碎操作合并，而非依赖 Host 侧模型"自己选对工具"

## 局限与生产风险
- **不支持 Agent 间通信**：如果你的场景是 Agent 委托另一个 Agent 完成子任务，MCP 不够用
- **静态发现**：必须手动配置 Server 地址，无法动态组合陌生 Agent 网络
- **无状态**：不适合需要跨多次调用保持长期记忆的场景（需要在 Host 侧额外设计状态管理，或采用 Stateful Session Server 模式）
- **工具粒度失控**：Server 设计者若不主动控制暴露的工具数量和描述质量，会直接拖累模型的工具选择准确率（见上方 159 号论文实证）
