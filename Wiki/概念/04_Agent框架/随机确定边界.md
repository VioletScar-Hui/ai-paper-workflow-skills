# 随机-确定边界（Stochastic-Deterministic Boundary, SDB）

## 一句话定义

生产 LLM Agent 运行时中，LLM 输出（随机）转化为系统行动（确定）的"接缝"，由四部件合约定义：提案者、验证者、提交步、拒绝信号。

---

## 寓言学习

### 寓言正文

小区门禁的摄像头一识别出车牌，会给出"抬杆放行"的建议——但道闸系统不会直接把杆抬起来，而是先拿这个车牌去核对当天的缴费记录和访客登记表，查到对得上号，杆才会真的抬起来；这一步一旦执行，车已经开进小区，没法收回。

有一次识别把"京A88888"看成了"京A88880"，系统拿去核对发现记录对不上号，没有抬杆，屏幕上打出的是"未查到该车牌今日缴费记录，请至岗亭核验"。司机一看提示，直接开去岗亭补登记，没耽误多久。

后来物业为了赶高峰期车流，把流程改成"识别到车牌像模像样就先抬杆，回头再补登记"——省掉了核对记录和抬杆之间那道硬性顺序。没过多久，真出了一回没交费、也不在访客名单里的车被放了进去，等发现时车已经停进了地库，什么都晚了。物业后来复盘，把提示语也一并改了：以前系统只打"失败"两个字，司机不知道是拍模糊了还是真没登记，只能干等岗亭人工处理；改成写清楚"未查到缴费记录"之后，司机自己就知道该去哪儿补手续。

### 概念解析

**概念名称**：随机-确定边界（Stochastic-Deterministic Boundary, SDB），属于生产级 LLM Agent 运行时架构问题域。

**学习卡片**
- 核心张力：识别/建议一出来就直接执行动作（快，但建议一旦有误，后果已经发生、不可撤销）vs 建议先过一道独立核验再执行（慢一点，但能把错误拦在造成后果之前）。
- 关键不变量：核验环节必须独立于给出建议的那一方、且是确定性的检查规则，不能是"建议者自己再想一遍"；真正产生外部后果的那一步必须排在核验通过之后，顺序不能颠倒；退回的提示必须说清楚具体错在哪，不能只说"不行"，更不能谎称"已经成功"。
- 触发条件：一个不完全可靠、带随机性的建议一旦被执行，会产生真实且不可逆的外部后果（放行、发货、扣款、改库存）时。
- 常见误解/失败模式：为了图快，把核验和执行之间的硬性顺序省掉，核验变成"回头再补"的事后动作；提示信息含糊或者干脆报错误的成功状态，导致建议方带着错误认知继续往下走。
- 非适用边界：建议本身不产生任何外部后果、可以随时撤回重来（比如只是在草稿里改改文字），不需要这套核验-放行-拒绝提示的四件套。

**一句话核心定义**：随机-确定边界是不可靠的建议转化为真实、不可逆动作之前的那道"接缝"，由提案者、独立核验者、执行动作的提交步、说清楚错在哪的拒绝提示四部分共同把关。

**它试图解决的问题**：语言模型这类带随机性的决策者给出的建议不总是对的，当这个建议一旦被执行就会产生不可逆的真实后果时，如何在"建议"和"后果发生"之间插入一道靠谱的关卡，把错误拦在成为后果之前。

**故事元素映射**：
- 摄像头识别车牌给出"抬杆"建议 = 提案者（Proposer），带随机性、可能出错的输出。
- 核对缴费记录和访客名单 = 验证者（Verifier），独立于识别环节的确定性检查。
- 杆真正抬起来、车开进小区 = 提交步（Commit Step），不可逆的外部动作，必须排在核验通过之后。
- 屏幕提示"未查到缴费记录，请至岗亭核验" = 拒绝信号（Reject Signal），说清楚具体原因，让司机知道下一步该做什么。
- 物业改成"先抬杆回头补登记" = 省掉核验与提交之间的硬性顺序，导致不该放行的车被放行，且已无法撤回。

**比喻边界**：故事里的核验规则相对简单（查一张名单），现实生产系统里验证者可能是 JSON schema 校验、业务规则引擎或状态机谓词等更复杂的形式，且同一个系统里往往有多个 SDB 接缝需要逐一检查，故事只展现了单个接缝的运作方式。

**非适用例**：如果只是保安随口说了句"这个我眼熟，放"，没有任何登记系统核对、也不产生真正不可逆的动作（比如只是打个招呼而已），就不构成这套四件套关系——建议和后果之间根本没有需要把关的接缝。

**现实例子**：Srinivasan（2026）分析 21 个生产环境的 Agent 失败案例发现，71% 的失败都能定位到 SDB 这道接缝的某个部件出了问题，其中一个典型案例是"90% 折扣被实际发货"——正是因为提交步和验证者之间没有硬性门控，建议一出来就被当成了已核验的结果直接执行；GitHub 上也有真实 issue（#1104）记录过系统返回 `status='completed'` 误导模型以为任务已完成，对应的正是拒绝信号设计失败的情形。

### 检验问题

1. 理解检验：物业把"先抬杆回头补登记"当成提速优化，问题出在识别摄像头不够准，还是出在别的地方？
2. 迁移检验：如果一个客服系统里，退款申请一提交就立刻打款，退款理由的审核放在打款之后再补做，结合这个故事，你会预判这套流程最可能在哪个环节出问题？

## 四部件合约

```
Proposer（提案者）：
  → LLM 的输出——从分布中采样的，不确定的
  → 职责：生成候选行动/内容，不直接执行任何副作用

Verifier（验证者）：
  → 对提案的确定性检查——不依赖另一个 LLM
  → 形式：JSON schema 验证 / 业务规则 / 状态机谓词 / 快速分类器
  → 职责：决定提案是否可接受

Commit Step（提交步）：
  → 验证通过后的持久写入或外部副作用
  → 性质：不可逆的、有记录的
  → 职责：执行真实世界的变更

Reject Signal（拒绝信号）：
  → 验证失败时返回给 LLM 的类型化响应
  → 性质：包含足够信息让 LLM 重试/修正
  → 典型错误：返回 status='completed' 误导 LLM 认为成功（GitHub issue #1104）
```

## 为什么这个边界很重要

```
实证数据（Srinivasan 2026，21个生产失败后报告）：
  71% 的 Agent 失败 → 定位于 SDB 弱点
  81% 的文档化修复 → 加强了 SDB 四部件之一
  
典型失败案例：
  • 90% 折扣实际发货 → 提交步和验证者之间无门控
  • 工作流进入错误状态 → 事件处理器响应了过期的 LLM 提案
  • 长视野流程丢失进度 → 状态模式选择错误（与 SDB 无直接关系但相关）
```

## 实现强度谱系

| 框架 | 实现强度 | 特征 |
|------|---------|------|
| openai/swarm core.py | 弱 | 单行 JSON 解析，无 schema 检查 |
| LangChain Agents | 中 | 有输出解析，错误重试有限 |
| AutoGen | 中强 | 有内容过滤，但 reject signal 可被改善 |
| MetaGPT ActionNode | 强 | 多阶段 pydantic + LLM-as-judge 自动审查 |

5 个框架 21 个 LLM→Action 调用点中，19 个有显式验证+提交逻辑（91%），但实现质量差异巨大。

## PM 实用决策指南

**如何诊断 Agent 故障（SDB 四部件检查）**：
1. 提案者有问题？→ 模型选择/提示工程问题
2. 验证者缺失/太弱？→ 加 schema 验证、策略规则、分类器
3. 提交步无门控？→ 有副作用的操作（支付/邮件/写DB）必须在验证通过后才执行
4. 拒绝信号含糊？→ LLM 收到错误信息后才能正确重试/修正

**强化 SDB 的低成本优先行动**：
- 任何对外部系统的写入 → 必须有验证者
- 验证失败 → 返回类型化错误（不是 `{"status": "failed"}`，而是 `{"error_type": "schema_mismatch", "field": "amount", "expected": "positive_integer"}`）
- Commit 之前 → 一定有 Verifier 先过
