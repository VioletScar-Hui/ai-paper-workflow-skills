# 学习型编排器（Learned Orchestrator）

> **一句话定义**：一个经过专门训练的语言模型，能在推理时动态决定如何调度、组合多个专业 LLM 完成复杂任务，而不依赖预先人工设计的固定流程。

## 寓言学习

### 寓言正文

调度站里，订单五花八门——有生鲜要求半小时内送到，也有大件家具得两人才抬得动。班长要把每一单派给合适的骑手：老周电动车跑得快但载重有限，小林车斗大但手脚慢半拍。

班长刚上任那会儿，谁负责什么全靠一张手写规则表："生鲜必须给老周，大件必须给小林。"有一次来了一单超大冷链设备，规则表上没这一条，班长愣了几秒，没有照搬规则，而是想起上个月一批相似的冷链单是老周和小林两人配合送的——老周抢时间冲主路，小林负责后段的搬运和安放，效果比单独派给谁都好。这次她照着这个搭配又派了一次，果然又准时又完整地送到了。

派单这件事，慢慢就不再是她照着规则表勾选了，而是无数单子派下来、送达结果反馈回来之后，她自己"练"出来的判断——连她自己都说不清这判断具体是怎么形成的，只知道这么配过，效果最好。

### 概念解析

**概念名称**：学习型编排器（Learned Orchestrator），属于多智能体编排 / AI 系统设计问题域。

**学习卡片**
- 核心张力：用人工写死的固定分工规则调度（简单透明，但遇到新情况就失灵）vs 让一个经过训练、能动态判断"这次该找谁、怎么组合"的调度者来决定（能应对新情况，但决策过程不透明、难以解释）。
- 关键不变量：调度策略本身是可以通过反馈不断学习和调整的，不是一次性写死的规则表；调度者给出的分工方案往往说不清具体依据，只有"以往这样做效果好"的经验积累。
- 触发条件：任务类型多样、执行者各有专长、单一固定规则无法覆盖所有情况时。
- 常见误解/失败模式：把调度逻辑写成固定 if-else 规则表，遇到没见过的任务类型就束手无策；或者过度迷信调度者的"学习能力"，却不给它提供任何关于分工效果的反馈信号，导致它根本没有可学习的依据。
- 非适用边界：任务类型单一、执行者也只有一个，不存在"选谁做、怎么组合"的问题，不需要专门的调度决策者。

**一句话核心定义**：学习型编排器是一个经过训练、能在运行时动态决定如何调度组合多个专长各异的执行者去完成任务的决策者，调度逻辑本身是学出来的，不是人工预先设计的固定流程。

**它试图解决的问题**：当任务类型多样、需要调用的执行者各有所长时，"怎么分工"这件事本身该不该也是可以持续学习优化的，而不是一套写死后就不再变化的规则。

**故事元素映射**：
- 班长 = 学习型编排器（经过训练的调度模型）。
- 老周、小林 = 各有专长的 Worker（不同底层 LLM）。
- 手写规则表 = 人工预设的固定编排逻辑，遇到冷链单这种边界情况就失效。
- 班长凭经验临场组合两人配合 = 编排器基于训练积累的调度策略，动态决定"如何组合"而非套用固定规则。
- 班长说不清具体依据 = 学习型编排器的调度决策不透明，难以逐条解释为什么选中了这个组合。

**比喻边界**：故事里班长的经验积累发生在日常工作中，现实中的学习型编排器（如 Sakana Fugu）是通过大规模监督微调、进化算法搜索、强化学习专门训练出来的，训练过程本身涉及海量编排轨迹数据，故事没有展现这套训练机制的工程复杂度。

**非适用例**：如果调度站只有一种订单类型、只有老周一个骑手，根本不存在"该派给谁"的问题，直接派给他就行，不需要一个专门学会调度的班长。

**现实例子**：Sakana Fugu / Fugu-Ultra（2026）是首个公开发布的学习型编排器产品，用一个轻量分类头判断该调用哪些 Worker LLM、如何组合输出，在 SWE-Bench Pro、GPQA-Diamond 等基准上超过任意单一模型，但代价是编排决策不透明、难以 debug 为什么选中了某个 Worker 组合，与故事里班长"说不清判断依据"是同一种局限。

### 检验问题

1. 理解检验：班长派冷链单时没有照搬规则表，这说明规则表本身是完全没用的，还是她的调度能力换了一种运作方式？
2. 迁移检验：如果一个系统只有一种任务类型、只对接一个执行模型，有人建议给它也配一个"学习型调度层"，结合这个故事，你会怎么判断这个建议是否必要？

## 解锁了什么产品能力

- 用一个 API 接口整合多家 LLM 提供商的能力，对用户透明
- 根据查询类型自动选择最合适的底层模型组合（如数学问题选定理证明强的模型，代码问题选代码模型）
- 性能超越任意单一 LLM，而无需访问模型内部权重

## 工程原理（简明版）

```
用户请求
    ↓
[编排器 LM 主干]  ← 普通预训练语言模型
    ↓
轻量级分类头（线性/低秩/稀疏）
（作用在最后一个 token 的 hidden state 上）
    ↓
路由决策：选哪些工作模型 + 如何通信 + 怎么合并输出
    ↓
[Worker Pool] → Worker A (API) + Worker B (API) + Worker C (API)
    ↓
合成最终回答 → 返回给用户
```

**训练方式**：大规模监督微调（SFT）+ 进化算法搜索编排策略 + 强化学习优化端到端任务表现。核心创新是把 **"如何编排"本身当成模型的输出**，而非硬编码逻辑。

## 落地代价

| 维度 | 评估 |
|------|------|
| 💰 算力 | 需要额外的编排器推理成本 + 多次 Worker 调用费用；总成本比单模型高 |
| 📊 数据 | 需要大量编排轨迹数据训练；自己训练门槛高 |
| ⏱️ 延迟 | Fugu（延迟敏感版）有优化，但多 Agent 调用天然增加延迟；不适合低延迟场景 |
| 🔧 工程 | 使用商业 API 零接入门槛；自建需要设计 Worker Pool 管理 |

## 工业落地案例

- **Sakana Fugu / Fugu-Ultra**（SakanaAI, 2026）：首个公开发布的学习型编排器产品，基准测试达到 SOTA（SWE-Bench Pro 58.7%, GPQA-Diamond 80%, HLE 56.1%）
- **Trinity**（Xu et al., 2025）：Fugu 的前身研究原型

## 产品决策要点

1. **适用场景**：高价值、高复杂度任务（代码、科研、分析），用户对延迟不敏感
2. **不适用场景**：实时对话、高频低延迟调用
3. **采购视角**：目前可通过 Sakana Fugu API 直接使用，无需自建
4. **竞争壁垒**：编排策略的训练数据和 RL 反馈是核心护城河

## 局限与生产风险

- 延迟不可控：多 Worker 串/并行调用，P99 延迟可能极高
- 成本叠加：每次请求消耗多个模型 token，成本估算难
- Worker Pool 依赖外部 API：第三方模型变化（价格/能力/停服）影响整体表现
- 编排决策不透明：难以 debug 为什么选择了某个 Worker 组合
