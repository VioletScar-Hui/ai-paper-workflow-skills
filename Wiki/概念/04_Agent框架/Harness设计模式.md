# Harness 设计模式

> **一句话定义**：Harness 是围绕 LLM 策略的外部执行框架，负责状态管理、工具调用、错误处理、上下文构建等"非语义"工作，使 LLM 只需专注于语义决策——是 Agent 系统的"地基"。

---


## 寓言学习

### 寓言正文

小陈刚入职做客服，一开始什么都要自己来：客户一来电，她得现翻聊天记录找上次沟通到哪了，自己去后台系统查订单状态，遇到系统卡顿要自己重试好几次，退款申请表格里十几个字段也得自己一项项填。一天下来，光是找信息和填表格就占去了大半时间，真正判断"这个客户到底该不该退款"反而变得仓促，出错率也不低。

公司后来给她配了一套工单系统：客户一来电，系统自动弹出这位客户的历史记录和当前订单状态；退款申请表格大部分字段已经预填好，她只需要核对再点确认；系统卡顿时，后台会自动重试三次，实在不行才提示她手动处理；一个工单如果超过一小时没处理，系统会自动转给她的主管。用了这套系统之后，小陈的判断明显更准了——她不再需要分心找信息、填表格，只需要专心想"这个客户的情况符不符合退款条件"。

有一次机房临时断网，工单系统整个打不开。小陈的判断力没有变差，但她连客户的订单状态都查不到，一个退款也处理不了，只能干等着——那天出的问题，不是她"不会判断"，是喂给她判断依据的那套系统掉线了。

### 概念解析

**概念名称**：Harness 设计模式，属于 LLM Agent 系统设计问题域。

**学习卡片**
- 核心张力：让决策者亲自处理状态记录、工具调用、错误恢复等一切细碎事务（负担过重，判断质量下降）vs 有一套专门的外部框架接住这些事务，决策者只需专注判断。
- 关键不变量：决策质量很大程度上取决于决策者拿到的信息是否被恰当整理、呈现，而不完全取决于决策者本身"聪不聪明"；很多失败其实是接口/流程问题，不是判断力问题。
- 触发条件：任务涉及多步执行、需要调用外部资源、可能出错需要恢复、跨越较长时间时，需要专门的执行框架来承接这些非语义工作。
- 常见误解/失败模式：把所有失败都归咎于决策者"不够聪明"，忽视了信息呈现、状态管理本身出问题的可能；反过来把流程固化得太死，又会让决策者无法应对新情况。
- 非适用边界：单步、无状态、不需要调用外部资源的简单判断任务，不需要专门的执行框架，直接问答即可。

**一句话核心定义**：Harness 是围绕决策者（LLM 策略）搭建的外部执行框架，负责状态管理、工具调用、错误处理、上下文构建这些"非语义"工作，让决策者只需要专注于语义判断本身。

**它试图解决的问题**：当决策者被状态追踪、工具调用格式、错误恢复等杂事分散精力时，如何把这些工作从决策者身上剥离出去，让判断质量不再被这些杂事拖累。

**故事元素映射**：
- 小陈 = LLM 策略（决策者），只负责语义判断（该不该退款）。
- 一开始自己翻记录、查系统、填表格 = 没有 Harness 时，决策者被迫承担状态追踪和工具调用，认知负担过重。
- 后来的工单系统（自动弹历史、预填表格、自动重试、超时转交）= Harness 的五个功能层：状态外化、工具集成、上下文构建、错误恢复、生命周期管理。
- 断网导致工单系统整个打不开、小陈判断力没变却什么都做不了 = "90% 的 Agent 失败是接口失败而非智能不足"——Harness 故障时，决策者的判断力再强也无用武之地。

**比喻边界**：故事里的"工单系统"是相对静态、人工设计好的，但真实的 Harness 设计谱系里还有"部分 Harness"（只固定初始步骤）、"完全结构化工作流"（每步都指定）等不同程度，甚至有 Self-Harness 这种 Harness 本身也能自我优化的形态，故事只呈现了其中一种典型形态。

**非适用例**：如果小陈的工作只是"客户问一句问路，她口头答一句"，不涉及查系统、填表格、多步操作，那就不需要一整套工单系统，直接对答就够了——这种单步、无状态的任务不需要 Harness。

**现实例子**：论文 Harness-1 中，搜索 Agent 把候选文档池、精选集、证据图等 7 类状态全部外化到 Harness 层维护，LLM 只需基于这些外化状态做"要不要深入阅读某文档"这类判断，最终一个 20B 参数的小模型配合好 Harness，性能超过了没有类似设计的更大前沿模型。

### 检验问题

1. 理解检验：断网那天小陈"什么都做不了"，这说明她的判断力出了问题吗？故事想让你区分的是哪两类失败原因？
2. 迁移检验：如果有人说"我们的 Agent 老是出错，说明这个模型不够聪明，得换个更大的模型"，结合这个故事，你会追问他先去检查什么？


## 核心概念

```
没有 Harness 的 Agent：
  LLM 策略 = 语义决策 + 状态追踪 + 工具格式化 + 错误恢复 + 上下文管理
  → 认知负担过重，训练信号模糊，泛化差

有 Harness 的 Agent：
  LLM 策略 = 纯语义决策
  Harness = 状态追踪 + 工具调用 + 错误恢复 + 上下文渲染 + 生命周期管理
  
  → LLM 就像"纯粹的大脑"，Harness 就像"身体 + 记忆 + 工具"
```

## 五个 Harness 功能层

| 功能层 | Harness 做 | LLM 做 |
|--------|-----------|--------|
| **状态外化** | 维护候选池/证据图/历史记录 | 基于状态做决策 |
| **工具集成** | 调用 API、解析响应、格式化 | 选择调用哪个工具 |
| **上下文构建** | Budget-safe 渲染，压缩历史 | 理解当前状态 |
| **错误恢复** | 重试、回退、超时处理 | 无感知工具失败 |
| **生命周期** | 启动/暂停/恢复/终止 | 任务级推理 |

## Harness 类型谱系

```
完全无结构 ──────────────────────────────── 完全结构化
│                                                    │
自由ReAct循环              部分Harness           全自动化工作流
(Agent自决策所有)         (只固定初始步骤)       (每步都指定)
│                               │                    │
论文73 ReAct             论文49 Partial Harness   论文42 编译进权重
                         
论文49的发现：
  部分Harness（只固定初始几步）往往 > 完全结构化（过于刚性）
  三种失败模式：
    - 过度分解（Over-decomposition）
    - 过度剪枝（Over-pruning）
    - 幻觉执行（Hallucinated Execution）
```

## LIFE-HARNESS 的生命周期层（论文45）

```
4 层接口适配（按 Agent 每步推理循环的实际顺序）：

Layer 1: 环境合约层（Environment Contract Layer）
  解析任务描述 → 校准工具 schema 与格式约束
  修复 JSON 参数名不匹配、标注必填/可选字段、注入合法操作白名单
  拦截失败类型：合约误解（23.2%）

Layer 2: 程序技能层（Programmatic Skill Layer）
  每步开始时用 BM25 从训练轨迹中检索匹配当前状态的操作技能
  （命令模板、SQL 查询模板、错误恢复流程）注入 prompt
  拦截失败类型：技能缺失导致的探索浪费

Layer 3: 动作实现层（Action Realization Layer）
  执行前静态校验 + 自动修复：JSON 格式修复、参数位置修正、
  危险命令拦截、空动作拒绝
  拦截失败类型：动作实现失败（33.6%，最大单类失败）

Layer 4: 轨迹调节层（Trajectory Regulation Layer）
  监控重复动作、步数预算、停滞信号 → 触发强制提交/回退/探索提示
  拦截失败类型：轨迹退化（33.3%，接近并列第一）

关键洞察：90% 的 Agent 失败是"接口失败"而非"智能不足"
改接口而不改模型 → 116/126 单元改善，均值 +88.5% 相对提升
```

### 环境合约（Environment Contract）：Layer 1 的核心机制

"环境合约"指模型与工具/环境之间关于调用格式、参数语义、动作空间边界的隐性约定——工具 schema 里参数名是否清晰、必填字段是否标注、非法操作是否有白名单约束。LIFE-HARNESS 发现，确定性规则环境中近 1/4 的失败（23.2%）根因是模型"误解了合约"而非推理能力不足：例如模型知道该查订单状态，但把 `customer_id` 传成了字符串、或用错了参数名。Layer 1 的工作就是在任务开始时把这份合约"讲清楚"——校准 schema、显式标注必填参数、补充格式规范 prompt，从源头减少这类误解。

### Agent 失败归因（Failure Attribution）：诊断优先于升级模型

LIFE-HARNESS 用训练轨迹的自动归因分类，把确定性环境中的 Agent 失败拆成四类，发现分布高度不均：

```
失败归因分布（126 格子汇总）：
  动作实现失败  ████████████████  33.6%
  轨迹退化      ████████████████  33.3%
  合约误解      ████████████      23.2%
  推理失败      █████            9.9%   ← 不到 1/10！
  接口问题合计: 33.6% + 33.3% + 23.2% ≈ 90.1%
```

对 PM/工程实践的启示：面对"Agent 老出错"，默认反应往往是"换个更强的模型"，但这份分布显示真正的模型智能瓶颈只占约 10%。正确的诊断顺序是先查 Layer 3（动作实现格式）→ Layer 4（轨迹退化/停滞）→ Layer 1（合约误解），最后才考虑升级模型——这个顺序对应各失败类型的占比排序，能以最低成本命中大概率根因。

## Harness vs Fine-tuning

```
Harness 设计（外部脚手架）：
  ✅ 不需要重训模型
  ✅ 失败原因可调试（接口层 vs 决策层分离）
  ✅ 快速迭代（几天改接口 vs 几周训练）
  ❌ 依赖模型能力上限
  ❌ 状态管理增加工程复杂度

Fine-tuning（编译进权重，论文42）：
  ✅ 推理时无 overhead（不需要外部状态机）
  ✅ 推理成本 ~1/100
  ✅ 失败率 5.5% vs LangGraph 24%
  ❌ 需要高质量工作流轨迹数据
  ❌ 泛化到新工作流需重训
```

## PM 决策框架

| 场景 | 推荐 |
|------|------|
| **生产 Agent，稳定工作流** | 编译进权重（论文42）：成本最低，失败率最低 |
| **探索期，工作流频繁变化** | Harness（可快速修改接口）|
| **复杂多跳搜索任务** | Harness-1 状态外化（7组件）|
| **长任务 Agent（>1小时）**| LIFE-HARNESS 4 层生命周期 |
| **多 Agent 协作** | 部分 Harness，不要完全固化（论文49）|
| **工具调用失败频繁** | LIFE-HARNESS 的动作实现层（Layer 3）|

## Harness 的扩展律（论文34）

```
Agent-Harness 有效反馈计算扩展律：
  发现：Harness 提供的反馈质量 × 反馈量 → Agent 性能呈幂律增长
  核心指标：有效反馈计算（Effective Feedback Compute, EFC）
  
  EFC = Σ (信息量I × 有效性V × 不冗余R × 记忆保留M)
  原始计算量（token/调用次数/时长）预测成功率 R²≈0~0.27
  EFC 预测成功率 R²=0.93~0.99（代理版/理论上界）
  
  实践意义：
    ① 投资更好的反馈设计 > 投资更多训练计算
    ② Harness 质量是 RL 训练效果的关键决定因素
    ③ 设计 Harness 时，先考虑"反馈信号设计"
```

> **命名提醒**：论文45（LIFE-HARNESS）在关联其他工作时也用了"EFC"这个缩写，但指的是"Environment-Following Capability（环境遵循能力）"，与论文34这里的"Effective Feedback Compute（有效反馈计算）"并非同一概念——两者只是缩写撞车。论文45想表达的实际含义是：LIFE-HARNESS 通过四层接口适配补足了小模型的"环境遵循能力"，而这一现象可以用论文34的 EFC 扩展律解释（LIFE-HARNESS 的记忆压缩/技能检索机制提升了 M、R 因子）。引用时注意区分。

### 反馈循环设计：从 EFC 四因子反推设计原则

EFC 不仅是一个事后度量指标，也直接给出了"如何设计 Agent 反馈循环"的四条准则：① 反馈要包含新信息（提高 I，避免只返回"OK"之类的确认信息）；② 反馈要能实际改变 Agent 后续行为（提高 V，避免格式正确但语义上被忽略的反馈）；③ 避免与历史反馈重复（提高 R，去重/摘要压缩是成本最低的改善手段）；④ 确保关键反馈留在 Agent 可访问的上下文里（提高 M，防止早期关键信息被截断遗忘）。论文34的实测数据显示，多数 harness 的效率指标 η（=EFC/原始计算量）只有 0.15-0.45，即超过一半的计算预算浪费在低质量反馈上——这意味着"反馈循环设计"的收益空间通常比"换更强模型"更大、成本更低。

### 工具调用优化：EFC 视角下的工具返回设计

五个 Harness 功能层中的"工具集成"层，其反馈质量同样可以用 I/V/R 三因子衡量：工具返回的内容是否携带新信息（如具体错误堆栈 vs 笼统的"failed"）、是否足以让 Agent 改变下一步策略、是否与之前的返回重复。这为"工具返回格式该设计成什么样"提供了可操作准则——优先保证错误信息具体、避免重复罗列 Agent已知的状态，而非单纯追求返回内容详尽。

## Harness 更新 vs 获益解耦（论文32）

```
问题：Agent 自进化时，性能提升来自什么？
  可能因素：①策略（LLM 权重）更新 ②Harness 设计改进 ③两者协同

论文32 发现：
  在某些场景中，Harness 更新（不改模型）能解释大部分性能提升
  → "Harness 更新 vs 获益"必须解耦，才能理解真实的能力来源
  
  方法：控制变量实验
    - 固定 LLM，只更新 Harness → 获得 A 点提升
    - 固定 Harness，只更新 LLM → 获得 B 点提升  
    - 都更新 → 获得 C 点提升
    - 结论：通常 A >> B（Harness 是主要因素）
```

## Self-Harness：自我改进框架（论文22）

```
进阶：Harness 本身也可以自动优化！

Self-Harness 思路：
  Agent 观察自己的失败模式 → 自动提出 Harness 改进建议 → 
  → 验证改进 → 部署改进后的 Harness
  
  类比：
  标准 Harness：工具书固定不变
  Self-Harness：Agent 能自己改写工具书
  
与 LIFE-HARNESS 区别：
  LIFE-HARNESS：人工设计好的 4 层结构
  Self-Harness：Harness 本身是动态演化的
```
