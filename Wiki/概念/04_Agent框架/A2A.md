# A2A（智能体间通信协议）

## 一句话定义
A2A 是 Google 制定的标准，让**不同团队、不同框架构建的 AI Agent 能互相识别、通信、协作**——不需要为每对 Agent 写专用的集成代码。

## 寓言学习

### 寓言正文

电商平台过去接入新的代工厂,每接一家就要让技术团队重新写一遍对接代码——有的工厂订单状态叫"已排产",有的叫"生产中",格式还都不一样,接一家要磨合小半个月。

后来行业换了个玩法。每家代工厂要在行业统一名录里注册一张"厂牌",写清楚自己能做哪些型号、订单怎么下、交期多长;品牌方下单以后,这张订单变成一个有生命周期的工单,状态按统一规则走——已接单、生产中、缺料等待、完工、取消,任何一家品牌方看到的状态定义都一样;订单执行过程中双方还能持续对话追加细节,不是一锤子买卖下完单就断联系。这样品牌方接入任何一家新代工厂,都不用再单独写对接代码了。

有一家小代工厂图省事,没把自己的厂牌注册进统一名录,只把联系方式私下发给了一家熟悉的品牌方。结果只有那一家品牌方知道它的存在,其他品牌方就算想找它下单也无从发现——协作范围被自己限制在了那一条私下建立的联系上。

### 概念解析

**概念名称**：A2A(Agent-to-Agent Protocol,智能体间通信协议),属于 AI Agent 系统/多 Agent 协作工程问题域。

**学习卡片**
- 核心张力：为每一对协作方单独定制对接方式(灵活但重复造轮子) vs 用统一标准让任意两方都能互认互通(通用但需要行业先达成共识)。
- 关键不变量：协作双方必须共享同一套“能力描述格式”和“任务状态生命周期定义”,不管协作对象换成谁,这套格式和状态流转规则保持不变。
- 触发条件：当协作场景是“多个独立开发、独立部署的系统需要互相委托任务、追踪进度”时才需要这类协议;单一系统内部调用不需要。
- 常见误解/失败模式：以为只要“发布一份能力说明”就够了,忽略了任务状态需要有生命周期追踪、双方需要保持会话上下文这些配套机制;或者把这类协议和“连接工具/数据”的协议混淆。
- 非适用边界：如果协作对象是工具、数据库、API 这类没有自主决策能力的资源,而不是另一个能自主执行任务的系统,就不需要这套“智能体互认”机制。

**一句话核心定义**：A2A 是让不同团队、不同框架构建的 AI Agent 通过统一的能力名片、任务状态生命周期和会话上下文机制互相识别、委托任务、追踪进度的标准,不需要为每一对协作方单独写集成代码。

**它试图解决的问题**：多个独立系统要协作完成任务时,过去只能靠为每一对系统单独写专用对接代码,协作对象一换、框架一换就要重写;A2A 用统一协议让任意实现了它的系统都能互相发现、通信、协作。

**故事元素映射**：
- 每接一家代工厂都要重写对接代码 = 没有统一协议前,Agent 间协作靠专用集成,不可复用。
- 代工厂在行业名录注册"厂牌",写清能力和交期 = Agent Card,描述这个 Agent 能做什么、怎么调用。
- 订单变成有状态生命周期的工单(已接单→生产中→缺料等待→完工/取消) = Task 的状态流转机制。
- 订单执行过程中双方持续对话追加细节 = Session State,协作过程中保持上下文,不是一次性交易。
- 小代工厂没注册进统一名录、只私下告诉一家熟客 = A2A 依赖集中式发现机制(注册中心)这一局限,不是真正去中心化的自发现网络。

**比喻边界**：故事把 Agent Card 简化成了一张写明能力的"名片",但现实中的 A2A 协议还规定了具体的 JSON schema、通信接口和安全认证机制,这些工程细节远比"写清楚能做什么"复杂;此外故事里的协作靠人和名录沟通,而 A2A 要解决的是不同代码框架、不同编程语言之间的机器对机器通信,两者的技术门槛并不相同。

**非适用例**：如果品牌方只是想让自己的系统去查一下某个第三方的库存数据库(而不是委托另一个能自主执行任务的系统去做事),这属于"连接数据/工具"的场景,应该用 MCP 这类协议,而不是 A2A。

**现实例子**：Google 在 2025 年发布 A2A 协议规范,定位为 MCP 的配对协议——MCP 让单个 Agent 能调用工具和数据,A2A 让多个独立开发的 Agent 能互相发现、委托子任务、协作完成更复杂的工作;LangChain、AutoGen 等主流 Agent 框架都在跟进对 A2A 的支持。

### 检验问题

1. 理解检验：如果只有"厂牌注册"这一项(能力描述),没有"工单状态流转"和"持续对话"这两项机制,代工厂协作平台会缺失什么能力?对应到 A2A 协议里,这体现了 Agent Card 之外还需要哪两个核心概念?
2. 迁移检验：一家公司想让自己内部的两个微服务模块(一个负责查询库存,一个负责计算价格)用 A2A 协议对接,你觉得这个用法合适吗?这两个模块之间的关系更接近"Agent 委托 Agent"还是"程序调用工具/数据"?

## 解锁了什么产品能力
**之前**：你有一个"搜索 Agent"和一个"写作 Agent"，让它们协作，需要手写它们之间的调用逻辑，换一个框架就要重写。

**之后**：每个 Agent 发布自己的 Agent Card（能力描述），任何实现了 A2A 的 Agent 都可以读取这张卡，发送任务，追踪进度——跨团队、跨框架、跨语言都能协作。

## 核心原理（工程师版）

**三个核心概念**：

| 概念 | 类比 | 含义 |
|------|------|------|
| **Agent Card** | 名片 | JSON 文件，描述这个 Agent 能做什么、怎么调用 |
| **Task** | 工单 | Agent 间通信的基本单位，有状态生命周期 |
| **Session State** | 对话上下文 | 多轮交互中保持状态，支持 streaming 更新 |

**Task 状态流转**：
```
submitted → working → (input-required ↔ working) → completed / failed / canceled
```

**关键设计决策**：
- **Counterparty**（连谁）：另一个 Agent（不是工具/数据）
- **Payload**（传什么）：Hybrid——文本消息 + 结构化数据都支持
- **Interaction State**（有无状态）：**有 Session State**——任务在整个生命周期保持上下文
- **Discovery**（怎么找对方）：**集中式**——通过注册中心发布/查找 Agent Card

## 落地代价

| 维度 | 评估 | 备注 |
|------|:----:|------|
| 💰 算力 | 低 | 协议层，不增加模型计算量 |
| 📊 数据 | 无需 | 纯工程集成 |
| ⏱️ 延迟 | 低-中 | 取决于被调用 Agent 的响应速度 |
| 🔧 工程复杂度 | 中 | 比 MCP 稍复杂，SDK 在完善中 |

## 工业落地案例
- **Google Vertex AI**：Agent Builder 开始支持 A2A 互通
- **LangChain、AutoGen**：主流框架在跟进 A2A 支持
- **与 MCP 互补**：Google 官方定位 A2A 为 MCP 的配对协议，两者组合是当前多 Agent 架构的主流方向

## 与 MCP 的分工（最重要的一张表）

| 维度 | MCP | A2A |
|------|-----|-----|
| **连接对象** | LLM ↔ 工具/数据 | Agent ↔ Agent |
| **适用场景** | 查数据库、调 API、用工具 | 委托子任务、多 Agent 协作 |
| **状态** | 无状态 | 有会话状态 |
| **发布方** | Anthropic | Google |
| **成熟度** | ✅ 行业标配 | 🏭 生产就绪 |

**MCP + A2A = 当前最主流的多 Agent 产品架构组合**（见 [[分层Agent协议栈]]）

## 产品决策要点
1. **如果你在构建多 Agent 协作产品**（如：主 Agent 拆解任务 → 分配给专门的子 Agent），A2A 是正确方向，现在就可以开始评估
2. **Google 出品 + 与 MCP 互补的定位** = 大概率成为事实标准，值得提前投入团队学习成本
3. A2A 不替代 MCP，两者各司其职：MCP 让 Agent 能用工具，A2A 让 Agent 能找到其他 Agent 并委托任务

## 局限与生产风险
- **集中式发现**：Agent 发现依赖注册中心，不是真正自主的去中心化网络（见 [[Agent发现机制]]）
- **生态仍在成熟**：2025 年发布，遇到问题的社区资源少于 MCP
- **Anthropic 未官方背书**：A2A 和 agntcy 都声称是 MCP 的扩展，但 Anthropic 没有正式认可——协议的最终演进方向存在不确定性
