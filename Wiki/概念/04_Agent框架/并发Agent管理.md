# 并发 Agent 管理

## 一句话定义
并发 Agent 管理是同时运行多个 AI Agent 实例时，协调任务依赖、解决资源竞争、同步共享状态的工程与产品能力，是 Agent 系统从单任务工具走向生产级平台的关键跃升。

## 寓言学习

### 寓言正文

车间今天同时开了三个工位修车，技师们各自忙自己的活，谁也不等谁——比排队一辆修完再修下一辆快了不少，一下午修完的车比平时多了近一倍。

车间只有一台举升机，两个技师前后都想用它查底盘，谁先谁后没个规矩，两人几乎同时伸手去按控制按钮，车没抬稳，惊出一身冷汗。车间后来定了规矩：谁先扫码登记谁先用举升机，其他人先做不需要抬车的活，比如换机油、查电路。

同一辆车的维修记录单上，两位技师前后都写了检查结果——一个把"刹车片正常"划掉改成"需要更换"，另一个没看到最新那版，照着旧的还是写了"正常"就签了字。交车时客户拿着单子问"到底要不要换刹车片"，两人对着单子答不上来。车间复盘那段时间的记录才发现：三个工位同时开工确实比一个工位干得多，但因为技师之间协调不过来，返工率也比只开一个工位时高了不少。

### 概念解析

**概念名称**：并发 Agent 管理，属于 AI Agent 生产系统工程问题域。

**学习卡片**
- 核心张力：让多个执行者各自独立全速推进（总产出快，但可能互相冲撞资源）vs 严格排队一个个来（不冲突，但慢）。
- 关键不变量：多个执行者同时操作同一份共享资源（工具/记录/数据）而没有协调机制时，后写的会覆盖或误判先写的状态；并发数越高，总体完成量上升的同时，出错率/返工率也会上升，不是纯收益。
- 触发条件：任务可以拆成多个相对独立的子任务，且这些子任务之间存在共享资源或依赖顺序时。
- 常见误解/失败模式：只追求"多开几路同时干"来提速，却没有设计资源竞争的处理规则（谁先谁后、如何合并冲突），导致数据被覆盖、结论前后矛盾。
- 非适用边界：任务本身不可拆分、只能单线程处理，或不涉及任何共享资源，不需要并发协调机制。

**一句话核心定义**：并发 Agent 管理是同时运行多个执行者处理有依赖或共享资源关系的任务时，协调谁先谁后、避免抢占冲突、及时发现状态不一致的工程能力。

**它试图解决的问题**：多个执行者同时工作能提升总产出，但也会带来资源竞争和状态冲突，需要专门的协调机制来把"并发带来的速度收益"和"并发带来的出错风险"都管起来。

**故事元素映射**：
- 三个工位同时开工 = 多个 Agent 并发执行独立子任务，总产出提升。
- 唯一一台举升机被两人同时抢用 = 共享工具资源的竞争，缺乏限流/排队规则时会直接冲突。
- 扫码登记排队使用举升机 = 限流策略（优先级队列/资源预约），把资源竞争变成有序等待。
- 维修记录单被前后覆盖、说法对不上 = 写-写冲突，缺乏状态同步机制导致的结论矛盾。
- 返工率随工位数上升 = 并发带来速度提升的同时也放大了协调失误，收益和风险同时增长。

**比喻边界**：故事里的冲突相对简单直观（举升机抢用、记录单覆盖），现实中的并发 Agent 系统还涉及任务依赖图（DAG）的关键路径识别、失败传播后的优雅降级、跨 Agent 的分布式追踪等更复杂的调度问题，故事只呈现了资源竞争和状态同步这两类最基础的冲突。

**非适用例**：如果车间只有一个工位、一位技师，修车任务本来就只能一辆接一辆做，不存在"谁抢举升机"或"记录被覆盖"的问题，就不需要专门的并发协调规则。

**现实例子**：OpenAI Codex 的产品数据显示，约 10% 的活跃用户会同时管理 3 个以上 Agent，这些重度用户的任务完成量是单 Agent 用户的 2.3 倍，但错误率也高出 1.8 倍——与故事里"三个工位产出更多但返工率也更高"是同一种规律，这也是 Codex 在产品设计上加入冲突高亮、依赖可视化等能力的原因。

### 检验问题

1. 理解检验：三个工位同时开工后返工率上升，这说明并发本身是个坏主意吗？故事想让你看到的是并发带来的哪两种效果在同时发生？
2. 迁移检验：如果一个团队想把处理客户咨询的 Agent 从 1 个扩展到 5 个同时跑，结合这个故事，你会追问他们先设计好了哪些机制？

## 核心挑战

### 任务依赖图（DAG）
多 Agent 系统的任务关系通常不是线性的，而是有向无环图（Directed Acyclic Graph）：
- **并行节点**：无依赖关系的子任务可同时执行（如：Agent A 写代码，Agent B 写测试）
- **同步节点**：下游任务需等待上游所有前置任务完成（Fan-in 模式）
- **条件节点**：根据上游结果动态决定下游路径（动态 DAG）

DAG 调度的核心难点：
1. **关键路径识别**：找出限制整体完成时间的路径，优先分配资源
2. **动态调整**：Agent 执行时间不确定，调度器需实时重计划
3. **失败传播**：上游 Agent 失败，下游如何优雅降级（跳过/重试/中止整链）

### 资源竞争

#### 工具层竞争
多 Agent 并发调用同一工具时产生竞争：
- **文件系统**：多 Agent 同时写同一文件 → 覆盖冲突
- **数据库**：并发写入事务 → 锁竞争/死锁风险
- **外部 API 限流**：GitHub API 每小时 5000 次，多 Agent 快速耗尽配额
- **计算资源**：GPU/CPU 密集型工具的并发调用导致响应时间急剧上升

#### 限流策略
```
全局 Rate Limiter → 按工具类型设置并发上限
优先级队列 → 高优先级 Agent 的工具调用优先执行
退避重试 → 指数退避 + Jitter，避免限流恢复时的"惊群效应"
预算分配 → 按 Agent 角色分配 API 配额（Orchestrator > Worker）
```

### 状态同步与冲突解决

#### 共享状态的类型
- **只读共享**：多 Agent 读取同一代码库/文档 → 无冲突，但需缓存一致性
- **写-写冲突**：两个 Agent 修改同一文件的不同部分 → 需合并策略
- **读-写冲突**：一个 Agent 读取另一个 Agent 正在修改的资源 → 需隔离机制

#### 冲突解决策略
| 策略 | 适用场景 | 代价 |
|------|---------|------|
| 悲观锁 | 写冲突高频，数据强一致要求 | 降低并发度 |
| 乐观锁 + 重试 | 写冲突低频 | 重试成本 |
| 操作转换（OT） | 实时协同编辑 | 实现复杂 |
| 事件溯源 | 需要完整审计历史 | 存储成本高 |
| 最后写入胜出 | 低价值、可接受少量丢失 | 数据风险 |

## Codex 并发 Agent 实践

### 用户行为数据
OpenAI Codex 的产品数据揭示了并发 Agent 使用模式：
- **约 10% 的活跃用户同时管理 3 个以上 Agent**
- 这些重度用户的任务完成量是单 Agent 用户的 2.3 倍，但错误率也高 1.8 倍
- 最常见的并发模式：一个 Agent 写实现 + 一个 Agent 写测试 + 一个 Agent 写文档

### 产品层设计
Codex 的并发管理 UI 设计要点：
- **统一进度仪表盘**：单视图查看所有活跃 Agent 的状态/进度/当前工具调用
- **依赖可视化**：将 Agent 间依赖关系渲染为可交互的任务图
- **中断与恢复**：用户可暂停特定 Agent，等待人工审查后继续
- **冲突高亮**：检测到写冲突时主动提醒用户，而非静默覆盖

## 监控与可观测性

### 关键观测维度
并发 Agent 系统的"黑盒"问题比单 Agent 更严重，可观测性是基础设施核心：

#### 追踪层
- **分布式追踪**：每个 Agent 的每次工具调用有唯一 TraceID，支持跨 Agent 关联分析
- **因果链重建**：从最终输出反向追溯触发它的 Agent 决策链
- **时序可视化**：甘特图展示各 Agent 的时间线，识别等待/阻塞热点

#### 指标层
```
并发度：当前活跃 Agent 数量
资源利用率：工具调用队列深度、API 配额消耗率
冲突率：每小时发生写冲突的次数
P99 任务完成时间：跟踪调度效率
Agent 错误率：按错误类型分类（工具失败/上下文丢失/超时）
```

#### 告警设计
- API 配额消耗超过 80% → 触发限速
- 单 Agent 等待时间 > 5 分钟 → 检测死锁
- 写冲突率突增 → 可能有逻辑 Bug 导致 Agent 争抢同一资源

### 调试工具
- **重放功能**：给定同样的初始状态和随机种子，重现 Agent 执行过程
- **沙箱对比**：在隔离环境中以不同并发度运行同一任务集，找出并发特定 Bug
- **Agent 日志聚合**：统一搜索所有 Agent 的日志，支持跨 Agent 全文检索

## 演进时间线
- **2023**：AutoGen、CrewAI 等多 Agent 框架兴起，并发管理开始成为工程问题
- **2024-Q1**：LangGraph 引入有状态多 Agent 图执行能力

## PM 决策视角

### 并发 Agent 的产品价值主张
- **速度倍增**：理论上 N 个并发 Agent 可将 N 个独立任务的总时间压缩至 1 个任务时间
- **角色分工**：不同 Agent 专注不同子领域，减少上下文切换成本
- **风险分散**：一个 Agent 失败不影响其他并发任务

### 用户教育优先
并发 Agent 管理的最大障碍不是技术，而是**用户认知负荷**：
- 多 Agent 系统对用户提出了更高的任务分解能力要求
- 需要配套文档/模板帮助用户将大任务拆解为并发友好的子任务结构
- 渐进式引导：从"2 个 Agent 协作"开始，再到 3+

### 定价与资源策略
- 并发 Agent 会放大 API 成本，定价模型需将并发度纳入考量
- 可设置用户级别的并发上限（Free: 1, Pro: 3, Enterprise: 无上限）
- 配额用尽时的降级体验需设计（排队 vs 报错 vs 降速）
