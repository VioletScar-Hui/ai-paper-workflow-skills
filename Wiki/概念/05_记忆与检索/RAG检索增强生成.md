# RAG（检索增强生成）

> **一句话定义**：在生成答案前，先从外部知识库检索相关文档片段，将其插入 prompt 上下文，让模型"有据可查"而非依赖参数记忆回答——解决幻觉、知识过时、专有知识等问题。

---


## 寓言学习

### 寓言正文

药房新来的药剂师遇到一位顾客，问"我在吃着一种降压药，能不能同时吃这盒感冒药"。她心里没底——药品的相互作用说明经常更新，光凭印象回答风险太大，于是转身去查最新的药物相互作用数据库，翻到匹配那两种药的条目，照着上面写的禁忌回答顾客，顾客满意地走了。

第二天，另一位顾客拿着一盒药来问同样的问题，药盒上印的是新换的商品名——同一种成分，厂家改了包装和名字。药剂师在数据库里用这个新商品名去查，没查到任何结果。她没有再深入核实，退而检索到一份年代较早、写的是另一种听起来相近但成分不同的药物的资料，觉得"应该差不多"，就照着那份资料回答了顾客。

一周后，那位顾客回来反映吃了之后有些不适，药房主管调出记录一查，才发现问题出在检索那一步：她查询用的商品名和数据库里登记的旧名字对不上，检索压根没找到真正对应的条目，后面拿来顶替的那份资料从一开始就答非所问——不是她不懂药理，是那次检索从源头上就没找对东西。

### 概念解析

**概念名称**：RAG（Retrieval-Augmented Generation，检索增强生成），属于大语言模型知识增强/幻觉缓解问题域。

**学习卡片**
- 核心张力：完全凭"脑子里记的"直接回答（快，但可能过时或编造）vs 先查外部资料再回答（更准，但如果查错资料或没查到，答案也会跟着错）。
- 关键不变量：最终回答质量的上限由"检索到的资料是否真正相关"决定，检索这一步一旦失败，后面答案组织得再好也无法弥补。
- 触发条件：需要的知识是外部的、会随时间变化的、专业小众的，或容易被凭印象说错的。
- 常见误解/失败模式：以为回答出错一定是"理解错了"，忽视问题很可能出在检索环节本身——查询用词和资料库里的实际措辞对不上，导致检索匹配失败或匹配到看似相关实则无关的内容。
- 非适用边界：需要的知识本身非常稳定、通用，回答者早就"记得很牢"（比如基础常识），这时现查资料反而多此一举，还可能因为查到无关内容被带偏。

**一句话核心定义**：RAG 是在生成答案之前，先从外部知识库中检索相关内容并插入上下文，让模型依据检索到的资料而非仅凭参数记忆来回答，用以缓解知识过时、专有知识缺失和编造事实等问题。

**它试图解决的问题**：当模型"记忆"里的知识可能过时、错误或根本没见过时，如何让它在回答前先去外部资料里核实，而不是凭内部参数编造一个听起来合理的答案。

**故事元素映射**：
- 药剂师 = 生成模型（回答者）。
- 药物相互作用数据库 = 外部知识库。
- 查最新条目再回答 = 标准 RAG 流程：检索相关资料，插入回答依据。
- 换了商品名导致查询词和数据库措辞对不上、检索落空 = RAG 的核心失败模式之一：Query 和文档在字面/语义上不匹配（如术语、命名变化），检索环节本身失败。
- 退而拿一份年代相近但实际不对应的资料顶替回答 = 检索到的内容看似相关实则无关，后续生成再怎么组织语言，答案依然是错的。

**比喻边界**：故事把"检索失败"简化成商品名对不上这一种具体原因，但真实系统中检索失败还包括分块切断语义、多跳推理跨文档信息缺失、检索到多份互相矛盾的资料等更复杂的情形；此外故事没有涉及向量检索、混合检索（稠密+稀疏）等具体检索技术的选择问题。

**非适用例**：如果顾客问的是"感冒了应该多喝水吗"，这是药剂师早就烂熟于心的通用常识，不需要去查数据库确认——需要的知识本身很稳定、很基础时，现查资料反而是多余的动作。

**现实例子**：Lewis et al.（2020）提出的 RAG 让模型在回答知识密集型问题前先检索相关文档片段；论文《Grep vs 向量检索》的实战对比发现，检索方式要和查询类型匹配——精确术语查找用关键词检索更可靠，语义模糊的概念查找用向量检索更合适，检索策略选错本身就是导致 RAG 效果差的常见原因。

### 检验问题

1. 理解检验：药剂师第二次回答出错，是因为她"不懂药理"吗？故事想让你看清的是哪一个环节出了问题？
2. 迁移检验：如果一个企业内部知识库助手总是答错"某个内部系统最新的操作流程"，而这个系统半年前刚改过名字，结合这个故事，你会先怀疑是知识库助手的哪个环节出了问题？


## 标准 RAG 流程

```
离线阶段（建索引）：
  文档 → 分块（Chunking，通常 256-512 tokens/块）
        → Embedding 模型 → 向量
        → 存入向量数据库（Faiss/Pinecone/Chroma/Weaviate）

在线阶段（检索+生成）：
  用户 Query → Embedding → 向量相似度搜索 → Top-K 文档块
             → 插入 Prompt：[System] + [Top-K 文档] + [用户 Query]
             → LLM 生成答案
```

## RAG 架构演进

```
Naive RAG（经典 RAG, 2020，Lewis et al.）：
  单次检索 + 单次生成，简单直接

Advanced RAG：
  Pre-retrieval：Query 重写、HyDE（假设文档嵌入）
  Post-retrieval：重排序（Re-ranker）、压缩（Context Compression）
  
Modular RAG：
  检索模块 + 生成模块分离，可独立优化
  支持迭代检索（Iterative RAG）、递归检索

GraphRAG（Microsoft, 2024）：
  离线：LLM 从文档抽取实体+关系 → 知识图谱 → 社区检测 → 社区摘要
  在线：检索相关社区摘要 → 聚合答案
  适合：全局理解、跨文档推理
  代价：高索引成本（需大量 LLM 调用）
```

## 检索策略对比

| 方法 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **稠密检索**（向量相似度）| 语义相关性 | 语义理解强 | 精确关键词差 |
| **稀疏检索**（BM25）| 精确关键词 | 速度快、可解释 | 语义理解弱 |
| **混合检索**（RRF 融合）| 通用场景 | 取两者之长 | 工程复杂 |
| **GraphRAG** | 全局分析、摘要 | 跨文档理解 | 索引成本极高 |
| **多跳检索** | 复杂推理链 | 处理关联问题 | 延迟高 |

## 多模态检索：文本+视觉双通道

传统 RAG 假设"HTML/文档的文本层足以提取信息"，但现代网页/文档大量关键数据（财报数值、产品参数、科学图表）只存在于图片、表格截图或图表中——纯文本通道会系统性丢失这部分信息。Project Fetch Phase 2（152号论文）给出的解法是**双通道检索**：

```
通道1（文本）：HTML → Markdown 文本流，走标准 RAG 流程
通道2（视觉）：目标页面全页截图 → VLM 视觉元素定位
              （表格边界识别 / 图表类型分类 / 数值 OCR）
两路 token 在同一 LLM Context 中拼接，做跨模态注意力融合
```

- **效果**：金融数据基准 FinFetch 上准确率提升 34%，VisualWebArena 提升 18%，说明"文字摘要够用"的假设在含图表的现代网页上不成立。
- **代价**：截图通道的 token 消耗约为纯文本的 2-3 倍，总成本增加 200-300%；截图质量（viewport 尺寸、懒加载时机、分辨率压缩）直接影响表格 OCR 精度。
- **与 GraphRAG 的关系**：两者都是"给标准 RAG 的文本假设打补丁"——GraphRAG 补的是跨文档关系推理的缺口，多模态双通道补的是非文本模态信息的缺口，可以叠加使用（先图结构组织文档关系，再对关键文档做视觉双通道提取）。
- **工程建议**：不要默认对所有页面做双通道检索——先判断目标页面是否含表格/图表（可用简单启发式如检测 `<table>` 标签或图片密度），对含视觉信息密度高的页面才触发截图通道，控制 token 成本。

## Chunking 策略的重要性

```
Fixed-size Chunking（固定大小）：简单，但可能截断语义单元
Sentence-based：保持句子完整性
Semantic Chunking：根据语义相似度动态分块
Hierarchical Chunking：父块（摘要）+ 子块（细节），检索父找子

关键参数：
  Chunk Size: 小→精确，大→上下文完整（但信噪比低）
  Chunk Overlap: 防止跨块信息丢失（通常 10-20% 重叠）
```

## RAG vs 长上下文 vs Fine-tuning

```
三角权衡：

RAG：
  ✅ 知识可更新（不需要重训）
  ✅ 知识来源可追溯
  ✅ 适合超大知识库（TB 级）
  ❌ 检索失败 = 答案失败
  ❌ 跨文档推理弱

长上下文（如 1M token）：
  ✅ 无需检索，直接喂全文
  ✅ 不丢失跨文档信息
  ❌ 成本随上下文长度线性增加
  ❌ "迷失在中间"问题（注意力分散）

Fine-tuning：
  ✅ 知识内化，推理快
  ✅ 无检索延迟
  ❌ 知识静态（更新需重训）
  ❌ 无法追溯来源
  ❌ 幻觉风险仍存在
```

## RAG 的核心失败模式

1. **检索失败**：Query 和文档的 Embedding 语义不匹配（如专业术语、缩写）
2. **文档分块破坏语义**：关键信息被切断在两个 chunk 之间
3. **上下文窗口噪声**：Top-K 文档中有很多无关内容，干扰生成
4. **多跳推理失败**：问题需要跨文档推理，单次检索无法覆盖全部信息
5. **知识冲突**：检索到的文档相互矛盾，模型无法判断

## 工程决策清单

| 决策点 | 选项 | 建议 |
|--------|------|------|
| Embedding 模型 | text-embedding-3-large/BGE-M3/Jina | BGE-M3 中文最佳，Ada 英文稳健 |
| 向量数据库 | Pinecone/Weaviate/Chroma/pgvector | 生产用 Pinecone/Weaviate，轻量用 Chroma |
| Chunk 大小 | 256/512/1024 tokens | 从 512 开始，根据检索质量调整 |
| Top-K | 3-10 | 从 5 开始 |
| Re-ranker | cross-encoder 精排 | 有 GPU 就加，效果提升明显 |
| 场景选择 | 局部精准/全局摘要 | 局部→向量 RAG；全局→GraphRAG |

## Grep vs 向量检索的实战对比（论文133）

```
直觉：向量检索一定比关键词检索好？

论文133 的发现（Agent 搜索场景）：
  Grep（精确字符串匹配）vs 向量检索的对比实验
  
  结论：任务类型决定最优策略
    - 需要精确代码/变量名查找：Grep >> 向量
    - 语义模糊的概念查找：向量 > Grep
    - 混合任务：混合检索（先 Grep 候选，再向量精排）
    
工程建议：
  不要默认用向量检索
  先分析你的检索查询类型
  代码 Agent → Grep 为主
  文档/知识 → 向量为主
```
