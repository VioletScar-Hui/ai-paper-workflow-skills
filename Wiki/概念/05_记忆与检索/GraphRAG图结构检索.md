# GraphRAG 图结构检索

## 一句话定义

GraphRAG 是 Microsoft Research 提出的一种将知识图谱与检索增强生成（RAG）结合的框架，通过构建实体关系图并生成社区摘要（Community Summary），使模型能够在"跨文档推理"场景下显著超越传统向量 RAG。

---

## 寓言学习

### 寓言正文

一位理赔调查员面对几百份索赔材料。上级问她"这份索赔单上写的事故日期是哪天"，她直接翻开这一份材料去找，几十秒就能确认，又快又准。

后来上级换了个问法："这批索赔里，有没有反复出现的同一批人、同一家诊所、同一个地址？"她一份份材料翻下去、凭印象去比对，翻了整整两天也理不出头绪。

她换了个做法：先把每份材料里出现的人名、诊所、地址、车牌都挑出来标成一个个点，再把"同一起事故里出现"、"同一个地址"这类关系连成线，画出一张关系网。关系网理清楚之后，把关系密集的那几团材料各自分成一个专题，比如"同一家诊所反复出现的几十起索赔"单独归成一组，每组写一段小结。这之后上级再问整体有没有共同套路，她把几段小结拼起来就能给出答案，不用再重新翻材料；但如果只是想确认某一份索赔单上写的事故日期是哪天，她还是直接翻那一份材料最快——为这点小事去查那张关系网，反而更慢。

过了些日子又进来几十份新索赔，她发现不能把新材料随手拼接到已有的关系网边上就算完事——这些新材料如果跟原来的诊所、地址扯上关系，得把受影响的那几个专题重新整理一遍，摘要也得跟着改，不能只打个补丁草草了事。理这张关系网和专题小结，本来就比单纯翻材料费工夫，材料一有实质更新，这份功夫还得再搭进去一次。

### 概念解析

**概念名称**：GraphRAG 图结构检索，属于检索增强生成（RAG）/ 知识图谱问题域。

**学习卡片**
- 核心张力：逐篇材料按关键词/原文直接定位（适合精确查单点信息，但看不出材料之间的关联全貌）vs 先把材料里的实体和关系整理成一张关系网、再按关系密集程度分组归纳成专题摘要（能回答"整体规律"和"谁与谁有关联"，但整理这张关系网的成本高很多）。
- 关键不变量：关系网整理得越准，回答关联性问题就越可靠；整理关系网和归纳专题摘要是提前一次性完成的工作（建索引阶段），不是每次提问现做；材料有实质更新时，受影响的那部分关系网和摘要必须重新整理，不能只做局部拼接。
- 触发条件：提问跨越大量材料，且问题本身涉及"材料之间的关联/共同规律"而不是"某一处具体写了什么"时。
- 常见误解/失败模式：明明是想精确定位一条信息，却动用了整张关系网和专题摘要去回答，成本高、还慢；反过来，问题明明是"这些材料整体上有什么共同模式"，却只用逐篇关键词匹配去答，答不全、看不出关联。
- 非适用边界：材料数量很少，或者问题就是精确定位某一处具体内容，不需要先整理出关系网和专题摘要。

**一句话核心定义**：GraphRAG 是先从大量文档中抽取实体和关系、构建知识图谱并按社区结构生成分层摘要，再依据"整体规律"还是"具体关联"两类不同问题，分别用全局摘要汇总或沿图谱局部遍历的方式检索作答的框架。

**它试图解决的问题**：传统按文本片段匹配的检索方式擅长精确定位单点信息，但回答"跨文档的整体规律"或"实体之间的关联"这类问题时表现很差，GraphRAG 试图通过提前整理出材料间的关系结构来补上这块能力。

**故事元素映射**：
- 直接翻材料确认某个日期 = 精确定位型查询，逐篇匹配就够，不需要关系网。
- 挑出人名、诊所、地址、车牌标成点，连成关系网 = 实体抽取与关系抽取，构建知识图谱。
- 把关系密集的材料分组、每组写小结 = 图社区检测（Leiden 算法）与分层社区摘要。
- 上级问整体套路时拼小结作答 = 全局查询（Global Search），遍历社区摘要做 map-reduce 汇总。
- 新索赔进来需要重新整理受影响的专题 = 图结构更新成本高，无法简单增量拼接。

**比喻边界**：故事里的"关系网"和"专题小结"由调查员一人手动整理，现实中的 GraphRAG 是由 LLM 自动完成实体抽取、关系抽取、共指消解（把"微软"和"Microsoft"合并成同一个点）和摘要生成的，这个自动化过程本身会引入抽取错误，一旦出错会固化进图结构、持续影响后续所有查询，故事没有展现这种"错误会传播"的风险。

**非适用例**：如果材料只有五六份，调查员想确认的也只是某一份写了什么，不需要为这么点材料量专门整理关系网和专题摘要，直接翻原文最快——这对应文档数量太少、或问题本身就是精确定位，GraphRAG 的优势发挥不出来。

**现实例子**：Microsoft Research 的 GraphRAG（2024）在跨文档问答上验证了这套思路，但索引构建阶段需要大量 LLM 调用来做实体/关系抽取和摘要生成，全局查询阶段又要对大量社区摘要重新调用 LLM，典型成本是向量 RAG 的 5–20 倍，且文档更新后受影响的实体关系需要重新抽取，难以增量更新——这与理赔调查员"关系网费工夫、且不能只打补丁"是同一个道理。

### 检验问题

1. 理解检验：理赔调查员用关系网小结回答"整体有没有共同套路"很顺手，但确认某份材料的事故日期时她为什么反而不用关系网？这说明关系网适合解决哪一类问题，不适合解决哪一类？
2. 迁移检验：如果一个团队只有 20 份产品评审文档，想知道"评审意见里最常见的争议点是什么"，结合这个故事，你觉得值得为此专门构建一套 GraphRAG 索引吗？为什么？

## 核心原理

### 1. 知识图谱构建阶段

传统 RAG 将文档切分为文本块并向量化，GraphRAG 则在此基础上额外执行一步：**从文档中抽取实体与关系，构建知识图谱**。

- **实体抽取**：LLM 扫描文本，识别人物、组织、地点、事件、概念等节点
- **关系抽取**：识别实体间的语义关系（A 创立了 B、X 导致 Y 等）
- **共指消解**：将不同提及合并为同一节点（"微软" / "Microsoft" / "MSFT"）

### 2. 图社区检测（Community Detection）

GraphRAG 对构建好的图应用 **Leiden 算法**（一种层次化社区检测算法）：
- 将图划分为若干"社区"——语义相关的实体簇
- 每个社区生成一份 **社区摘要（Community Summary）**，由 LLM 对该社区所有相关原文归纳而成
- 社区具有层次结构：高层社区是低层社区的聚合，形成"语义树"

### 3. 两种查询模式

| 查询模式 | 触发条件 | 检索路径 | 典型问题 |
|---|---|---|---|
| **全局查询（Global Search）** | 跨文档全局理解 | 遍历所有社区摘要，map-reduce 合并 | "这批合同中最常见的违约原因是什么？" |
| **局部查询（Local Search）** | 定向实体追踪 | 从目标实体出发，沿图边扩展 | "张三与哪些公司有关联？" |

全局查询的 **map-reduce** 结构：
1. Map 阶段：对每个社区摘要分别生成部分答案
2. Reduce 阶段：汇总所有部分答案生成最终回答

### 4. 成本结构

GraphRAG 比向量 RAG 显著更贵：
- **索引构建**：需要 LLM 调用来抽取实体、关系、生成社区摘要（离线，一次性）
- **全局查询**：需要对大量社区摘要调用 LLM（在线，每次查询）
- 典型成本是向量 RAG 的 **5–20 倍**，视文档规模和社区数量而定

## PM 决策视角

### 何时选择 GraphRAG（而非向量 RAG）

**选 GraphRAG 的信号：**
1. 用户问题跨越多个文档（"整个季报文件夹中..."）
2. 问题涉及实体间关系（"谁与谁合作过"、"A 如何影响 B"）
3. 文档有隐性关联需要推断（法律条款互相引用、研究论文引用链）
4. 用户愿意付出更高延迟和成本换取更高答案质量

**不选 GraphRAG 的信号：**
1. 查询是精确信息定位（"第23页写了什么"）——向量 RAG 更快更便宜
2. 文档数量少于 50 篇——图结构收益不明显
3. 实时性要求高——全局查询延迟通常 10–30 秒
4. 预算敏感型产品

### 适用场景矩阵

| 行业 | 典型问题类型 | GraphRAG 优势 |
|---|---|---|
| 法律 | 合同风险交叉分析 | 跨文档条款冲突检测 |
| 金融 | 行业研报综合分析 | 多报告观点汇聚 |
| 医药 | 文献综述 | 实体关系（药物-靶点-疾病）图谱 |
| 企业知识库 | 跨部门知识整合 | 概念关联发现 |

### 关键 Metrics

- **全局查询准确率**（Global Query Accuracy）：相比向量 RAG 的提升幅度
- **索引构建成本**（Index Build Cost）：每百万 token 的图构建费用
- **社区摘要质量**（Community Summary Quality）：人工抽样评估
- **实体歧义率**（Entity Ambiguity Rate）：共指消解错误导致的图噪声

## 局限性与风险

1. **幻觉传播**：若实体/关系抽取阶段出错，错误会固化进图结构，后续查询持续受影响
2. **动态更新成本高**：文档更新需重新抽取受影响的实体关系，难以增量更新
3. **领域专用性**：通用 LLM 抽取专业领域实体（如医学术语）时质量下降，需 Fine-tuning
4. **图规模爆炸**：海量文档会产生巨型图，社区检测计算复杂度上升
