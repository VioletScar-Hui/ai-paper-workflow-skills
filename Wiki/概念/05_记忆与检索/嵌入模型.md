# 嵌入模型

## 一句话定义

嵌入模型（Embedding Model）是将文本、图像、音频等异构内容映射为稠密向量的神经网络，是语义检索与 RAG 系统的核心基础设施，其质量直接决定检索精度的上限。

---

## 寓言学习

### 寓言正文

香氛工作室有六百多瓶试用装，柜台后面的顾问阿桐负责帮客人找"和这瓶差不多"的味道。六百多瓶，客人来一次不可能每瓶都现场闻一遍再比对——那样一个客人就得耗上一整天。所以阿桐平时有空的时候，会把每瓶新到的香水提前拆开闻一遍，记下几个关键印象——前调偏柑橘还是偏木质、甜度高低、留香时长——写成一张小卡片贴在瓶身上，谁都不用现场重新判断。

有个客人拿着自己一瓶用完的香水来，说想找"差不多但便宜点"的。阿桐没有把六百瓶全部现场重新闻一遍比对，而是先把客人那瓶的印象也记成一张卡片，跟柜子里六百张卡片挨个对一遍谁的关键印象最接近——这一步很快，几分钟就筛出十瓶候选。

但只靠卡片挑出的十瓶，阿桐自己心里没底——卡片记的是几个粗略维度，两瓶卡片写得差不多的香水，实际喷在纸巾上放在一起闻，味道可能差得比想的远。于是她把这十瓶跟客人那瓶挨个做了个更认真的动作：各喷一点在同一张纸巾上，凑近了直接比对，闻完一组换下一组。这一步慢，十组要闻上小半个小时，但选出来的那三瓶，客人当场就点了头，说是这几瓶最接近。

阿桐后来跟同事说，要是反过来——六百瓶全部都用"直接凑近比对"这种做法，客人恐怕等到打烊都选不完；可要是只靠卡片选到底，选出来的那瓶，说不定跟客人原来那瓶其实不是一回事。

### 概念解析

**概念名称**：嵌入模型 / 双塔模型与交叉编码器（Embedding Model / Bi-Encoder vs Cross-Encoder），属于语义检索与 RAG 系统的核心基础设施问题域。

**学习卡片**
- 核心张力：独立编码（先各自打分/建档案）可以预先算好、检索飞快，但丢失了查询与候选之间的细粒度交互，精度有限；联合编码（拼一起比对）精度高，但无法预先计算，每一对候选都要重新推理一次，慢。
- 关键不变量：大规模候选集合下，检索系统必须先有一层可预计算、可复用的快速表示（不管查询是什么，候选的表示提前算好），才能在合理时间内把候选范围缩小，再对缩小后的少量候选做代价更高的精细比对。
- 触发条件：候选集合规模大到无法对每一个都做代价高的联合推理时（比如海量文档库），需要先做一轮快速召回。
- 常见误解/失败模式：要么图快只用双塔式的粗粒度独立表示做最终排序，精度不够却难以直接察觉原因；要么图精度对全部候选都上交叉编码器，导致延迟不可接受。
- 非适用边界：候选集合本身很小（几十个以内）时，直接对每一对都做联合精细比对完全扛得住，不需要引入"先粗筛再精排"的两阶段流程。

**一句话核心定义**：嵌入模型是把内容（文本/图像/音频）独立编码为可预计算、可比较的稠密向量的方式（双塔/Bi-Encoder），用于快速召回；而交叉编码器则对查询和候选联合编码、捕捉细粒度交互，用于精度更高但更慢的重排序——生产系统通常把两者串联成"召回+精排"流水线。

**它试图解决的问题**：当候选内容规模巨大、无法对每个候选都做代价高的精细比对时，如何先用一种可预计算、检索速度快的表示方式把候选范围大幅缩小，再用代价更高但精度更好的方式对缩小后的候选做最终排序。

**故事元素映射**：
- 提前写好的印象卡片 = 双塔模型（Bi-Encoder）预计算的嵌入向量：查询和候选各自独立编码，可提前算好存起来。
- 卡片之间快速比对筛出十瓶 = 用向量相似度（如余弦相似度）做的快速召回（ANN 近似最近邻检索）。
- 十瓶逐一凑近直接比对 = 交叉编码器（Cross-Encoder）：查询与候选联合编码，有充分交互，精度更高但无法预计算、必须逐对现场推理。
- 全场景全量比对不现实、全场景只靠卡片选到底不放心 = 双塔与交叉编码器各自的短板：前者规模化但精度有限，后者精度高但延迟高。

**比喻边界**：故事里"卡片"和"凑近比对"都是人的主观感官判断，但真实的嵌入模型是用神经网络把内容映射到高维向量空间（维度通常在 512-3072 之间），相似度计算是数学上的余弦距离，而不是感官经验；此外故事只体现了"先粗筛再精排"这一个工程实践，没有体现 MTEB 这类标准化评测体系，也没有体现嵌入模型本身还需要针对领域做 Fine-tuning（比如法律、医疗术语）才能达到理想精度。

**非适用例**：如果这家工作室只有八瓶香水，阿桐大可以每次都直接把客人的香水和全部八瓶逐一凑近比对，不需要先做印象卡片这道预筛选的功夫——候选太少时，两阶段流程反而是多余的开销。

**现实例子**：生产级 RAG 系统的典型流水线是"向量数据库 → 双塔模型召回 Top-100 → 交叉编码器精排 → Top-10 → 交给 LLM"，双塔模型（如 text-embedding-3-large、GTE 系列）负责在百万级文档库中毫秒级筛出候选，交叉编码器（Reranker）再对这上百个候选做更精细的相关性打分，兼顾了速度与精度。

### 检验问题

1. 理解检验：阿桐如果把"逐一凑近比对"这一步直接套用到全部六百瓶香水上，会遇到什么具体问题？这个问题对应到嵌入检索系统里，通常出现在候选集合规模处于什么量级的时候？
2. 迁移检验：如果你在设计一个企业内部的 500 万篇文档检索系统，产品经理提出"干脆用最精确的比对方式，把每篇文档都跟用户的查询做一次联合推理，这样最准"，结合这个故事，你会怎么评估这个提议，应该怎么设计检索流程？

## 核心原理

### 1. 嵌入的本质

嵌入（Embedding）是将离散的符号或内容编码为连续向量空间中的点，使得**语义相似的内容在向量空间中距离更近**。核心假设：

> 语义相似 ≈ 向量余弦相似度高

一个维度为 d 的嵌入向量 **v ∈ ℝᵈ** 压缩了原始内容的语义信息，可用于：
- **语义检索**：给定查询，找最近邻文档
- **聚类分析**：发现语义相近的内容群
- **重排序**：对候选结果排序
- **跨模态对齐**：图文联合检索

### 2. 双塔模型 vs 交叉编码器

这是嵌入系统架构的核心权衡：

#### 双塔模型（Bi-Encoder）

```
查询 → Encoder → v_q
文档 → Encoder → v_d
相关性 = cosine(v_q, v_d)
```

- **特点**：查询和文档**独立编码**，可预计算文档向量并存入向量数据库
- **优势**：检索速度极快（ANN 近似最近邻算法，毫秒级）
- **劣势**：查询与文档之间无注意力交互，丢失细粒度语义
- **典型模型**：sentence-transformers、text-embedding-ada-002、GTE 系列

#### 交叉编码器（Cross-Encoder）

```
[查询 + 文档] → Encoder → 相关性分数
```

- **特点**：查询和文档**拼接后**联合编码，有充分的注意力交互
- **优势**：相关性判断精度远高于双塔
- **劣势**：无法预计算，每次需对 (查询, 文档) 对单独推理，延迟高
- **典型用途**：重排序（Reranker）阶段，对双塔召回的 Top-K 文档精排

#### 工程实践：召回 + 精排 流水线

```
向量数据库 → 双塔召回 Top-100 → 交叉编码器精排 → Top-10 → LLM
```

### 3. MTEB 基准

**MTEB（Massive Text Embedding Benchmark）** 是嵌入模型的标准评测框架：

| 评测维度 | 任务数 | 说明 |
|---|---|---|
| 检索（Retrieval） | 15 | 给定查询找相关文档（BEIR 子集） |
| 语义相似度（STS） | 10 | 判断句对相似度 |
| 分类（Classification） | 12 | 嵌入用于下游分类 |
| 聚类（Clustering） | 11 | 聚类质量评估 |
| 重排序（Reranking） | 4 | 候选重排精度 |
| 摘要（Summarization） | 1 | 摘要质量 |

MTEB 覆盖 56 个数据集，8 种任务类型，是目前最权威的嵌入模型排行榜。

**2025 年 MTEB 排行榜头部模型（参考）：**
- Gemini Embedding（Google）：首个原生多模态嵌入
- text-embedding-3-large（OpenAI）：3072 维，支持维度截断
- E5-mistral-7b（Microsoft）：大参数量嵌入模型
- GTE-Qwen2-7B（Alibaba）：中文检索表现优异

### 4. Gemini Embedding 的原生多模态嵌入

**Paper 117** 描述了 Gemini Embedding 2 的核心创新：

传统多模态嵌入：图文分别编码后对齐（CLIP 范式）
- 图：Vision Encoder → v_image
- 文：Text Encoder → v_text
- 对齐：拉近匹配对的距离

**Gemini 原生多模态嵌入**：图文统一编码至同一嵌入空间
- 任意模态输入（文本/图像/音频/视频）→ 同一 Gemini 主干 → 同维度向量
- **优势**：跨模态语义对齐更自然，不需要额外的对齐训练阶段
- **应用**：同一个向量数据库可以混合存储文本与图像向量，实现真正的跨模态检索

### 5. 嵌入维度与检索精度的权衡

| 维度 | 检索精度 | 存储成本 | 计算成本 | 典型场景 |
|---|---|---|---|---|
| 128–256 | 低 | 极低 | 极低 | 大规模低成本场景 |
| 512–768 | 中 | 低 | 低 | 通用检索 |
| 1024–1536 | 高 | 中 | 中 | 生产环境主流 |
| 3072+ | 极高 | 高 | 高 | 精度优先场景 |

OpenAI text-embedding-3 系列支持**维度截断**（Matryoshka Representation Learning, MRL）：可以使用低维子向量保持较好性能，平衡成本与精度。

## Fine-tuning 嵌入模型

### 何时需要 Fine-tuning

通用嵌入模型在领域专用术语上表现差，典型场景：
- 法律条文中的专有名词
- 医疗诊断代码（ICD-10）与临床文本
- 代码检索（函数名、API 名称）

### Fine-tuning 方法

**对比学习（Contrastive Learning）**是主流范式：
```
损失 = max(0, margin - sim(q, pos) + sim(q, neg))
```
- **正样本**：(查询, 相关文档) 对
- **负样本**：(查询, 不相关文档) 对——难负样本（Hard Negative）尤为关键

**数据构建策略：**
1. 人工标注查询-文档相关性
2. 利用 LLM 合成查询（给定文档段落，让 LLM 生成可能的问题）
3. 利用用户点击日志作为弱监督信号

## 向量数据库接口

嵌入模型与向量数据库形成生产闭环：

```
文档 → 嵌入模型 → 向量 → [Pinecone / Weaviate / Chroma / pgvector] → ANN 索引
查询 → 嵌入模型 → 查询向量 → Top-K 检索 → 文档候选
```

主流向量数据库特性对比：

| 产品 | 类型 | 特色 |
|---|---|---|
| Pinecone | 托管云服务 | 无运维，企业级 SLA |
| Weaviate | 开源 + 托管 | GraphQL 接口，内置多模态 |
| Chroma | 开源 | 开发友好，本地优先 |
| pgvector | PostgreSQL 扩展 | 融合关系型+向量，SQL 接口 |
| Milvus | 开源 | 高性能，大规模场景 |

## PM 决策视角

### 模型选型框架

1. **先跑 MTEB**：在目标语言和领域子集上对比候选模型
2. **成本计算**：嵌入 API 按 token 计费，大规模索引时成本可观
3. **延迟测试**：本地嵌入 vs API 嵌入的 P99 延迟差异
4. **Fine-tuning ROI**：标注 1000 对 vs 准确率提升 5% 是否值得

### 关键 Metrics

- **Recall@K**：Top-K 结果中相关文档的比例
- **MRR（Mean Reciprocal Rank）**：第一个相关结果的排名倒数均值
- **NDCG@K**：考虑排名位置的归一化折损增益
- **嵌入吞吐量（QPS）**：每秒可处理的查询数
