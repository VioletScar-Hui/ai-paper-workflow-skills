# 上下文压缩与 KV 缓存

> **一句话定义**：Transformer 的注意力机制需要把每个 token 的 Key-Value 矩阵存在内存里，上下文越长显存占用越大、计算越慢——上下文压缩技术通过稀疏化、量化、动态丢弃等手段，在不损失太多精度的前提下把这个瓶颈打下来。

---

## 寓言学习

### 寓言正文

三号堆场每天要处理几百个集装箱。空间有限，调度员老周定了一条规矩：离船期越近、越可能被随时调用的箱子，摆在最靠近吊车的三排，谁都能一伸手就拿到；不那么紧急但还留着用的，往后挪半个身位，暂时不动它，但要用的时候得先挪开旁边几个箱子才能拿到；真的用不上、船期排得很后的，直接叫车拉去码头外面的临时仓库放着，省出场地来。

那天来了一批插单货，要求三天后就装船，按理该排进最前三排。可老周那天忙着处理另一拨到货，图省事，直接按"进场时间"排序——只要是三天前进场的箱子，一律先拉去外仓库腾地方，不管里面装的是什么。插单货刚好卡在那个时间点之前进场，结果被一并拉走了。

三天后要装船，调度员满堆场找那个箱子，才发现它已经在几公里外的临时仓库里，现场紧急叫车往返多花了两个多小时，差点误了船期。老周后来才想明白：他不该只看"进场时间早晚"，得看"接下来还有没有可能用到"。同样是早进场的箱子，有的确实可以扔到最外面，有的其实马上要用，得单独留着。

### 概念解析

**概念名称**：上下文压缩与 KV 缓存管理（KV Cache Compression / Context Compression），属于 Transformer 推理优化 / 长上下文工程问题域。

**学习卡片**
- 核心张力：保留全部历史信息最准确但显存/算力扛不住；只留最近的省资源但可能把还有用的旧信息一并丢掉。
- 关键不变量：压缩必须按"重要性"分层处理（热/温/冷，或稀疏/量化/丢弃），不能对所有历史一视同仁，也不能对所有历史无差别按时间一刀切。
- 触发条件：历史信息总量超过硬件承载能力（显存/带宽瓶颈）时，才需要触发压缩策略。
- 常见误解/失败模式：用"最近的留、早的一律丢"这种固定窗口式的简单规则代替真正的重要性判断，把还有用但出现较早的信息也一并丢弃，且问题在丢弃当下不会暴露，直到真正要用到那条信息时才发现。
- 非适用边界：历史信息总量本来就没有超过容量上限时，引入压缩机制是多余的工程开销，直接全量保留即可。

**一句话核心定义**：上下文压缩/KV 缓存管理是指在 Transformer 推理中，当历史 token 的 Key-Value 存储超出显存承载能力时，通过稀疏化、量化、分层丢弃等手段，有选择地保留"重要"信息、压缩或丢弃"不重要"信息，以在可接受的精度损失下换取显存和速度的技术。

**它试图解决的问题**：长上下文推理中，历史信息量随对话/任务长度线性甚至平方级增长，显存和计算带宽无法无限扩容，需要一种机制决定"哪些历史该原样保留、哪些该压缩、哪些可以丢"，而不是简单地全部保留（扛不住）或全部截断（丢失关键信息）。

**故事元素映射**：
- 堆场空间 = GPU 显存容量，有限且被多个任务（集装箱）争抢。
- 最靠近吊车的三排（热区，全精度可取）= 热缓存（Hot Cache），保留原始精度的最近或高重要性 KV。
- 后挪半个身位、需要倒箱才能取（温区）= 温缓存，经过量化（INT8 等）压缩但仍在场内可取的 KV。
- 拉去码头外临时仓库（冷区）= 冷缓存，被丢弃或压缩到几乎不可用精度的 KV，取回代价极高。
- 老周按"进场时间"一刀切丢弃插单货 = 固定窗口截断策略，忽视了"重要性"而只看"时间早晚"。
- 插单货被误拉走、临时抢救 = 该保留的关键信息被压缩策略误伤，问题直到被检索使用才暴露。

**比喻边界**：故事里"重要性"是调度员凭直觉判断插单货该留下，但真实系统中，重要性的判断依赖注意力分数、语义相关度等可计算指标（如 FlashMemory 用注意力分数衡量 KV 重要性），是自动化、量化的决策，不是人工经验；而且真实压缩策略（稀疏注意力、MLA 潜空间压缩、量化）往往是模型架构层面的设计，不只是"存哪里"的仓储调度问题，还涉及如何用低维表示重建、如何在计算图里省算力。

**非适用例**：如果三号堆场本来货柜就没几个，场地绰绰有余，调度员却非要折腾出"热温冷三区"的复杂流程，那反而是多余的管理成本——对应"任务上下文长度没有超过模型窗口"时，不需要引入任何压缩策略，直接全量保留使用即可。

**现实例子**：DeepSeek-V4 的 MLA（Multi-head Latent Attention）把 KV 矩阵压缩到低维潜空间存储，需要时重建，将 KV Cache 大小减少约 5-13 倍；FlashMemory 则用注意力分数把 KV 分成热/温/冷三层，分别做全精度保留、INT8 量化、直接丢弃——这正是"按重要性分层压缩"而非"一刀切按时间截断"的工程实现。

### 检验问题

1. 理解检验：老周最后想明白的那句话——"不该只看进场时间早晚，得看接下来还有没有可能用到"——对应到 KV 缓存压缩策略里，是在纠正哪一类具体的失败模式？为什么这类失败不容易在"当下"被发现？
2. 迁移检验：如果你在设计一个多轮对话 Agent 的上下文管理策略，某天用户在对话第 3 轮提到了一个关键的个人限制条件（比如"我对海鲜过敏"），后续第 50 轮才会再次涉及饮食相关请求。结合这个故事，你觉得单纯用"只保留最近 N 轮"的固定窗口策略会有什么风险？该怎么设计才能避免类似"插单货被误拉走"的问题？

## 为什么上下文越长成本越高？

```
标准注意力计算：
  对长度为 n 的序列：
    计算复杂度 = O(n²)
    KV 缓存显存 = O(n × d_model × num_layers × 2)

具体数字（Llama-3-70B 为例）：
  1K token  →  KV 缓存 ~1.6 GB
  32K token →  KV 缓存 ~50 GB   ← 单卡 A100 撑不住
  128K token → KV 缓存 ~200 GB  ← 需要多机
  1M token  →  KV 缓存 ~1.5 TB  ← 理论上不可行

"长上下文税"：
  每次生成一个新 token，都要和历史所有 KV 做注意力计算
  → 生成延迟随上下文线性增加
  → API 成本 ∝ 输入 token 数（平方量级显存 + 线性量级计算）
```

## KV 缓存原理

```
Transformer 推理时两个阶段：

1. Prefill（预填充）：
   输入 prompt 全部并行处理
   计算每层每个 token 的 K、V 矩阵 → 存入 KV Cache
   
   KV Cache 结构（每层）：
   ┌─────────────────────────────────────────┐
   │  Token 1  │  Token 2  │  ...  │  Token n │
   │  [K1, V1] │  [K2, V2] │  ...  │  [Kn, Vn]│
   └─────────────────────────────────────────┘
   
2. Decode（解码）：
   逐 token 生成，每步只需处理 1 个新 token
   新 token 的 Q 矩阵 → 与历史全部 KV 做注意力 → 得到输出
   
   瓶颈：随序列增长，每步 decode 需要读取越来越大的 KV Cache
   → 显存带宽成为瓶颈（不是算力）

为什么 KV Cache 无法无限大？
  - GPU 显存有限（A100 80GB，H100 80GB）
  - 显存带宽 < 计算带宽（读取速度跟不上）
  - batch size 和 context length 互相抢显存
```

## 四类压缩策略

### 策略一：稀疏注意力（只关注重要 token）

```
核心思想：不是每个 token 都需要关注所有历史 token
          只保留"重要"的注意力连接

MiniMax（论文21）的方法：
  Lightning Attention（闪电注意力）：
    - 局部窗口：每个 token 只关注最近 K 个 token（局部依赖）
    - 全局 token：额外保留少量"全局锚点"token
    
  实现效果：
    O(n²) → O(n × K) 复杂度
    128K 上下文：速度 3x，显存 60% 减少
    精度损失：<2%（下游任务评测）

其他稀疏模式：
  Sliding Window（Mistral）：固定窗口大小，只看最近
  BigBird：随机 + 局部 + 全局的混合稀疏
  Longformer：文档任务专用稀疏模式
```

### 策略二：KV 缓存压缩（量化 / 丢弃不重要的 KV）

```
FlashMemory（论文27）— KV 缓存动态压缩：
  原理：不是所有历史 token 的 KV 都重要
        用注意力分数衡量 KV 重要性
        对低注意力分数的 KV 进行量化或丢弃
  
  三层策略：
  ┌────────────────────────────────────────┐
  │ 热缓存（Hot Cache）：最近 N token，全精度│
  │ 温缓存（Warm Cache）：中等重要，INT8 量化│
  │ 冷缓存（Cold Cache）：低重要性，丢弃    │
  └────────────────────────────────────────┘
  
DeepSeek-V4（论文82）的 MLA（Multi-head Latent Attention）：
  将 KV 矩阵压缩到低维潜空间（Latent Space）
  KV Cache 大小减少 ~5-13x
  原理：KV = W_down × C（C 是低维压缩表示）
         存 C 而不存 KV，需要时重建
  代价：解码时多一次矩阵乘法，轻微延迟增加

量化（Quantization）：
  FP16 → INT8：显存减半，精度损失 <1%（大多数任务）
  FP16 → INT4：显存减为 1/4，精度损失 2-5%（任务相关）
```

### 策略三：动态上下文管理（Agent 层面）

```
思路：在应用层而非模型层管理上下文
      不是压缩 KV，而是决定"哪些内容放进上下文"

AdaCoM（论文36）— 自适应上下文管理：
  Agent 执行期间动态决策：
  ┌────────────────────────────────────────────────┐
  │ 每步判断：                                      │
  │   当前上下文 token 数 > 阈值？                  │
  │     是 → 触发压缩策略                           │
  │       选项1：摘要（Summary）历史信息             │
  │       选项2：检索（Retrieve）相关片段            │
  │       选项3：丢弃（Drop）低相关内容             │
  │     否 → 继续正常执行                           │
  └────────────────────────────────────────────────┘
  
  关键发现：相比固定窗口截断，AdaCoM 在长任务上
            准确率提升 12%，成本降低 40%

效率前沿框架（论文46）：
  将上下文管理问题形式化为"成本-精度权衡曲线"
  不同任务有不同最优压缩率：
    代码生成：需要保留完整上下文（压缩代价高）
    问答：关键段落即可（大量压缩可行）
    对话：最近 N 轮 + 摘要（混合策略最优）
```

### 策略四：长上下文预训练（模型本身支持更长上下文）

```
Lighthouse-Attention（论文132）：
  核心：在预训练阶段就用长文档训练
        而不是事后打补丁（RoPE 外推等）
  
  关键技术：
    - 位置编码从头设计支持 128K+
    - 训练数据：长文档比例 >30%
    - 注意力 Sink：模型学会将全局信息"停靠"在特定位置
  
  vs. RoPE 外推（post-hoc 方案）：
    外推：训练时 4K，推理时强行扩展到 128K
         → 性能在 8K 后快速下降
    Lighthouse：训练时就见过 128K，性能曲线平滑

DeepSeek-V4（论文82）：
  1M token 上下文目标
  关键：YaRN + MLA + 长上下文微调三合一
```

## 成本-精度权衡

| 策略 | 显存减少 | 速度提升 | 精度损失 | 实现复杂度 |
|------|---------|---------|---------|-----------|
| 稀疏注意力（MiniMax）| 40-60% | 2-4x | <2% | 高（需改模型）|
| MLA 潜空间压缩 | 5-13x | 1.5x | <1% | 高（需改模型）|
| KV 量化 INT8 | 50% | 1.2x | <1% | 中 |
| KV 量化 INT4 | 75% | 1.3x | 2-5% | 中 |
| 动态丢弃（AdaCoM）| 30-50% | 可变 | 1-3% | 中（应用层）|
| 摘要压缩 | >80% | 可变 | 5-15% | 低（提示层）|
| 长上下文预训练 | 无减少 | 1x | 0%（原生）| 极高（训练期）|

## PM 决策：按任务类型选策略

```
决策树：

你的任务上下文长度 > 模型窗口？
├── 否 → 不需要压缩，标准用法即可
└── 是 → 进入压缩决策：
    
    你能修改模型/推理框架？
    ├── 否（只能用 API）→
    │     应用层压缩：AdaCoM 式动态管理
    │     + 摘要历史 + 检索关键片段
    │
    └── 是 →
          任务精度要求高？
          ├── 是 → MLA + 稀疏注意力（DeepSeek-V4/MiniMax）
          └── 否 → KV 量化 INT8 即可（简单高效）
```

| 产品场景 | 推荐策略 | 原因 |
|---------|---------|------|
| **长文档问答**（合同/报告）| 稀疏检索 + 摘要压缩 | 多数位置无关，检索足够 |
| **代码审查/大代码库**| MLA 或原生长上下文 | 代码依赖全局，不能随便丢 |
| **多轮对话 Agent**| 动态摘要（AdaCoM）| 历史信息随时间衰减，摘要最优 |
| **实时推理（低延迟）**| KV 量化 INT8 | 低精度损失，延迟最小 |
| **批量离线分析**| 稀疏注意力 | 吞吐量优先，精度次之 |
| **1M Token 超长文本**| DeepSeek-V4 / MiniMax 类模型 | 只有原生支持才可靠 |

## 补充:更严谨的机制与公式(源自 Alisa's Book of LLMs)

### KV Cache 显存公式的完整形式

标准 MHA 下 KV cache 的显存占用为：

```
num_layers × num_heads × seq_len × head_dim × 2   (× 2 是因为 K 和 V 各存一份)
```

用更细粒度的记号写：批大小 B、序列长度 S、K 个 KV 头 × 每头维度 H、共 L 层：

```
显存 ≈ B × S × (K·H) × L × 2 × 每元素字节数
```

本页现有的"O(n × d_model × num_layers × 2)"是同一公式的简化写法，这里补充了 batch 维度和"KV 头数×头维度"的更细拆分，为下面 MQA/GQA/MLA 的压缩比提供对照基准。

### MQA / GQA:本页尚未涉及的两种基础压缩方式

本页目前讲了稀疏注意力、KV 量化冷热分层、MLA、动态上下文管理，还没有提到 KV cache 压缩里最基础的两种架构级方案：

- **多查询注意力（MQA, Multi-Query Attention）**：所有注意力头共享同一组 K、V，只有 Q 仍然是每个头独立的。KV cache 按 num_heads 倍数直接缩小（相当于上面公式里 K=1），推理速度和显存效率大幅提升，但因为所有头共享同一份 K/V，会损失一些表征能力。
- **分组查询注意力（GQA, Grouped-Query Attention）**：把 num_heads 个头分成若干组，组内共享一组 K、V。是 MHA（K=num_heads，无压缩）和 MQA（K=1，压缩最狠）之间的折中，目前是 LLaMA、Qwen 等主流模型的默认选择。

### 跨层 KV 共享

除了跨"头"共享（MQA/GQA）和压缩到潜空间（MLA），另一种正交的思路是跨"层"共享：多个 Transformer 层共用同一份 KV cache，而不是每层都单独存一份，用层数上的冗余换取显存。

### MLA 与 RoPE 不兼容(本页现有 MLA 描述中缺失的关键限制)

本页已经介绍了 MLA 把 KV 压缩到低维 latent 向量、解码时再投影回完整 KV 这一机制，这里补充一个容易被忽视但很关键的限制：**MLA 与 RoPE 不兼容**。原因在于 RoPE 需要在每个位置对完整维度的 Q/K 向量做旋转，而 MLA 缓存的是压缩后的低维 latent，旋转操作和"先压缩、再投影回原维度"的顺序无法直接兼容；DeepSeek V2/V3 实际实现里对此做了专门的解耦处理（把 RoPE 需要的维度单独拎出来不参与压缩）。这是 MLA 工程落地时必须解决的问题，而不是可以忽略的细节。

### 局部注意力窗口:KV cache 与序列长度无关

本页"稀疏注意力"部分已经描述了 MiniMax 的局部窗口+全局锚点方案，这里补充一个更基础的定性结论：只要采用局部注意力（滑动窗口），一旦某个 token 滑出窗口范围，就可以直接把它的 K、V 从缓存里丢弃——KV cache 的大小因此与序列长度完全无关（恒定为窗口大小），这是局部注意力相比标准注意力在"无限长流式生成"场景下的根本优势，区别于 MQA/GQA/MLA 这类"仍然为整段历史保留 KV、只是缩小每个位置存储"的压缩思路。
