# Agent 记忆系统四模块（Agent Memory System Modules）

> **一句话定义**：Agent 持久记忆系统可拆解为四个模块 —— 表示与存储（R）、抽取（E）、检索/路由（Q）、维护（U），这四个模块的组合方式决定了系统的能力与成本。

## 寓言学习

### 寓言正文

健身教练带着几十个长期学员，一开始每次上完课就随手记一笔："今天练了腿，状态还行。"记录很轻，占的地方也小。半年后一个学员旧伤复发，教练翻聊天记录，翻出来的全是一串"状态还行"，压根想不起来当时具体做了哪个动作、哪次训练可能是诱因，细节早就没了。教练后来改了记法，除了当天的总结，把动作组数、重量、学员当场说的原话都留了下来——记录变厚了，但真出问题的时候，能翻回去查到具体是哪一次、哪个细节。

找学员本周的训练情况，教练脑子里回想一下最近几次课就能想起来，又快又准；但要找这个学员三年前刚入门时的体测数据，光靠"印象里好像是这样"经常想岔，得翻出当年的记录本逐条核对——时间隔得越远，单凭脑子里的印象去联想就越不靠谱。

有个学员之前被记录过"膝盖有旧伤，深蹲要减重"，后来做了康复训练完全恢复了，这条记录却一直没人去更新或划掉。换了一位教练顶班带这个学员，翻记录一看，以为伤还在，照旧让他做减重深蹲——学员觉得莫名其妙，旧伤明明早就好了。

### 概念解析

**概念名称**：Agent 记忆系统四模块，属于 Agent 长期记忆系统设计问题域。

**学习卡片**
- 核心张力：把什么都原样记下来（信息全，但越堆越多、找起来慢）vs 只记提炼过的摘要（找起来快，但需要细节时找不回来）。
- 关键不变量：记什么、怎么存（表示与存储）、记录时怎么筛选提炼（抽取）、要用时怎么找回来（检索）、旧记录怎么更新/淘汰/合并（维护）是四件相对独立的事，任何一件设计不当都会拖累整体；记忆越久远，单纯靠"感觉像不像"去联想找回的准确率会明显下降。
- 触发条件：使用者需要跨越多次、长时间地调用之前积累的信息，且信息量已经大到不能每次都全部带在身边时。
- 常见误解/失败模式：为了省地方把记录过度压缩摘要，结果需要细节时找不回来；只依赖一种检索方式（比如只靠印象联想），对时间跨度大的旧记录效果明显变差，却没意识到该换个检索方式；旧记录该更新或淘汰时没有及时处理，反而成了误导。
- 非适用边界：只处理一次性、当场就能说完的事情，不需要跨时间保留和调取，不需要这套记忆设计。

**一句话核心定义**：Agent 持久记忆系统可以拆解成表示与存储、抽取、检索/路由、维护四个相对独立的模块，这四者的组合方式共同决定了系统能记住什么、记多细、多久后还能准确找回来。

**它试图解决的问题**：一个需要长期、跨会话使用的执行者，不可能每次都把全部历史塞进当下的处理范围，如何设计"记什么、怎么存、怎么找、怎么维护"这四件事，决定了它的记忆是真正有用还是形同虚设。

**故事元素映射**：
- 教练随手记一笔"状态还行"再到改为保留动作组数和学员原话 = 抽取模块（E）从"过度摘要"调整为"保留更多原始细节"。
- 最近训练靠回想、三年前的数据靠翻记录本 = 检索模块（Q）在时间跨度变大后，单纯的联想式检索明显失效，需要更可靠的检索方式。
- 旧伤记录没有被及时更新划掉，被顶班教练误读 = 维护模块（U）缺失，导致过时信息继续误导后续使用。
- 记录本身存在哪儿、以什么形式存 = 表示与存储模块（R），故事中体现为"记录变厚了但更可靠"这一权衡。

**比喻边界**：故事里教练只用了一种记录方式，现实中的生产级记忆系统往往同时组合多种存储和检索手段（向量检索+关键词检索+图结构遍历），论文发现混合检索比单一方式召回准确率更高，故事没有展现这种"多手段并用"的组合设计。

**非适用例**：如果学员只上一次体验课就不再来了，教练当场记完这堂课就结束，不需要考虑跨时间保留和调取旧记录的问题，不需要这套四模块设计。

**现实例子**：论文《Agent 记忆系统综述》的实证发现里，O8 指出"保留原始内容比激进压缩更有效"，对应教练从"只记摘要"改成"保留动作细节和原话"的调整；O7 指出"相似度检索在时间距离大时显著下降"，对应教练找三年前数据时单凭印象联想会经常出错；O3 指出"图结构在知识更新上最可靠"，则提示如果教练用的是一张学员-伤病-训练动作的关系图，旧伤恢复后的更新会比零散笔记式记录更容易被系统性地捕捉到。

### 检验问题

1. 理解检验：教练把"膝盖有旧伤"这条记录误用给已经恢复的学员，问题出在他记性不好，还是记忆系统的哪个环节没做好？
2. 迁移检验：如果一个 Agent 系统只优化了"存得多、存得细"（表示与存储），却从没设计过旧记录怎么更新和淘汰，结合这个故事，你预测它长期使用下去会出现什么问题？

## 四模块详解

```
┌────────────────────────────────────────────────────────┐
│               Agent 记忆系统 M_sys = ⟨R, S, Q, U⟩        │
├──────────────┬─────────────────────────────────────────┤
│  R 表示与存储  │ 如何编码记忆？存在哪里？                  │
│              │ ① token 级序列（上下文缓冲）              │
│              │ ② 图/树结构（知识图谱、层级树）            │
│              │ ③ 异构复合（向量DB + 图DB + 关系DB）       │
├──────────────┼─────────────────────────────────────────┤
│  E 记忆抽取   │ 何时写？写什么？                          │
│              │ ① 原始拼接（不过滤）                      │
│              │ ② 无结构语义抽取（LLM 摘要）              │
│              │ ③ 结构化约束抽取（三元组、JSON Schema）    │
├──────────────┼─────────────────────────────────────────┤
│  Q 检索/路由  │ 查询时如何找到相关记忆？                   │
│              │ ① 原生注意力（KV Cache 内）               │
│              │ ② 语义密集检索（向量相似度）               │
│              │ ③ 拓扑子图遍历（图数据库）                 │
│              │ ④ 自主 Agent 路由（LLM 决策）             │
│              │ ⑤ 多阶段混合执行（Dense + BM25 + 图）     │
├──────────────┼─────────────────────────────────────────┤
│  U 记忆维护   │ 如何更新、合并、淘汰旧记忆？               │
│              │ ① 时间戳版本控制                          │
│              │ ② 容量驱动物理淘汰（热度/LRU）             │
│              │ ③ LLM 语义合并（主动整合相似记忆）          │
└──────────────┴─────────────────────────────────────────┘
```

## 解锁了什么产品能力

- 让 Agent 跨会话、跨任务持久地记住用户偏好、历史事件、已学技能
- 支持长时程任务（数小时/数天的 Agent 持续执行）
- 替代"每次都把所有历史塞进 context window"的低效方案

## 关键实验结论（PM 决策参考）

| 结论编号 | 发现 | 产品含义 |
|---------|------|---------|
| O1 | 没有任何单一架构在所有场景占优 | 选型要看具体任务类型 |
| O3 | 图结构在知识更新上最可靠 | 需要频繁更新事实的 Agent → 选图结构 |
| O5 | 混合检索（Dense + BM25）最大化召回准确率 | 生产系统优先用混合检索 |
| O7 | 相似度检索在时间距离大时显著下降 | 长期记忆需要时间维度的特殊处理 |
| O8 | 保留原始内容比激进压缩更有效 | 不要过度摘要，保留原文更好 |

## 落地代价

| 维度 | 评估 |
|------|------|
| 💰 算力 | 高质量系统（MemoryOS, Cognee）延迟是简单系统的 30-150x |
| 📊 数据 | 初始数据无需标注；运行时自动积累 |
| ⏱️ 延迟 | LightMem: ~3.67s/query；MemoryOS: ~28.6s/query；Cognee/Zep: 100s+ |
| 🔧 工程 | Mem0/Zep/Letta 等有商业 API，接入门槛低 |

## 局限与生产风险

- 没有"一个系统通吃所有场景"的方案，必须根据任务选型
- 时间维度的记忆退化：时间远的记忆检索精度显著下降
- 高质量系统往往延迟极高（100s+），不适合实时交互

## 与 Agent-Harness EFC 扩展律的关系

Agent-Harness 有效反馈计算扩展律（EFC，见 [[Wiki/概念/04_Agent框架/Harness设计模式]]）把反馈质量拆解为 I（信息量）×V（有效性）×R（不冗余）×M（记忆保留）四因子，其中 **M 因子直接指向本页四模块中的 U（维护）与 R（表示与存储）模块的设计质量**——如果关键反馈在 Agent 的记忆系统中被过早淘汰、压缩过度或检索不到，M 就会偏低，即使 I/V/R 三项都很好，整条反馈的 EFC 仍会大打折扣（四因子是乘积关系，任一为 0 则整条反馈 EFC 为 0）。这为记忆系统的工程优先级提供了一个具体的诊断切入点：当 Agent"记性不好"导致任务失败时，可以用 M 因子的视角检查是维护策略（U）淘汰过快，还是存储表示（R）本身就丢失了细节。
