# MCP 服务器架构模式（MCP Server Architecture Patterns for LLM-Integrated Applications）

📄 **原文 PDF**：[[RAW/159 - MCP Server Architecture Patterns for LLM-Integrated Applications.pdf]]

## PM 速判（30秒）
> 论文从 15 个真实 MCP Server（5 个 ANSYR 语音 AI 生产服务器 + 10 个官方公共 Server）中归纳出 5 种可复用的服务端架构模式和 4 种反模式，并用量化实验证明：单个 Server 暴露的工具数一旦超过 10-15 个（Claude Haiku 4.5 场景），工具选择准确率会跌破 90%——这是所有做 MCP 集成的 PM 在设计工具目录粒度时必须尊重的硬指标，不是工程师的偏好问题。

## 双层费曼 🗣️
> **给CEO的一句话**：给 AI 接入的工具越多不是越强，而是越"选不准"——本文告诉你在哪个数量该拆分工具目录、什么时候该给 AI 一个"会记事"的会话，什么时候该把多个系统封装成一个傻瓜操作。
>
> **给工程师的一段话**：论文用 Gamma 等人的 GoF 结构化格式（context/problem/solution/consequences/known uses）编目了 Resource Gateway、Tool Orchestrator、Stateful Session Server、Proxy Aggregator、Domain-Specific Adapter 五种模式，每种都对应经典架构祖先（Repository、Facade、Session/Memento、Proxy、Adapter），差异在于 LLM 客户端通过自然语言描述而非文档来选择操作这一约束。两轮质性编码（开放编码+模式编码）+ 54 服务器留出集双评审（Cohen's κ=0.76）验证了分类可靠性，并定位了三个模式边界的系统性模糊区。

## 问题域定位 🎯
- **根本约束**：MCP（Anthropic, 2024年11月发布）标准化了 LLM 与外部工具/数据/服务的接口，几个月内 GitHub 上出现数百个社区 MCP Server，但没有任何软件维护文献描述这个生态在生产中是如何被结构化的。工程师反复遇到的问题是：工具该如何拆分（一个工具何时该拆成两个）？服务端状态何时是合理的、该怎么管理？运营者该如何从多个 Server 聚合能力？何时该把一个复杂 API 包一层而不是直接暴露？
- **这不是 MCP 独有的问题**，而是"API 设计问题"透过"LLM 客户端"这个特殊约束的重新显现：LLM 靠阅读自然语言描述来选工具，而不是像人类开发者那样浏览文档或审查 schema；对 schema 复杂度的敏感度也和人类工程师不同——一个人类工程师觉得显而易见的工具，如果描述缺失或写得差，对 LLM 可能就是不可见或含糊的。
- **之前卡在哪**：LSP（Language Server Protocol）解耦了编辑器和语言服务，但没有先例告诉从业者"面向 LLM 客户端的服务端"该怎么设计；已有的 MCP 文献（Hou et al. 综述安全威胁、Hasan et al. 挖掘安全/可维护性坏味道、Guo et al. measurement study 测量 >8000 个公开 Server 的生态规模）都是"生态包含什么/哪里脆弱"的视角，没有人编目服务端设计结构本身。
- **开启的路线**：一套跨框架可复用的模式词汇表 + 反模式清单 + 工具数量的可操作阈值，把"选架构"从直觉变成可审计的工程决策；同时把"状态性""领域逻辑"识别为横切属性而非互斥类别（见证据审计部分），这是本文对分类学本身的一个方法论修正。
- **关闭的路线**：论文明确不解决"验证器/校验逻辑该怎么写"这类实现细节，也不是新架构范式的发明——所有模式都有经典祖先（Table I），贡献在于 LLM 客户端带来的增量（delta），而不是结构本身的新颖性。

## 核心机制
（基于 PDF Table I / Section IV 真实内容绘制五种模式的结构差异）

```
① Resource Gateway（祖先：Repository / REST 资源）
   LLM ── ListResources/ReadResource ──▶ [ Gateway ]──sanitize()──▶ Backend(DB/文档库/API)
                                            │ 读操作→Resource；不安全的查询参数→Tool
                                            └ 单一清洗层拦截 prompt injection

② Tool Orchestrator（祖先：Facade / Mediator）
   LLM ── 1次 call(create_and_notify_ticket) ──▶ [ Orchestrator ]
                                            ├─▶ Jira.createIssue()
                                            ├─▶ Slack.postMessage()
                                            └─▶ Email.send()
   LLM只看到"一个动作"，编排/中间失败处理全在服务端

③ Stateful Session Server（祖先：Session / Memento）
   LLM ── call(open_file, _sessionId) ──▶ [ Session Server ]
                                            └ Map<sessionId, Context> (内存 / Redis 横向扩展)
   LLM ── call(edit_file, _sessionId) ──▶ 读取同一 Context，状态对 prompt 隐式存在

④ Proxy Aggregator（祖先：Proxy / API Gateway）
   LLM ── call("github__create_pr") ──▶ [ Proxy ]── 按命名空间路由 ──▶ Server_github
                                          │                        ├─▶ Server_slack
        变体A 静态合并：一次性暴露全部工具的并集（配置简单，工具数会爆）
        变体B 按需检索（scoped/retrieval-over-tools）：每次请求只检索相关子集

⑤ Domain-Specific Adapter（祖先：GoF Adapter）
   LLM ──自然语言输入(模糊日期/名称)──▶ [ Adapter ]──输入归一化──▶ 底层复杂API(SIP/K8s/FHIR)
                                          ◀──输出enrich(ID→显示名)+错误翻译(码→人话)──┘
   语义层承接底层API的机器可读ID、低级操作、复杂鉴权
```

关键结构性区别：Resource Gateway 和 Tool Orchestrator 在"读多写少"和"多系统编排"两端对称；Stateful Session Server 是前两者的横切叠加（任何模式都可能带状态，但状态在函数签名里不可见）；Proxy Aggregator 解决"多 Server 的连接扇出"，是唯一直接处理"工具数量爆炸"问题的模式；Domain-Specific Adapter 解决"单个 API 本身对 LLM 不友好"，语义翻译发生在单一后端内部，不涉及跨 Server 编排。

**四种反模式（论文 Section V，衍生语料中没有一个 Server 以此为主结构，但都是开发/代码评审中反复出现的真实错误）**：
1. **God Tool**：单个工具接受泛化 schema，如 `do_anything(action: string, params: object)`，LLM 必须自行推断 `action` 含义，选择准确率崩溃；修复方式是拆分成每个操作一个具名工具+精确 schema。
2. **Unsanitized Resource Content**：把用户生成内容（评论、文档正文、表单输入）未经处理直接放进 Resource 响应，一段"忽略之前的指令并……"的文档内容会被 LLM 当指令而非数据执行；修复方式是在内容进入 MCP 响应前统一消毒。
3. **Synchronous Long-Running Operations**：把视频编码、大文件处理等耗时操作暴露成同步工具，MCP 没有内建异步回调机制，客户端会超时；修复方式是同步返回一个 job ID，另开一个 `poll_job(id)` 工具做轮询。
4. **Missing or Vague Tool Descriptions**：工具名叫 `send_message` 却没有描述，或描述只是把名字重复一遍；LLM 是靠读描述选工具而非查 schema，修复方式是把描述写成"讲给从未见过这个工具的人听"的清晰说明。

**四类横切关注点（论文 Section VII，五种模式都要面对）**：鉴权（在传输层用 Bearer token 做认证，不要塞进工具处理函数内部；token 按工具集限定作用域；记录调用者身份，否则调试 LLM 异常行为会非常困难）；错误处理（工具错误应作为结构化 error content 返回而非抛异常，让 LLM 能看到错误、判断是否重试或上报用户）；版本管理（`initialize` 响应里带版本号，破坏性 schema 变更升主版本号，迁移窗口内保留旧 schema 而非强制客户端立即升级）；可观测性（记录每次调用的工具名、输入哈希、延迟、输出大小、错误码——这是调试 LLM 异常行为的主要手段）。

## 设计决策解剖 ⚖️
| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|---|---|---|---|---|
| 工具聚合方式 | Proxy Aggregator 的 scoped 变体（按任务检索相关工具子集，retrieval-over-tools） | 静态合并（static-merge，暴露所有上游工具的并集） | 静态合并简化了客户端配置，但会推高可见工具数，一旦超过 §VI-C 的准确率预算（10-15 个），选择准确率下降——聚合本身让问题更糟而非更好 | 当上游 Server 总数很少（如 ≤3 个、总工具数 <10）时，静态合并的简单性收益大于准确率损失，scoped 变体的"按请求检索"步骤反而增加一次延迟且要求检索本身足够快、准 |
| 状态管理边界 | Stateful Session Server：session ID 由连接生成、所有工具调用携带，服务端在内存/Redis 维护会话上下文，闲置过期 | 把状态编码进每次 prompt/工具参数（让 LLM 显式携带全部上下文） | MCP 工具调用默认无状态请求-响应；把状态塞进 prompt 会造成冗余数据传输且不可靠（LLM 不保证正确传递大段上下文） | 当会话不需要跨调用依赖（如纯查询型只读工具）时引入 Session Server 是纯负担：需要预算会话回收（reaping），否则内存泄漏；横向扩展还要求分布式会话存储 |
| 数据暴露形式 | Resource Gateway：读操作用 Resource（URI 寻址），不安全的查询参数用 Tool | 把所有后端数据访问都做成 Tool | 开放 URI 模板对复杂/不安全的查询参数不适用，且 Resource 天然贴合"LLM 检索并 grounding"的读取语义 | 当查询涉及复杂 join 或聚合时，用 Resource 表达会很别扭（论文明确列为 liability），此时该退回 Tool 或 Tool Orchestrator |
| 复杂 API 的封装深度 | Domain-Specific Adapter：加人类可读描述、输入归一化、输出 enrich、错误翻译四件套 | 直接透传底层 API（不加语义层） | 底层 API 常有机器可读 ID、低级操作、复杂鉴权，LLM 选择准确率会因描述精度不足而受损；Adapter 把复杂度隔离在一层 | 当底层 API 已经对 LLM 友好（描述清晰、参数语义化）时，再加 Adapter 是过度工程（over-engineering，论文原话），且 Adapter 本身要随底层 API 变更同步维护 |
| 工具颗粒度 | 每个操作一个具名工具、精确 schema + 描述 | God Tool：一个 `do_anything(action, params)` 泛化工具（反模式A） | LLM 靠读描述选工具，泛化 schema 让 LLM 无法可靠推断 `action` 语义，选择准确率崩溃 | 没有失效场景——论文把这列为反模式，任何生产 Server 都不应保留这种结构 |

## 成本与量级 💰
- **工程复杂度量级**：论文未给出统一的人月/代码行数披露；但从代码示例可见各模式复杂度递增——Resource Gateway/Tool Orchestrator 是单文件级别的 handler 逻辑；Stateful Session Server 额外需要 `Map<sessionId, Context>` 或 Redis；Proxy Aggregator 的 scoped 变体额外需要一个"足够快且准"的检索子系统（论文明确指出这是新增的复杂度来源）。
- **部署成本（协议层，真实测量）**：stdio 本地传输 p50 0.01ms / p95 0.02ms / p99 0.02ms；streamable-http loopback p50 0.39ms / p95 0.45ms / p99 0.48ms——同机部署时协议开销可忽略不计（远低于1毫秒）。
- **跨主机部署成本（modeled，非直接测量，基于同区域网络 RTT 校准常数 30ms p50/80ms p95/180ms p99 叠加）**：streamable-http 跨区域 remote p50 30.4ms；叠加 Stateful Session Server 后 p50 38.4ms；叠加 Proxy Aggregator 单跳后 p50 62.4ms。论文的结论是：传输开销被网络 RTT 主导，不是协议编码本身，架构上真正重要的选择是"服务端是否与客户端同机部署"以及"Proxy Aggregator 是否引入额外网络跳数"，而不是 stdio vs streamable-http 的选型。
- **最小可行配置（工具数量硬预算，真实生产遥测）**：单个上下文中工具数控制在 10-15 个以内（Claude Haiku 4.5 场景），Claude Sonnet 4 可放宽到 20 个左右；一旦预计会超过这个预算，就必须切到 Proxy Aggregator 的 scoped 变体而非继续静态合并。

## 证据审计 🔬
- **实验设计公平吗**：本文本质是案例分析/编目型工业经验论文（industry experience paper），不是受控实验。三项量化实验中，只有传输延迟的两行（stdio、loopback streamable-http）是端到端真实测量，其余三行（跨区域 remote、叠加 Session Server、叠加 Proxy Aggregator）都是"测量的本机开销 + 引用的网络 RTT 校准常数"的建模值，论文在方法列（Method）里逐行明确标注 measured vs modeled，这一点做得比较诚实，没有把建模值伪装成实测。
- **基线选取有什么猫腻**：分类可靠性实验里有一个值得警惕的对比——用"点名架构"的规范化描述做分类，两个 rater 一致率高达 97%；但用"架构中立"的功能性描述（不点名任何架构，只说"暂存变更、提交、看diff、切分支"）做分类时，与作者原始标签的一致率骤降到 68.5%(Haiku)/75.9%(Sonnet)。论文自己指出 97% 那个基线"测的是描述措辞，不是分类法能否扛住真实、架构中立的输入"——这是论文里最诚实的一次自我拆台，值得称赞但也说明分类法的真实鲁棒性明显低于表面数字。
- **最强证据**：工具数量-准确率关系（§VI-C）：Claude Haiku 4.5 在 10 个工具时 91% 准确率（p50 延迟 245ms），15 个工具时降到 87%（跌破 90% 阈值）；Claude Sonnet 4 在 20 个工具内维持 90%+，30 个工具时跌破。成立条件：数据来自 ANSYR 语音 AI 平台 2025 Q1 生产遥测，每个工具数分桶 N=200 次真实生产会话轮次，Wilson 95%置信区间在 ±4 个百分点内——但这是观察性数据（observational），非受控实验，且来自单一组织、单一领域（语音 AI）的工具清单，论文自己提醒"语义重叠工具或故意模糊描述的工具库结果可能不同"。
- **最可疑的数字**：Cohen's κ=0.76（"substantial agreement"），因为它的置信区间是 [0.62, 0.88]，区间下界 0.62 按 Landis-Koch 标准只能算"中等一致"（moderate），而且这是两个 LLM rater（Claude Haiku 4.5 + Claude Sonnet 4）之间的一致性，两者共享同一家族的"盲点"，并不能替代独立人类双编码——论文在威胁效度部分自己承认了这一点。
- **审稿人会要求补充**：(1) 独立人类双编码验证 15 个衍生语料的分类结果（目前只是二作复核而非独立双编码）；(2) 更大规模、跨组织的语料复现（Guo et al. 已测得 >8000 个公开 Server 的生态规模，本文只用了 15+54=69 个）；(3) 把"模式选择"和"实测延迟/可靠性"直接挂钩的预测性研究，把目前的描述性词汇表变成实证工具。
- **最小复现实验**：代理指标——固定一个 MCP Server 语料（如官方 registry 前 20 个），让两个不同家族的 LLM（而不是两个 Claude 系列模型）各自读"架构中立"描述做五分类，测一致率是否仍在 framework 报告的 68-76% 区间，还是因为跳出 Claude 系列而进一步下降；预算：20 个服务器 × 2 模型 × 单次分类调用，成本可控制在几美元以内，主要成本是人工撰写架构中立描述的时间。

## 可复用点（PM决策）
- **何时采用**：当产品要接入 3 个以上第三方工具/数据源，且预计工具目录会持续增长时，在设计阶段就应该按论文的决策树选型——只读数据接入用 Resource Gateway + 消毒层；多系统联动动作用 Tool Orchestrator；只有当"后一轮调用真的依赖前一轮建立的状态"时才上 Stateful Session Server（否则不要为了"看起来更智能"而引入状态，要为会话回收预算工程资源）；聚合多个 Server 时默认选 scoped Proxy Aggregator 而非静态合并；底层 API 本身对人类都不友好（机器 ID、复杂鉴权）时才上 Domain-Specific Adapter。
- **何时规避**：底层 API 已经语义清晰、参数命名可读时不要再加 Domain-Specific Adapter，这是论文明确点名的"过度工程"陷阱；工具总数在预算内（10-15个）时不要为了"面向未来扩展"提前上 Proxy Aggregator，徒增一跳网络延迟和运维复杂度。
- **供应商拷问清单**（用于评估任何声称"生产就绪"的 MCP Server/网关产品）：
  1. 你们单个上下文暴露的工具总数是多少？如果超过 10-15 个，用的是静态合并还是按需检索（retrieval-over-tools）？检索本身的延迟和准确率是否单独测过？
  2. 你们的 Server 是无状态还是有状态？如果有状态，会话由谁生成、存在哪里（内存/Redis）、多久回收一次、横向扩容时会话如何迁移？
  3. 从外部数据源（文档、用户生成内容）读进来的内容，在返回给 LLM 之前有没有独立的消毒层拦截 prompt injection？这一层是在网关统一做，还是分散在各个工具里各自实现？

## 动手练习 💻
> 练习目标：实现论文 Pattern 2（Tool Orchestrator）+ Pattern 4（Proxy Aggregator 的命名空间路由）的最小骨架——工具注册 + 按命名空间的调用路由，用来体会"LLM 只看到一个复合动作"和"多 Server 聚合时如何避免命名冲突"这两个核心机制。

```python
"""
MCP 架构模式最小骨架：Tool Orchestrator + Proxy Aggregator（命名空间路由）
仅为教学骨架，非真实 MCP SDK 实现，不含网络传输层。
"""

class MCPServerStub:
    """模拟一个上游 MCP Server：只有工具注册表 + 调用执行两件事。"""

    def __init__(self, name):
        self.name = name
        self.tools = {}  # 工具名 -> 处理函数

    def register_tool(self, tool_name, handler):
        """注册一个具名工具（对应论文反模式A的反面：拒绝 God Tool）。"""
        self.tools[tool_name] = handler

    def call_tool(self, tool_name, arguments):
        if tool_name not in self.tools:
            # 论文 Pattern2 Consequences: 错误应结构化返回而非抛异常（Section VII-B）
            return {"error": f"unknown tool: {tool_name}"}
        return self.tools[tool_name](arguments)


# ---------- Pattern 2: Tool Orchestrator ----------
def create_and_notify_ticket(args):
    """
    对应论文 Listing 2：一次调用内部完成三个子系统调用，
    LLM 只看到"一个动作"，编排失败处理是服务端的责任（Liabilities 之一）。
    """
    title, assignee = args["title"], args["assignee"]
    ticket_key = f"TICKET-{hash(title) % 1000}"
    # 模拟三次子系统调用：建单、通知、发邮件
    log = [
        f"jira.createIssue(title={title!r})",
        f"slack.postMessage(to={assignee!r}, ticket={ticket_key})",
        f"email.send(to={assignee!r}, ticket={ticket_key})",
    ]
    return {"content": f"Created {ticket_key}, notified {assignee}", "sub_calls": log}


orchestrator = MCPServerStub("orchestrator")
orchestrator.register_tool("create_and_notify_ticket", create_and_notify_ticket)


# ---------- Pattern 4: Proxy Aggregator（命名空间路由） ----------
class ProxyAggregator:
    """
    对应论文 Listing 4：连接 N 个上游 Server，用命名空间前缀防止工具名冲突，
    按前缀路由到正确的上游。这里只实现"静态合并"变体（简单版）；
    scoped 变体需要额外一个按任务检索工具子集的步骤，此处略去。
    """

    def __init__(self):
        self.upstreams = {}  # namespace -> MCPServerStub

    def register_upstream(self, namespace, server: MCPServerStub):
        self.upstreams[namespace] = server

    def list_tools(self):
        """静态合并：暴露所有上游工具的并集（论文指出这会推高可见工具数）。"""
        merged = []
        for ns, server in self.upstreams.items():
            for tool_name in server.tools:
                merged.append(f"{ns}__{tool_name}")
        return merged

    def call_tool(self, namespaced_name, arguments):
        # "github__create_pr" -> 拆出命名空间 "github" 和真实工具名 "create_pr"
        ns, _, real_name = namespaced_name.partition("__")
        if ns not in self.upstreams:
            return {"error": f"unknown upstream namespace: {ns}"}
        return self.upstreams[ns].call_tool(real_name, arguments)


if __name__ == "__main__":
    proxy = ProxyAggregator()
    proxy.register_upstream("support", orchestrator)

    print("聚合后可见工具列表:", proxy.list_tools())
    # 模拟 LLM 发起一次带命名空间前缀的调用
    result = proxy.call_tool(
        "support__create_and_notify_ticket",
        {"title": "打印机卡纸", "assignee": "李滨辉"},
    )
    print("调用结果:", result)
```
