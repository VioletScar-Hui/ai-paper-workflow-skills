# Agent-Harness有效反馈计算扩展律：原始计算量是糟糕的预测指标

📄 **原文 PDF**：[[RAW/34 - Scaling Laws for Agent Harnesses via Effective Feedback Compute.pdf]]

## PM 速判
> 一句话：原始token消耗、工具调用次数、运行时间几乎无法预测Agent任务成功率（R² ≈ 0~0.27，其中token R²最低仅-0.08），只有EFC——信息量(I)×有效性(V)×不冗余(R)×记忆保留(M)的乘积——才能做到接近决定性预测（Oracle-EFC R²=0.99，代理版NRS-EFC R²=0.93）；核心启示是"反馈质量碾压反馈数量"。

## 双层费曼 🗣️
> **给CEO**：假设你让员工反复修改方案。每次反馈如果只是"再改改"而没有具体指向，改100遍也没用——花的钱和成功率几乎无关。但如果每次反馈都准确指出问题在哪、怎么改，且不重复之前说过的话，那三五轮就能搞定。这篇论文用数学证明了这件事：Agent也一样，花在"有效反馈"上的计算量才是唯一靠谱的成功率预测指标，原始开销（token数、调用次数、耗时）全是噪音。这意味着预算应该投向反馈质量而非反馈次数。
> **给工程师**：EFC定义为Σ(I_i × V_i × R_i × M_i)，其中I测量反馈是否包含新信息（非冗余于已有知识），V测量反馈是否实际改变了Agent的后续行为，R惩罚与历史反馈重复的内容，M测量Agent是否在上下文中保留了该反馈。四个因子是乘积关系——任一因子为0，该条反馈的EFC即为0。任务成功率拟合为f(EFC/D_task)，D_task为任务难度归一化。Oracle-EFC使用事后全知标注，NRS-EFC使用基于规则+模型的代理度量，后者R²=0.93仍远超原始指标。

## 问题域定位 🎯
- **回应的根本约束**：Agent harness（工具增强层/反馈循环层）的效率评估长期缺乏理论坐标。此前社区默认用token消耗、工具调用次数、wall-clock时间衡量harness"开销"，但从未有人系统验证这些指标是否预测任务成功。这导致harness优化方向可能是错的——你可能在降低token而实际在破坏有效反馈。
- **之前卡在哪**：LLM scaling law（Chinchilla, Kaplan）研究的是预训练阶段的"更多计算→更低loss"关系，但Agent harness场景引入了一个根本不对称性——计算不仅用于推理，还用于与环境交互并从反馈中学习。这个交互过程中的计算"质量"差异极大，原始计算量掩盖了质量维度。
- **开启的路线**：为Agent harness建立了第一条经验验证的扩展律，给出可操作的效率度量η=EFC/C_raw。从此harness设计有了优化目标函数，而非凭直觉调参。这直接催生了EFC-ADAPTER等基于EFC的harness伴侣层工作。
- **关闭的路线**：终结了"用token消耗评估harness质量"的简单化做法——数据显示R²≈0，这条路走不通。
- **与邻近工作的关系**：这篇工作处于"LLM预训练scaling law"和"Agent系统工程"的交叉地带。Kaplan/Chinchilla回答了"预训练需要多少计算"，但Agent场景的计算发生在推理+交互阶段，其效率取决于反馈质量而非矩阵乘法次数。EFC架起了从模型scaling到Agent scaling的桥梁。没有EFC框架，Agent harness设计就停留在"经验调参→看成功率→再调参"的循环中，缺乏可优化的目标函数。

## 核心机制（ASCII图必备）

EFC的核心直觉：不是所有计算都是平等的。一次工具调用返回的错误堆栈可能改变Agent的patch策略（I=1,V=1），而另一次只返回"OK"的确认信息可能在上下文中被稀释（I=0.1,V=0）。两者的token消耗可能相同，但对任务成功率的贡献天差地别。EFC通过四因子乘积量化这种"计算质量"，并发现其与成功率之间遵循类似预训练scaling law的幂律关系。

## 设计决策解剖 ⚖️
| 决策点 | 选择 | 被放弃方案 | 为什么 | 何时失效 |
|--------|------|-----------|--------|----------|
| 因子聚合方式 | 四因子乘积 I×V×R×M | 加权加和 αI+βV+γR+δM | 乘积天然编码"短板效应"：任一因子归零则整条反馈无效。加和无法表达这种逻辑AND关系——一条完全被忽略的反馈（V=0）在加和中仍有贡献，这不符合直觉 | 当因子间存在补偿效应时（如高V可部分弥补低I），乘积可能低估实际EFC。论文未验证加和形式的对比实验 |
| 任务难度归一化 | EFC除以D_task | 直接使用原始EFC | 同一EFC在不同难度任务上效果不同——简单任务可能100 EFC就够，困难任务需要1000。不归一化则跨任务比较无意义。D_task通过基线Agent在该任务上的成功率反推 | 如果任务难度本身是EFC的函数（即反馈质量改变了任务的有效难度），则D_task不是外生变量，归一化引入循环依赖 |
| Oracle-EFC vs NRS-EFC | 区分两个版本 | 只报告Oracle版本 | Oracle版本需要人工事后标注I/V/R/M，不可部署但证明理论上界存在（R²=0.99说明EFC概念本身是正确的）。NRS-EFC使用代理度量（规则判断冗余、LLM评分信息量），可实时计算但精度略低。两者并存建立了"理论完备→工程可用"的桥梁 | 当代理度量与真实I/V/R/M偏差大时（如LLM评分系统性地高估自身反馈的信息量），NRS-EFC可能误导优化方向 |
| 扩展律函数形式 | f(EFC/D_task)——幂律或对数线性 | 直接线性回归EFC→成功率 | 论文发现EFC与成功率的关系在不同任务难度上有不同斜率，除以D_task后各任务的曲线"坍缩"为单一扩展律曲线。这暗示存在统一的"有效信息→任务表现"的映射，类似LM的"计算量→loss"的scaling law | 如果任务难度不是稳定的外生属性（如任务难度随Agent能力变化而漂移），则D_task归一化会失效。此外，幂律形式在极高EFC区域可能低估边际收益递减效应 |

## 成本与量级 💰
- **EFC测量成本**：Oracle-EFC需要人工标注者对每条反馈的I/V/R/M四维度评分，假设每个标注点2分钟，1000条反馈≈33人时，约$500-1000。NRS-EFC使用LLM代理评分，每条反馈约消耗200-500 token（$0.001-0.003/条），1000条约$1-3。
- **最小可行配置**：对于harness评估，NRS-EFC在50+条反馈、3+个任务上的测量即可给出有统计意义的η估计。不需要Oracle标注即可开始优化。
- **η效率指标的量级参考**：论文中典型harness的η在0.15-0.45之间（即只有15%-45%的原始计算量转化为有效反馈）。η<0.1为"严重低效"——90%+的预算被浪费在无信息量/无效/冗余/被遗忘的反馈上。
- **规模化考量**：EFC框架本身随任务规模线性扩展（每条反馈独立评分后求和），不存在组合爆炸。但Oracle-EFC的人工标注成本限制了大规模采用——10000+条反馈需要多人周级别的标注投入。实践中建议先用NRS-EFC筛查低效harness（成本<$10），仅对候选harness做Oracle-EFC验证（成本<$500），形成"粗筛→精验"的两阶段评估管线。
- **与Token成本的换算关系**：假设典型Agent任务消耗100K token（≈$0.3-1.0），其中harness反馈消耗约占30-60%。如果η=0.2，则有效反馈仅占6-12%的总token消耗。将η从0.2提升到0.4，在相同的成功率下可节省约50%的反馈相关token开销——这对大规模部署有直接的经济意义。

## 证据审计 🔬
- **实验公平性**：中等。对比了多个harness和任务集，但harness选择可能存在幸存者偏差——被选中的harness都是已发表的工作，其EFC可能系统性地高于随机harness。任务集偏向代码/推理类，对话类Agent未充分覆盖。
- **最强证据**：Oracle-EFC/D_task对成功率的R²=0.99，且这个关系在多个harness上一致（非过拟合单一harness）。NRS-EFC的R²=0.93说明代理版本已可用。原始token的R²=0.27的对比极其干净——不是"EFC略好一点"，而是定性差异。
- **最可疑数字**：(1) I/V/R/M四个因子的代理测量方法——NRS-EFC中I用LLM自评信息量，存在自评偏差（LLM倾向于认为自己给出的反馈信息量高）；V用行为变化检测，但"行为变化"的阈值选择会影响V值；(2) D_task的基线成功率测量需要足够样本，论文中部分任务的基线样本量偏小（<20次运行），可能导致D_task估计不稳定；(3) 乘积形式的假设未做消融实验——没有对比I×V×R×M与I+V+R+M或其他多项式形式的预测差异。
- **审稿补充问题**：(a) Oracle-EFC的四因子人工标注的inter-annotator agreement是多少？(b) 能否在训练过程中动态估计EFC（而非事后），用于在线harness优化？(c) EFC框架是否适用于多Agent协作场景——此时"反馈"来自其他Agent而非环境？
- **最小复现设计**：用SWE-bench Lite（300实例）+ 1个开源harness（如SWE-agent），记录每条工具调用后环境返回的反馈，用规则（R：embedding相似度>0.9判冗余）+ LLM评分（I/V/M：单次GPT-4o-mini调用评分三维度）计算NRS-EFC，对成功率做线性回归。预计GPU/API成本<$50，可在一周内完成。
- **外部有效性边界**：论文的主要实验在代码Agent（SWE-bench风格）上完成，任务特点是反馈明确（编译错误、测试失败）、成功标准客观。在开放式对话Agent、创意生成Agent、多模态Agent等场景中，反馈的I/V/M度量更依赖主观判断，EFC框架的适用性需要额外验证。此外，论文未讨论Agent自身能力（底层LLM的强弱）与EFC的交互——更强的基座模型可能对低质量反馈有更好的容错能力，这可能改变EFC-成功率的函数形态。

## 可复用点
- **何时采用**：当你需要评估或优化Agent harness的效率时；当你想解释"为什么加更多工具调用没提升成功率"时；当你在设计harness的反馈策略并需要一个目标函数指导设计时。
- **何时规避**：单步任务（无反馈循环）不适用；实时系统如果NRS-EFC的计算开销占比过高（>5%预算）需权衡；反馈高度主观的任务（如创意写作）的I/V/M评分可靠性存疑。
- **供应商拷问清单**：(1) 你们的harness的η（EFC/C_raw）是多少？能否给出按I/V/R/M分解的瓶颈分析？(2) 你们的反馈设计中，有多少比例的反馈属于"低信息量"（I<0.3）或"高冗余"（R<0.5）？(3) Agent的上下文管理策略是否导致M（记忆保留）偏低——即关键反馈是否在长对话中被截断或遗忘？
- **工程落地路线图**：第一阶段（1-2周）：在现有harness上部署NRS-EFC测量管线，建立η基线；第二阶段（2-4周）：按四因子瓶颈排序，优先修复最低分因子（通常是R或M最容易通过工程手段改善）；第三阶段（持续）：建立EFC回归测试——每次harness改动后自动重测η，防止"优化token消耗反而降低EFC"的退化。
- **常见误区纠正**：(a) "减少工具调用次数就能提高效率"——错误。如果减少的是高EFC反馈，反而降低成功率。应该减少的是低I/高R的冗余调用。(b) "上下文窗口越大M越高"——不一定。更大的上下文可能稀释关键信息，反而降低M的有效部分。(c) "人工标注Oracle-EFC就是金标准"——Oracle-EFC只在标注者一致性高时才是金标准；如果标注者间agreement低（<0.7），Oracle本身的信度就需要质疑。

## 动手练习 💻
**练习目标**：模拟不同反馈质量下Agent迭代收敛速度的数值实验

**代码**（30-80行可运行Python，逐行中文注释）：

本模拟将EFC抽象为"每轮反馈中有效修正信号的比例"，噪声与(1-EFC)成正比（低质量反馈噪声更大），演示EFC如何通过影响迭代效率来改变相同预算下的最终收敛精度。

```python
import numpy as np
import matplotlib.pyplot as plt

# ===== 参数设置 =====
np.random.seed(42)
T = 30  # 最大迭代轮数
D_task = 5.0  # 任务难度归一化因子
target = 1.0  # 目标状态（Agent需要收敛到的值）

# 三种EFC水平对应的有效信息比例
efc_levels = {"低EFC(0.2)": 0.2, "中EFC(0.5)": 0.5, "高EFC(0.8)": 0.8}

# ===== 模拟函数 =====
def simulate_convergence(efc_per_round, noise=0.3, n_trials=100):
    """模拟Agent在给定EFC水平下的迭代收敛过程"""
    errors = np.zeros((n_trials, T))  # 存储每次试验每轮的误差
    for trial in range(n_trials):
        state = np.random.uniform(-2, 2)  # 随机初始状态
        for t in range(T):
            # 当前误差
            error = target - state
            # EFC决定有效反馈比例：只有efc_per_round比例的反馈真正有效
            effective_correction = efc_per_round * error
            # 噪声模拟反馈的不精确性，与EFC负相关（高质量反馈噪声更小）
            noise_scale = noise * (1 - efc_per_round)  
            state += effective_correction + np.random.normal(0, noise_scale)
            errors[trial, t] = abs(target - state)
    return errors.mean(axis=0)  # 返回所有试验的平均误差曲线

# ===== 实验1：不同EFC水平的收敛曲线 =====
fig, axes = plt.subplots(1, 2, figsize=(12, 5))

for label, efc in efc_levels.items():
    avg_errors = simulate_convergence(efc, noise=0.3, n_trials=200)
    axes[0].plot(range(1, T+1), avg_errors, label=label, linewidth=2)

axes[0].set_xlabel("迭代轮数"), axes[0].set_ylabel("平均误差")
axes[0].set_title("不同EFC水平下的Agent收敛曲线")

# ===== 实验2：多轮低质量 vs 少轮高质量的总预算效率 =====

low_efc, high_efc = 0.2, 0.8
low_rounds = total_budget // low_quality_cost   # 50轮
```

## 自测三层 🎓
**L1 复述**：
- Q: EFC由哪四个因子组成？各因子的含义是什么？
- A: I（信息量：反馈是否包含新信息）、V（有效性：反馈是否改变Agent行为）、R（不冗余：反馈是否与历史重复，越低越好）、M（记忆保留：反馈是否被保留在Agent上下文中）。四因子乘积关系，任一为零则整条EFC为零。
- Q: 原始计算量（token/工具调用/时间）预测任务成功率的R²分别是多少？
- A: Token消耗R²≈0.27，工具调用次数R²≈0.10，运行时间R²≈0.05。三个指标均接近零预测力，说明"计算量"和"成功率"之间没有简单的线性关系——花更多钱不等于更高成功率。

**L2 解释**：
- Q: 为什么原始token消耗的R²只有0.27而EFC的R²高达0.93-0.99？这个差距在方法论上说明了什么？
- A: R²差距约3.5-3.7倍说明不是"EFC略好"而是定性差异——原始计算量几乎不包含成功率信号，因为它混淆了大量无信息量/无效/冗余/被遗忘的计算。方法论上说明：在Agent系统中，"计算的质量维度"是主导因素，纯粹的量维度几乎没有解释力。这也意味着任何基于token消耗的harness优化都可能在南辕北辙。
- Q: 为什么EFC需要除以D_task（任务难度归一化）？如果不除以D_task会有什么问题？
- A: 同一EFC值在简单任务和困难任务上的效果差异巨大——100单位的有效反馈可能让简单任务成功率达到90%，但困难任务可能只有30%。不归一化会使得跨任务的EFC-成功率关系出现大量散点（不同任务形成不同曲线），无法拟合为统一的扩展律。除以D_task相当于把所有任务"对齐"到同一难度尺度。

**L2 解释（续）**：
- Q: Oracle-EFC和NRS-EFC的R²差距（0.99 vs 0.93）说明了什么？在什么场景下这个差距会扩大？
- A: 0.06的R²差距说明代理度量（NRS）仍有6%的不可解释方差。差距可能来自：(1) LLM自评信息量时的过度自信偏差；(2) 行为变化检测的阈值不精确；(3) 记忆保留M的代理度量（基于上下文窗口位置推断）与真实记忆效果之间的gap。在反馈语义复杂（讽刺、隐喻、多义）或Agent行为变化微妙的任务上，代理度量误差会更大，这个R²差距会扩大。这意味着在安全关键场景中，不应仅依赖NRS-EFC做决策。

**L3 应用**：
- Q: 假设你部署了一个Agent harness，用户反馈"工具调用很多但成功率没提升"。请用EFC框架给出系统性诊断方案。
- A: 按四因子逐项诊断：(1) **I诊断**：抽样50条反馈，人工或LLM评分——每条反馈是否提供了Agent尚不知道的新信息？如果大量反馈只是确认已知状态，I低。(2) **V诊断**：对比反馈前后Agent的行为轨迹——如果Agent收到反馈后行为无明显变化，V低。(3) **R诊断**：计算连续反馈之间的语义相似度——如果相似度>0.8的比例高，说明反馈冗余严重。(4) **M诊断**：检查Agent的上下文窗口——关键反馈是否在对话后期仍可访问？如果早期反馈被截断，M低。综合给出η估算和各因子瓶颈排序，优先修复最低分因子。
- Q: 设计一个基于EFC的在线harness自适应策略：如何在Agent运行过程中动态调整反馈策略以最大化η？
- A: 核心思路：在每轮反馈后实时计算滑动窗口内的NRS-EFC（如最近10轮），当检测到R（冗余度）超过阈值时触发反馈去重或摘要压缩；当检测到V（有效性）持续偏低时切换反馈格式或增加反馈的具体性；当检测到M（记忆保留）下降时（如关键早期信息接近上下文窗口边界），触发关键信息回注或外部记忆写入。整个策略实现为一个轻量级monitor模块，每轮消耗<200 token做NRS-EFC估算，开销控制在总预算的2%以内。
- Q: 如果你只能优化I/V/R/M中的一个因子，基于论文数据应该优先选哪个？为什么？
- A: 优先优化R（减少冗余）。原因：(1) R的改善通常成本最低——去重和摘要压缩是成熟技术，不需要改变Agent行为或反馈生成逻辑；(2) 冗余反馈不仅浪费token，还挤占上下文窗口间接降低M，有级联负效应；(3) 论文数据显示高冗余是大多数harness的共性问题（η<0.3的harness中，R是首要瓶颈的比例最高）。但具体选择应基于NRS-EFC在目标harness上的实测瓶颈排序——如果某个因子得分远低于其他，优先修复该因子。
