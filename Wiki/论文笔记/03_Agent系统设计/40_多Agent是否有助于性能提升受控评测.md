# 多 Agent 是否有帮助？LLM Agent 工作流的受控对齐评测

📄 **原文 PDF**：[[RAW/40 - Do More Agents Help Controlled and Protocol-Aligned Evaluation of LLM Agent Workflows.pdf]]

## PM 速判（3 分钟）

> **这篇论文给 PM 的一句话**：在公平受控条件下（相同基准加载器/工具/答案合约/日志）对比了 6 个多 Agent 系统（MAS）与匹配的单 Agent — **最多 1 个 MAS 超过单 Agent 基准**（+1.44 点，且在统计误差范围内），其余 5 个落后 2.56-11.29 点，且成本更高；**"加更多 Agent 就更好"的直觉在受控实验中不成立**。

| 项目 | 评估 |
|------|------|
| **评测框架** | BenchAgent（统一基准加载 + 工具访问 + 账务统计 + 轨迹日志）|
| **核心结论** | 6 个 MAS 中最多 1 个超过单 Agent，其余 5 个落后 2.56-11.29 点 |
| **例外** | 运行时生成工作流（Claude Code 风格）：GAIA 66.72%，比最强非 Claude 基线高 20+ 点 |
| **成熟度** | 🧪 在审，多机构联合 2026 |

## 核心发现

### 固定 MAS / 进化 MAS 对比单 Agent：工作流提升通常为负

```
实验设计：
  10 个基准（MATH/AIME/GSM8K/DROP/BBH/MMLU-Pro/HumanEval/MBPP/HotpotQA/IFEval）
  GPT-4.1 后端，固定 MAS 和进化 MAS vs 匹配的单 Agent

结论：
  ✗ 5/6 MAS 系统落后 2.56-11.29 点（且成本更高）
  ~ 1/6 (EvoAgent) 超出 +1.44 点（在 Wilson 置信区间内，统计不显著）
  → "更多 Agent = 更好性能" 在受控实验下不成立
```

### 运行时生成工作流：不同情况

Claude Code 风格的运行时生成工作流（动态 spawn 任务专用 Agent）：
- GAIA 整体准确率 **66.72%**，Level 3 **69.23%**
- 比最强非 Claude 固定 MAS（Jarvis）高 **20+** 点
- 使用 token 反而更少（更高效）

```
关键区别：
  固定 MAS = 预定义角色分工 + 固定通信拓扑 → 不适应任务
  运行时生成 = 根据任务内容动态创建 Agent + 分配专属上下文 → 按需调度
```

---

## 核心结论（带时间锚）

1. **预定义多 Agent 架构不如设计良好的单 Agent** 📅 2026  
   在工具、基准、评估协议完全对齐的情况下，MAS 的"劳动分工"优势几乎不存在。

2. **运行时生成工作流是真正的差异点** 📅 2026  
   动态 spawn Agent + 分配私有上下文是有效的——但这更像"一个强 Agent 生成任务专用 Agent"，而非传统的多 Agent 协作。

3. **过去 MAS 看起来更好，可能是因为测试条件不公平**（不同工具/不同基准实现/不同评估标准）

## 对 AI PM 的启示

| 场景 | 洞察 |
|------|------|
| **架构选型** | 不要因为"专业分工"就默认选 MAS；优先测试强单 Agent，在公平条件下对比 |
| **MAS 的实际价值** | MAS 在并行/独立子任务上有价值（非因为"协作"，而因为"并行化"）|
| **评估避坑** | 比较 Agent 架构时必须统一：benchmark loader / 工具 / answer contract / token 计费 |
| **投资回报** | 构建复杂 MAS 架构的工程成本很高；受控实验证明通常不值得 |

## 论文精读卡片

**一句话**：在统一受控条件下评测 6 个多 Agent 系统 vs 匹配单 Agent，5/6 的 MAS 落后 2.56-11.29 点且成本更高，"更多 Agent = 更好"在受控实验中不成立。

**问题**：现有 MAS 评测因基准实现/工具配置/评估协议不统一而存在系统性偏差，导致 MAS 看起来比单 Agent 更好——但这是测试条件不公平的结果还是 MAS 本身的优势？

**核心方法**：
- 构建 BenchAgent：统一基准加载器 + 工具访问 + 答案合约 + token 计费 + 轨迹日志
- 在 10 个基准（MATH/AIME/GSM8K/DROP/BBH/MMLU-Pro/HumanEval/MBPP/HotpotQA/IFEval）上，以 GPT-4.1 为后端，对比 6 个固定/进化 MAS vs 匹配单 Agent
- 额外测试运行时生成工作流（Claude Code 风格动态 spawn Agent）

**关键图/公式**：固定 MAS 失败的核心原因：预定义角色分工 + 固定通信拓扑无法适应任务，而运行时生成工作流（按任务内容动态创建 Agent + 分配专属上下文）打破了这一限制，在 GAIA 上达 66.72%。

**实验设置**：
- 规模/数据：10 个基准，GPT-4.1 后端，6 个 MAS 系统（含 EvoAgent、Jarvis 等）
- 对比：固定 MAS / 进化 MAS vs 匹配的单 Agent；运行时生成工作流 vs 最强固定 MAS

**最强证据**：5/6 MAS 落后 2.56-11.29 点；运行时生成工作流 GAIA 66.72%（Level 3 69.23%），比最强非 Claude 固定 MAS（Jarvis）高 20+ 点且 token 更少。

**最弱证据**：仅用 GPT-4.1 作为后端，未验证结论是否在其他 LLM（Gemini/Llama）上泛化；10 个基准覆盖范围有限，缺少开放式/创意/长期任务。

**可复用点**：BenchAgent 的四元统一协议（benchmark loader / tool access / answer contract / token accounting）是任何 Agent 架构对比实验的必备对照设计；"先单 Agent 基线，再在受控条件下加 MAS"的评估方法论。

> [!question]- 1. BenchAgent 统一了哪四个维度，解决了什么具体的评测偏差？
> **参考答案**：统一 benchmark loader（基准加载方式）、工具访问（tool access）、答案合约（answer contract）、token 计费（token accounting）四个维度；解决的是"过去 MAS 看起来更好，可能只是因为测试条件不公平（不同工具/不同基准实现/不同评估标准）"这一系统性偏差。
> **判分点**：必须答出四个维度名称、以及"消除条件不公平导致的虚高对比"这一目的（缺一不可）

> [!question]- 2. 6 个 MAS 中有几个超过了单 Agent 基线？差距范围是多少？
> **参考答案**：最多 1 个（EvoAgent）超过，+1.44 点且在 Wilson 置信区间内统计不显著；其余 5 个落后 2.56-11.29 点，且成本更高。
> **判分点**：必须答出"至多 1 个且统计不显著"+ 5 个落后的具体区间（缺一即卡点）

> [!question]- 3. 运行时生成工作流和固定 MAS 的本质区别是什么？
> **参考答案**：固定 MAS 是预定义角色分工 + 固定通信拓扑，无法适应任务；运行时生成工作流是根据任务内容动态创建 Agent + 分配专属上下文，按需调度——本质上更接近"一个强 Agent 生成任务专用 Agent"，而非传统多 Agent 协作。
> **判分点**：必须答出"预定义/固定拓扑 vs 动态创建+专属上下文"的对比，且指出运行时生成不算传统协作

> [!question]- 4. 这篇论文对 MAS 的结论是否是绝对否定，还是有条件的？（并行化价值 vs 协作价值）
> **参考答案**：有条件否定——否定的是"协作"带来的性能提升（受控条件下几乎不存在），但不否定 MAS 在并行/独立子任务上的价值（价值来自"并行化"而非"协作"）。
> **判分点**：必须区分"协作价值"（论文否定）与"并行化价值"（论文未否定），只答"MAS 没用"算未命中

> [!question]- 5. 如果你要在公司内做 Agent 架构的 A/B 测试，你会如何设计受控条件？
> **参考答案**：至少统一 BenchAgent 的四要素——相同 benchmark loader、相同工具访问权限、相同 answer contract、相同 token 计费口径，并先建立强单 Agent 基线，再在此受控条件下加 MAS 做对比。
> **判分点**：必须提到"先建单 Agent 基线"+ 至少 2 个受控维度（工具/基准/计费口径任选其二）
