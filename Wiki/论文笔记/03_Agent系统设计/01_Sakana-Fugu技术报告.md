# Sakana Fugu Technical Report

## PM 速判（3 分钟）

> **这篇论文给 PM 的一句话**：SakanaAI 发布了一个"编排器模型"——一个专门训练来动态调度多个 LLM 的语言模型，用组合集成的方式在多项顶级 Benchmark 上超过了任意单一模型。

| 项目 | 评估 |
|------|------|
| **核心能力** | 动态多 LLM 编排：一个接口调用多个 LLM，按需组合 |
| **成熟度** | 🧪 研究 + 商业产品并行（API 已上线 sakana.ai/fugu） |
| **开源实现** | 无（闭源） |

---

## 解锁了什么产品能力

1. **用组合代替单模型**：不需要等一个更强的大模型，通过调度现有多个模型的组合就能突破单模型天花板
2. **单一接口透明集成**：用户感知到的是一个模型，底层是多个 Worker LLM 在协同
3. **能力可配置**：Worker Pool 可以按合规/隐私/厂商偏好灵活配置，无需重新训练

---

## 技术架构（工程视角）

### 整体设计
```
用户请求
    ↓
[Fugu 编排器 LM]
  └─ 预训练 LM 主干（理解查询语义）
  └─ 轻量分类头（线性/低秩/稀疏，作用在最后一个 token）
     └─ 输出：哪些 Worker + 如何沟通 + 如何合并
    ↓
Worker Pool（多家厂商 API 模型）
  ├─ Worker A：GPT 系列（数学/推理）
  ├─ Worker B：Claude 系列（代码/安全）
  └─ Worker C：Gemini 系列（其他）
    ↓
合成回答 → 返回用户
```

### 两个产品变体
- **Fugu**：性能与延迟平衡，适合日常交互；基于 Trinity 架构扩展到生产规模
- **Fugu-Ultra**：优先答题质量，调用更大的 Worker Pool，延迟较高

### 训练流程
```
① 大规模监督微调（SFT）
   ↓ 用现有编排轨迹数据学习"如何分配任务"
② 进化算法搜索
   ↓ 搜索最优的编排策略组合（"编排食谱"）
③ 强化学习（RL）
   ↓ 以端到端任务结果为奖励信号，进一步优化
```

**关键工程直觉**：把"怎么编排"这个决策本身参数化为模型输出，而非写死成规则。这样模型可以根据每个查询定制最优的 Agent 交互拓扑。

## 值得追踪的产业含义

1. **"编排即产品"时代来临** 📅 2026.06
   能力天花板不再只由单模型决定，谁的编排系统更聪明，谁就赢。PM 要关注编排层的差异，不只是基础模型的差异。

2. **多厂商 LLM 集成成为标配** 📅 2026.06
   高端 AI 产品越来越可能同时调用 OpenAI + Anthropic + Google，而不是押注单一厂商。供应商锁定风险下降，但成本管控和延迟优化难度上升。

3. **能力可解耦于训练规模** 📅 2026.06
   Fugu 展示了不需要训练更大的模型，只需更聪明地"组合"现有模型，也可以达到 SOTA。这可能降低前沿 AI 能力的资金门槛。

4. **产品 Worker Pool 配置成为竞争因素** 📅 2026.06
   哪些厂商模型在 Pool 里、比例如何、能否自定义——这些将成为 B2B AI 产品的差异化点。

## 局限与生产风险

| 风险 | 说明 |
|------|------|
| 成本不可控 | 多 Worker 调用，单次请求成本可能是单模型的 3-10x |
| 延迟不稳定 | P99 延迟受最慢 Worker 影响，实时交互场景慎用 |
| 黑盒编排 | 为什么选这些 Worker？出错了怎么追溯？可解释性差 |
| 竞品依赖 | Worker Pool 里的模型能力随时更新/停服，系统稳定性受威胁 |
| 基准 vs 产品 GAP | Benchmark SOTA 不等于垂直业务 SOTA，需要行业特定评测 |

## 论文精读卡片

**一句话**：SakanaAI 通过训练专用"编排器 LM"动态调度多厂商 LLM 的组合，在 Humanity's Last Exam 上以 56.1% 超越单一最强模型（53.3%），证明编排系统可突破单模型天花板。

**问题**：单一 LLM 存在能力天花板，不同任务类型（数学/代码/语言）往往需要不同模型；但手写规则的路由脆弱、不可扩展。如何让路由决策本身成为可训练的模型行为？

**核心方法**：
- 将编排决策参数化为 LLM 输出：在预训练 LM 主干上加轻量分类头（线性/低秩/稀疏），作用于最后一个 token，输出 Worker 选择方案和合并策略
- 三阶段训练：大规模 SFT（学编排轨迹）→ 进化算法搜索（最优"编排食谱"）→ RL 以端到端任务结果为奖励信号
- Worker Pool 与编排器解耦：Pool 可按合规/厂商偏好配置而无需重新训练编排器

**关键图/公式**：编排器 LM 的核心洞察是将"如何编排"这个决策本身参数化为模型输出而非规则，使得每个查询可获得定制的 Agent 交互拓扑。分类头极轻量（作用于单 token），决策延迟接近零，Worker 才是主要延迟来源。

**实验设置**：
- 规模/数据：多项顶级 Benchmark；Worker Pool 含 GPT/Claude/Gemini 系列；Fugu（平衡版）和 Fugu-Ultra（质量优先版）
- 对比：与 Claude Opus 4.8、GPT-5、Gemini 等最强单一模型对比

**最强证据**：Fugu-Ultra 在 Humanity's Last Exam（56.1%）超过 Claude Opus 4.8（53.3-54.2%），Terminal Bench（95.5% vs 92.0%），GPQA-Diamond（80.0% vs 78.2%）。在多个 Benchmark 上同时超越所有单一 Worker 模型，说明组合效应是真实且稳定的。

**最弱证据**：论文未公开 Worker 调用策略（哪类任务选哪些 Worker），无法独立验证编排决策质量；Benchmark SOTA 未证明垂直业务场景的优势；单次请求成本可能是单模型 3-10x，但无成本与性能 tradeoff 的详细数据。

**可复用点**：将路由/编排决策从"写规则"改为"训练模型"的范式——可在内部多 LLM 平台中，用 SFT 在历史调用数据上训练轻量路由器，成本远低于从头训练大模型但可显著提升整体性能。

**我能拿它做什么**：
- 在多 LLM 产品平台设计中，优先考虑"编排器 + Worker Pool"分层架构，而非固定路由规则
- 用公开评测数据向业务方论证"组合 LLM 系统"的必要性，将 Fugu 作为对标案例
- 在 Worker Pool 设计中纳入合规/成本/延迟维度，利用编排器可配置性做差异化
