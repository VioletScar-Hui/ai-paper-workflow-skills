## 解锁了什么产品能力

1. **自动最优模型选择**：不再"一刀切"用最贵模型，每任务动态选最合适的
2. **成本/性能比可控**：在路由奖励函数中平衡性能权重 ε₁ 和成本权重 ε₂，按需调节
3. **自适应优化**：路由系统随运行积累经验，无需重新训练整个路由器

## 技术架构（工程视角）

### 三组件设计（ACRouter）

→ 核心框架详见：[[Wiki/概念/04_Agent框架/模型路由与CAF循环]]

```
任务流输入 T = (t₁, t₂, ..., tₙ)
         ↓
    编排器（Orchestrator）
    ├─ 输入：任务提示词 + 任务维度元数据 + 历史kNN检索结果
    ├─ 核心：Qwen3.5-0.8B（微调）+ 启发式规则（加权投票）
    └─ 输出：选择模型池中的哪个 LLM
         ↓
    选定 LLM 执行任务
         ↓
    验证器（Verifier）
    ├─ 代码任务：沙箱执行 + AST解析 → 客观得分 [0,1]
    └─ 输出：(性能得分 ŝᵢ, 成本 κ̂ᵢ)
         ↓
    记忆模块（Memory）
    ├─ 存储：(任务, 选择模型, 得分, 成本) 四元组
    └─ 检索：kNN 找相似历史任务 → 提供给下次编排器
         ↓
    上下文更新 → 下一个任务决策更有据可循
```

### CodeRouterBench（评测基准）

- **~10K 任务**：9 个编程维度（代码理解/补全/测试/调试/文档 等）
- **8 个前沿 LLM**：Claude Opus/Sonnet、GPT-5.4、Qwen3.5 系列等
- **OOD 任务**：Agentic Programming（更复杂的仓库级编程任务，检验泛化）
- **评估方式**：流式设定下的累积遗憾（低 = 更接近最优路由）

## 关键实验结果

### 路由性能对比（平均性能分 AvgPerf%）

| 路由策略 | AvgPerf% | 说明 |
|---------|---------|------|
| Per-task Oracle（理论上界） | 最高 | 每次都选最优模型 |
| ACRouter（本文） | **最低遗憾** | C-A-F 自适应路由 |
| DimensionBest（启发式最优） | 47.50% | 基于维度的静态路由 |
| LLM + Perf stats | 47.74% | 给 LLM 补充历史统计 |
| 单最强模型（Claude Opus）| ~45%? | 固定用最强模型 |
| Vanilla LLM Router | 41.41% | 无历史经验的基线 |

**关键发现**：路由的瓶颈是信息缺失（+15.3% 来自补充历史统计），不是 AI 推理能力不足。

---

## 核心结论（带时间锚）

1. **任务-模型适配性差异远大于想象** 📅 2026.06
   在 8 个前沿模型 + 9 个编程维度的实验中，不同任务的"最优模型"差异显著。总用最强模型并不总是最优选择（Qwen 在测试生成上甚至优于 Claude Opus）。

2. **路由瓶颈 = 信息缺失，非推理缺失** 📅 2026.06
   给 LLM 路由器提供历史性能统计（而不是改进其推理能力），就能提升 15.3%。这意味着数据 > 模型能力 在路由任务中。

3. **闭环反馈让路由器自我改善** 📅 2026.06
   C-A-F 循环使路由器随时间积累领域知识，无需重新训练。这是"数据飞轮"在路由层面的应用。

4. **OOD 泛化能力强** 📅 2026.06
   ACRouter 在 OOD 的 Agentic Programming 任务上同样表现优秀，说明经验积累有跨任务类型的泛化性。

## 与 Sakana Fugu 的对比

| 对比维度 | ACRouter（本文） | Sakana Fugu (Paper 01) |
|---------|---------------|----------------------|
| 路由策略 | 按任务特征选最优单模型 | 可能同时调用多个模型并合成 |
| 经验积累 | ✅ C-A-F 实时积累 | 未提（模型本身训练好） |
| 透明度 | 较高（可追踪选了哪个模型） | 较低（内部编排不透明） |
| 适用规模 | 中小规模（单任务路由） | 大规模（复杂任务编排） |

## 论文精读卡片

**一句话**：NUS+阿里 DAMO 提出 C-A-F 自适应路由框架，发现路由瓶颈是信息缺失而非推理能力——仅靠补充历史性能统计就提升 15.3%（Vanilla LLM Router 41.41% → 47.74%），在 8 个前沿 LLM × 9 个编程维度的 CodeRouterBench 上验证。

**问题**：多 LLM 产品中每次都用最贵的模型（如 Claude Opus）并非最优，因为不同任务有不同最佳模型（Qwen 在测试生成上甚至超过 Opus）；但有效路由需要历史经验，而现有路由器缺乏积累机制。

**核心方法**：
- ACRouter 三组件：编排器（Qwen3.5-0.8B 微调 + 启发式规则）→ 选定 LLM 执行 → 验证器（沙箱执行 + AST 解析获取客观得分）→ 记忆模块（kNN 检索相似历史任务）
- C-A-F 闭环：Context 积累（存储四元组 = 任务+模型+得分+成本）→ Adaptation（kNN 检索历史给编排器）→ Feedback（验证器输出更新记忆）
- 奖励函数：R = ε₁ × 性能得分 + ε₂ × 成本效益，按需调节性能与成本权重

**关键图/公式**：关键公式 R = ε₁ × ŝᵢ + ε₂ × (1/κ̂ᵢ)，其中 ε₁、ε₂ 为可调权重，ŝᵢ 为验证器输出的性能得分，κ̂ᵢ 为成本。这个奖励函数将成本-性能 tradeoff 变为可调参数，PM 可直接通过调节 ε 比值控制路由策略。

**实验设置**：
- 规模/数据：CodeRouterBench，约 10K 任务，9 个编程维度（代码理解/补全/测试/调试/文档等），8 个前沿 LLM，含 OOD 的 Agentic Programming 任务
- 对比：Per-task Oracle（理论上界）、DimensionBest（静态启发式）、LLM + Perf stats、Vanilla LLM Router

**最强证据**：给 LLM 路由器补充历史性能统计（而非改进推理能力）就提升 15.3%（41.41%→47.74%），直接证明"路由瓶颈 = 信息缺失"而非推理缺失。且 ACRouter 在 OOD 的 Agentic Programming 上同样有效，说明经验积累有跨任务泛化性。

**最弱证据**：实验局限于代码领域，其他任务类型（写作/分析/图像）的路由效果未验证；轻量路由器（0.8B）的选择对其他领域是否适用未探讨；CodeRouterBench 是自建数据集，外部可重复性未经独立验证。

**可复用点**：C-A-F 闭环的最小实现：在多 LLM 产品中加一个结果记录表（任务类型、选择模型、成功/失败），用 kNN 检索历史记录辅助路由决策——不需要完整框架，记录 + 检索这两步就能带来显著提升。
