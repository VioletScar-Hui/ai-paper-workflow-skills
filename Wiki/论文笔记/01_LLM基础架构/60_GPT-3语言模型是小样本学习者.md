# GPT-3：语言模型是小样本学习者

📄 **原文 PDF**：[[RAW/60 - Language Models are Few-Shot Learners.pdf]]

## PM 速判
> 一句话：GPT-3（175B 参数）首次以 convincing 规模证明：语言模型可以通过 In-Context Learning（在 prompt 中放几个示例，不做任何梯度更新）达到甚至超越有监督微调模型的水平。这是"规模带来质变"的最经典案例，也是今天所有 LLM API 产品的直接技术前提。

## 双层费曼
> **给 CEO 的一句话**：GPT-2 证明了"不用训练就能做翻译"这条路可行但还不够好。GPT-3 证明了"把模型做大 100 倍 + 在问题前面放几个例子"，效果就能追上甚至超过专门训练过的专用模型。这意味着：以后做 AI 产品，你不再需要为每个任务收集数据、训练模型——你只需要设计好 prompt 和几个示例，一个通用模型就能搞定几乎所有语言任务。API 经济的基础就是这篇论文建立的。

> **给工程师的一段话**：GPT-3 是一个 175B 参数的自回归 Transformer（96 层，d_model=12288，96 个 attention heads），在 300B tokens 的混合语料（Common Crawl 过滤版 60% + WebText2 22% + Books1/2 16% + Wikipedia 3%）上训练。关键创新不是架构（与 GPT-2 几乎相同），而是 In-Context Learning（ICL）范式的系统验证：在模型输入中直接拼接 k 个任务示例（zero-shot k=0, one-shot k=1, few-shot k=10-100），模型通过 attention 在上下文中"学习"任务模式，输出时跟随该模式——整个过程没有任何参数更新。核心发现：(1) few-shot 性能随模型规模呈 log-线性增长，存在明显的"涌现"现象——125M-13B 的模型 few-shot 几乎无用，175B 突然能用；(2) 在 TriviaQA 上 few-shot 71.2%（超越当时的 fine-tuned SOTA 68.0%），CoQA 85.0%，SuperGLUE few-shot 接近 fine-tuned BERT-Large。

## 问题域定位
- **回应什么根本约束？** 微调的根本局限性。即使是 BERT/GPT-1 的"预训练-微调"范式，仍然需要：(1) 数千到数万条标注数据，(2) 对每个新任务做一次梯度更新（意味着需要保存和部署 N 个模型副本用于 N 个任务），(3) 微调可能导致 catastrophic forgetting 和 overfitting（在小数据集上）。根本问题是：能否完全消除 micro-level 的梯度更新，让模型仅通过 prompt 中的示例就能适应新任务？
- **之前卡在哪？** GPT-2 尝试了 zero-shot 但效果不稳定（多数任务远不如微调）。没人知道"加上示例会不会有用"——因为 GPT-2 的规模不够大，加上示例后效果不仅不提升反而可能下降（模型把示例当成了要续写的文本而不是任务指令）。一个关键的技术障碍：需要在同一个 batch 中放下 prompt + 多个示例 + 实际输入，这对上下文窗口和 attention 计算都提出更高要求。
- **开启/关闭了哪条技术路线？** 开启了：(1) In-Context Learning 作为主要 NLP 交互范式（所有现代 LLM API 的基础），(2) 规模涌现的系统研究（scaling laws for emergent abilities），(3) 提示工程（prompt engineering）作为一个独立的技术方向。关闭了：GPT-3 之后，"要不要做预训练-微调"不再是问题——问题变成了"用多大的预训练模型 + 放多少个示例"。fine-tuning 没有消亡（GPT-3 也报告了 fine-tuning 的结果），但被推到了特定高精度需求场景。

## 设计决策解剖

| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| 训练数据混合策略 | 高质量数据（Wikipedia, Books, WebText2）以极高权重过采样——虽然它们只占总 token 的 3-22%，但在训练中被采样的概率远高于其占比 | 按数据量比例的均匀采样（Common Crawl 占绝大多数，模型主要学习低质量文本） | 核心洞察：模型从高质量文本中学得更高效。如果按 token 比例采样，Common Crawl 中的噪声会主导训练信号。过采样高质量数据相当于"课程学习"——用少量精品数据引导模型建立好的语言先验，再用大量数据扩充知识面 | 当过采样比例过高时（如 Wikipedia 权重 10×），模型会在这些数据上过拟合，减少对 Common Crawl 中长尾知识的覆盖。GPT-3 的后续工作（如 Gopher, Chinchilla）通过更精细的数据质量建模（分类器过滤 + 动态加权）替代了手工权重设计 |
| 模型并行策略 | Megatron-LM 风格的模型并行（将 attention heads 和 FFN 的列切分到不同 GPU）+ 数据并行 | Pipeline 并行（GPipe 方式，将不同层放到不同 GPU）或纯数据并行 | 模型并行对于 175B 是必须的（单 GPU 装不下完整模型）。Megatron 的切分方式在 attention 和 FFN 中各自只需要一次 all-reduce 通信（而不是每层的每个操作都通信），通信量更小。GPU 间用 InfiniBand 连接，带宽 100+ GB/s | 当模型规模进一步增大到 500B+ 时，纯模型并行也不够——需要 tensor parallelism + pipeline parallelism + data parallelism 的三维混合并行（如 Megatron-Turing NLG 530B 采用的方式） |
| 上下文窗口 | 2048 tokens | 更大的窗口（如 4096 或 8192）或可变长度 | 2048 是 GPT-2 (1024) 的两倍，足以放下 few-shot 示例（10-20 个示例通常需要 500-1500 tokens）。更大的窗口需要 O(n²) 的 attention 计算和显存，在 175B 规模下成本极高 | 当需要更长的上下文：(1) 放更多示例（k>50），(2) 处理长文档（法律合同、论文），(3) 做多轮对话。2048 很快成为瓶颈。GPT-4 扩展到 8192/32K，Claude 扩展到 100K。但长上下文的成本问题至今没有根本解决——需要 sparse/flash attention 等技术缓解 |
| 模型架构 | 与 GPT-2 几乎相同的 Transformer decoder（仅调整了初始化），使用 alternating dense and locally banded sparse attention patterns | 引入稀疏注意力（Sparse Transformer）、线性注意力（Linformer）、或改用 encoder-decoder 架构 | 故意保持架构不变——论文的核心问题是"规模能带来什么"，而非"什么架构更好"。如果改了架构，就无法干净地归因于规模。这种"控制变量"的严谨性使论文的规模涌现结论更加可信 | sparse attention 实际上被 GPT-3 部分采用了（在部分层中用 banded attention 替代 full attention），这降低了深层 attention 的计算量。但当任务需要长程依赖（代码、长文档）时，sparse attention 会损失信息。因此 GPT-3 之后的模型（GPT-4, Claude）重新回到 full attention 并依赖工程优化（flash attention）来解决效率问题 |
| 评估方式 | 主要依赖 20+ 个标准 NLP 基准，外加少量人工评估 | 大规模人工评估（RLHF 风格）或用户产品数据（A/B 测试） | 标准基准可以精确量化、可复现、与之前的工作直接对比。但这也是 GPT-3 论文的一个局限——基准得分好不等于产品好用 | 当产品进入真实部署时，标准基准不够：(1) 任务分布不匹配产品需求，(2) 基准存在数据污染风险（GPT-3 的训练数据可能包含了评估集），(3) 无法衡量用户体验的重要维度（语气、安全性、拒绝能力）。InstructGPT/GPT-4 后续大量使用 RLHF 和人工评估来弥补这一点 |

## 成本与量级
- **训练成本**：175B 的 GPT-3 在微软 Azure 的超级计算机（~10,000 块 V100 GPU）上训练，具体时间和费用未公开。按公开信息估算：约 3640 PFLOP-days（比 GPT-2 1.5B 的约 100 PFLOP-days 大 36 倍）。按 2020 年云 GPU 价格约 $4.6M 的纯计算成本（不包括人力、实验、失败重试）。如果今天复现（2024 A100/H100），成本约 $500K-$1M。
- **推理成本**：175B 参数的 GPT-3 需要约 350GB 显存（FP16），单次推理延迟约 200-500ms（2020 V100）。API 服务需要 8 张 A100 80GB（或更多 V100）。这是 OpenAI 推出 API 而非开源模型的核心原因——普通用户根本无法运行。
- **最小可行配置**：用 GPT-NeoX-20B 或 LLaMA-7B 等开源模型替代 GPT-3 做 ICL 实验。这些模型在 1-2 张 A100 上即可运行，且同样展现出显著的 few-shot 能力。如果只验证 ICL 的涌现现象，用 GPT-2 系列（125M → 1.5B）+ 开源小模型（1.3B, 2.7B, 6.7B, 13B）对比即可。

## 证据审计
- **实验设计公平吗？** 从科学上讲，实验设计非常严密——8 个模型规模 + 20+ 个基准 + 3 种 shot 设定 + 多次采样（temperature=0 的 greedy decoding 和 temperature=1 的采样评估），结论呈现了清晰的趋势而非孤立的数字。但从实用角度，有一个重要的不公平：GPT-3 few-shot vs fine-tuned SOTA 的对比。fine-tuned SOTA 模型的参数量通常远小于 GPT-3（如 BERT-Large 340M），而 GPT-3 few-shot 有 175B 参数。这不是"方法"的对比，而是"计算量"的对比。公平的对比应该控制总训练/推理计算量。
- **最强证据**：规模涌现曲线。TriviaQA 上 zero-shot 从 125M 的 1.0%（几乎随机猜测 4 选 1 的 25%）→ 175B 的 64.3%；few-shot 进一步到 71.2%。这个提升不是线性的——125M 到 13B 的 few-shot 提升缓慢（~10-20 百分点），13B 到 175B 突然跳跃（+30 百分点）。这种"非连续性"的涌现是论文最震撼的证据。SuperGLUE 上 few-shot 175B 的 71.8 接近 fine-tuned BERT-Large 的 71.9（且只用 32 个示例），这在 2020 年是不可想象的。
- **最可疑的数字**：LAMBADA（长程上下文完形填空）的 zero-shot 准确率 76.2% vs SOTA 68.0%——但 LAMBADA 评估时用的具体 prompt 格式是 "text →" 还是 "text" 还是别的？ICL 对 prompt 格式高度敏感（GPT-3 论文自己提到同一任务不同 prompt 格式的差异可达 5-10 个百分点）。此外，TriviaQA 80.0%（few-shot 64 shot）vs fine-tuned SOTA 68.0% 这个数字尤其可疑——TriviaQA 是一个"冷知识问答"任务（如"哪个国家有最多的岛屿？"），GPT-3 175B 的训练数据中可能包含了维基百科和书籍中的大量 TriviaQA 答案。数据污染的评估不充分，尽管论文声称排除了与评估集重叠的数据，但语义重叠和近义改写是难以完全消除的。
- **审稿人会要求补充**：(1) 数据污染的系统检测——对每个评估集，计算训练数据中的 n-gram 重叠率和语义相似度分布，报告污染指标。(2) ICL 的工作机制分析——attention 究竟是"从示例中学习映射"还是"从示例中检索模式"？两者有本质区别。(3) 计算量公平的对比——给定相同的总 FLOPs 预算，few-shot ICL (大模型 + 零训练) vs fine-tuning (小模型 + 全微调) 哪个更好？(4) 示例顺序的影响——few-shot 结果对示例排列顺序的敏感度，以及如何选择最优的示例序列。
- **最小复现实验**：用 LLaMA-7B（或 GPT-2 系列）在分类任务上测试 k = 0, 1, 5, 10, 20 的 few-shot 示例数量对准确率的影响。用 SST-2（情感分析）或 AG News 做代理任务。预算：单 A100，数小时（如果本地运行 LLaMA-7B）。核心验证：(1) few-shot > one-shot > zero-shot，(2) 示例数量增加到一定程度后边际收益递减，(3) 模型规模越大 ICL 能力越强。

## 可复用点
- **何时采用**：任何需要"快速适应新任务 + 零标注成本"的场景，ICL 都是第一选择。现代最佳实践：(1) 用 GPT-4/Claude API + few-shot prompt（3-10 个精心挑选的示例，覆盖任务的各种边界情况）是最快的验证方式；(2) 如果 ICL 效果不够，再考虑 prompt fine-tuning 或 full fine-tuning。ICL 也是 A/B 测试 prompt 设计时的核心工具——改变示例能产生巨大差异。
- **何时规避**：(1) 任务需要极高的准确率（>99%）和低方差（ICL 的随机性不可避免），→ 用 fine-tuning；(2) 任务需要大量领域专业知识且不常见于预训练数据（如特定行业的法律/医疗术语），→ ICL 示例不够，需要领域微调或 RAG；(3) 成本敏感且调用量大——ICL 每次推理需要把全部示例放入输入（增加 token 成本），→ 可考虑 distillation 把 ICL 行为蒸馏到小模型。
- **供应商拷问清单**："你们的 API 支持多少 token 的上下文窗口？我能放多少个 few-shot 示例？""ICL 示例的 token 是按输入同样计费吗？""你们是否检测和防止评估数据污染？用什么方法？""你们的模型在多少参数时出现了涌现现象？有没有规模 vs 能力的公开发布曲线？"

- [[Wiki/论文笔记/10_RAG检索/59_RAG知识密集型NLP任务的检索增强生成]] — ICL 和 RAG 是两种互补的知识利用方式：ICL 将知识放在 prompt 中（上下文窗口限制知识量），RAG 从外部数据库检索（无上下文窗口限制但增加检索延迟）。GPT-3 证明了前者可行，但也暴露了 2048 token 窗口的局限——驱动了 RAG 的研究
- [[Wiki/概念/03_推理与评测/思维链与推理模型]] — Chain-of-Thought prompting (Wei et al., 2022) 完全建立在 GPT-3 的 few-shot ICL 基础上——通过在 few-shot 示例中添加推理步骤（而非只给最终答案），引导模型输出中间推理链
- [[Wiki/概念/03_推理与评测/测试时计算扩展]] — GPT-3 的规模涌现现象是 scaling law 研究的关键数据点。测试时计算扩展（如 best-of-N sampling, majority voting）也是建立在 GPT-3 首先展示的"大模型 + ICL 本身已经够好"的前提上
- **冲突/印证**：与 scaling laws (Kaplan et al., 2020, OpenAI) 直接印证——GPT-3 论文本身就是 scaling laws 研究的产物，其规模选择（8 个点构成 log 均匀间隔）就是为了验证幂律。与 Chinchilla (Hoffmann et al., 2022, DeepMind) 存在微妙冲突：GPT-3 训练了 300B tokens 在 175B 参数上（token:param ≈ 1.7:1），Chinchilla 后来证明这个比例严重不足——最优应该是 ~20 tokens per parameter，即 175B 模型应该训练 3.5T tokens 而非 300B。这意味着 GPT-3 是"欠训练"的——如果有更多训练预算，同规模的模型能力会更强。这个"冲突"不是否定 GPT-3，而是说明了 scaling 研究的进展。
