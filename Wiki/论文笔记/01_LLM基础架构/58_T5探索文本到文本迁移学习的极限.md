# T5：用统一 Text-to-Text Transformer 探索迁移学习的极限

📄 **原文 PDF**：[[RAW/58 - Exploring the Limits of Transfer Learning with a Unified Text-to-Text Transformer.pdf]]

## PM 速判（30秒）
> 一句话：T5 把所有 NLP 任务统一成"输入文本 → 输出文本"一种格式，用 50+ 组对照实验系统回答了"预训练该怎么做"，并发布了 C4 数据集和 60M-11B 五档模型。PM 必须知道它，因为今天所有 LLM 产品的"一个模型做所有任务 + prompt 里写任务说明"范式，源头就在这里；而它与 GPT-3 的架构路线之争（encoder-decoder vs decoder-only）是理解现代模型选型的必修课。

## 双层费曼 🗣️
> **给 CEO 的一句话**：以前每种语言任务（翻译、摘要、分类）要做一个专门模型，T5 证明一个模型加一句"任务说明"就能全做——这是"一个 AI 助手干所有事"这门生意在技术上成立的第一份系统性证据。
>
> **给工程师的一段话**：T5 用标准 encoder-decoder Transformer，把翻译、分类、回归（STS-B 输出 "3.8" 字符串）全部转成 seq2seq 文本生成，共享同一个交叉熵损失。预训练用 span corruption：随机遮盖平均长度 3 的连续 token 片段（总遮盖率 15%），target 只生成被盖的片段（哨兵 token 分隔），比 BERT 式 MLM 的输出序列短、训练更省。论文核心价值是控制变量消融：在同等算力预算下对比架构（enc-dec / decoder-only LM / prefix LM）、目标函数、数据过滤、微调策略，结论是 enc-dec + span corruption + 过滤后的 C4 组合最优，最后把配方放大到 11B 拿下 18/24 个基准 SOTA。

## 问题域定位 🎯
- **根本约束**：迁移学习方法大爆炸（BERT/GPT/XLNet 各有架构、目标、数据），彼此实验设置不可比，领域无法回答"到底哪个设计真正有用"。
- **之前卡在哪**：BERT 系 encoder-only 做不了生成；GPT 系纯 LM 在理解类基准上落后；每个任务还要接不同的输出头和损失函数，工程碎片化。
- **开启/关闭的路线**：开启了"任务即文本前缀"（今天的 system prompt / instruction 的前身）和"用统一框架做可比消融"的方法论；同时发布 C4 成为之后五年开源预训练的默认数据底座。它没有关闭 decoder-only 路线——GPT-3 半年后用纯规模给出了另一个答案。

## 核心机制

```
所有任务 → 同一个模型、同一个损失：

"translate English to German: That is good."  ─┐
"cola sentence: The course is jumping well."  ─┤    ┌─────────┐      ┌─────────┐
"summarize: state authorities dispatched..."  ─┼──→ │ Encoder │ ──→  │ Decoder │ ──→ 文本输出
"stsb sentence1: ... sentence2: ..."          ─┘    │ (双向)   │      │ (因果)   │    "Das ist gut."
        ↑ 任务前缀写进输入文本                        └─────────┘      └─────────┘    "not acceptable"
                                                                                     "3.8" ←回归也输出字符串

预训练目标（Span Corruption）：
原文:   Thank you for inviting me to your party last week .
输入:   Thank you <X> me to your party <Y> week .        ← 连续片段被哨兵替换
目标:   <X> for inviting <Y> last <Z>                     ← 只生成被盖片段，序列短、省算力
```

三种架构对同一输入的注意力可见性（本篇消融的核心对象，动手练习会实现它）：

```
Encoder-Decoder          Prefix LM (decoder-only)     纯因果 LM (decoder-only)
输入部分: 全双向可见       输入部分: 双向可见             输入部分: 只能看左边
输出部分: 因果+看全输入    输出部分: 因果+看全输入        输出部分: 因果
```

## 设计决策解剖 ⚖️

| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| 模型架构 | Encoder-Decoder | decoder-only 因果 LM、prefix LM | 消融中同等算力下 enc-dec 在理解+生成任务上综合最强；输入侧双向注意力对理解任务有利 | 规模拉到百亿以上、以开放式生成/对话为主业务时——decoder-only 训练更简单、KV cache 增量推理更高效，GPT-3→LLaMA 路线最终胜出 |
| 预训练目标 | Span corruption（盖片段、只生成片段） | 标准 LM、BERT 式 MLM、句子重排 deshuffling | target 序列短，同算力下见过更多数据；效果与 MLM 相当或更好 | 需要模型直接做开放式长文生成/零样本 prompting 时——span corruption 模型不会"接着写"，必须再做 LM adaptation（后来 FLAN-T5、UL2 都补了这一课） |
| 预训练数据 | C4：Common Crawl 严格过滤（去重、去坏词、去代码页、留完整句） | 未过滤 Common Crawl 全量、纯 Wikipedia/书籍 | 消融显示脏数据显著拖累下游任务；领域内数据有帮助但量太小 | 数据总量成为瓶颈时（Chinchilla 时代"token 不够用"）——过滤太狠丢多样性，重复 epoch 训练反而不如留下部分低质数据；以及一切非英文场景 |
| 任务接口 | 文本前缀（"summarize: "），输出也是文本 | 任务专属分类头 + 各自损失函数 | 一套权重、一个损失服务所有任务，加新任务零架构改动 | 需要输出概率校准（风控打分）、严格结构化输出（JSON schema）时——文本生成可能产出不合法标签，分类头的 logits 更可控 |
| 迁移方式 | 下游任务全参数微调 | adapter 层、逐层解冻 | 消融中全参微调效果最稳 | 模型大到微调一次成本过高、要同时服务几十个任务时——LoRA/PEFT（2021 后）和 ICL（GPT-3）都是对这条的否定 |

## 成本与量级 💰
- **训练成本**：T5-11B 预训练 1T token，用 TPU v3 pod（1024 核）级别算力；社区估算单次训练超过百万美元量级。更贵的是论文的 50+ 组消融——这是"Google 才做得起的公共品"。
- **推理成本 vs 基线**：11B vs 220M（Base）≈ 50× 参数量，当年几乎无法生产部署；但 enc-dec 的一个优势是输入只编码一次，长输入短输出任务（摘要/分类）的单位成本低于同参数 decoder-only。
- **我的产品要用**：不要用原始 T5，用 Flan-T5-Base/Large（250M/780M）——单张消费级 GPU 可跑，边缘端多任务分类/抽取场景至今仍是性价比之选。

## 证据审计 🔬
- **实验设计公平吗**：整体是领域少见的高规范消融，但架构对比的参数/算力对齐口径有猫腻——enc-dec "P 参数、M FLOPs" 与 decoder-only "P 参数、2M FLOPs"（或 2P 参数）的换算方式，天然让 enc-dec 显得高效；且所有消融在 Base 规模（约 34B token 预算）上做，结论直接外推到 11B 乃至百亿以上并无证据。
- **最强证据**：SuperGLUE 88.9（人类基准 89.8），当时首次逼近人类；成立条件是 11B 参数 + 下游全参微调 + 多任务预训练混合，不是零样本能力。
- **最可疑的数字**："encoder-decoder 优于 decoder-only" 的消融结论，因为它在小规模、带下游微调的设定下得出——GPT-3（2020.5）和之后整个开源生态证明在大规模 + ICL 设定下 decoder-only 才是赢家，这个结论的适用域比论文暗示的窄得多。
- **如果我是审稿人，会要求补充**：架构对比在 3B+ 规模复测；span corruption 模型的零样本生成能力评测（这是它最大的暗坑）；C4 过滤各步骤的单独消融。
- **最小复现实验**：代理指标——用 HuggingFace 的 t5-small（60M）和 gpt2（124M）在同一个情感分类任务上分别以 text-to-text 和续写方式做零样本/少量微调对比；Colab 免费额度即可，预算 $0，半天。

## 可复用点（PM 决策）
- **何时采用**：多任务 NLP 中台（分类+抽取+摘要共用一个模型）、边缘端小模型、需要"加任务不改架构"的敏捷迭代——text-to-text 接口设计至今是最佳实践。
- **何时规避**：开放式长对话/创作为主的产品别选 T5 系（span corruption 底子不擅长自由生成）；需要严格结构化输出时给文本接口加约束解码或改用分类头。
- **供应商拷问清单**：
  1. "你们的模型是 encoder-decoder 还是 decoder-only？如果是前者，开放式生成质量怎么保证？做过 LM adaptation 吗？"
  2. "你们的预训练数据过滤流程和 C4 比强在哪？去重是精确去重还是模糊去重？"
  3. "你们声称的多任务能力，是每个任务一个微调权重，还是真正一套权重全任务共享？"

## 动手练习 💻（约 30 分钟）
练习目标：用 numpy 亲手构造三种架构（encoder-decoder / prefix LM / 纯因果 LM）的注意力可见性掩码，直观看懂"同一个翻译任务，三种架构的信息流有什么不同"——这正是 T5 消融的核心对象。

```python
# 练习：对比 encoder-decoder vs decoder-only 对同一任务的注意力可见性
# 只需要 numpy：pip install numpy
import numpy as np

# ---------- 1. 构造一个翻译任务的 token 序列 ----------
# 输入部分（源句）4 个词，输出部分（译文）3 个词
src = ["translate:", "That", "is", "good"]   # 任务前缀 + 英文原句
tgt = ["Das", "ist", "gut"]                  # 德文译文（模型要生成的部分）
tokens = src + tgt                           # 拼成一条完整序列，共 7 个位置
n_src, n = len(src), len(tokens)             # n_src=4 是输入长度，n=7 是总长度

# ---------- 2. 三种架构的注意力掩码 ----------
# 掩码是 n×n 矩阵：mask[i][j]=1 表示"位置 i 可以看到位置 j"

# (a) 纯因果 LM（GPT 式 decoder-only）：每个位置只能看自己和左边
causal = np.tril(np.ones((n, n), dtype=int))         # 下三角矩阵，np.tril 保留对角线及以下

# (b) Prefix LM：输入部分内部互相全可见（双向），输出部分仍是因果
prefix = np.tril(np.ones((n, n), dtype=int))          # 先从因果掩码出发
prefix[:n_src, :n_src] = 1                            # 把左上角"输入×输入"块全部置 1（双向可见）

# (c) Encoder-Decoder：拆成两个模块
enc = np.ones((n_src, n_src), dtype=int)              # 编码器：输入内部完全双向可见
dec_self = np.tril(np.ones((len(tgt), len(tgt)), dtype=int))  # 解码器自注意力：输出内部因果
dec_cross = np.ones((len(tgt), n_src), dtype=int)     # 交叉注意力：每个输出位置看全部输入

# ---------- 3. 打印对比 ----------
def show(name, mask, row_labels, col_labels):
    """把掩码矩阵打印成可读的表：■=可见, ·=不可见"""
    print(f"\n=== {name} ===")
    print(" " * 12 + " ".join(f"{c[:4]:>4}" for c in col_labels))   # 列标题（截断到4字符）
    for i, row in enumerate(mask):                                   # 逐行打印
        cells = " ".join("   ■" if v else "   ·" for v in row)       # 1 画实心块，0 画点
        print(f"{row_labels[i][:10]:>10} |{cells}")

show("纯因果 LM（GPT/decoder-only）", causal, tokens, tokens)
show("Prefix LM（输入双向+输出因果）", prefix, tokens, tokens)
show("Encoder（T5 输入侧：完全双向）", enc, src, src)
show("Decoder 交叉注意力（每个输出看全部输入）", dec_cross, tgt, src)
show("Decoder 自注意力（输出内部因果）", dec_self, tgt, tgt)

# ---------- 4. 数一数信息流差异 ----------
print("\n输入部分 token 平均能看到的位置数：")
print(f"  纯因果 LM : {causal[:n_src].sum() / n_src:.1f} 个")   # 只能看左边，平均 (1+2+3+4)/4
print(f"  Prefix LM : {prefix[:n_src].sum() / n_src:.1f} 个")   # 输入内全可见
print(f"  Encoder   : {enc.sum() / n_src:.1f} 个")              # 同样全可见
print("→ T5 消融的发现：输入侧双向可见（后两者）对理解类任务更有利；")
print("  纯因果 LM 处理输入时'看不到右边'，前缀里的关键信息利用不充分。")
```

跑完后思考：为什么 GPT-3 明知输入侧单向"吃亏"，还坚持纯因果 LM？（提示：训练时每个位置都产生损失信号、推理时 KV cache 可增量复用——工程效率换架构劣势，规模补回能力。）
