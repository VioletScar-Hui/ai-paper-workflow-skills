## 核心机制

```
问题：通用 LLM 能理解数学，但无法一次性写出正确 Lean 证明
      → 专用证明模型在 Lean 上更好，但缺乏通用推理能力

LEAP 的解法：分解 × 迭代 × 验证

1. AND-OR DAG 层级分解：
   - 根目标：待证定理
   - 遇到无法直接证明的目标 → 拆分为子引理（AND 节点）
   - 每个子引理各自成为新的 OR 目标
   - 编译器验证：sketch 通过 + 所有子目标被证 → 主定理成立

2. 非正式-正式交错规划：
   - 先生成中文/英文的非正式证明蓝图（利用 LLM 的推理强项）
   - 再将蓝图翻译为 Lean 代码（利用 Lean 的机械验证强项）
   - 编译器反馈 → 修改 → 迭代
   → 每步都可追溯：知道为什么这样分解

3. 验证引导搜索：
   - Lean 编译器：语法/类型检查（硬验证）
   - LLM 评审：策略评估（软验证）
   - 两层验证 → 高质量 + 高效

瓶颈分析（重要）：
  通用 LLM 的问题不是"不理解 Lean"
  而是"无法在一次尝试中生成足够长和正确的证明"
  → 迭代 + 分解 是解法，不是专用训练
```

## 论文精读卡片

**一句话**：LEAP 通过 AND-OR DAG 层级分解 + 非正式蓝图规划 + Lean 编译器验证反馈，使通用 LLM 在 Lean-IMO-Bench 上达到 70% 成功率（超越专用金牌级证明模型的 48%），并解决 Putnam 2025 全部 12 题。

**问题**：通用 LLM 拥有强大数学推理能力，但无法在单次尝试中生成足够长且正确的 Lean 形式化证明。而专用证明模型（在 Lean 数据上微调）虽然语法熟练，却缺乏通用推理深度——两者形成能力剪刀差。如何把通用 LLM 的推理能力与形式化验证的机械可靠性结合？

**核心方法**：
- AND-OR DAG 层级分解：将根目标定理递归拆分为子引理（AND 节点），每个子引理独立证明；编译器验证 sketch 通过且所有子目标被证则主定理成立
- 非正式-正式交错规划：先生成自然语言非正式证明蓝图（利用 LLM 推理强项），再翻译为 Lean 代码（利用编译器机械验证），蓝图提供可追溯的分解依据
- 双层验证引导搜索：Lean 编译器做硬验证（语法/类型），LLM 评审做软验证（策略评估），两层反馈驱动迭代修改

**关键图/公式**：AND-OR DAG 结构——根节点=目标定理，AND 节点=必须全部完成的子引理集，OR 节点=可以任选一个证明路径；关键洞察：只要每个叶节点子引理足够短，LLM 就能一次性正确生成，将"一次生成长证明"转化为"多次生成短证明"。

**实验设置**：
- 规模/数据：Lean-IMO-Bench（IMO 风格形式化定理，本文新发布）、Putnam 2025 竞赛（12 题）
- 对比：无 Agent 框架的直接 LLM 生成（<10%）vs 专用 Lean 证明模型（48%，金牌级）vs LEAP（70%）

**最强证据**：LEAP 70% vs 专用模型 48%（Lean-IMO-Bench），且用的是通用 LLM 而非特定 Lean 训练模型；Putnam 2025 全题（12/12）完美解决，建立了竞赛数学形式化能力的新标杆。

**最弱证据**：Lean-IMO-Bench 由本文团队新发布，基准独立性存在疑问；专用证明模型（"48% 金牌级"）的具体来源和版本未完整披露；框架的总 token 消耗和运行时间未与基线对比，实际部署成本不清楚。

**可复用点**："分解为可单次生成的子问题"的思路可迁移到任何需要长且正确输出的场景（合同生成、代码生成、多步推理）；非正式蓝图→正式代码→验证反馈的流程是通用的"可验证输出生成"范式；AND-OR DAG 分解可作为 Agent 任务规划的模板。

- 将"非正式规划→正式代码→验证器反馈→迭代"的流程应用于需要确定性验证的软件产品（如合规代码生成、API 规范验证）
