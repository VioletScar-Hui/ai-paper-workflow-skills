# RAG：知识密集型 NLP 任务的检索增强生成

📄 **原文 PDF**：[[RAW/59 - Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks.pdf]]

## PM 速判（30秒）
> 一句话：2020 年 FAIR 提出"密集检索器 + seq2seq 生成器联合训练"，用 400M 生成器 + 维基百科索引在开放域 QA 上打败 11B 纯参数模型（NQ 44.5% EM），奠定了今天所有"向量库 + LLM"产品的架构原型。PM 必须知道它，因为你产品里 RAG 的每一个核心卖点（知识可更新、可溯源、抗幻觉）和每一个核心瓶颈（检索 recall 决定上限）都写在这篇论文里。

## 双层费曼 🗣️
> **给 CEO 的一句话**：与其把全部知识"背"进模型（改一条知识就要重新训练、还说不清出处），不如让模型带一个可随时换页的"外挂资料库"，回答前先查资料再作答——知识更新成本从"重训模型"降到"换个索引文件"。
>
> **给工程师的一段话**：RAG 把生成概率写成对检索文档的边缘化：p(y|x) = Σ_z p_η(z|x)·p_θ(y|x,z)。检索端是 DPR 双塔 BERT（问题编码器 + 段落编码器），用 FAISS 做 MIPS 取 top-k（k=5/10）；生成端是 BART-large，把问题和每篇检索段落拼接后生成。训练时只微调问题编码器和 BART，**文档编码器和索引全程冻结**（区别于 REALM 的周期性重建索引）。两种边缘化变体：RAG-Sequence 对整个输出序列共用一份文档后验，RAG-Token 允许每个 token 依赖不同文档。检索概率可微，所以监督信号能穿透生成器反向传播到问题编码器——不需要"哪篇文档是对的"的标注。

## 问题域定位 🎯
- **根本约束**：参数化模型把世界知识压进权重——知识固化在训练截止日、无法给出处、幻觉无法审计；而知识密集型任务（开放域 QA、事实核查）恰恰要求知识新鲜、可溯源。
- **之前的方案卡在哪里**：① 纯参数路线（T5/GPT）靠堆参数背知识，NQ 上 T5-11B 闭卷只有 ~34.5%，且更新知识 = 重训。② 抽取式流水线（DPR + reader）只能从原文里"抠"答案片段，无法综合多篇文档、无法做生成任务。③ REALM 端到端训练检索但要周期性重建整个索引，工程代价大且只做了抽取式任务。
- **开启/关闭的路线**：开启了"检索器与生成器解耦、知识外置于非参数记忆"的路线——LlamaIndex/LangChain/所有企业知识库产品都是它的工程化后代。同时它也埋下了被后人挑战的假设：「检索 = 一次性向量相似度查询」，这个假设后来被 Agent 式多轮检索（见 [[Wiki/论文笔记/10_RAG检索/133_Grep-vs-向量检索Agent搜索对比]]）打破。

## 核心机制

```
                     离线（一次性）
  维基百科 2100 万个 100 词段落
        │  BERT 文档编码器（训练中冻结）
        ▼
  FAISS 向量索引 z₁...z_N
                     在线（每次查询）
  问题 x ──BERT问题编码器──▶ 查询向量 q(x)
                              │ MIPS 最大内积检索
                              ▼
                     top-k 段落 {z₁..z_k}（k=5/10）
                              │ 每篇段落分别与 x 拼接
                              ▼
                  BART-large 生成器（400M）
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
  RAG-Sequence：整句答案                    RAG-Token：每个 token
  对 k 篇文档做边缘化                        可"混合"不同文档的证据
        └────────────── p(y|x) = Σ_z p(z|x)·p(y|x,z) ──────────┘
  训练：QA 对 (x,y) 直接端到端反传 → 同时更新问题编码器 + BART
```

## 设计决策解剖 ⚖️
| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| 文档索引是否随训练更新 | 冻结文档编码器，索引只建一次 | REALM 式周期性重编码全库 | 重建 2100 万段落索引极贵；实验表明只调问题编码器已够好 | 语料领域与 DPR 预训练分布差距大时（如法律/医疗内部文档），冻结的文档表示质量不够，必须重训编码器或换嵌入模型 |
| 检索方式 | DPR 密集向量检索 | BM25 词法检索 | 语义匹配能召回改写/同义表达，FEVER 之外的任务上密集检索显著更好 | 查询依赖精确字面量（版本号、人名、日期、代码符号）时，密集检索会漏掉稀有 token——这正是 2026 年 [[Wiki/论文笔记/10_RAG检索/133_Grep-vs-向量检索Agent搜索对比]] 证明 grep 反超的场景 |
| 生成方式 | BART 自由生成（抽象式） | DPR + 抽取式 reader | 能综合多篇文档、能回答原文中没有逐字出现的答案、能做生成任务（MS-MARCO/Jeopardy） | 高合规场景（医疗/法务）要求答案逐字可溯源时，自由生成的幻觉风险不可接受，抽取式反而更安全 |
| 如何利用 k 篇文档 | 对 top-k 做概率边缘化（软融合） | 只取 top-1 硬选择；或把 k 篇全部塞进一个超长输入 | 边缘化可微、能端到端训练检索器；top-1 太脆，全拼接超出 BART 1024 token 上限 | 长文档/长答案场景下逐 token 边缘化解码成本高；现代长上下文 LLM 直接把 k 篇全拼进 prompt 更简单——今天的生产 RAG 实际上放弃了边缘化，只保留了"检索+拼接" |
| 端到端训练检索器 | QA 信号反传微调问题编码器 | 用现成检索器零训练拼接 | 让检索器学会"为生成器服务"，NQ 提升数个点 | 今天用冻结的商用嵌入 API + 强 LLM 时，端到端训练的收益被 LLM 的容错能力掩盖，多数产品直接跳过这步 |

## 成本与量级 💰
- **训练成本**：2020 年量级——BART-large 400M + DPR 问题编码器，在单个 8 卡节点上微调数天即可（远小于预训练 T5-11B 的成本）；这正是卖点：1/15 的参数打败 11B。
- **推理成本 vs 基线**：比闭卷模型多一次 ANN 检索（毫秒级）+ 输入变长约 k 倍（k=5 篇 ×100 词）；RAG-Sequence 解码需对 k 篇分别打分，推理成本约为闭卷的 5-10 倍，但远低于跑一个 11B 模型。
- **我的产品要用（2026 视角）**：最小可行配置 = 任意 Chat API + 嵌入 API + numpy 余弦相似度。文档量 <10 万 chunk 根本不需要向量数据库，一个 npy 矩阵足够；先跑通再谈基础设施。

## 证据审计 🔬
- **实验设计公平吗**：和 T5-11B"闭卷"比是不对等比较——RAG 带着整个维基百科开卷考试，赢 11B 并不神奇。更公平的对手是同样开卷的 DPR 抽取式系统（NQ 41.5%），对它的领先只有约 3 个点，优势真实但没有标题党那么大。
- **最强证据**：NQ 44.5% EM（当时 SOTA），且成立条件清晰：答案在维基百科中可检索、单跳问题。索引热插拔实验（换 2016/2018 版维基百科，答案随之改变）直接证明了"知识外置可更新"这一核心主张。
- **最可疑的数字**：MS-MARCO 上 Bleu-1"超过人类 3.3%"——因为 Bleu 奖励与参考答案的 n-gram 重合，人类答案表达多样反而吃亏，且 RAG 没用 MS-MARCO 的黄金段落，该数字更像指标伪影而非"超人类"。
- **如果我是审稿人，会要求补充**：① 检索 recall@k 与最终 EM 的关系曲线（检索失败时生成器表现如何）；② 多跳问题的失败分析；③ 索引过时（stale index）对准确率的量化影响。
- **最小复现实验**：不必复现训练——用"冻结嵌入 + 拼接 prompt"复现范式即可（见下方练习）。代理指标：同一组问题，闭卷 vs 开卷（带检索）的准确率差。预算：几十次 API 调用，<1 美元。

## 可复用点（PM 决策）
- **何时采用**：知识频繁更新、需要给出处、语料远大于上下文窗口、幻觉代价高的问答/客服/企业知识库场景。
- **何时规避**：知识量小到能塞进 system prompt（直接塞更便宜）；需要跨全库全局归纳（用 [[Wiki/论文笔记/10_RAG检索/81_GraphRAG图结构增强的查询聚焦摘要]]）；查询以精确字面量为主的 Agent 场景（先试 grep，见 Paper 133）。
- **供应商拷问清单**：
  1. "你们的检索 recall@k 是多少？在**我们的**语料上测过吗？"——RAG 的上限由 recall 决定，答不出这个数的供应商没做过评估。
  2. "知识更新后多久生效？增量索引还是全量重建？"——原始 RAG 索引不支持增量，很多产品继承了这个坑。
  3. "答案能否逐字定位到源文档段落？错误答案的归因流程是什么？"

## 动手练习 💻（30分钟）
练习目标：用约 50 行代码实现最小 RAG——文本分块 → 嵌入 → 余弦检索 → 拼接 prompt → 生成，亲手触摸"检索 recall 决定答案质量"这条铁律。

```python
# 最小 RAG：分块 -> 嵌入 -> 余弦检索 -> 拼 prompt -> 生成
# 依赖：pip install openai numpy    需设置环境变量 OPENAI_API_KEY
import numpy as np              # numpy：做向量数学运算（余弦相似度）
from openai import OpenAI       # OpenAI 官方客户端，用来调嵌入和对话接口

client = OpenAI()               # 创建客户端，自动读取环境变量里的 API Key

# ---------- 第 1 步：准备知识库（实际项目中这里是你的文档） ----------
docs = """RAG 论文由 Patrick Lewis 等人于 2020 年在 Facebook AI Research 发表。
RAG 使用 DPR 双塔编码器做密集检索，用 FAISS 索引 2100 万个维基百科段落。
生成器是 BART-large，参数量约 4 亿，通过边缘化 top-k 文档来生成答案。
RAG 在 NaturalQuestions 上取得 44.5% 的 exact match，超过 T5-11B 闭卷模型。
RAG 的知识可以通过替换索引来更新，不需要重新训练模型。
GraphRAG 是微软 2024 年提出的扩展，用知识图谱和社区摘要解决全局问题。"""

def chunk(text, size=2):        # 分块函数：把长文本切成小段
    lines = text.split("\n")    # 按行切开（真实项目常按 token 数或段落切）
    # 每 size 行合并成一个 chunk，range 的第三个参数是步长
    return ["\n".join(lines[i:i+size]) for i in range(0, len(lines), size)]

chunks = chunk(docs)            # 得到 chunk 列表，这就是"知识库的最小单元"

# ---------- 第 2 步：嵌入（把文字变成向量，语义相近 -> 向量相近） ----------
def embed(texts):               # 一次性把一批文本转成向量矩阵
    resp = client.embeddings.create(model="text-embedding-3-small", input=texts)
    return np.array([d.embedding for d in resp.data])  # 形状: (文本数, 1536)

doc_vecs = embed(chunks)        # 离线步骤：整个知识库只需嵌入一次并缓存

# ---------- 第 3 步：余弦检索（RAG 论文里 FAISS 干的事，我们用 numpy 手写） ----------
def retrieve(query, k=2):       # 输入问题，返回最相关的 k 个 chunk
    q = embed([query])[0]                       # 问题也嵌入成向量
    # 余弦相似度 = 点积 / (模长乘积)；一行算出问题和所有 chunk 的相似度
    sims = doc_vecs @ q / (np.linalg.norm(doc_vecs, axis=1) * np.linalg.norm(q))
    top = np.argsort(sims)[::-1][:k]            # 从大到小排序，取前 k 个下标
    print(f"[检索] 相似度: {[round(sims[i],3) for i in top]}")  # 打印出来观察
    return [chunks[i] for i in top]             # 返回命中的文本块

# ---------- 第 4 步：拼 prompt + 生成（"开卷考试"） ----------
def rag_answer(query):
    context = "\n---\n".join(retrieve(query))   # 把检索结果拼成上下文
    prompt = f"仅根据以下资料回答，资料中没有就说不知道。\n资料:\n{context}\n\n问题: {query}"
    resp = client.chat.completions.create(      # 调对话模型生成答案
        model="gpt-4o-mini", messages=[{"role": "user", "content": prompt}])
    return resp.choices[0].message.content

# ---------- 第 5 步：对比实验——这就是论文的核心结论 ----------
q = "RAG 的生成器是什么模型？在 NQ 上得分多少？"
print("【开卷/RAG】", rag_answer(q))            # 有检索：答案有据可查
resp = client.chat.completions.create(model="gpt-4o-mini",
    messages=[{"role": "user", "content": q}])  # 闭卷：纯靠参数记忆
print("【闭卷】", resp.choices[0].message.content)
# 进阶实验：把问题换成知识库里没有的内容，观察 RAG 是否老实说"不知道"，
# 再把 retrieve 的 k 改成 1，观察检索漏掉关键 chunk 时答案如何劣化——
# 这就是"recall 决定 RAG 上限"的手感。
```
