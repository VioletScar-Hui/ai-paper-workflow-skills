# 将 Agent 工作流编译进 LLM 权重：近前沿质量，低 100× 成本

📄 **原文 PDF**：[[RAW/42 - Compiling Agentic Workflows into LLM Weights.pdf]]

## PM 速判（3 分钟）

> **这篇论文给 PM 的一句话**：把程序化工作流（流程图）通过微调"编译"进小 LLM 权重（而不是用 LangGraph/CrewAI 每次注入），创造"地下 Agent"（subterranean agent）—— **3B 编译模型失败率比 LangGraph 低 4.4×（5.5% vs 24%）**，8B 模型质量达前沿模型的 87-98%，成本约为前沿 Orchestrator 的 **1/100**。

| 项目 | 评估 |

## 架构对比

| | 表面 Orchestrator（现有主流）| 地下 Agent（本文）|
|--|---------------------------|-----------------|
| **运行时** | User + Orchestrator + LLM | User + LLM（Orchestrator 只在训练时用）|
| **程序如何运行** | Orchestrator 每轮注入指令 | 程序已编译进权重 |
| **成本** | 前沿模型 API × 每轮调用 | 小模型，零 Orchestrator 开销 |
| **程序保护** | 程序暴露给第三方 API | 程序封装在权重内 |
| **灵活性** | 高（程序可随时改）| 低（需重新微调）|
| **失败率** | 高（24% / 17%）| 低（5.5% / 9%）|

```
典型场景：
  - 流程固定的企业工作流（保险理赔、客服支持、预订流程）→ 编译模型
  - 程序需要频繁改动的探索场景 → 继续用 Orchestrator
```

## 三个常见障碍的实证回答（带时间锚）📅 2026

1. **质量障碍**：3B 编译模型在 4/5 质量指标上超越同款 3B Orchestrator；8B 模型达前沿 87-98%
2. **失败率障碍**：编译模型失败率低于 Orchestrator（旅行 5.5% vs 24%，保险 9% vs 17%）
3. **成本障碍**：~1/100 前沿模型 Orchestrator 的推理成本

## 对 AI PM 的启示

| 场景 | 洞察 |
|------|------|
| **程序化 Agent 产品决策** | 如果工作流相对固定（流程图节点 ≤55），优先考虑编译模型而非 Orchestrator |
| **保护专有流程** | 编译到权重中比通过 Prompt 注入更安全（不会被 API 提供方看到）|
| **客服/审批类产品** | 这类产品工作流稳定 + 高并发 → 编译模型的 ROI 极高 |
| **微调技术选择** | LoRA 对程序内化不够；需要全参数微调（全参微调是必要成本）|
| **何时不用编译** | 工作流频繁变化、或有大量分支变体（不值得反复微调）|

## 论文精读卡片

**一句话**：将程序化工作流通过全参数微调"编译"进小 LLM 权重（地下 Agent），3B 编译模型失败率比 LangGraph 低 4.4×（5.5% vs 24%），成本约为前沿 Orchestrator 的 1/100。

**问题**：现有 Agent 系统（LangGraph/CrewAI）需要每次在 Orchestrator 中注入完整工作流，导致高延迟、高成本、程序暴露给第三方 API——能否把工作流一次性"编译"进模型权重，让模型在推理时无需 Orchestrator？

**核心方法**：
- 将工作流流程图转化为合成训练轨迹（包含每个节点的决策和工具调用）
- 对目标模型进行全参数微调（非 LoRA），将程序逻辑内化到权重
- 运行时只保留 User + LLM，Orchestrator 只在训练阶段使用

**关键图/公式**：地下 Agent vs 表面 Orchestrator 对比：运行时从"User + Orchestrator + LLM"变为"User + LLM"；程序从每轮注入变为权重内置；LoRA 不够用，全参数微调是必要条件。

**实验设置**：
- 规模/数据：旅行预订任务（3B 模型）、保险理赔流程（55 节点/6 决策枢纽，8B 模型）
- 对比：LangGraph Surface Orchestrator、同规模 Surface Orchestrator、前沿模型（GPT-4 级别）

**最强证据**：3B 编译模型旅行预订失败率 5.5% vs LangGraph 24%（低 4.4×）；8B 模型保险理赔达前沿模型 87-98% 质量；成本约为前沿 Orchestrator 的 1/100。

**最弱证据**：仅在 2 个任务域测试（旅行/保险），泛化性待验证；全参数微调成本高，工作流变更需重新微调；55 节点是否是上限未说明；未测试对抗性输入或边缘案例的鲁棒性。

**可复用点**：对流程固定的企业工作流（客服/审批/预订）使用编译模型替代 Orchestrator 的架构决策树：流程节点数 ≤55 且变更频率低 → 编译模型；反之 → 保留 Orchestrator。程序保护（不暴露给第三方 API）是额外好处。
