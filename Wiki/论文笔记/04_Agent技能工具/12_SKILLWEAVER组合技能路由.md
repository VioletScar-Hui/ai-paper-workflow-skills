# SKILLWEAVER：LLM Agent 的组合技能路由

📄 **原文 PDF**：[[RAW/12 - Compositional Skill Routing for LLM Agents - Decompose, Retrieve, and Compose.pdf]]

## PM 速判（3 分钟）

> **这篇论文给 PM 的一句话**：真实用户查询往往需要组合多个工具（API/技能），但 LLM Agent 的工具路由目前只能处理单工具选择；SKILLWEAVER 提出"分解→检索→组合"三阶段框架，最关键发现：**任务分解质量是瓶颈**（不是工具检索），当分解正确时，端到端链路完成率达 76.7%。

| 项目 | 评估 |
|------|------|
| **评测基准** | COMPSKILLBENCH：300个组合查询，2,209个真实 MCP 技能，24类 |
| **核心发现** | 分解质量是瓶颈（DA 51.0%→67.7% 是关键改进） |
| **链路完成率** | 76.7%（30个查询，平均2.8步） |
| **成熟度** | 🧪 学术研究，提供了 MCP 生态的实测数据 |

## 核心问题：组合技能路由

```
传统工具路由：
  用户："查天气"  →  [选择1个工具：weather-api]  ✓ 好解决

组合技能路由（本文）：
  用户："下载数据集、处理它、生成可视化报告"
        ↓
  需要：api-client（下载）+ csv-parser（处理）+ chart-gen（可视化）
        ↓ 按顺序执行
  
  从2,209个 MCP 技能中选出正确的3个，并确定执行顺序
  → 这是一个组合优化问题，当前 LLM 只能做到 34.2% 正确率
```

---

## SKILLWEAVER 三阶段架构

```
Stage 1: Decompose（任务分解）
  LLM（Qwen2.5-7B）把复杂查询分解为原子子任务
  → 问题：LLM 可能分解成错误的步骤数量
  → 解法：SAD（技能感知分解，见下）

Stage 2: Retrieve（技能检索）
  双编码器（all-MiniLM-L6-v2）+ FAISS 精确内积搜索
  每个子任务 → Top-k 候选技能（k=10）
  → 检索延迟 < 15ms（2,209个技能的索引）

Stage 3: Compose（构建计划）
  目标：最大化 ∑[相关性 + 跨步兼容性]
  输出：DAG（有向无环图）—— 允许可并行执行的步骤同时运行
  兼容性判断：输入/输出类型匹配、类别 Jaccard、关键词共现
```

---

## 关键创新：SAD（技能感知分解）

```
问题：LLM 不知道技能库里"有什么"，分解时可能生成库里不存在的子任务

SAD 解法：检索信号反馈到分解阶段

迭代过程：
  第0轮: LLM 生成初始分解 D₀
  第i轮: 
    1. 用 D(i) 中的每个子任务去检索 H=15 个候选技能
    2. 把候选技能 hints 喂给 LLM
    3. LLM 根据"真实存在的技能"重新分解 → D(i+1)
    4. 若 Jaccard(H(i), H(i-1)) > 0.6 则收敛

效果：
  分解正确率 DA: 51.0% → 67.7%（+32.7%，p < 10⁻⁶）
```

---

## 关键发现：分解是瓶颈

```
实验分析：
  所有查询的 CatR@1 = 34.2%
  
  当分解步骤数完全正确（DA=1）时：
  CatR@1 = 41.2%（提升 7pp）
  
  → 说明：解决分解问题，检索质量会自然提升
  → 检索本身不是核心瓶颈，分解才是

进一步验证：
  Cross-encoder 重排（在检索后加精排）: CatR@1 +10.3%
  换更强的双编码器（BGE-base）: CatR@1 +14.5%
  → 两者提升有限，根本还是分解
```

## 端到端执行结果

```
30个查询，平均2.8步链路（模拟执行器，80-95%单步成功率）：

DA（步骤数正确率）: 86.7%
SES（步骤执行成功率）: 86.9%（73/84 步成功）
CCR（链路完成率）: 76.7%（23/30 全链成功）

SES 86.9% vs. CCR 76.7% 的差距 = 复合失败效应
（即使每步 87% 成功，三步链路只有 87%³ ≈ 66% 全成功）
→ 错误恢复和重试机制是 Agent 可靠性的关键工程需求
```

## 核心结论（带时间锚）

1. **Agent 工具路由的真正难点是"如何分解任务"而非"如何检索工具"** 📅 2025
   DA 51%→67.7% 是关键改进，但即便检索近乎完美，分解错误也会导致失败——这对 Agent 产品架构有直接指导：**先投资任务分解模块的质量**，再优化工具检索。

2. **MCP 技能生态已是 Agent 工具标准的事实基础** 📅 2025
   2,200+ 注册 MCP 服务器涵盖24类——从金融到开发者工具到知识管理——说明 Anthropic 定义的 MCP 规范已成为 Agent 工具接口的工业标准。

3. **76.7% 链路完成率是真实 Agent 能力的估算下限** 📅 2025
   模拟执行器显示，即使在 80-95% 单步成功率下，多步链路的全程完成率约 77%——产品 SLA 设计时需要把"复合失败"纳入考量。

## 对 Agent 产品 PM 的启示

| 产品决策 | 洞察 |
|---------|------|
| **工具库设计** | 工具描述的质量（名称+文档）直接影响路由准确率，不是"有工具就行" |
| **错误处理** | 多步 Agent 任务的错误应是"可重试"而非"全部重来"——需要 checkpoint 机制 |
| **用户期望管理** | 即使最好的路由，3步任务的全链完成率约 76%，不能承诺"100%自动化" |
| **MCP 标准化** | 优先支持 MCP 规范的工具，而非私有格式——利用生态积累效应 |

## 论文精读卡片

**一句话**：阿里云 SKILLWEAVER 证明多工具组合路由中任务分解是真正瓶颈——SAD（技能感知分解）将分解正确率从 51.0% 提升至 67.7%（+32.7%），使端到端链路完成率达 76.7%，且基于 2,209 个真实 MCP 技能的评测证明 MCP 生态是 Agent 工具的工业标准。

**问题**：真实用户查询往往需要组合 3-5 个工具按顺序执行，但当前 LLM Agent 工具路由只处理单工具选择——从 2,200+ MCP 技能中找出正确的 3-5 个并排好顺序，基础 LLM 只有 34.2% 成功率。且分析显示瓶颈不在工具检索，而在任务分解。

**核心方法**：
- 三阶段框架：Decompose（任务分解，Qwen2.5-7B）→ Retrieve（双编码器 + FAISS，<15ms）→ Compose（DAG 最大化相关性+跨步兼容性）
- SAD（技能感知分解）：迭代循环让检索候选反馈到分解步骤——LLM 根据"真实存在的技能"重新分解，直到候选集稳定（Jaccard>0.6）
- 兼容性评分：输入/输出类型匹配 + 类别 Jaccard + 关键词共现，构建 DAG 允许可并行步骤同时运行

**关键图/公式**：复合失败效应：单步成功率 86.9% × 三步链路 ≈ 87%³ ≈ 66%，但实测 CCR 是 76.7%（高于纯概率乘积），说明步骤间有正向相关性（分解正确后后续步骤容易成功）。这个数字是多步 Agent 系统 SLA 设计的重要基准。

**实验设置**：
- 规模/数据：COMPSKILLBENCH，300 个组合查询（Easy 150/Medium 100/Hard 50），2,209 个真实 MCP 技能，24 类
- 对比：Cross-encoder 重排（+10.3%）、更强双编码器 BGE-base（+14.5%）均弱于 SAD（+32.7%），证明分解是瓶颈

**最强证据**：消融实验直接证明分解是瓶颈：当分解步骤数完全正确（DA=1）时 CatR@1 从 34.2% 提升至 41.2%（+7pp），而换更强的检索器只提升 14.5%——这个对比使"分解优先"的结论有明确的数字支撑，而非假设。

**最弱证据**：COMPSKILLBENCH 是自建数据集，外部可重复性未经独立验证；30 个查询的端到端执行实验样本量偏小；模拟执行器（80-95% 单步成功率）的设置是否代表真实 MCP 调用环境存疑；分解模型（7B）的选择对更大/更小模型的效果未讨论。

**可复用点**：多步 Agent 产品的设计原则：先投资任务分解模块的质量（而非工具检索精度），并加入 checkpoint + 重试机制（因为 76.7% 链路完成率意味着 23% 的任务需要人工介入或重试）。向用户设定期望：3 步自动化任务的成功率约 75-80%，不是 100%。
