# SpatialClaw: 重新思考 Agentic 空间推理的动作接口

📄 **原文 PDF**：[[RAW/11 - SpatialClaw - Rethinking Action Interface for Agentic Spatial Reasoning.pdf]]

## PM 速判（3 分钟）

> **这篇论文给 PM 的一句话**：NVIDIA 提出"代码作为动作接口"的 Agentic 空间推理框架——比"一次性代码执行"和"结构化工具调用"都更有效，关键在于持久化状态内核让 Agent 可以"看到中间结果再调整策略"，在 20 个空间推理基准上全面领先。

| 项目 | 评估 |

## 三种动作接口的对比

这是本文最核心的产品/工程洞察：

| 接口类型 | 机制 | 优点 | 缺点 |
|---------|------|------|------|
| **无工具（纯 VLM）** | 直接推理，无外部工具 | 简单 | 精度低，无数值计算 |
| **一次性代码执行** | 写完整程序，一次运行 | 可自定义计算 | 执行前看不到中间结果 |
| **结构化工具调用** | 预定义 API + JSON 参数 | 接口规范 | 难以动态组合工具 |
| **SpatialClaw（本文）** | **迭代代码 + 持久化内核** | **每步看到结果再调整** | 需要代码生成能力 |

## 核心机制：持久化 Python 内核

```
初始化：
  - 预加载：InputImages（帧序列）
  - 预加载：tools（SAM3, Reconstruct, Depth等感知工具）
  - 预加载：scipy, numpy 等科学计算库

循环（每一步）：
  Step 1: 规划者生成分析计划（不看图，只看文字问题）
  Step 2: Agent 生成下一个 Python Cell
  Step 3: 安全检查 → 执行
  Step 4: 反馈：
    ├─ stdout 输出
    ├─ 变量摘要（seg_mask: ndarray, shape=(1024,1024)...）
    └─ 可视化（show()注册的图像）
  Step 5: 基于反馈决定下一步
        ↓
  直到 ReturnAnswer() 或达到最大步数
```

**关键设计**：中间变量（分割掩码、深度图、点云）**跨步骤保留**——Agent 可以在步骤3中使用步骤1和步骤2创建的变量。

## 真实案例（距离测量）

问题："加热器和门之间的距离是多少（米）？"

```
一次性代码执行（失败）：
  1. 写完整程序 → 执行
  2. 结果：1.638m（错误，因为用了质心而非最近点）
  原因：没有机会查看分割效果就提交了距离计算

SpatialClaw（成功）：
  Step 1: 重建 3D 场景
  Step 2: 分割加热器 → show() 查看效果 → 确认分割正确
  Step 3: 分割门 → 确认
  Step 4: 发现"距离应该用最近点而非质心" → 用 KDTree
  结果：0.94m（正确，接近 Ground Truth 0.9m）
```

## 对 AI 产品的启示

### 动作接口设计原则

从 SpatialClaw 提炼的通用原则（不只适用于空间推理）：

```
✅ 好的动作接口：
  - 支持迭代：每步执行后观察结果，再决定下一步
  - 状态持久：中间结果可在后续步骤复用
  - 表达力强：不限于预定义 API，可自由组合

❌ 差的动作接口：
  - 一次性提交：必须在看到任何结果前规划完整策略
  - 工具固定：只能调用预设工具，无法自定义组合
```

## 核心结论（带时间锚）

1. **动作接口设计比工具能力更重要** 📅 2026.06
   相同的感知工具（SAM3、Reconstruct），在不同接口下性能差异巨大——接口设计是 Agentic 系统的核心架构决策。

2. **"看到中间结果再调整"是复杂推理的必要条件** 📅 2026.06
   空间推理（以及类似的复杂分析任务）无法提前规划完整策略，必须在执行中观察并调整——这对所有复杂 Agentic 任务都是通用洞察。

3. **持久化状态内核 = Jupyter Notebook 式的 Agentic 工作方式** 📅 2026.06
   这种设计本质上是把科学家用 Jupyter Notebook 做探索性分析的工作模式，赋予了 AI Agent。

## 论文精读卡片

**一句话**：NVIDIA 的 SpatialClaw 证明"持久化 Python 内核 + 迭代代码执行"作为动作接口，在 20 个空间推理基准上全面超越一次性代码执行和结构化工具调用，核心机制是让 Agent 在每步执行后看到中间结果再调整策略（而非提前规划完整程序）。

**问题**：空间推理（3D 测量、多视角理解、深度估计）任务无法提前规划完整策略，因为中间结果（分割质量、深度图精度）直接影响后续步骤选择；现有"一次性代码执行"接口迫使 Agent 在看到任何结果前就提交完整程序，导致系统性错误。

**核心方法**：
- 持久化 Python 内核：跨步骤保留中间变量（分割掩码、深度图、点云），后续步骤可直接引用前步创建的变量
- 规划者-执行者分离：规划者（Planning Agent）先分析任务不看图 → 执行者（Execution Agent）逐步生成 Python Cell → 安全检查后执行
- 反馈三通道：stdout 文本输出 + 变量摘要 + show() 注册的可视化图像，让 Agent 全面感知执行状态

**关键图/公式**：距离测量案例（加热器到门的距离）：一次性代码执行用质心计算得 1.638m（错误）；SpatialClaw 分步执行：Step 1 重建 3D → Step 2 分割加热器并查看效果确认 → Step 3 分割门确认 → Step 4 发现应用最近点（KDTree）而非质心 → 得 0.94m（接近 GT 0.9m）。这个案例说明"观察中间结果"是产生正确推理策略的必要条件。

**实验设置**：
- 规模/数据：20 个空间推理基准，涵盖多视角（ScanQA/EmbodiedScan）、视频、单图、通用推理；感知工具：SAM3（分割）、DepthAnything3（深度）、Reconstruct（3D 重建）
- 对比：无工具纯 VLM、一次性代码执行、结构化工具调用（JSON 参数预定义 API）

**最强证据**：20 个基准上全面领先，且与同一感知工具集（SAM3/DepthAnything3）在不同接口下对比——排除了工具能力的差异，直接证明接口设计本身带来性能提升。距离测量案例提供了定性机制解释。

**最弱证据**：只在空间推理任务上验证，对代码生成/文档分析等非空间任务的迁移性未测；持久化内核需要代码生成能力，对指令遵循弱的小模型效果未测；安全检查机制的具体实现未详细说明，可能有执行风险。

**可复用点**：迭代代码执行接口的设计原则可直接应用到任何复杂分析 Agent：在 Agent 工作流中加入"执行-观察-决策"循环，每步执行后将 stdout + 变量摘要 + 可视化反馈注入下一步 prompt，而非一次性生成完整脚本。
