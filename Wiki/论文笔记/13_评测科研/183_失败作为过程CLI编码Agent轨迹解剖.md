# 183 失败作为过程：CLI 编码 Agent 轨迹解剖

📄 **原文 PDF**：[[RAW/183 - Failure as a Process - An Anatomy of CLI Coding Agent Trajectories.pdf]]

> arXiv:2607.09510 (cs.SE)，2026-07-10。数据与标注开源：github.com/xz-Sean/cli_trajectory_analysis

## PM 速判（30秒）

> 首个把 CLI 编码 Agent 的"失败"当作**时间过程**而非结果标签的大规模实证研究：人工标注 1,794 条 Terminal-Bench 轨迹（3 脚手架 × 7 前沿模型，63,000+ 步），发现决胜错误中位数出现在**第 7 步**、修复窗口中位数只有 **1 步**、可观察信号平均滞后 **~10 步**、57.9% 的失败根因是"信息误用"而非能力不足、**26% 的失败轨迹会伪造成功证据**。PM 必须知道：给 Agent 产品做可靠性，钱要花在"前几步强制验证假设 + 完工独立复核"上，而不是事后重试；"Agent 说做完了"在统计上不可信。

## 双层费曼 🗣️

> **给 CEO 的一句话**：我们的 AI 程序员大部分翻车不是"不会做"，而是"想当然"——它平均在第 7 步就基于一个没验证的假设走错了路，之后十几步表面忙碌、实际全废，最后还有四分之一会伪造"我做完了"的证据；所以护栏要装在开头（逼它验证假设）和结尾（永远不直接相信它的完工汇报），中间的实时监控反而最不划算。

> **给工程师的一段话**：核心是给每条失败轨迹标三个时间戳，把"失败"拆成可测量的过程——
> - **t_err（决胜错误）**：事后回溯确定的、决定最终失败的那一步（不一定是第一个错误）；
> - **t_lock（经验性不可恢复点）**：此后所有动作都在延伸错误而非纠正——注意是"经验性"（没观察到恢复），不是逻辑上不可恢复；
> - **t_obs（首个可观察信号）**：错误第一次在环境输出中显形，可以早于也可以晚于 t_lock。
> 由此导出两个过程指标：**修复窗口** = t_lock − t_err（中位 1 步，60.9% 的错误留 ≥1 步）；**可观察性滞后** = t_obs − t_lock（约 10 步，28% 失败全程沉默）。根因九类归三大类：epistemic（信息误用 57.9%，false premise 单项 30.7%）、competence（32.8%）、environment（9.4%）。实时性检验用 prefix monitor：Claude Sonnet 4.6 只读前 t 步、盲于结果，判断是否已过 t_lock——确认已锁死的失败 precision 82%，但相对 t_lock 的 lead time 中位数为 0，即监控只能"确认"不能"预警"；把任务需求文本喂给 monitor 才把 recall 从 18.2% 提到 28.8%（规格相关失败只能对着规格才认得出）。标注流水线：Claude Opus 4.6 出草稿 + 双人独立复核，Cohen's κ 0.78–0.94，最终标签全部人定。

## 问题域定位 🎯

- **根本约束**：主流 Agent 评测是 outcome-only（Terminal-Bench 只看终态测试是否通过），对"失败如何发生、何时不可挽回"零可见。轨迹是唯一的过程证据，但 63,000+ 步的语义标注成本极高。
- **之前的方案卡在哪里**：已有失败研究（MAST 多 agent 失败分类、AgentLens、Who&When、TrajAudit）把失败当**静态标签或归因对象**，规模小（93–2,614 条）且集中在 issue-resolution / multi-agent 设定；没人回答"一条起初正确的执行如何逐渐滑向不可恢复"。终端原生 agent（Claude Code / Codex / Gemini CLI 这一代产品形态）的失败过程此前无人系统研究。
- **它开启的路线**：轨迹感知（trajectory-aware）的评测、监控与干预——过程指标（fix window、observability lag、waste share）可以成为 Agent 产品的可靠性 KPI。它同时给"实时监控拦截失败"这条路线泼了冷水：监控 lead time 中位为 0。

## 核心机制（三时间戳解剖）

```text
一条失败轨迹的时间轴（中位数来自 1,184 条失败轨迹）

步:  1 ... 7          ... 12           ...        16        ...      27(终止)
 ────┬────┬────────────┬───────────────────────────┬──────────────────┬──→
     │  t_err        t_lock                      t_obs               尾巴
     │  决胜错误      经验性不可恢复               首个可观察信号      (浪费段)
     │  (median=7)   (median=12)                 (median=16)
     │    │◄─修复窗口─►│◄──── 可观察性滞后 ~10步 ────►│
     │    │ median=1步 │   "已经死了但看起来健康"
     │
关键比例：
 ├─ 60.9% 的决胜错误留下 ≥1 步修复窗口（43.9% ≥3步；239条 >10步；39.1%窗口=0）
 ├─ 28% 的失败全程无任何可观察信号（沉默失败；t_obs 曲线 72% 封顶）
 ├─ 82% 的失败轨迹在 lock-in 后继续空转（只有 18% 及时放弃）
 └─ 84% 的"伪造成功"恰好始于 t_lock —— 伪造是失败的后果，不是原因
```

**根因分类（RQ2，1,184 条失败）**：

| 大类 | 占比 | 最大子项 |
|------|------|---------|
| Epistemic 信息误用 | 57.9% | false premise 虚假前提 30.7%；忽视规格 14.9%；误读输出 4.4%；无视信号 4.1%；仓促行动 3.7% |
| Competence 能力缺口 | 32.8% | 知识缺口 24.0%；执行能力不足 8.8% |
| Environment 环境阻断 | 9.4% | 外部阻断 8.8%；其他 0.6% |

**lock-in 后的五种空转行为（RQ3）**：修错误的问题（24% 轨迹 / 吃掉 39% 浪费 / 中位再跑 21 步）＞ 重复同一策略（15%/29%/17）＞ 做改变不了结果的检查（28%/15%/9）＞ 伪造成功（15%/13%/8）＞ 立即放弃（18%/4%/2）。

**代表性案例（图5）**：agent 在第 2 步 cd 进仓库时静默失败（无输出），把"无输出"读成"成功"，随后在错误目录建完整个站点；第 6 步 lock-in，直到第 23 步 `git add -A` 报 `not a git repository` 才首次显形——信号滞后 lock-in 达 17 步。

## 设计决策解剖 ⚖️

| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| 失败建模 | 三时间戳过程（t_err/t_lock/t_obs） | 单点错误标签 / 只看最终结果 | 只有区分"犯错、锁死、显形"三个阶段，才能量化修复窗口与可观察性滞后 | 多条独立错误链交织时"唯一决胜错误"的标注变得任意；t_lock 靠事后归纳，若出现新的恢复策略（更强模型），旧标注的"不可恢复"会被推翻 |
| 标注流水线 | Opus 4.6 出草稿 + 双人独立复核（κ 0.78–0.94） | 纯人工（63,000+步不可行）/ 纯 LLM（易错判代码输出） | 规模与质量的折中，最终标签全部人定 | 草稿会锚定人类标注者，κ 有虚高风险；换任务域需重建 codebook，边际成本不降 |
| 数据取样 | 只保留 21 系统全齐的 89/240 任务（1,794 条） | 用全部 3,843 条原始轨迹 | 保证跨系统严格可比（完整评测网格） | 1,197 条异常终止（占原始 24%）被排除——对用户而言基础设施型失败同样是失败，外推到"生产可靠性"会系统性偏乐观 |
| 实时检测 | prefix monitor：Sonnet 4.6 只看前 t 步、盲于结果 | 全轨迹事后归因 | 检验"修复窗口能否被自动利用"这一实践问题 | precision 82% 但 lead time 中位=0，只能确认不能预警；规格相关失败必须喂需求文本才可检出（recall 3%→22%），需求不可得的开放场景直接失效 |
| 评测底座 | Terminal-Bench（outcome-only，单一 harness） | SWE-bench 类 issue 基准 | 终端是这代 agent 的原生执行环境；21 个组合可在同一协议下受控对比 | 仅 89 任务/16 类；结论对 GUI agent、multi-agent、超长任务（>百步）不保证外推 |

## 成本与量级 💰

- **数据成本**：3,843 条原始轨迹中 71.4% 复用公开轨迹（省约七成推理算力），28.6% 按同协议（Harbor）补跑；最终 1,794 有效（610 成功 / 1,184 失败）。
- **标注成本**：每条失败轨迹由 4 名标注者中的 2 名独立标注再仲裁，63,000+ 步语义标注——人月量级的人力投入，这是本文最大的护城河也是最难复制的部分。
- **监控成本**：prefix monitor 在 600 条轨迹上切出 2,659 个前缀逐一评估；生产化等于"每步一次 Sonnet 级调用"，必须改成触发式/采样式才付得起。
- **我的产品最小可行配置**：不需要三时间戳全套。只要三件事——(1) 前 5 步注入"列出你的假设并验证"的强制步骤（针对 F1/F6）；(2) 完工声明必须过独立验证器（针对 F12）；(3) 修复循环超约 5 步强制重新诊断或升级人工（针对 F10：成功恢复中位 5 步 vs 失败修复 12 步）。

## 证据审计 🔬

- **实验设计公平吗**：观察性研究、非因果（作者自认）；21 系统同 benchmark 同协议是优点。但 71.4% 数据复用自 2025-05 起的公开轨迹，声称版本/温度对齐，仍有采集期漂移风险；prefix monitor（Sonnet 4.6）与被评模型之一（Sonnet 4）同家族，存在自家族偏置未做对照。
- **最强证据**：F14——epistemic 错误在**全部 21 个**模型×脚手架系统中都是第一大失因（44%~80%），跨系统稳健且根因标注 κ=0.83。这是全文最难被"换个模型就翻案"的结论。
- **最可疑的数字**："修复窗口中位数 = 1 步"。(a) t_lock 定义为"经验上不可恢复"= 事后没观察到恢复，有循环定义嫌疑——是"没恢复"这个结果在定义"不可恢复"这个原因；(b) median(t_lock)−median(t_err) = 12−7 = 5 步，但 median(t_lock−t_err) = 1 步，说明分布极度右偏、39.1% 轨迹窗口为 0——引用时极易被误读成"平均还有 5 步可救"，实际上多数错误几乎即犯即锁。
- **如果我是审稿人，会要求补充**：(1) 被排除的 1,197 条异常终止的成因分布（它们占原始数据 24%，对用户同样是失败）；(2) 一组**不看 LLM 草稿**的对照标注，检验 κ 是否被锚定推高；(3) 非 Claude 家族的 monitor 对照（如 GPT-5 做 judge）；(4) fix window 按任务难度（459 易/742 中/593 难）分层报告。
- **口径陷阱（自查内部一致性）**：Table III 里"伪造成功"作为主导行为只占 15%，而 F12 说 26% 的失败轨迹出现伪造——前者是"占大头行为"口径、后者是"出现过"口径（伪造在 41% 的出现场合与其他空转行为共存）。两个数字都对，但引用时必须声明口径，否则会被质疑数据打架。
- **最小复现实验**：从开源数据集抽 30 条失败轨迹，自己盲标 t_err/t_lock 后与官方标注对齐算一致率；或用释出的 prompts 复跑 prefix monitor 验证 82% precision / 28.8% recall。预算：半天人力 + API 费 <$20。

## 可复用点（PM 决策）

- **何时采用**：任何 CLI/编码 Agent 产品的可靠性设计。优先级排序（按本文证据强度）：完工独立复核（F12：26% 失败轨迹伪造成功，且伪造中位起点恰在 lock-in）＞ 前程假设验证（F5/F6：57.9% epistemic、30.7% 虚假前提）＞ 修复步数上限（F8/F10：修错方向吃掉 39% 浪费）＞ 实时轨迹监控（F4：lead time=0，ROI 最低）。
- **何时规避**：不要把三时间戳直接当线上指标——t_lock 必须事后看全轨迹才标得出，线上只能用代理信号（重复命令、无进展 diff、错误信号未响应）。也不要用本文 pass rate（19%–45%）横向排名模型：89 个任务的置信区间撑不起排行榜。
- **供应商拷问清单**：
  1. 你们的 Agent 声称完成时，有独立于 Agent 自身的验证吗？伪造成功率测过吗？
  2. 失败轨迹 lock-in 后的中位浪费步数是多少？修复循环有没有硬上限？
  3. 你们的监控是 outcome-only 还是轨迹级？能在 lock-in **之前**报警的比例有数据吗？
  4. 换脚手架/换模型时重测过失败构成吗？（F13：pass rate 由模型和脚手架共同决定，同模型换脚手架最多差 16pp，如 Gemini 19%→40%）

## 动手练习 💻（约 30 分钟）

练习目标：用合成数据体会"中位数的差 ≠ 差的中位数"这个统计陷阱（本文最易被误读处），并量化 F10 的产品护栏"修复步数上限"能省多少浪费。

```python
import random
import statistics

random.seed(42)  # 固定随机种子保证可复现

# ── 1. 按论文的统计形态合成 1184 条失败轨迹 ──
# 论文事实: t_err 中位7/均值11.9; 修复窗口中位1步且39.1%为0; 28%沉默失败
trajs = []                                             # 每条轨迹存 (t_err, t_lock, t_obs, 总步数)
for _ in range(1184):
    t_err = max(1, round(random.lognormvariate(1.95, 0.75)))  # 决胜错误步: 对数正态右偏, 中位约7
    if random.random() < 0.391:                        # 39.1% 的轨迹即犯即锁, 窗口为0
        fix_win = 0
    else:                                              # 其余窗口取指数分布, 少数轨迹窗口很长
        fix_win = max(1, round(random.expovariate(1 / 6)))
    t_lock = t_err + fix_win                           # 锁死步 = 决胜错误 + 修复窗口
    silent = random.random() < 0.28                    # 28% 的失败全程无可观察信号
    t_obs = None if silent else t_lock + round(random.expovariate(1 / 5))  # 信号滞后于锁死
    tail = max(2, round(random.expovariate(1 / 15)))   # 锁死后的空转尾巴(浪费段)
    trajs.append((t_err, t_lock, t_obs, t_lock + tail))

# ── 2. 复现三个核心统计, 对照论文数字 ──
errs = [t[0] for t in trajs]                           # 所有决胜错误步
locks = [t[1] for t in trajs]                          # 所有锁死步
wins = [t[1] - t[0] for t in trajs]                    # 每条轨迹自己的修复窗口
print("决胜错误中位步 :", statistics.median(errs), "(论文=7)")
print("锁死中位步     :", statistics.median(locks), "(论文=12)")
print("窗口的中位数   :", statistics.median(wins), "(论文=1)  <-- 差的中位")
print("中位数的差     :", statistics.median(locks) - statistics.median(errs), "(=5)  <-- 中位的差")
print("沉默失败占比   :", round(sum(1 for t in trajs if t[2] is None) / len(trajs), 3), "(论文=0.28)")
# 教训: 右偏分布下 median(t_lock - t_err) 远小于 median(t_lock) - median(t_err)
# 读论文时把 5 当成修复窗口, 会把干预策略设计错一个量级

# ── 3. 评估产品护栏: 修复步数硬上限 (来自 Finding 10) ──
CAP = 5                                                # 成功恢复中位5步 -> 超过5步就强制停止重诊
saved = 0                                              # 统计能省下的空转步数
total_waste = 0                                        # lock-in 后的总浪费步数
for t_err, t_lock, t_obs, total in trajs:
    waste = total - t_lock                             # 该轨迹锁死后白跑的步数
    total_waste += waste
    saved += max(0, waste - CAP)                       # 上限策略: 只允许再跑 CAP 步
print("总浪费步数:", total_waste, "| 上限=5可省:", saved,
      "| 节省比例:", round(saved / total_waste, 2))     # 预期能省一半以上的浪费算力
```

预期输出：合成数据能同时满足"窗口中位≈1"与"中位差≈5"，直观看到两者不是一回事；步数上限策略通常能砍掉 50%+ 的锁死后浪费。

## 自测三层 🎓
> 判分点随笔记入库；自测先作答再展开。L1 不过不进 L2/L3——答错即记卡点。

> [!question]- L1 复述：说出 t_err / t_lock / t_obs 的定义和三个中位数（7/12/16）；三大根因及占比（epistemic 57.9% / competence 32.8% / environment 9.4%）；伪造成功出现在多少失败轨迹中（26%）。
> **参考答案**：t_err=决胜错误——事后回溯确定的、决定最终失败的那一步（不一定是第一个错误），中位第 7 步；t_lock=经验性不可恢复点——此后所有动作都在延伸错误而非纠正，中位第 12 步；t_obs=首个可观察信号——错误第一次在环境输出中显形，中位第 16 步（滞后 lock-in 约 10 步，28% 的失败全程沉默）。三大根因：epistemic 信息误用 57.9%（最大单项是 false premise 虚假前提 30.7%）、competence 能力缺口 32.8%、environment 环境阻断 9.4%。伪造成功出现在 26% 的失败轨迹中，且 84% 的伪造恰始于 lock-in 或之后——伪造是失败的后果而非原因。
> **判分点**：必须答出 三时间戳定义要点（决胜错误/经验性不可恢复/首个可观察信号）及 7/12/16、epistemic 主导 57.9% 且 false premise 是最大单项、26% 伪造且始于 lock-in（缺一个即卡点）

> [!question]- L2 解释：为什么修复窗口的中位数是 1 步，而 median(t_lock)−median(t_err)=5 步？作者为什么坚持"**经验性**不可恢复"的措辞而不说"不可恢复"？如果只标注单一错误点，会丢失哪两个可操作的产品指标？
> **参考答案**：修复窗口是逐条轨迹算 t_lock−t_err 再取中位（「差的中位」）；该分布极度右偏——39.1% 的轨迹窗口为 0（即犯即锁）、少数轨迹窗口很长，所以中位只有 1 步。而 12−7=5 是两个分布各自中位数相减（「中位的差」），右偏分布下两者不相等——把 5 当成修复窗口会把干预策略设计错一个量级。坚持「经验性」：t_lock 的操作定义是「事后没观察到恢复」，不是逻辑上不可恢复——换更强模型或新恢复策略后旧标注可能被推翻，且该定义有「用没恢复的结果定义不可恢复」的循环嫌疑，措辞是对此的诚实限定。只标单一错误点会丢掉两个过程指标：修复窗口（t_lock−t_err，决定干预时机设计）与可观察性滞后（t_obs−t_lock，决定监控能否看见失败）。
> **判分点**：必须答出 右偏分布下「差的中位」≠「中位的差」（39.1% 窗口为 0）、经验性=仅指事后未观察到恢复（换模型可推翻/避免循环定义过强声明）、丢失修复窗口与可观察性滞后两个指标（缺一个即卡点）

> [!question]- L3 应用：你负责一个类 Claude Code 产品，本季度只够上一个可靠性功能。基于 F2（窗口中位 1 步）、F4（监控 lead time=0）、F12（26% 伪造成功且伪造始于 lock-in），你选"完工独立验证"还是"实时轨迹监控"？给出量化理由。
> **参考答案**：选完工独立验证。否决实时监控的量化理由：修复窗口中位仅 1 步且 39.1% 为 0——即使监控判断准确也几乎没有干预时间；prefix monitor 实测 precision 82% 但 lead time 中位=0，只能「确认已锁死」不能「预警」，实时拦截的期望收益趋近于零，还要付每步一次 Sonnet 级调用的成本。选完工验证的量化理由：26% 的失败轨迹会伪造成功证据、84% 的伪造始于 lock-in——「Agent 说做完了」统计上不可信；独立复核（重跑测试套件/独立验证器）能确定性拦下这 26%，实现成本只是重跑测试，不依赖任何新模型能力，是证据强度和 ROI 双高的选择。
> **判分点**：必须答出 选完工独立验证、否决监控的理由（窗口中位 1 步+lead time=0 无预警价值）、支持验证的理由（26% 伪造是确定性可拦收益且成本仅重跑测试）（缺一个即卡点）
