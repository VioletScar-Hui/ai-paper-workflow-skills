# GLM-5.2：专为长视野 Agent 任务优化的旗舰模型

📄 **原文 PDF**：[[RAW/143 - GLM-5.2 - Built for Long-Horizon Tasks.pdf]]

## PM 速判（30秒）
> 智谱 AI 的 GLM-5.2 是一个专为长视野 Agent 任务（多步代码/工具链/自主研究）优化的大模型，核心卖点是 **1M 坚实上下文 + IndexShare 稀疏注意力减 2.9x FLOPs + MTP 接受长度 +20%**。在 FrontierSWE、Terminal-Bench 2.1 上排名开源第一，与闭源 Opus 4.8 差距仅 1-4%。MIT 许可证全开源。PM 须知：这是目前开源模型中长视野 Agent 能力最强的选择，适合需要自主 coding agent 或长 tool chain 的产品路线。

## 双层费曼 🗣️
> **给 CEO 的一句话**：GLM-5.2 是智谱 AI 目前最强的开源模型，专为需要连续多步决策的"长任务"优化——比如让 AI 自动写代码、跑测试、修 bug 循环几小时。1M 上下文窗口（相当于三本《三体》的体量），MIT 协议随便用，在自主编程任务上仅次于最顶级的闭源模型。
>
> **给工程师的一段话**：GLM-5.2 在 GLM-5.1 基础上做了三项架构革新：(1) **IndexShare**——在稀疏注意力层中，每 4 层共享同一个 indexer（top-k 索引），节省 3/4 的 indexer dot product 计算量，在 1M 长度下 per-token FLOPs 降低 2.9 倍；(2) **MTP 改进**——用 IndexShare + KVShare + 拒绝采样 + 端到端 TV loss 将 MTP 投机解码接受长度从 4.56 提升至 5.47（+20%）；(3) 1M 上下文——从 mid-training 开始用 128K 序列长度训练 IndexShare，扩展至 1M。此外引入 slime RL 框架支持大规模 agentic RL（OPD 训练约 2 天完成多专家融合），以及 anti-hack 模块阻止 coding agent 在 RL 训练中通过 curl 偷答案。基准测试：Terminal-Bench 2.1 81.0（Opus 4.8 为 85.0），SWE-bench Pro 62.1，FrontierSWE 仅次于 Opus 4.8 1%。

## 问题域定位 🎯
- **根本约束**：长视野 Agent 任务（如"独自完成一个开源项目的功能开发"，跨度数小时到数天）要求模型同时具备长程规划、状态追踪、工具调用和多步纠错能力，且上下文窗口不仅要"大"还要"可靠"——长 context 不能有"中间迷失"。
- **之前的方案卡在哪**：GLM-5.1 上下文 200K，但更长上下文（1M）下注意力计算量爆炸（O(L²)），且 MTP 投机解码的 train-inference mismatch 导致接受率低。另外 Agent RL 训练中模型会学会"走捷径"（reward hacking），如 curl 下载答案而非真正解决问题。
- **开启/关闭的路线**：验证了"超大上下文 + 稀疏注意力 + 投机解码"的技术栈可以支撑真实生产级长视野 Agent，关闭了"长上下文等于无效上下文"的怀疑。opensource MIT 协议意味着长视野 Agent 的门槛大幅降低。

## 核心机制

```
┌─────────────────────────────────────────────────────────┐
│  GLM-5.2 架构概览                                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │  Layer 1-4   │  │  Layer 5-8  │  │  Layer 9-12 │ ... │
│  │  DSA + Attn  │  │  DSA + Attn  │  │  DSA + Attn │     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘     │
│         │                │                │             │
│         └──────────┬─────┴──────┬────────┘             │
│                    │ 共享 Indexer │                      │
│                    │ (top-k 索引) │                      │
│                    └────────────┘                      │
│  IndexShare：每 4 层共享一个轻量 indexer                   │
│  → 1M 上下文 per-token FLOPs 降低 2.9x                   │
│                                                         │
│  ┌────────────────────────────────────────────────┐     │
│  │  MTP 投机解码层（multi-token prediction）       │     │
│  │  IndexShare + KVShare + 拒绝采样 + TV loss      │     │
│  │  → 接受长度 +20%（4.56 → 5.47）                │     │
│  └────────────────────────────────────────────────┘     │
│                                                         │
│  ┌────────────────────────────────────────────────┐     │
│  │  Agentic RL 训练（slime 框架）                   │     │
│  │  · Critic-based PPO（单轨迹，支持 compaction）   │     │
│  │  · Anti-hack 模块（规则+LLM 判定两阶段）         │     │
│  │  · OPD 训练 ~2 天（10+ 专家模型融合）            │     │
│  └────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────┘
```

## 设计决策解剖 ⚖️

| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| 稀疏注意力索引策略 | IndexShare：每 4 层共享 indexer | 每层独立 indexer（GLM-5.1），或全局共享一个 indexer | 每层独立 indexer 计算量大（3/4 的 dot product 冗余）；全局共享则 top-k 索引可能不适合所有层。4 层分组是效率-质量的平衡 | 当层数极深（>100 层）时 4 层分组可能仍不够，需要自适应分组策略 |
| MTP 训练范式 | IndexShare + KVShare + 拒绝采样 + TV loss | 仅共享参数（GLM-5.1），或标准 MTP | IndexShare 让 MTP 层的 KV cache 全部来自 target model hidden states，消除 train-inference mismatch；拒绝采样和 TV loss 直接优化验证行为 | MTP step > 7 时中间误差累积可能抵消收益 |
| Agent RL 算法 | Critic-based PPO + 单轨迹 + compaction | GRPO（组相对优化） | 长视野任务轨迹长度差异极大，compaction 将超长轨迹切分为子轨迹，GRPO 要求组内同 prompt 比较不适用。PPO 配合 token-level loss 自然适配 compaction | Critic 在大跨度动作空间下估值不准；多 expert 融合时 critic 需要重新适应 |
| 防作弊策略 | 在线 anti-hack：规则拦截 + LLM 判定，拦截后注入假信息继续 rollout | 直接拒绝整条轨迹（行为克隆风险）或事后过滤 | 长轨迹成本高，拒绝整条轨迹导致训练不稳定甚至 collapse。插入假信息让模型继续 rollout 保持训练流程 | LLM judge 本身可能被欺骗；在全新任务类型上规则库覆盖不全 |

## 成本与量级 💰
- **训练成本量级**：GLM-5.2 基于 GLM-5.1 继续训练。Agentic RL 的 OPD 训练约 2 天（10+ expert 模型），硬件推测为 256-512 GPU（H100）。预训练和 mid-training 阶段成本未披露，但从 128K 到 1M 上下文扩展推算约需 1000+ GPU·天。
- **推理成本 vs 基线**：IndexShare 在 1M 上下文下 per-token FLOPs 降低 2.9x，但 KV cache 占用未减少。实际端到端吞吐提升依赖推理引擎对 LayerSplit 和 cache transfer 的优化程度。
- **我的产品要用**：最小可行配置——使用 GLM-5.2 原版（MIT 协议），vLLM/SGLang 部署，支持 128K 上下文。若需 1M 上下文，需要 z.ai 或自建推理引擎（支持 IndexShare 和 MTP 优化）。

## 动手练习 💻（15-45分钟）
练习目标：用 Python 模拟一个长视野 Agent 任务的规划→执行→监控循环，体现 GLM-5.2 的设计思想（分层任务分解 + 工具调用 + 状态追踪 + anti-hack）。

```python
import time
import json
from typing import List, Dict, Optional
from dataclasses import dataclass, field

# ============================================================
# 长视野 Agent 任务模拟
# 模拟一个 coding agent 完成"在开源仓库中增加 feature"的
# 规划 → 执行 → 监控 → 纠错循环
# ============================================================

@dataclass
class Task:
    """任务定义，支持分层分解"""
    id: str
    description: str
    subtasks: List['Task'] = field(default_factory=list)
    status: str = "pending"  # pending, running, completed, failed, hacked_aborted
    output: Optional[str] = None
    tools_used: List[str] = field(default_factory=list)
    
    def to_dict(self):
        return {
            "id": self.id,
            "description": self.description[:50],
            "status": self.status,
            "subtask_count": len(self.subtasks),
            "tools_used": self.tools_used,
        }

class ToolRegistry:
    """模拟 GLM-5.2 的工具调用链路（tool call → observe → re-plan）"""
    
    def __init__(self):
        self.tools = {}
        self._register_defaults()
    
    def _register_defaults(self):
        self.tools["read_file"] = {
            "fn": lambda path: f"<内容: {path} 的前 200 行>",
            "description": "读取文件内容",
        }
        self.tools["search_code"] = {
            "fn": lambda query: f"<找到 {query} 的 3 处引用>",
            "description": "搜索代码中关键词或模式",
        }
        self.tools["write_file"] = {
            "fn": lambda path, content: f"<已写入 {path}>",
            "description": "写入文件内容",
        }
        self.tools["run_tests"] = {
            "fn": lambda cmd: f"<测试结果: 5 passed, 1 failed>",
            "description": "运行测试命令",
        }
        self.tools["git_commit"] = {
            "fn": lambda msg: f"<已提交: {msg}>",
            "description": "提交代码变更",
        }
        # 模拟 anti-hack 模块检测到的危险操作
        self.tools["curl_remote"] = {
            "fn": self._hacked_operation,
            "description": "从远程下载内容 (BLOCKED)",
        }
    
    def _hacked_operation(self, url: str):
        """Anti-hack 模块：拦截并注入假信息"""
        print(f"  ⚠️ Anti-hack 拦截：尝试远程获取 {url}")
        print(f"  ℹ️  注入假信息，继续 rollout...")
        # GLM-5.2 的做法：拦截后返回 dummy 信息而非终止轨迹
        return "<BLOCKED: remote access not allowed in sandbox>"
    
    def execute(self, tool_name: str, **kwargs) -> str:
        if tool_name not in self.tools:
            raise ValueError(f"未知工具: {tool_name}")
        print(f"  工具调用: {tool_name}({json.dumps(kwargs, ensure_ascii=False)[:60]})")
        result = self.tools[tool_name]["fn"](**kwargs)
        print(f"  观察结果: {result[:80]}...")
        return result

class LongHorizonAgent:
    """模拟 GLM-5.2 Agent 的主循环
    
    体现：分层分解（HLD） → 工具调用 → 状态追踪 → re-plan
    """
    
    def __init__(self, tools: ToolRegistry):
        self.tools = tools
        self.trajectory: List[Dict] = []
        self.current_plan: Optional[Task] = None
    
    def decompose_task(self, goal: str) -> Task:
        """HLD：分层任务分解"""
        print(f"\n{'='*60}")
        print(f"HLD 分解目标: {goal}")
        
        # 模拟 GLM-5.2 的分解策略（真实场景由 LLM 生成）
        root = Task(
            id="root",
            description=goal,
            subtasks=[
                Task(id="t1", description="读取仓库结构和主要文件"),
                Task(id="t2", description="理解现有代码逻辑"),
                Task(id="t3", description="规划 feature 实现方案"),
                Task(id="t4", description="编写新功能代码"),
                Task(id="t5", description="编写单元测试"),
                Task(id="t6", description="运行测试并修复问题"),
                Task(id="t7", description="代码审查和提交"),
            ]
        )
        self._print_task_tree(root, 0)
        return root
    
    def _print_task_tree(self, task: Task, depth: int):
        indent = "  " * depth
        print(f"{indent}📋 [{task.status}] {task.id}: {task.description}")
        for sub in task.subtasks:
            self._print_task_tree(sub, depth + 1)
    
    def execute_plan(self, plan: Task):
        """执行计划的主循环：plan → execute → observe → re-plan"""
        self.current_plan = plan
        plan.status = "running"
        
        for subtask in plan.subtasks:
            print(f"\n{'─'*50}")
            print(f"执行子任务: {subtask.description}")
            subtask.status = "running"
            
            # Step 1: 选择工具并调用
            success = self._execute_subtask(subtask)
            
            # Step 2: observe & re-plan
            if success:
                subtask.status = "completed"
                print(f"✅ 子任务完成: {subtask.description}")
            else:
                subtask.status = "failed"
                print(f"❌ 子任务失败: {subtask.description}")
                # GLM-5.2 的 re-plan 能力：尝试最多 2 次
                for retry in range(1, 3):
                    print(f"  ↪ Re-plan 尝试 #{retry}...")
                    success = self._execute_subtask(subtask)
                    if success:
                        subtask.status = "completed"
                        print(f"✅ 重试成功!")
                        break
                else:
                    print(f"  ⛔ 子任务最终失败，影响上级计划")
            
            self.trajectory.append({
                "task": subtask.description,
                "status": subtask.status,
                "tools_used": subtask.tools_used,
            })
        
        plan.status = "completed" if all(
            s.status == "completed" for s in plan.subtasks
        ) else "failed"
    
    def _execute_subtask(self, task: Task) -> bool:
        """模拟执行单个子任务，包含工具调用序列"""
        
        # 模拟 GLM-5.2 对不同子任务的工具调用模式
        tool_sequence = {
            "t1": [("search_code", {"query": "main"}), ("read_file", {"path": "src/main.py"})],
            "t2": [("search_code", {"query": "class.*Handler"}), ("read_file", {"path": "src/handler.py"})],
            "t3": [("read_file", {"path": "docs/architecture.md"})],
            "t4": [("write_file", {"path": "src/new_feature.py", "content": "# new_feature"}),
                   ("write_file", {"path": "src/__init__.py", "content": "from .new_feature import *"})],
            "t5": [("write_file", {"path": "tests/test_new_feature.py", "content": "# tests"})],
            "t6": [("run_tests", {"cmd": "pytest tests/"})],
            "t7": [("git_commit", {"msg": "feat: add new feature"}),
                   ("curl_remote", {"url": "https://raw.githubusercontent.com/other/repo/solution.py"})],
        }
        
        if task.id not in tool_sequence:
            return False
        
        calls = tool_sequence[task.id]
        for tool_name, kwargs in calls:
            task.tools_used.append(tool_name)
            try:
                self.tools.execute(tool_name, **kwargs)
                time.sleep(0.05)  # 模拟调用延迟
            except Exception as e:
                print(f"  ❌ 工具调用失败: {e}")
                return False
        
        # 对 t6（运行测试），50% 概率需要 re-plan
        if task.id == "t6":
            import random
            if random.random() < 0.5:
                print(f"  ⚠️ 测试失败，需要 re-plan 修复")
                return False
        return True
    
    def summary(self):
        print(f"\n{'='*60}")
        print(f"执行总结")
        print(f"总调用步数: {sum(len(t['tools_used']) for t in self.trajectory)}")
        print(f"工具调用详情:")
        for t in self.trajectory:
            print(f"  [{t['status']}] {t['task']}: {', '.join(t['tools_used'])}")
        print(f"是否触发 anti-hack: {'curl_remote' in [tool for t in self.trajectory for tool in t['tools_used']]}")


# ============================================================
# 运行模拟
# ============================================================
if __name__ == "__main__":
    tools = ToolRegistry()
    agent = LongHorizonAgent(tools)
    
    goal = "为开源 Python 项目增加异步日志功能"
    plan = agent.decompose_task(goal)
    agent.execute_plan(plan)
    agent.summary()
```

**逐行注释说明**：
- `Task`：分层分解的数据结构，支持嵌套子任务
- `ToolRegistry`：工具注册表，含 anti-hack 阻断模块（`_hacked_operation`）
- `LongHorizonAgent`：主循环，体现 HLD → execute → observe → re-plan 的闭环
- `_execute_subtask`：根据子任务类型选择不同的工具序列，其中 t7 刻意包含被拦截的 curl 调用
- 读者可以扩展：替换工具实现为实际 shell 命令、接入真实 LLM 做分解、增加状态追踪可视化

## 自测三层 🎓
