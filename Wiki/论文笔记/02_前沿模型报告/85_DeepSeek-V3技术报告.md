# DeepSeek-V3 技术报告

📄 **原文 PDF**：[[RAW/85 - DeepSeek-V3 Technical Report.pdf]]

## PM 速判（30秒）
> 一句话：671B 总参数（每 token 只激活 37B）的开源 MoE 模型，用 MLA 压缩 KV 缓存 + 无辅助损失负载均衡 + MTP + FP8 训练，仅花 2.788M H800 GPU 小时（约 $5.58M 租金成本）就逼近 Claude 3.5 Sonnet——它把"顶级模型必须烧一亿美元"这个行业假设打碎了，是所有 PM 做"开源 vs 闭源"选型时的成本参照系原点，也是 R1 的基座。

## 双层费曼 🗣️
> **给 CEO 的一句话**：DeepSeek 用不到 600 万美元的算力租金，训练出了一个接近国际顶级闭源水平、且免费开放权重的 AI 模型——这意味着大模型的成本门槛比我们以为的低一个数量级，供应商的定价权正在被侵蚀。
> **给工程师的一段话**：V3 是 61 层、671B 参数的 MoE Transformer，每层 1 个共享专家 + 256 个细粒度路由专家，每 token 激活 8 个路由专家（37B 参数）。注意力用 MLA：把 K/V 联合压缩成 512 维潜在向量 c^KV，外加 64 维解耦 RoPE key，推理时每 token 每层只缓存 576 个数——比 128 头 MHA 的 32768 个数小约 57 倍。负载均衡不用辅助损失，只靠给每个专家的路由分数加一个动态调整的 bias。再叠加 MTP（额外预测下一个 token 的 token）、FP8 混合精度和 DualPipe 流水线，14.8T token 全程无损失尖峰、零回滚。

## 问题域定位 🎯
- **根本约束**：训练顶级 LLM 的算力成本（当时估计 GPT-4 级别 $100M+）和 MoE 推理时 KV 缓存的显存墙——大模型好用但训不起、部署不起。
- **之前的方案卡在哪里**：① 稠密模型（Llama-405B）算力利用率低；② 传统 MoE 用辅助损失做负载均衡，会干扰主任务梯度、损伤模型质量；③ GQA/MQA 压 KV 缓存靠"砍头数"，容量受损。
- **开启/关闭的路线**：开启了"极致工程 + 架构协同设计压成本"的路线（V3.2 的 DSA、V4 的 CSA/HCA 都是这条线的延伸），也开启了"以 V3 为基座做推理 RL"的 R1 路线；基本关闭了"开源模型只能追随、永远差一代"的叙事。

## 核心机制

```
                DeepSeek-V3 单层数据流
输入 h_t ─────────────────────────────────────────────┐
   │                                                  │
   ▼  MLA（推理时只缓存蓝框内容）                        │
 ┌─────────────────────────────────────┐              │
 │ h_t ──W^DKV──> [c^KV_t  512维]───┐   │              │
 │ h_t ──W^KR───> [k^R_t    64维]───┤   │  ← 每token每层 │
 │                    │  升维还原K,V  │   │    仅缓存576数 │
 │ h_t ──W^DQ──> c^Q(1536)──> q(128头×128)             │
 │                    └──> Attention ──> 输出           │
 └─────────────────────────────────────┘              │
   ▼                                                  │
 DeepSeekMoE：router(h_t) + bias_i  ──> Top-8 路由专家  │
 （bias 只影响选谁，不进梯度；专家超载则调低 bias）        │
   1 共享专家 + 256 路由专家（每个中间维度仅 2048）        │
   ▼                                                  │
 残差相加 <───────────────────────────────────────────┘

训练目标 = 主 LM loss + MTP loss（用轻量模块多预测 1 个未来 token）
训练精度 = FP8 GEMM + 关键路径 BF16/FP32（细粒度分块量化）
```

## 设计决策解剖 ⚖️
| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|--------|----------|------------|--------|---------------|
| KV 缓存压缩 | MLA：低秩联合压缩 K/V 到 512 维潜在向量 | GQA/MQA（砍 KV 头数）、滑动窗口注意力 | GQA 靠减少头数省显存但损容量；MLA 压缩后可还原全部 128 头，质量≈MHA 而缓存缩 ~57 倍 | 上下文长到百万级时 KV 仍随 n 线性增长，必须再叠稀疏化（V3.2 DSA / V4 CSA 就是为此）；此外 MLA 多一次升维矩阵乘，算力瓶颈型（而非显存瓶颈型）部署收益打折 |
| MoE 负载均衡 | 无辅助损失：仅用每专家 bias 动态调路由 + 极小的序列级平衡损失兜底 | Auxiliary loss（GShard/Switch 传统做法） | 辅助损失的梯度会和语言建模目标打架，平衡越狠模型越差；bias 不参与梯度，零污染 | bias 更新速率调不好时会震荡；专家数继续放大或数据分布剧烈漂移时，单靠 bias 可能出现序列内瞬时热点（所以他们仍留了小平衡损失） |
| 专家粒度 | 细粒度：256 个小专家（中间维 2048）+ 1 共享专家 | 少量大专家（如 Mixtral 的 8×大专家） | 小专家组合数多、专业化更充分；共享专家兜住通用知识，减少路由专家冗余 | 专家太碎会放大 all-to-all 通信开销，跨节点带宽不足的集群上通信变瓶颈（V3 靠限制每 token 最多路由 4 个节点缓解） |
| 训练目标 | MTP：额外预测第 2 个未来 token | 只做标准 next-token；或多头并行预测多个 token | 密集化训练信号、提升数据效率；推理时该模块可拆掉或用于投机解码（约 1.8x 解码加速） | MTP 深度加大收益递减；如果产品推理端不启用投机解码，这部分训练成本换不回推理收益 |
| 训练精度 | FP8 混合精度（细粒度分块缩放）| 全程 BF16 | GEMM 提速近一倍、显存减半，是 $5.58M 成本的关键一环 | 硬件不支持细粒度量化缩放时精度崩；对激活异常值敏感的模块（如注意力后投影）仍须保留高精度，否则损失发散 |

## 成本与量级 💰
- **训练成本**：预训练 2664K + 长上下文扩展 119K + 后训练 5K = 2788K H800 GPU 小时；按 $2/GPU 小时租金 = **$5.576M**（论文 Table 1）。注意：这只是"最后一次正式训练"的租金，**不含**前期消融实验、数据构建、人力和失败尝试。
- **推理成本 vs 基线**：MLA 使 KV 缓存 ≈ MHA 的 1/57、GQA-8 的 1/3.6（见动手练习）；MoE 每 token 只算 37B/671B ≈ 5.5% 的参数，同能力档稠密模型（405B）激活参数约为其 11 倍。
- **我的产品要用：最小可行配置**：官方权重 BF16 需约 1.4TB 显存（多机 H100/H800 集群）；个人/小团队应直接用 API 或量化版（如 INT4 约 350GB+），或者选 distill 后的小模型——V3 本体不是单卡产品。

## 证据审计 🔬
- **实验设计公平吗？** 基线选取总体规范（Qwen2.5-72B、Llama-405B、Claude-3.5-Sonnet-1022、GPT-4o-0513），但全部由 DeepSeek 自己复测，解码配置（8192 token 上限、AIME 平均 16 次采样）对不同模型的友好度不一。
- **最强证据**：MATH-500 90.2%（GPT-4o 74.6%、Claude 78.3%）；Codeforces 51.6 百分位（对比模型均 <36）；条件是数学/竞赛类、非 Agent 场景。成本证据 2.788M GPU 小时有分阶段明细，可信度较高。
- **最可疑的数字**：**"$5.58M 训练成本"**，因为它按 $2/时租金计价且只算正式训练——媒体普遍误读为"总研发成本"，实际总投入（自有集群、消融、数据、人力）至少高一个量级；其次 SimpleQA 24.9%（Claude 28.4%、GPT-4o 38.2%）显示世界知识明显偏弱，宣传中很少提。
- **如果我是审稿人，会要求补充**：① 消融实验总算力（衡量方法可复制性）；② MLA vs GQA 在同规模下的严格对照（V3 里 MLA 继承自 V2，无同代对照）；③ SWE-Verified 42.0% vs Claude 50.8% 差距的错误分析。
- **最小复现实验**：不可能复现全模型，代理指标 = 在 1B 级 MoE 上对比"辅助损失 vs bias-only 负载均衡"的验证 loss 与专家负载熵；预算约 8×A100 × 3-5 天（数千美元）。

## 可复用点（PM 决策）

## 动手练习 💻（15-45分钟）
练习目标：亲手算出 MLA 相对标准 MHA / GQA / MQA 的 KV 缓存压缩率，理解"为什么 MLA 让长上下文部署成本骤降"。

```python
# mla_kv_cache.py
# 计算 DeepSeek-V3 的 MLA 相比 MHA/GQA/MQA 能省多少 KV 缓存
# 运行方式：python mla_kv_cache.py   （只依赖 numpy，pip install numpy）

import numpy as np                       # 导入 numpy，用于数值计算

# ===== 1. DeepSeek-V3 的真实架构参数（来自技术报告 4.2 节）=====
N_LAYERS = 61                            # Transformer 层数
N_HEADS  = 128                           # 注意力头的数量
D_HEAD   = 128                           # 每个注意力头的维度
D_C      = 512                           # MLA 的 KV 压缩维度（潜在向量 c^KV）
D_ROPE   = 64                            # MLA 解耦 RoPE key 的维度（k^R）
BYTES    = 2                             # 每个数值占 2 字节（BF16 半精度）

# ===== 2. 定义各注意力方案"每个 token、每一层"要缓存的数值个数 =====
def kv_elems_mha():
    """标准 MHA：128 个头的 K 和 V 全都要缓存"""
    return 2 * N_HEADS * D_HEAD          # 2 表示 K、V 各存一份

def kv_elems_gqa(n_groups):
    """GQA：多个查询头共享一组 KV，只缓存 n_groups 组"""
    return 2 * n_groups * D_HEAD         # 组数越少，缓存越小，但容量受损

def kv_elems_mla():
    """MLA：只缓存 512 维压缩向量 + 64 维 RoPE key，共 576 个数"""
    return D_C + D_ROPE                  # K/V 都能从这 576 个数升维还原

# ===== 3. 把"每 token 每层的数值个数"换算成整模型显存（GB）=====
def kv_gb(elems_per_token_layer, context_len):
    """总字节 = 每token每层数值数 × 层数 × 上下文长度 × 每数值字节数"""
    total_bytes = elems_per_token_layer * N_LAYERS * context_len * BYTES
    return total_bytes / 1024**3         # 换算成 GB（1GB = 1024^3 字节）

# ===== 4. 对比四种方案在不同上下文长度下的 KV 显存 =====
schemes = {                              # 用字典存"方案名 → 每token每层数值数"
    "MHA (128头)":  kv_elems_mha(),
    "GQA-8":        kv_elems_gqa(8),     # Llama-3 系列常用 8 组
    "MQA (1组)":    kv_elems_gqa(1),     # 极端方案：所有头共享 1 组 KV
    "MLA (V3)":     kv_elems_mla(),
}

print(f"{'方案':<12}{'每token每层数值数':>16}{'相对MHA压缩率':>14}")
mha = kv_elems_mha()                     # 先取 MHA 作为分母基准
for name, e in schemes.items():          # 遍历每个方案
    print(f"{name:<14}{e:>14,}{mha / e:>13.1f}x")   # 压缩率 = MHA / 本方案

print("\n不同上下文长度下的 KV 缓存显存（GB，BF16）：")
ctx_list = [8_192, 32_768, 131_072, 1_000_000]      # 8K/32K/128K/1M
header = "上下文".ljust(10) + "".join(n.ljust(14) for n in schemes)
print(header)
for ctx in ctx_list:                     # 每种上下文长度算一行
    row = f"{ctx:>8,}  "
    for e in schemes.values():           # 每种方案算一列
        row += f"{kv_gb(e, ctx):>10.1f}GB  "
    print(row)

# ===== 5. 自己验证论文结论 =====
# 预期输出：MLA 每 token 每层只存 576 个数，约为 MHA 的 1/56.9、GQA-8 的 1/3.6
# 在 128K 上下文时，MHA 需要约 478GB 而 MLA 只要约 8.4GB —— 这就是
# "一台 8 卡机能不能服务长上下文"的分水岭，也是 V3 可部署性的核心来源。
```
