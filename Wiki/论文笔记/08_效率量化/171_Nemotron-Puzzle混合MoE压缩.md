# Nemotron-Labs-3-Puzzle-75B-A9B：压缩混合 MoE 大模型（Compressing Hybrid MoE LLMs）

📄 **原文 PDF**：[[RAW/171 - Nemotron-Labs-3-Puzzle-75B-A9B - Compressing Hybrid MoE LLMs.pdf]]

## PM 速判（30秒）
> 一句话：NVIDIA把混合 Mamba-Attention-MoE 架构的 Nemotron-3-Super（120.7B总参数/12.8B激活参数）压缩成 Puzzle-75B-A9B（75.3B总参数/9.3B激活参数），用一套"迭代式 Puzzle"神经架构搜索（分多轮做非均匀剪枝+短程蒸馏愈合，而非一次性剪到位）+ 大规模知识蒸馏 + 针对软件工程能力的强化学习 + FP8/NVFP4量化 + 投机解码（MTP）组合拳，在单节点8×B200上实测交互式服务吞吐提升约2倍（不同场景1.6~2.14倍），在单张H100上把百万token超长上下文的并发请求数从1提到8，且在推理/编程/长上下文等大部分基准上精度损失控制在1~2分以内。PM必须关注：这是一套只有拥有原始教师模型和工业级算力（Megatron-LM、1600万token全局批次、200轮沙盒RL环境）的团队才能复现的压缩流水线，报告里也坦诚"RL阶段带来的提升很小"——这提醒PM在评估任何"我们通过强化学习大幅提升了压缩后模型能力"的供应商话术时，要分清"蒸馏在做主要工作、RL只是锦上添花"和"RL确实是核心杠杆"这两种截然不同的情况。

## 双层费曼 🗣️
> **给CEO的一句话**：把一个又大又贵的AI模型变成一个更小、跑得更快、更省显存的版本，同时尽量不让它变笨——这篇论文的做法是不一次性大刀阔斧地砍，而是"砍一刀、缓一缓（让模型重新适应）、再砍一刀"，分好几轮完成压缩，并且砍的时候不是每个部位砍一样多，而是先摸清楚模型内部哪些部分对最终表现影响大、哪些部分冗余多，把预算优先留给关键部位——最终这个瘦身后的模型在同一台服务器上能多接待将近2倍的用户请求，处理超长文档时能同时服务的用户数从1个变成8个，但绝大多数能力测试的分数只掉了一两分。
>
> **给工程师的一段话**：论文的核心方法是 Iterative Puzzle——对原版一次性神经架构搜索（Puzzle: 定义离散的层级替换候选空间"拼图块"、给每个候选块打效率/精度分、用混合整数规划在约束下为每层选一块）的序列化扩展。原版 Puzzle 假设不同层替换的质量影响近似可加（用替换单层后的局部分数之和作为目标函数），但这忽略了层间高阶交互（剪掉某个MoE层会改变后续层看到的表示分布）；Iterative Puzzle 因此把压缩拆成 M₀→M₁→...→M_R 的序列，每轮先在当前模型 M_{r-1} 的上下文里重新打分候选块、解一次约束优化得到 M_r，再用短程知识蒸馏"愈合"M_r 作为下一轮起点。最终模型经过三阶段压缩+愈合（MoE权重依次压到教师的75%→60%→最终把激活路由专家预算约束到50%且由Puzzle在层间异构分配，愈合token量依次为24B/43.2B/52.8B），配合Mamba SSM状态从128通道剪到96通道（用贡献度而非随机选择通道）、长上下文蒸馏（128K→512K序列长度，最多各100B token）、针对软件工程能力专门做的RL恢复（最长200轮沙盒交互）、FP8/NVFP4训练后量化、以及continued-trained的共享头MTP投机解码（把训练时teacher-forcing与推理时自回归drafting之间的分布失配问题专门用continued training修复，平均接受长度提升25~30%）。

## 问题域定位 🎯
- **回应什么根本约束**：大模型在推理侧的效率受多个维度联合制约——不只是总参数量，还有激活参数量、KV缓存大小、Mamba状态大小、以及输入/输出序列长度比例；不同部署场景的瓶颈还不一样：长输入请求通常是计算受限，长输出请求通常是IO受限（除非批量很大），超长上下文请求则常常直接被设备显存卡死。论文明确指出：现有压缩技术（剪枝、量化、蒸馏）通常面临效率与能力保留之间的两难，混合MoE架构下这个矛盾尤其突出，因为精度对总参数量、激活参数量、KV缓存、Mamba状态四者的敏感度并不一致，单一维度的压缩很难同时优化多个部署场景。
- **之前卡在哪**：原版Puzzle框架（Bercovich et al. 2025, ICML）用一次性架构搜索解决了"该在哪些层用什么替换方案"这个组合优化问题，但其可加性假设（每个候选块的质量影响可以独立打分再求和）没有考虑层间的高阶交互——论文明确指出剪掉一个MoE层会改变后续层看到的表示分布，导致某些块在原始教师模型语境下算出的"重要性分数"，放到压缩到一半的中间模型语境下可能已经不准。
- **开启/关闭了什么技术路线**：论文没有发明全新的压缩算法，而是把"迭代式压缩-愈合循环"系统化为一套可复现的三阶段流水线，并额外验证了两个此前较少系统研究的方向：(1) 用模型自身在正常前向计算里已产生的信号（Mamba层贡献度）指导SSM状态剪枝，而非随机剪；(2) 把"prefill-decode解耦部署"当作一个额外的压缩维度——用一个专门为处理长prompt优化的更小模型做prefill、用完整压缩模型做decode，二者通过联合训练（Star Elastic）保证KV缓存/Mamba状态无需任何适配层就能跨界兼容。论文同时报告了一个负面结果：探索过的"MoE隐层瓶颈维度剪枝"（latent dimension pruning）在当前压缩比下并未跑赢"通道+top-k剪枝"这条主线，最终未被采纳进正式架构。

## 核心机制

Iterative Puzzle 三阶段压缩-愈合流水线 + 双部署目标场景（复现自论文 §2.1-2.3 与 §1 的部署设定）：

```
教师模型 Nemotron-3-Super（120.7B总/12.8B激活，Mamba+Attention+MoE混合架构，88个block）

┌─────────────────────────── Iterative Puzzle 压缩-愈合循环 ───────────────────────────┐
│  M₀（教师） ──Puzzle搜索──▶ 压缩候选 ──短程KD愈合──▶ M₁ ──重新打分──▶ ... ──▶ M_R    │
│  每轮：在"当前模型"语境下重新评估候选块质量分，而非只用原始教师模型语境的旧分数        │
│                                                                                        │
│  Stage1: MoE权重→75%教师容量，Mamba状态→75%，愈合24B token                             │
│  Stage2: MoE权重→60%教师容量，愈合43.2B token                                          │
│  Stage3: 激活路由专家预算→50%教师（由Puzzle在层间异构分配），愈合52.8B token（最终模型）│
│                                                                                        │
│  搜索空间：MoE路由专家中间维度（异构，按层分配）+ top-k激活专家数（异构）               │
│           Mamba SSM状态通道数（全模型统一剪，受推理框架限制）                          │
│           Attention层不动（教师已足够KV缓存高效）                                      │
└────────────────────────────────────────────────────────────────────────────────────┘
                                        │
                          长上下文KD恢复（128K→512K序列，各≤100B token）
                          + 软件工程/Agentic RL恢复（最长200轮沙盒，KL惩罚=0）
                          + FP8/NVFP4训练后量化 + continued-trained共享头MTP
                                        ▼
              Nemotron-Labs-3-Puzzle-75B-A9B（75.3B总/9.3B激活）

两个目标部署场景（论文§1明确给出的设计目标）：
┌─────────────────────────────┐   ┌──────────────────────────────────┐
│ 场景1：交互式服务             │   │ 场景2：超长上下文Agent工作负载        │
│ 单节点8×B200，吞吐受限         │   │ 单张H100，显存受限                   │
│ 输入50K/输出2K（长文档分析RAG） │   │ 100万token上下文，多并发请求          │
│ 输入8K/输出64K（推理生成）      │   │ 目标：H100 80GB显存下并发从1提到8      │
│ 目标：100 TPS/用户时吞吐×2      │   │ 关键：Puzzle权重44.5GB(NVFP4) vs      │
│                               │   │ Super权重70GB，省下的显存换更多并发    │
└─────────────────────────────┘   └──────────────────────────────────┘
```

## 设计决策解剖 ⚖️

| 决策点 | 他们的选择 | 被放弃的方案 | 为什么 | 这个选择何时失效 |
|---|---|---|---|---|
| 压缩执行方式 | 迭代式Puzzle：分多轮压缩，每轮在"当前压缩模型"语境下重新打分候选替换块，轮间插入短程KD愈合 | 单步Puzzle：一次性对原始教师模型打分、直接求解出最终目标架构 | 原版Puzzle假设块替换质量影响近似可加，忽略层间高阶交互（剪一层会改变后续层看到的表示分布）；受控消融（同一最终压缩目标下对比）显示迭代版本平均分+0.57 | 消融表也显示迭代版本在IFBench-Inst（-0.2）和IFBench-Prompt（-0.5）上略有退步，说明迭代并非在每个指标上都严格占优；且多轮迭代增加了搜索+愈合的总计算成本，压缩比不激进时单步方案的可加性假设本就够用，加迭代未必划算 |
| 层间容量分配方式 | 异构分配：按每层对精度的"测量敏感度"非均匀分配MoE路由专家容量（实测层间相对容量范围8.7%~62.3%，均值30.9%） | 均匀缩放：所有MoE层统一压到同一比例 | Figure 2显示Puzzle自动学到的分配高度非均匀——中后段部分层保留远高于平均的容量，说明"一刀切"式均匀缩放会在敏感层上过度损伤精度、在冗余层上浪费预算 | 该方案本身也受限于推理框架能力——论文明确说明Mamba SSM状态之所以选择"全模型统一剪"而非层间异构，正是因为"当前推理框架不支持逐层不同的SSM状态大小"（附录A.2原话），即异构分配这一设计只在MoE层上落地，Mamba层因工程限制未能享受同样的优化 |
| Prefill/Decode压缩策略 | 解耦压缩：额外训练一个更小的prefill专用模型（FastPuzzleV1/V2），与完整decode模型联合训练（Star Elastic）以保证KV缓存/Mamba状态跨界兼容，无需任何适配层 | 用同一个压缩后模型同时处理prefill和decode | 关键对照实验：若把同一个更小模型同时用于prefill和decode，公共基准均分从79.9骤降到72.8（GPQA/LiveCodeBench/IFBench/AA-LCR降幅尤其大）；证明收益专门来自"只压缩计算密集的prefill路径、保留decode模型的生成质量"，而非单纯"模型更小就更快" | 需要部署基础设施已经支持prefill-decode解耦服务（多数自建团队未必具备），且要多维护、同步一个独立模型版本；这不是每个团队都能低成本复用的部署形态 |
| MoE隐层瓶颈维度剪枝 | 探索后明确不采纳进最终架构，压缩预算全部投入通道剪枝+top-k削减 | 把隐层瓶颈维度（latent bottleneck）也纳入联合搜索空间 | 论文附录D报告：在其压缩比下，把预算投入隐层剪枝并未跑赢投入通道/top-k剪枝；且当前NVFP4 MoE推理核要求隐层维度是512的倍数，从1024只能跳到512这一档，剪幅过粗、缺乏单独恢复训练时代价过高 | 论文自己给出假设边界："隐层剪枝可能在通道剪枝轴趋于饱和的更激进压缩比下变得有价值"——即这个"不采纳"的决策是针对当前约62%总参数压缩比的判断，压缩目标更激进时结论可能反转 |

## 成本与量级 💰
- 压缩+恢复训练成本量级：Iterative Puzzle三阶段愈合共计约24B+43.2B+52.8B=120B token；随后的长上下文KD恢复阶段在128K和512K两档序列长度上各最多再用100B token（全局批次1600万token，基于Megatron-LM框架）；RL恢复阶段给出了rollout配置（SWE1阶段每prompt 16条rollout、批次1024、最长131072 token；SWE2阶段每prompt 32条rollout、批次512、最长131072 token、单条轨迹最多200轮工具交互）但论文全文未给出GPU卡时或美元成本数字——综合来看压缩+恢复所需的token总量达数百亿至接近半万亿量级，远小于从零预训练一个120B模型的成本，但仍是只有工业级算力团队才能承担的规模。
- 模型体积变化：总参数120.7B→75.3B（62.4%），激活参数12.8B→9.3B（73.1%），Mamba SSM状态128→96通道（75%），提供BF16/FP8/NVFP4三种公开checkpoint。
- 部署收益量级：单节点8×B200交互式服务，单步解码（不含MTP）吞吐提升1.6~2.14倍（视场景与用户吞吐阈值而定，设计目标是UT=100 tok/s时1.6倍）；叠加MTP投机解码后，Puzzle-75B-A9B相对Super的有效请求完成率提升到约4.91倍（vs Super自身MTP版本的3.04倍——即Puzzle不仅比Super快，配合MTP后领先优势进一步拉开）；单张H100上百万token并发请求数从1提升到8（约8倍），该并发下聚合解码吞吐约为Super的4倍，990K token长prompt的prefill速度约快1.2倍。
- 我的产品要用的最小可行配置：绝大多数团队不具备复现这套完整压缩流水线的条件（需要原始教师模型访问权限、Megatron-LM级分布式训练基础设施、千万token量级全局批次、200轮沙盒Agent RL环境）；现实可行的"最小配置"是直接采用NVIDIA公开发布的BF16/FP8/NVFP4三种checkpoint之一，根据自身硬件（Hopper用FP8、Blackwell用NVFP4）和场景（交互式服务优先BF16/FP8，超长上下文优先NVFP4省显存）选型，而非自行复现压缩训练。

## 证据审计 🔬
- **实验设计公平吗？基线选取有什么猫腻**：核心对照（Puzzle-75B-A9B vs Super）严格采用同精度匹配（都是NVFP4，或都是BF16，或都是FP8），论文明确说明这样做是为了让"测出的差距只反映压缩本身，而非数值格式变化"，是扎实的受控变量设计；吞吐对比采用Pareto前沿方法学（对TP∈{1,2,4,8}、EP开关、批次网格做完整扫描，每个配置重复两次，在匹配的用户吞吐阈值下取Pareto最优总吞吐），也是严谨的系统级基准测试实践而非挑单点配置。但与Nemotron-3-Nano的对比用了论文自定义的"按生成冗长度调整后的有效请求完成率（Rel. Req./min）"指标——这是一个合理但服务于自身叙事的指标：按该指标Puzzle-75B-A9B+MTP达到5.14倍、Nano仅5.84倍原始吞吐调整后降到3.87倍（Nano因verbosity更高被扣分）——但如果只看官方摘要一句"以Nano级有效吞吐拿到接近Super的精度"，容易忽略这是作者精心设计的自定义指标而非行业标准指标。
- **最强证据（PDF中的真实数字+成立条件）**：迭代式vs单步Puzzle的受控消融（表6）是全文最干净的证据——两者压缩到完全相同的最终目标架构，唯一变量是压缩过程分几轮进行。结果：MMLU-Pro 81.4→82.1（+0.7）、GPQA 75.9→77.4（+1.5）、AA-LCR 55.3→57.5（+2.2）、平均68.48→69.05（+0.57），同时诚实报告了IFBench两项指标的小幅退步（-0.2、-0.5）。Prefill/Decode解耦的负对照实验同样扎实：把同一个更小模型同时用于prefill和decode，公共基准均分从79.9暴跌到72.8，直接证伪了"效果只是因为模型变小了"这一替代假设，证明收益确实来自"只压缩prefill、保留decode质量"这一目标机制。
- **最可疑的数字**：表3中"RULER 512k""RULER 1M"以及"Multilingual"（MMLU-ProX、WMT24++）几行在PDF文本提取结果中未能读出具体数值（可能是复杂多栏表格排版导致的提取问题，也可能确实缺失），本笔记未能核实这几项的精确读数，仅能引用论文正文的概括性表述"RULER在256K/512K/1M上下文长度上，压缩模型与教师模型差距大致在1~2分以内"——PM若要引用这几项具体分数，建议直接打开原PDF核实表格截图，不要仅凭本笔记转述的概括性文字。附录D的隐层剪枝消融表（表8）同样存在数字与方法名对齐疑似错位的情况（768×768一栏"projection-based method"数值看似高于/劣于Minitron，与正文"projection-based方法在每一档都占优"的论断存在表面矛盾），本笔记因此只采信了正文中明确用连续文字重申的896×896一档对比（0.979 vs 1.013~1.024 vs reverse-Minitron的1.763），未采信768×768这一档的具体数字。

## 动手练习 💻
练习目标：用一个可运行的最小示例模拟论文核心论断——"迭代式压缩+中间愈合"相比"单步压缩到底"更能保留模型质量，通过一个简化的玩具剪枝场景直观体会"层间高阶交互"为什么会让单步压缩的可加性假设失效。

```python
"""
最小复现实验：模拟论文核心论断——
迭代式压缩（分多轮剪枝+愈合）相比单步压缩（一次剪到目标），
在存在"层间交互"效应时能更好地保留整体质量。
不依赖真实模型，用一个简化的多层"重要性传播"玩具模型代替，便于本地直接运行。
"""
import random

random.seed(3)

NUM_LAYERS = 8
INITIAL_CAPACITY = [1.0] * NUM_LAYERS  # 每层初始容量（归一化，1.0=教师满容量）
TARGET_TOTAL_CAPACITY = NUM_LAYERS * 0.5  # 目标：整体容量压到50%


def layer_importance(capacities, layer_idx):
    """
    模拟"层间高阶交互"：某一层的真实重要性不仅取决于自身容量，
    还受相邻层当前容量的影响（相邻层容量越低，本层需要承担更多、重要性相应升高）。
    这模拟了论文提到的"剪掉一层会改变后续层看到的表示分布"这一现象。
    """
    base_importance = 0.5 + 0.3 * random.random()  # 每层固有的基础重要性（含随机扰动）
    neighbor_pressure = 0.0
    if layer_idx > 0:
        neighbor_pressure += (1.0 - capacities[layer_idx - 1]) * 0.2
    if layer_idx < len(capacities) - 1:
        neighbor_pressure += (1.0 - capacities[layer_idx + 1]) * 0.2
    return base_importance + neighbor_pressure


def prune_step(capacities, prune_amount, importance_fn):
    """
    单次剪枝：按当前"重要性"给每层打分（重要性越低越先剪），
    从总容量里按比例剪掉 prune_amount，剪枝对象是重要性最低的层。
    """
    importances = [importance_fn(capacities, i) for i in range(len(capacities))]
    # 重要性越低，剪得越多（简化：按重要性倒数分配剪枝量）
    inv_importance = [1.0 / imp for imp in importances]
    total_inv = sum(inv_importance)
    new_capacities = capacities.copy()
    for i in range(len(capacities)):
        share = inv_importance[i] / total_inv
        new_capacities[i] = max(0.05, capacities[i] - prune_amount * share * len(capacities))
    return new_capacities


def total_quality(capacities):
    """简化质量代理指标：总容量之和，但加上'层间失衡惩罚'——
    某层被剪得过狠而相邻层还很满时，代表交互没被正确建模，扣质量分。"""
    base = sum(capacities)
    imbalance_penalty = sum(
        abs(capacities[i] - capacities[i + 1]) * 0.15 for i in range(len(capacities) - 1)
    )
    return base - imbalance_penalty


def single_step_prune():
    """单步压缩：只用初始教师模型的重要性打分，一次性剪到目标容量。"""
    capacities = INITIAL_CAPACITY.copy()
    prune_amount = (sum(capacities) - TARGET_TOTAL_CAPACITY) / len(capacities)
    # 重要性只在初始状态下计算一次，不随剪枝过程更新（模拟"可加性假设"）
    capacities = prune_step(capacities, prune_amount, lambda caps, i: layer_importance(INITIAL_CAPACITY, i))
    return capacities


def iterative_prune(rounds=3):
    """迭代压缩：分多轮，每轮基于'当前模型'重新计算层间交互后的重要性再剪一部分。"""
    capacities = INITIAL_CAPACITY.copy()
    total_prune_needed = sum(capacities) - TARGET_TOTAL_CAPACITY
    per_round_prune = (total_prune_needed / len(capacities)) / rounds
    for _ in range(rounds):
        # 每轮都用"当前"容量分布重新计算重要性（模拟层间交互的动态更新）
        capacities = prune_step(capacities, per_round_prune, layer_importance)
    return capacities


def main():
    single = single_step_prune()
    iterative = iterative_prune(rounds=3)

    print(f"{'层':<4}{'单步压缩容量':<14}{'迭代压缩容量':<14}")
    for i in range(NUM_LAYERS):
        print(f"{i:<4}{single[i]:<14.3f}{iterative[i]:<14.3f}")

    print(f"\n单步压缩总质量代理分: {total_quality(single):.3f}（总容量{sum(single):.3f}）")
    print(f"迭代压缩总质量代理分: {total_quality(iterative):.3f}（总容量{sum(iterative):.3f}）")
    print("\n结论：两者压到相近的总容量，但迭代压缩因为每轮都重新评估层间交互后的重要性，")
    print("层间分布更平衡（失衡惩罚更小），质量代理分通常更高——这正是论文表6里")
    print("'3轮迭代Puzzle平均分比1步Puzzle高0.57'背后的直觉简化版。")


if __name__ == "__main__":
    main()
```

预期输出会显示：单步压缩由于只在初始教师模型状态下打一次重要性分数、不随剪枝过程更新，容易在某些层剪得过狠、相邻层却保留过多，导致层间分布失衡；迭代压缩因为每轮都重新计算"当前模型"语境下的重要性，能更平滑地在层间分配剪枝量，质量代理分通常更高——这是论文"迭代Puzzle优于单步Puzzle"这一核心消融结论背后机制的最简化直觉演示。
