> **文献中的矛盾、路线分歧和未解争议。** 当两篇论文的结论直接冲突时，理解"为什么不同"比"谁对"更有价值。

## 冲突 1：Attention Is All You Need vs SSM（Mamba）路线

| | Transformer 路线 | SSM/Mamba 路线 |
|---|---|---|
| **代表** | [[Wiki/概念/01_架构技术/自注意力机制]] | [[Wiki/概念/01_架构技术/SSM状态空间模型]] |
| **复杂度** | O(L²) 注意力 | O(L) 递推 |
| **长上下文** | 需要稀疏注意力补偿 | 天然线性复杂度 |
| **硬件利用** | GPU 高度优化 | 需要 CUDA 自定义 kernel |
| **现状** | 绝对主流，行业标准 | 有前景但未证明可完全替代 |

**关键论文：**
- [[Wiki/论文笔记/01_LLM基础架构/51_AttentionIsAllYouNeed-Transformer原始论文]] vs [[Wiki/概念/01_架构技术/SSM状态空间模型]]
- [[Wiki/论文笔记/05_推理思维链/105_Hunyuan-TurboS自适应思维模型]] — Mamba-Transformer 融合尝试

**裁决**：2026 年，混合架构（Mamba-Transformer 融合）成为最有希望的中间路线。纯 SSM 尚未在旗舰模型上证明可完全替代注意力。

## 冲突 2：多 Agent 是否优于单 Agent？

| | 多 Agent 阵营 | 单 Agent 阵营 |
|---|---|---|
| **代表论文** | [[Wiki/论文笔记/03_Agent系统设计/25_Agentopia-长期生命仿真和Agent社会学习]]、[[Wiki/论文笔记/03_Agent系统设计/43_AutoScientists自组织Agent团队科学发现]] | [[Wiki/论文笔记/03_Agent系统设计/40_多Agent是否有助于性能提升受控评测]] |
| **核心主张** | 多 Agent = 集体智能涌现 | 公平对比下，单 Agent + 好 Harness 不逊于多 Agent |
| **关键变量** | 角色分工+辩论提升质量 | 架构公平性控制不当时偏向多 Agent |
| **成本代价** | 推理成本 × N（Agent 数） | 单模型成本 |
| **陷阱** | [[Wiki/概念/04_Agent框架/一致性幻觉]]（共识≠正确） | 依赖单个模型能力上限 |

**裁决**：关键在于" Harness 质量是否受控"。在受控条件下，单 Agent + 好 Harness 与多 Agent 相当；但多 Agent 在多样性探索和鲁棒性上有独特价值。**不矛盾，而是适用于不同约束条件。**

## 冲突 3：RLHF 家族——DPO vs GRPO vs PPO

| | PPO（InstructGPT） | DPO | GRPO |
|---|---|---|---|
| **代表** | [[Wiki/论文笔记/06_训练对齐RL/70_InstructGPT训练语言模型遵循人类指令]] | [[Wiki/概念/02_训练方法/DPO直接偏好优化]] | [[Wiki/概念/02_训练方法/GRPO优化算法]] |
| **奖励模型** | 需要独立 RM | 不需要 | 不需要 |
| **Critic 网络** | 需要 | 不需要 | 不需要 |
| **偏好形式** | 人类对比标注 | 人类对比标注 | 组内相对奖励 |
| **稳定性** | 容易崩溃 | 稳定但保守 | 适中 |
| **适合** | 通用对齐 | 偏好优化 | 推理模型训练（如 R1） |

**裁决**：三者不完全是竞争关系。GRPO 正成为推理模型后训练的主流（[[Wiki/论文笔记/05_推理思维链/84_DeepSeek-R1强化学习激励推理能力]] 证明其有效），DPO 更稳定适合通用场景，PPO 仍是工业级对齐的黄金标准。实际上，生产系统常组合使用（SFT→DPO/GRPO）。

## 冲突 4：上下文越长越好？

| | 长上下文优势 | 长上下文风险 |
|---|---|---|
| **证据** | [[Wiki/论文笔记/09_长上下文记忆/82_DeepSeek-V4百万Token高效长上下文]] — 百万 Token 有效 | [[Wiki/论文笔记/03_Agent系统设计/140_记忆诅咒扩展记忆损害多Agent协作]] — 28 个模型-游戏组合中 18 个出现"记忆诅咒" |
| **机制** | 更多上下文 = 更多参考信息 | 更长上下文 = 更多噪声信号，注意力稀释 |
| **折中** | [[Wiki/论文笔记/09_长上下文记忆/46_效率前沿LLM上下文管理成本性能优化框架]] | [[Wiki/概念/05_记忆与检索/上下文压缩与KV缓存]] |

**裁决**："上下文越长越好"是 naive 假设。有效上下文长度受注意力稀释和信息密度两个因素制约。**关键在于上下文质量而非长度**——这也解释了为什么 RAG + 检索优于全量上下文输入。

## 冲突 5：数据规模 vs 数据质量

| | 规模派 | 质量派 |
|---|---|---|
| **代表** | Scaling Law（[[Wiki/论文笔记/01_LLM基础架构/60_GPT-3语言模型是小样本学习者]]） | "教科书就是一切"（[[Wiki/论文笔记/07_数据合成蒸馏/78_教科书就是你所需要的phi-1代码模型]]） |
| **结论** | 更多数据+更大模型→涌现 | 1.3B 参数 + 7B 高质量 token 即可 | 
| **现状** | 前沿模型仍依赖大规模数据 | 但高质量数据筛选成为标配 |
| **调和** | [[Wiki/论文笔记/07_数据合成蒸馏/37_从潜在表示而非Token学习的样本复杂度理论]] — 从理论角度分析样本效率 |

**裁决**：不是非此即彼。Phi-1 证明小模型+高质量数据可以取得惊人结果，但 GPT-4/DeepSeek 证明大规模预训练仍是上限天花板。**高质量数据是必要条件，大数据是充分条件。**

## 冲突 6：外部 Harness  vs 编译进权重

| | Harness 外部化 | 编译进权重 |
|---|---|---|
| **代表** | [[Wiki/概念/04_Agent框架/Harness设计模式]]（整个 04_Agent框架 类别） | [[Wiki/论文笔记/04_Agent技能工具/42_将Agent工作流编译进LLM权重]] |
| **灵活性** | ✅ 可快速修改接口 | ❌ 需重新训练 |
| **推理成本** | ❌ 外部状态管理增加 overhead | ✅ 无 overhead，成本 ~1/100 |
| **失败率** | ❌ 24%（LangGraph） | ✅ 5.5% |
| **调试** | ✅ 接口层 vs 决策层分离 | ❌ 黑盒 |
| **适用** | 探索期、工作流频繁变化 | 生产期、稳定工作流 |

**裁决**：同一枚硬币的两面。[[Wiki/论文笔记/03_Agent系统设计/49_执行轨迹对齐的Harness推理时设计理论]] 提出"部分 Harness"作为中间路线：只固定初始几步，其余交给 Agent 自主。**成熟度不同选择不同路径，不是路线之争而是阶段之分。**

## 冲突 7：RAG  vs 参数化知识注入

| | RAG 路线 | 参数化知识路线 |
|---|---|---|
| **代表** | [[Wiki/概念/05_记忆与检索/RAG检索增强生成]] | [[Wiki/论文笔记/01_LLM基础架构/56_ERNIE知识增强表示学习]] |
| **优点** | 知识可更新，可追溯来源 | 推理时无外部依赖，延迟低 |
| **缺点** | 检索质量瓶颈，增加延迟 | 知识固化，更新需重训 |
| **最新** | [[Wiki/概念/05_记忆与检索/GraphRAG图结构检索]] — 图结构增强 | [[Wiki/论文笔记/02_前沿模型报告/87_GLM-5V-Turbo多模态Agent原生基础模型]] — 多模态知识内嵌 |

**裁决**：生产系统两者结合。RAG 提供事实性和可追溯性，参数化知识提供流畅性和速度。GraphRAG 和 Agentic RAG 是 2026 年的主要融合方向。

## 冲突 8：Agentic  vs Agentive——Agent 的本质之争

| | Agentic（代理性） | Agentive（自主性） |
|---|---|---|
| **定义** | 外部工程化流程（脚手架、工具、工作流）完成任务 | 能力从模型自身内部涌现 |
| **代表** | [[Wiki/概念/04_Agent框架/Agentic与Agentive区分]] | (尚无公认实现) |
| **现状** | 当前所有"AI Agent"产品都是 Agentic | 未来可能的方向 |
| **争议** | 是否"真正的"Agent？工程堆叠还是本质突破？ | 模型能力提升后是否自然涌现 Agentive 能力？ |

**裁决**：[[Wiki/论文笔记/03_Agent系统设计/04_Agent模型批判]] 认为当前 Agent 产品的命名有误导性——它们都是"Agentic 系统"而非"Agentive 智能体"。这个区分有助于避免对 AI 能力的过度承诺。但 [[Wiki/论文笔记/06_训练对齐RL/07_自博弈与数据调味]] 展示自博弈 RL 可能是通往 Agentive 的技术路径。

## 如何阅读此页

1. **寻找冲突的根源**：通常来自不同的约束假设（成本/质量/延迟的权衡）
2. **注意时间锚**：2023 年的共识可能 2026 年已被推翻
3. **关注调和方案**：大部分"冲突"最终是互补而非对立
4. **标记你的观点**：在这些冲突中，你的产品/团队的立场是什么？
